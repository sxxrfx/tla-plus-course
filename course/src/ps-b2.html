Problem set 12: make the argument, not just the run.

Four problems about reasoning beyond one TLC run. You'll find the inductive invariant behind a ledger, shrink a connection pool's state space without hiding a bug, compose a client with a rate limiter, and write a hierarchical proof for the locked wallet from {{ref:ps-b1}}. They draw on this chapter's four lessons, and on PlusCal and refinement from the two chapters before it.

Every module below was checked with TLC exactly as shown, including the inductiveness checks that start from INIT Inv. No proof in this set was checked by a prover: TLAPS wasn't available where these problems were checked, so the proof in Problem 4 was only parsed by SANY, and its invariant checked by TLC.

Problem 1●○○Databases

A ledger that never mints money

Draws on {{ref:invariants}}, {{ref:impl-general}} and {{ref:transactions}}.

A payments ledger moves money between accounts in two steps, because the accounts may live in different database shards. Debit takes the amount from the sender and marks the transfer debited. Credit later pays the receiver. Auditors care about one promise above all: the ledger never creates money, so the balances never add up to more than the money that was put in. Transfer 1 moves 1 from alice to bob, and transfer 2 moves 2 back.

---------------- MODULE PSb2_Ledger ----------------
EXTENDS Naturals
Accounts == {"alice", "bob"}
Xfers == {1, 2}
From == [x \in Xfers |-> IF x = 1 THEN "alice" ELSE "bob"]
To   == [x \in Xfers |-> IF x = 1 THEN "bob" ELSE "alice"]
Amt  == [x \in Xfers |-> IF x = 1 THEN 1 ELSE 2]
Total == 3
VARIABLES bal, status
vars == <<bal, status>>
Init == /\ bal = [a \in Accounts |-> IF a = "alice" THEN 2 ELSE 1]
        /\ status = [x \in Xfers |-> "new"]
Debit(x) == /\ status[x] = "new"
            /\ bal[From[x]] >= Amt[x]
            /\ bal' = [bal EXCEPT ![From[x]] = bal[From[x]] - Amt[x]]
            /\ status' = [status EXCEPT ![x] = "debited"]
Credit(x) == /\ status[x] = "debited"
             /\ bal' = [bal EXCEPT ![To[x]] = bal[To[x]] + Amt[x]]
             /\ status' = [status EXCEPT ![x] = "credited"]
Next == \E x \in Xfers : Debit(x) \/ Credit(x)
Spec == Init /\ [][Next]_vars

RECURSIVE SumOver(_, _)
SumOver(f, S) == IF S = {} THEN 0
                 ELSE LET s == CHOOSE e \in S : TRUE
                      IN  f[s] + SumOver(f, S \ {s})
InFlight == [x \in Xfers |-> IF status[x] = "debited" THEN Amt[x] ELSE 0]

TypeOK == /\ bal \in [Accounts -> 0..Total]
          /\ status \in [Xfers -> {"new", "debited", "credited"}]
NoMint == SumOver(bal, Accounts) <= Total
Conservation == SumOver(bal, Accounts) + SumOver(InFlight, Xfers) = Total
IndNoMint == TypeOK /\ NoMint
IndCons   == TypeOK /\ Conservation
====================================================
SPECIFICATION Spec
INVARIANT TypeOK NoMint Conservation
CHECK_DEADLOCK FALSE
  1. Run the cfg above. Then check whether NoMint is inductive, starting TLC from every state of IndNoMint. Describe the counterexample, and say whether it is a bug.
  2. Check IndCons the same way. Then argue by hand that Conservation is preserved by Debit(x) and Credit(x), and that it implies NoMint.
  3. Support asks for a Refund(x) action that returns a transfer's amount to its sender and marks it "refunded". Write it with the guard status[x] # "new", check it with the normal cfg and with INIT IndCons, then find the right guard.

TLC finds a counterexample to induction for IndNoMint. What does it show?

Hint

For the inductiveness checks, use a cfg with INIT IndNoMint, NEXT Next, INVARIANT IndNoMint and CHECK_DEADLOCK FALSE, as in {{lesson:invariants}}. NoMint ignores money that has left one account but not arrived in the other. Where is it?

Solution

(a) The normal check finds no error in 5 distinct states, the top row of the figure. Starting from IndNoMint, TLC computes 90 initial states and reports a violation after two: from alice = 0, bob = 2 with transfer 2 debited, Credit(2) pays alice 2 and the balances add up to 4. That start state satisfies NoMint (0 + 2 ≤ 3) but is unreachable: transfer 2 has taken 2 from bob, so 4 units exist in all. It isn't a bug. It shows that NoMint doesn't constrain money in flight, so it can't explain why a credit is safe.

(b) Starting from IndCons, TLC computes 27 initial states and finds no error, so Conservation is inductive for these values. By hand: Debit(x) lowers one balance by Amt[x] and moves x from "new" to "debited", which adds Amt[x] to the in-flight sum. Credit(x) moves x from "debited" to "credited", removing Amt[x] from the in-flight sum, and adds it to a balance. Each step moves money between places, as in Transfer from {{lesson:invariants}}. Since in-flight amounts are never negative, balances plus in-flight equal to 3 implies balances at most 3, which is NoMint. TypeOK needs no separate argument: the guard of Debit keeps balances nonnegative, and Conservation keeps each one at most 3.

(c) With the guard status[x] # "new" (module PSb2_LedgerRefundBug), the normal check reports NoMint violated after four states: Debit(1), Credit(1), then Refund(1) returns 1 to alice although bob was already paid, and the balances add up to 4. That is a real bug, refunding a completed transfer. Starting from IndCons, TLC also finds a counterexample to induction, with a refund of a credited transfer. The right guard is status[x] = "debited":

Refund(x) == /\ status[x] = "debited"
             /\ bal' = [bal EXCEPT ![From[x]] = bal[From[x]] + Amt[x]]
             /\ status' = [status EXCEPT ![x] = "refunded"]

With it (module PSb2_LedgerRefund), the normal check finds 7 distinct states, and the check from IndCons starts from 52 states and finds no error. A refund takes money out of flight and returns it, just as a credit does; Conservation told you which guard to write before any trace did.

Problem 2●●○Infrastructure

Shrink a connection pool, and keep the admin

Draws on {{ref:scaling}}, {{ref:paxos-commit}}, {{ref:transactions}} and {{ref:sets}}.

An application server keeps a pool of database connections. Clients request one, wait, check one out, and return it, or give up waiting. The pool must never hand one connection to two clients, and a client is busy exactly when it holds one connection. Clients are interchangeable, and so are connections, which makes this a natural place for symmetry.

---------------- MODULE PSb2_Pool ----------------
EXTENDS Naturals, FiniteSets, TLC
CONSTANTS Clients, Conns, Free
ASSUME Free \notin Clients
VARIABLES owner, state
vars == <<owner, state>>
Init == /\ owner = [k \in Conns |-> Free]
        /\ state = [c \in Clients |-> "idle"]
Request(c) == /\ state[c] = "idle"
              /\ state' = [state EXCEPT ![c] = "waiting"]
              /\ UNCHANGED owner
Checkout(c, k) == /\ state[c] = "waiting"
                  /\ owner[k] = Free
                  /\ owner' = [owner EXCEPT ![k] = c]
                  /\ state' = [state EXCEPT ![c] = "busy"]
Return(c, k) == /\ owner[k] = c
                /\ owner' = [owner EXCEPT ![k] = Free]
                /\ state' = [state EXCEPT ![c] = "idle"]
Timeout(c) == /\ state[c] = "waiting"     \* gave up waiting for a connection
              /\ state' = [state EXCEPT ![c] = "idle"]
              /\ UNCHANGED owner
Next == \E c \in Clients : \/ Request(c) \/ Timeout(c)
                           \/ \E k \in Conns : Checkout(c, k) \/ Return(c, k)
Spec == Init /\ [][Next]_vars
TypeOK == /\ owner \in [Conns -> Clients \cup {Free}]
          /\ state \in [Clients -> {"idle", "waiting", "busy"}]
\* A client is busy exactly when it holds one connection.
HoldsOne == \A c \in Clients :
              (state[c] = "busy") = (Cardinality({k \in Conns : owner[k] = c}) = 1)
              /\ Cardinality({k \in Conns : owner[k] = c}) <= 1
Sym == Permutations(Clients) \cup Permutations(Conns)
==================================================
SPECIFICATION Spec
CONSTANTS Clients = {c1, c2, c3}
          Conns = {k1, k2}
          Free = Free
INVARIANT TypeOK HoldsOne
  1. Fill in distinct states for 3 clients and 2 connections, 4 and 2, 5 and 3, and 7 and 3, with and without SYMMETRY Sym. Also note how long the 7-and-3 runs take.
  2. Explain why the symmetry is sound here, using the rule from {{lesson:paxos-commit}}.
  3. The pool now keeps one connection for an admin client that runs health checks: other clients may check out a connection only if at least two are free. Add CONSTANT Admin with ASSUME Admin \in Clients, the guard, and the invariant AdminCanConnect below. Then make the bug of writing >= 1 in place of >= 2, and check the buggy pool with Admin = c1 and 3 clients and 2 connections, with and without SYMMETRY Sym.
  4. Write a symmetry that is sound for the admin pool, and check the buggy pool again.
FreeConns == {k \in Conns : owner[k] = Free}
Checkout(c, k) == /\ state[c] = "waiting"
                  /\ owner[k] = Free
                  /\ c # Admin => Cardinality(FreeConns) >= 2
                  /\ owner' = [owner EXCEPT ![k] = c]
                  /\ state' = [state EXCEPT ![c] = "busy"]
AdminCanConnect == state[Admin] = "waiting" => FreeConns # {}

What does TLC report for the buggy admin pool with SYMMETRY Sym?

Hint

A symmetry set is sound only if swapping its elements maps behaviors to behaviors and leaves the property's truth unchanged. Look for a constant that names one particular client. For (d), only the clients that are really interchangeable may be permuted.

Solution

(a) TLC's counts:

Clients × connectionsDistinct statesWith SYMMETRY Sym
3 × 2449
4 × 212812
5 × 399218
7 × 38,86426

On the machine these were checked on, the 7 × 3 run took about 1 second without symmetry and 17 seconds with it. The reduction is large, but TLC must try 7! × 3! = 30,240 permutations on each state it stores, the same effect {{lesson:scaling}} showed for two-phase commit. Symmetry pays when states are expensive and identities few.

(b) No client or connection is named anywhere in the spec or in TypeOK and HoldsOne. They appear only through quantifiers and set operations over Clients and Conns, so swapping two clients, or two connections, turns any behavior into another behavior and doesn't change whether an invariant holds. Free is a separate model value and isn't permuted.

(c) Without symmetry, the correct admin pool passes in 40 distinct states, and the buggy one fails: TLC reports AdminCanConnect violated after six states, in which c1 (the admin) and c2 request, c2 checks out k1, c3 requests and checks out k2, and the admin is left waiting with nothing free. With SYMMETRY Sym, TLC reports no error in 9 distinct states. Admin breaks the symmetry: swapping c1 and c2 turns a violating state into one that satisfies the invariant, as in the figure. TLC explores only one state of each class, so it can miss the violating member entirely, and here it does. Nothing in TLC's output warns you.

(d) Leave the admin out of the permutations:

SymSafe == Permutations(Clients \ {Admin}) \cup Permutations(Conns)

With SYMMETRY SymSafe, TLC reports the violation in the buggy pool again, and the correct admin pool passes in 15 distinct states. The general rule: any constant that singles out an element, like a leader, an admin or a home region, removes that element from the symmetry set.

Problem 3●●○Infrastructure

Compose a client with a token-bucket rate limiter

Draws on {{ref:composition}}, {{ref:refinement}}, {{ref:invariants}} and {{ref:counter}}.

An API gateway protects a service with a token bucket. The bucket holds up to Cap tokens and is refilled over time; each admitted request spends one token, and when the bucket is empty the gateway answers 429 Too Many Requests. One team wrote the bucket and another wrote a client, each as its own module:

---------------- MODULE PSb2_Bucket ----------------
EXTENDS Naturals
CONSTANTS Cap, MaxRefills
VARIABLES tokens, refills
bvars == <<tokens, refills>>
Init == tokens = Cap /\ refills = 0
Take == /\ tokens > 0
        /\ tokens' = tokens - 1
        /\ UNCHANGED refills
Refill == /\ tokens < Cap
          /\ refills < MaxRefills       \* bounds the model
          /\ tokens' = tokens + 1
          /\ refills' = refills + 1
Empty == tokens = 0
Next == Take \/ Refill
Spec == Init /\ [][Next]_bvars
====================================================
---------------- MODULE PSb2_Client ----------------
EXTENDS Naturals
CONSTANT MaxReqs
VARIABLES issued, ok, limited
cvars == <<issued, ok, limited>>
Init == issued = 0 /\ ok = 0 /\ limited = 0
Outstanding == issued > ok + limited
Send == /\ ~Outstanding                 \* one request at a time
        /\ issued < MaxReqs
        /\ issued' = issued + 1
        /\ UNCHANGED <<ok, limited>>
GotOk == /\ Outstanding
         /\ ok' = ok + 1
         /\ UNCHANGED <<issued, limited>>
Got429 == /\ Outstanding
          /\ limited' = limited + 1
          /\ UNCHANGED <<issued, ok>>
Next == Send \/ GotOk \/ Got429
Spec == Init /\ [][Next]_cvars
====================================================

The gateway composes them, renaming the client's variables and fixing the constants with INSTANCE … WITH. Admitting a request is a shared step: the client's GotOk and the bucket's Take happen together.

---------------- MODULE PSb2_Gateway ----------------
EXTENDS Naturals
VARIABLES reqs, served, throttled, tokens, refills
vars == <<reqs, served, throttled, tokens, refills>>
C == INSTANCE PSb2_Client WITH MaxReqs <- 4, issued <- reqs,
                               ok <- served, limited <- throttled
B == INSTANCE PSb2_Bucket WITH Cap <- 2, MaxRefills <- 1
Init == C!Init /\ B!Init
\* Shared step: the gateway forwards the request and spends a token.
Admit    == C!GotOk /\ B!Take
\* Gateway answers 429 only when the bucket is empty.
Throttle == C!Got429 /\ B!Empty /\ UNCHANGED <<tokens, refills>>
Next == \/ C!Send /\ UNCHANGED <<tokens, refills>>
        \/ Admit
        \/ Throttle
        \/ B!Refill /\ UNCHANGED <<reqs, served, throttled>>
Spec == Init /\ [][Next]_vars
\* Every admitted request spent a token.
TokensAccounted == served + tokens = 2 + refills
=====================================================
SPECIFICATION Spec
INVARIANT TokensAccounted
CHECK_DEADLOCK FALSE
  1. Run it. Then add ClientContract == C!Spec and BucketContract == B!Spec and check both as properties. Why must they hold for any composition written this way?
  2. Someone suggests composing more simply, with each component stepping its own variables: [C!Next]_<<reqs, served, throttled>> /\ [B!Next]_<<tokens, refills>> as the next-state relation. Check TokensAccounted on that spec and explain the counterexample.
  3. The client's assumption about the gateway is that a 429 means the bucket was really empty. Write that as an action property HonestThrottle, check it, then delete B!Empty from Throttle and check again.

What is the step in TLC's counterexample for the simpler composition?

Hint

TLC accepts only one [][…]_v conjunct in a behavior spec, so write the simpler composition as one next-state relation, like OwnVars in {{lesson:composition}}. For (c), an action property has the form [][P]_vars, where P may mention primed variables.

Solution

The complete module:

---------------- MODULE PSb2_Gateway ----------------
EXTENDS Naturals
VARIABLES reqs, served, throttled, tokens, refills
vars == <<reqs, served, throttled, tokens, refills>>
C == INSTANCE PSb2_Client WITH MaxReqs <- 4, issued <- reqs,
                               ok <- served, limited <- throttled
B == INSTANCE PSb2_Bucket WITH Cap <- 2, MaxRefills <- 1
Init == C!Init /\ B!Init
\* Shared step: the gateway forwards the request and spends a token.
Admit    == C!GotOk /\ B!Take
\* Gateway answers 429 only when the bucket is empty.
Throttle == C!Got429 /\ B!Empty /\ UNCHANGED <<tokens, refills>>
Next == \/ C!Send /\ UNCHANGED <<tokens, refills>>
        \/ Admit
        \/ Throttle
        \/ B!Refill /\ UNCHANGED <<reqs, served, throttled>>
Spec == Init /\ [][Next]_vars
\* Every admitted request spent a token.
TokensAccounted == served + tokens = 2 + refills
\* A 429 is sent only when the bucket is empty.
HonestThrottle == [][throttled' > throttled => tokens = 0]_vars
ClientContract == C!Spec
BucketContract == B!Spec
\* The naive composition: conjoin the components, each stepping its own variables.
NaiveNext == [C!Next]_<<reqs, served, throttled>> /\ [B!Next]_<<tokens, refills>>
Naive == Init /\ [][NaiveNext]_vars
=====================================================

(a) TLC finds no error: 24 states generated, 19 distinct. With PROPERTY HonestThrottle ClientContract BucketContract added (the cfg PSb2_Gateway.cfg), it still finds none. Every disjunct of Next is a step of the client and a step or stutter of the bucket, and the other way round. Send and Throttle leave the bucket's variables unchanged, Refill leaves the client's unchanged, and Admit is a step of both. So each component's spec is implied, by the argument of {{lesson:implementation}}, with the WITH renaming as the refinement mapping.

(b) With SPECIFICATION Naive, TLC reports TokensAccounted violated after two states: one NaiveNext step in which reqs becomes 1 and tokens becomes 1. The client did Send and the bucket did Take in the same step, and nothing ties a Take to a served request. The conjunction of {{lesson:composition}} is still intersection: each conjunct allows its own component's steps, so their intersection allows every combination of them, including simultaneous steps that shouldn't be connected. It also allows GotOk with no Take at all. The fix is to say which steps are shared, as Admit does.

(c) HonestThrottle == [][throttled' > throttled => tokens = 0]_vars holds for the gateway. Without B!Empty (module PSb2_GatewayLoose), TLC reports HonestThrottle violated after three states: the client sends, and the gateway answers 429 with 2 tokens in the bucket. TokensAccounted still holds, because a throttle spends nothing. This is assume-guarantee reasoning made concrete: the client's correctness argument may assume a 429 means "slow down", and the gateway must guarantee it. Each guarantee needs its own property, because the conservation invariant can't see this one.

Problem 4●●●Databases

Prove the locked wallet never loses a refund

Draws on {{ref:proofs}}, {{ref:invariants}}, {{ref:pluscal}} and {{ref:ps-b1}}.

{{ref:ps-b1}} fixed the lost refund with SELECT … FOR UPDATE and checked it for two and three clients. A proof covers any number. Here is that wallet again, module PSb1_WalletLock: each client locks the row and reads the balance, writes the balance plus 10, and commits, which releases the lock.

---------------- MODULE PSb1_WalletLock ----------------
EXTENDS Naturals, FiniteSets
CONSTANT Clients
(*--algorithm WalletLock
variables balance = 100, holder = "none";
define
    AllDone == \A c \in Clients : pc[c] = "Done"
    NoLostUpdate == AllDone => balance = 100 + 10 * Cardinality(Clients)
end define;
process Refund \in Clients
variable local = 0;
begin
Select:  \* SELECT balance FROM accounts WHERE id = 1 FOR UPDATE
    await holder = "none";
    holder := self;
    local := balance;
Update:  \* UPDATE accounts SET balance = $1 WHERE id = 1
    balance := local + 10;
Commit:  \* COMMIT releases the row lock
    holder := "none";
end process;
end algorithm; *)
========================================================

The translator produces these actions, with Refund(self) their disjunction and Next the usual (\E self \in Clients : Refund(self)) \/ Terminating:

Init == (* Global variables *)
        /\ balance = 100
        /\ holder = "none"
        (* Process Refund *)
        /\ local = [self \in Clients |-> 0]
        /\ pc = [self \in ProcSet |-> "Select"]
Select(self) == /\ pc[self] = "Select"
                /\ holder = "none"
                /\ holder' = self
                /\ local' = [local EXCEPT ![self] = balance]
                /\ pc' = [pc EXCEPT ![self] = "Update"]
                /\ UNCHANGED balance
Update(self) == /\ pc[self] = "Update"
                /\ balance' = local[self] + 10
                /\ pc' = [pc EXCEPT ![self] = "Commit"]
                /\ UNCHANGED << holder, local >>
Commit(self) == /\ pc[self] = "Commit"
                /\ holder' = "none"
                /\ pc' = [pc EXCEPT ![self] = "Done"]
                /\ UNCHANGED << balance, local >>

A candidate inductive invariant, in a module that extends the wallet:

---------------- MODULE PSb2_WalletProof ----------------
EXTENDS PSb1_WalletLock, TLAPS
ASSUME ClientsOK == IsFiniteSet(Clients) /\ "none" \notin Clients

Money == Nat
Paid == {c \in Clients : pc[c] \in {"Commit", "Done"}}
TypeOK == /\ balance \in Money
          /\ local \in [Clients -> Money]
          /\ holder \in Clients \cup {"none"}
          /\ pc \in [Clients -> {"Select", "Update", "Commit", "Done"}]
LockHeld  == \A c \in Clients : (pc[c] \in {"Update", "Commit"}) <=> (holder = c)
FreshRead == \A c \in Clients : pc[c] = "Update" => local[c] = balance
Ledger    == balance = 100 + 10 * Cardinality(Paid)
Inv == TypeOK /\ LockHeld /\ FreshRead /\ Ledger
  1. Nat is infinite, so for TLC replace Money by a finite set: add MoneyModel == {0, 100, 110, 120} and the cfg line CONSTANT Money <- MoneyModel. Check that Inv is inductive for two clients, starting from INIT Inv.
  2. Drop FreshRead, and separately LockHeld, and check each weaker candidate the same way. Explain each counterexample to induction.
  3. Write a hierarchical proof of THEOREM Spec => []NoLostUpdate, in the style of {{lesson:proofs}}, with a case for each action. State the facts about Cardinality you need as lemmas with PROOF OMITTED. Make SANY parse it.
  4. Say exactly what your answer to (c) establishes, and what it doesn't.

Which conjunct of Inv says that the value about to be written was read under the lock?

Hint

Only Update changes Paid: it adds self, which wasn't there because pc[self] was "Update". So you need "adding a new element to a finite set raises its cardinality by one" and "a subset of a finite set is finite", plus IsFiniteSet(Clients) as an assumption. For the step case, copy the shape of <1>2 in InventoryProof.

Solution

(a) The cfg (PSb2_WalletProof.cfg):

INIT Inv
NEXT Next
CONSTANT Clients = {A, B}
CONSTANT Money <- MoneyModel
INVARIANT Inv
INVARIANT NoLostUpdate
CHECK_DEADLOCK FALSE

TLC computes 144 initial states and finds no error, so Inv is inductive for two clients on this finite set of values, and it implies NoLostUpdate in each of them. With three clients and {0, 100, 110, 120, 130}, it finds 2800 states and no error.

(b) Without FreshRead, TLC starts from a state where A holds the lock at "Update" with local[A] = 0 and the balance 100, and Update(A) writes 10. Nothing in the weaker candidate says A's local value is current. Without LockHeld, TLC starts with both clients at "Update", both holding 100. Update(A) writes 110, and B's FreshRead fails, because B's read is now stale. Both are unreachable states. FreshRead carries the argument about values, and LockHeld is why no one else can make a fresh read stale.

(c) The proof, in the tree of the figure:

---------------- MODULE PSb2_WalletProof ----------------
EXTENDS PSb1_WalletLock, TLAPS
ASSUME ClientsOK == IsFiniteSet(Clients) /\ "none" \notin Clients

Money == Nat
Paid == {c \in Clients : pc[c] \in {"Commit", "Done"}}
TypeOK == /\ balance \in Money
          /\ local \in [Clients -> Money]
          /\ holder \in Clients \cup {"none"}
          /\ pc \in [Clients -> {"Select", "Update", "Commit", "Done"}]
LockHeld  == \A c \in Clients : (pc[c] \in {"Update", "Commit"}) <=> (holder = c)
FreshRead == \A c \in Clients : pc[c] = "Update" => local[c] = balance
Ledger    == balance = 100 + 10 * Cardinality(Paid)
Inv == TypeOK /\ LockHeld /\ FreshRead /\ Ledger

LEMMA CardEmpty == Cardinality({}) = 0
    PROOF OMITTED
LEMMA CardSubset == \A S, T : IsFiniteSet(T) /\ S \subseteq T => IsFiniteSet(S)
    PROOF OMITTED
LEMMA CardAdd == \A S, x : IsFiniteSet(S) /\ x \notin S =>
    Cardinality(S \cup {x}) = Cardinality(S) + 1
    PROOF OMITTED

THEOREM Safety == Spec => []NoLostUpdate
<1>1. Init => Inv
    BY ClientsOK, CardEmpty DEF Init, ProcSet, Inv, TypeOK, Money,
       LockHeld, FreshRead, Ledger, Paid
<1>2. Inv /\ [Next]_vars => Inv'
    <2> SUFFICES ASSUME Inv, [Next]_vars PROVE Inv'
        OBVIOUS
    <2>1. ASSUME NEW self \in Clients, Select(self) PROVE Inv'
        \* holder goes from "none" to self, and local[self] gets balance.
        BY <2>1, ClientsOK DEF Select, Inv, TypeOK, Money, LockHeld,
           FreshRead, Ledger, Paid
    <2>2. ASSUME NEW self \in Clients, Update(self) PROVE Inv'
        \* FreshRead gives balance' = balance + 10, and self joins Paid.
        <3>1. self \notin Paid /\ Paid' = Paid \cup {self}
            BY <2>2 DEF Update, Inv, TypeOK, Paid
        <3>2. IsFiniteSet(Paid)
            BY ClientsOK, CardSubset DEF Paid
        <3>3. Cardinality(Paid') = Cardinality(Paid) + 1
            BY <3>1, <3>2, CardAdd
        <3>4. QED
            BY <2>2, <3>3 DEF Update, Inv, TypeOK, Money, LockHeld,
               FreshRead, Ledger
    <2>3. ASSUME NEW self \in Clients, Commit(self) PROVE Inv'
        \* holder returns to "none"; Commit and Done are both in Paid.
        BY <2>3, ClientsOK DEF Commit, Inv, TypeOK, LockHeld, FreshRead,
           Ledger, Paid
    <2>4. CASE Terminating \/ UNCHANGED vars
        BY <2>4 DEF Terminating, vars, Inv, TypeOK, LockHeld, FreshRead,
           Ledger, Paid
    <2>5. QED
        BY <2>1, <2>2, <2>3, <2>4 DEF Next, Refund
<1>3. Inv => NoLostUpdate
    \* When all are Done, Paid = Clients.
    BY DEF Inv, Ledger, Paid, NoLostUpdate, AllDone
<1>4. QED
    BY <1>1, <1>2, <1>3, PTL DEF Spec

\* For TLC only: a finite stand-in for Money, and the weaker candidates.
MoneyModel == {0, 100, 110, 120}
NoFresh == TypeOK /\ LockHeld /\ Ledger
NoLock  == TypeOK /\ FreshRead /\ Ledger
MoneyModel3 == {0, 100, 110, 120, 130}
=========================================================

SANY parses this module with no errors, using a stand-in for the TLAPS module that defines PTL, since TLAPS itself wasn't available. The definitions after the comment For TLC only serve the checks in (a) and (b). In <2>2, FreshRead gives balance' = local[self] + 10 = balance + 10, and <3>3 gives one more paid client, so Ledger is preserved. In <2>1, LockHeld and holder = "none" mean no client is at "Update" or "Commit", so the new holder is the only one. In <1>3, when every client is "Done", Paid = Clients.

(d) What was done: TLC checked that Inv is inductive and implies NoLostUpdate for two and three clients, and SANY checked that the proof is well formed.
