Keep resending until the right bit comes back.

{{lesson:abspec}} said what should happen and {{lesson:fairness}} said it must. Now comes how. Sender A and receiver B talk over two channels that can lose messages, and all they have to work with is the one bit from ABSpec. You'll check that the protocol implements its spec, then see weak fairness fail on a real counterexample and strong fairness repair it.

How it works

A repeatedly sends its current AVar on channel AtoB, since any copy might be lost. B repeatedly sends the bit of BVar on channel BtoA, as an acknowledgement. Then the bits do all the work:

  • When B receives a message whose bit differs from its own, it's a new value, so B sets BVar to it. A message with the same bit is one B already has.
  • When A receives a bit equal to its own, its current value has been acknowledged, so it chooses a new value and flips its bit. A different bit is a stale ack for the previous value.

The specification

Module AB has nothing new except sequence operators. A send appends to a channel, a receive takes the head, and LoseMsg uses Remove to delete any message.

--------------------------------- MODULE AB ---------------------------------
EXTENDS Integers, Sequences

CONSTANT Data

Remove(i, seq) ==
  [j \in 1..(Len(seq) - 1) |-> IF j < i THEN seq[j] ELSE seq[j + 1]]

VARIABLES AVar, BVar, AtoB, BtoA

vars == <<AVar, BVar, AtoB, BtoA>>

TypeOK == /\ AVar \in Data \X {0, 1}
          /\ BVar \in Data \X {0, 1}
          /\ AtoB \in Seq(Data \X {0, 1})
          /\ BtoA \in Seq({0, 1})

Init == /\ AVar \in Data \X {1}
        /\ BVar = AVar
        /\ AtoB = <<>>
        /\ BtoA = <<>>

ASnd == /\ AtoB' = Append(AtoB, AVar)
        /\ UNCHANGED <<AVar, BtoA, BVar>>

ARcv == /\ BtoA # <<>>
        /\ IF Head(BtoA) = AVar[2]
             THEN \E d \in Data : AVar' = <<d, 1 - AVar[2]>>
             ELSE AVar' = AVar
        /\ BtoA' = Tail(BtoA)
        /\ UNCHANGED <<AtoB, BVar>>

BSnd == /\ BtoA' = Append(BtoA, BVar[2])
        /\ UNCHANGED <<AVar, BVar, AtoB>>

BRcv == /\ AtoB # <<>>
        /\ IF Head(AtoB)[2] # BVar[2]
             THEN BVar' = Head(AtoB)
             ELSE BVar' = BVar
        /\ AtoB' = Tail(AtoB)
        /\ UNCHANGED <<AVar, BtoA>>

LoseMsg == /\ \/ /\ \E i \in 1..Len(AtoB) : AtoB' = Remove(i, AtoB)
                 /\ BtoA' = BtoA
              \/ /\ \E i \in 1..Len(BtoA) : BtoA' = Remove(i, BtoA)
                 /\ AtoB' = AtoB
           /\ UNCHANGED <<AVar, BVar>>

Next == ASnd \/ ARcv \/ BSnd \/ BRcv \/ LoseMsg

Spec == Init /\ [][Next]_vars

ABS == INSTANCE ABSpec

THEOREM Spec => ABS!Spec

FairSpec == Spec /\ SF_vars(ARcv) /\ SF_vars(BRcv)
                 /\ WF_vars(ASnd) /\ WF_vars(BSnd)

THEOREM FairSpec => ABS!FairSpec
=============================================================================

The new line is ABS == INSTANCE ABSpec. A plain INSTANCE ABSpec is illegal here, because it would import a second Spec; TLC reports multiple definitions. Naming the instance imports everything with a prefix, so ABS!Spec is ABSpec's formula. The variables AVar and BVar carry over by name. This is the theorem pattern from {{lesson:implementation}} again.

Checking safety needs a bound

A and B can send faster than messages are received or lost, so channels can grow without limit. There are infinitely many reachable states, and TLC would run forever. You could change the spec, but you shouldn't have to change a spec to check it. Instead, give TLC a state constraint:

Bound == (Len(AtoB) <= 2) /\ (Len(BtoA) <= 2)

Normally TLC takes an unexplored state, computes its successors, and repeats. With a constraint, it first tests the state, and if the test fails it doesn't go on from there. That is a limit on what was checked, so say so when reporting a result. A cfg can't name ABS!Spec directly, so a small wrapper module extends AB and defines HighSafety == ABS!Spec. The Toolbox accepts ABS!Spec in its property list.

SPECIFICATION Spec
CONSTANT Data = {d1, d2}
CONSTRAINT Bound
INVARIANT TypeOK
PROPERTY HighSafety

TLC finds no error: 1286 states generated, 216 distinct, depth 13. With the lecture's model, three data values and channel length at most 3, it finds no error in 960 distinct states.

Predict: delete the bit test from ARcv, so any ack makes A choose a new value. And separately, delete the test from BRcv, so B always copies the head. Which breaks?

Only the first. With A broken, TLC reports ABS!Spec violated in five states, shown below. With B broken, this model still gives no error, with the same 216 states. Channels are first-in first-out, so on this model a message carrying B's own bit always equals BVar, and copying it changes nothing. The test that does the work on this model is the one at A. B's test only says, in the spec's terms, when nothing new arrived.

Read the fairness conditions against it. ASnd, BSnd and BRcv steps keep occurring. ARcv is enabled in State 3 and disabled again in State 4, so it's never continuously enabled and weak fairness asks nothing of it. Your run may find a different loop; the lecture shows one where messages in both directions get lost. Both have the same cause: LoseMsg keeps disabling a receive.

Strong fairness from {{lesson:fairness}} closes the gap. BSnd is always enabled, so weak fairness makes B keep sending. Each send enables ARcv, so ARcv is repeatedly enabled, and SF_vars(ARcv) requires it to happen, however often loss disables it. The argument from A to B is symmetric. Strong fairness doesn't stop losses. It says that if you keep sending, something eventually gets through, which is the assumption a lossy channel has to meet to be usable at all.

Why is weak fairness enough for ASnd and BSnd?

What good is eventually?

Something that happens a million years from now is no use, and you could never observe strong fairness failing. But a spec is a compromise between accuracy and simplicity. Requiring receipt within 4.7 ms would mean specifying delivery times, loss rates, and retransmission rates. And if a message is never received, it isn't received in 4.7 ms. So for systems without hard real-time requirements, liveness checking finds errors that prevent things from happening. Timeouts that exist only so that something eventually happens can be plain actions with weak fairness and no clocks. A failed liveness check can also reveal a safety part that's too strict.
