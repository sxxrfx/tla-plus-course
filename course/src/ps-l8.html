Problem set 8: a spec is a formula, and implementing it is implying it.

Four problems on lecture 8: stuttering, reading formulas that are true or false of whole behaviors, and checking that one spec implements another with PROPERTY. The last problem asks whether the two-phase commit booking from {{ref:ps-l6}} and {{ref:ps-l7}} still implements all-or-nothing agreement once operators get a manual override.

As before, every module shown was checked with TLC exactly as printed. When a problem uses TwoPhase, put the TwoPhase and TCommit modules from the lessons in the same folder.

Problem 1●○○Infrastructure

Add minutes to the dashboard clock

Draws on {{ref:temporal}}, {{ref:implementation}} and {{ref:paxos-commit}}.

An operations dashboard has a tile showing the current hour. The on-call team's alerting rules ("page only between 8 and 20") were written and reviewed against this tiny spec of the tile:

--------------------------- MODULE PSl8_HourClock ---------------------------
\* The "current hour" tile on an ops dashboard: a 24-hour clock.
EXTENDS Integers
VARIABLE hr
HInit == hr \in 0..23
HNext == hr' = IF hr = 23 THEN 0 ELSE hr + 1
HSpec == HInit /\ [][HNext]_hr
=============================================================================

A redesign shows hours and minutes. The designer asks whether the alert rules must be reviewed again. They don't need to be if the new tile still satisfies the old spec, that is, if Spec => HourSpec. The new module imports the old one with a named INSTANCE, as PaxosCommit did with TCommit. It also includes the daylight-saving jump that product wants next quarter.

--------------------------- MODULE PSl8_Dashboard ---------------------------
\* The redesigned tile shows hours and minutes. Does it still satisfy the
\* hour-clock spec that the alerting rules were written against?
EXTENDS Integers
VARIABLES hr, min
vars == <<hr, min>>
Init == hr \in 0..23 /\ min \in 0..59
Tick == /\ min' = IF min = 59 THEN 0 ELSE min + 1
        /\ hr' = IF min = 59 THEN (IF hr = 23 THEN 0 ELSE hr + 1) ELSE hr
\* Daylight saving time starts: the local clock jumps from 01:59 to 03:00.
SpringForward == /\ hr = 1 /\ min = 59
                 /\ hr' = 3 /\ min' = 0
Spec == Init /\ [][Tick]_vars
DSTSpec == Init /\ [][Tick \/ SpringForward]_vars

H == INSTANCE PSl8_HourClock
HourSpec == H!HSpec
\* The same claim with stuttering allowed only when hr AND min are unchanged.
HourSpecNoStutter == H!HInit /\ [][H!HNext]_vars
=============================================================================
SPECIFICATION Spec
PROPERTY HourSpec
  1. Take the behavior 13:58, 13:59, 14:00, 14:01. For each of its three steps, say whether it is an HNext step, a stuttering step of HSpec, or neither.
  2. Run the cfg as shown. Report TLC's result and the number of distinct states, and explain that number.
  3. Change the property to HourSpecNoStutter. What does TLC report, and how long is the trace?
  4. Change the specification to DSTSpec and the property back to HourSpec. Which step does TLC reject, and what should the team do about the alert rules?

A behavior goes 10:05, then 10:37, then 11:02. Does it satisfy HourSpec?

Hint

[HNext]_hr is HNext \/ UNCHANGED hr. A step that changes only min satisfies the second disjunct. HourSpecNoStutter excuses a step only when <<hr, min>> is unchanged.

Solution

1. 13:58 → 13:59 leaves hr unchanged, so it's a stuttering step of HSpec. 13:59 → 14:00 is an HNext step. 14:00 → 14:01 is stuttering again. The diagram marks each one.

2. No error, 1440 distinct states. Every state of the dashboard is reachable, as Init allows all 24 × 60. So Spec => HourSpec holds on this model: whatever the alert rules relied on about the hour tile is still true.

3. TLC reports the action property violated after 2 states, on the first Tick it tries (in this run, 0:04 → 0:05). Nearly every tick changes min but not hr. If stuttering meant "nothing changes at all", the hour spec would forbid the minutes from moving, and no clock with a finer display could ever implement it. That's the reason every spec allows steps that leave its own variables unchanged.

4. TLC reports the action property of HourSpec violated after 2 states: from 01:59, SpringForward sets hr to 3. That's neither hr' = hr + 1 nor stuttering. Any alert rule that assumed every hour is visited (for example "the 02:00 batch job always runs") must be reviewed, and that rule really does break on such a night. The spec found the one change that matters and accepted the rest.

Problem 2●○○Design system

Read temporal formulas on a confirm dialog

Draws on {{ref:temporal}}, {{ref:implementation}} and {{ref:states}}.

A design system has a ConfirmDialog component: the user opens it, then confirms or cancels. Confirm runs an async request. While the request is in flight, the dialog shows a spinner, and the form must not come back. If the request fails, an error is shown with Retry and Cancel. The component team writes the contract as a spec, then writes a few properties that QA asked for as temporal formulas:

---------------------------- MODULE PSl8_Dialog -----------------------------
\* A design-system confirm dialog whose Confirm button runs an async request.
VARIABLE dialog
Status == {"closed", "open", "submitting", "error"}
Init == dialog = "closed"
Open    == dialog = "closed"     /\ dialog' = "open"
Cancel  == dialog \in {"open", "error"} /\ dialog' = "closed"
Confirm == dialog = "open"       /\ dialog' = "submitting"
Succeed == dialog = "submitting" /\ dialog' = "closed"
Fail    == dialog = "submitting" /\ dialog' = "error"
Retry   == dialog = "error"      /\ dialog' = "submitting"
Next == Open \/ Cancel \/ Confirm \/ Succeed \/ Fail \/ Retry
Spec == Init /\ [][Next]_dialog

TypeOK == dialog \in Status
AlwaysTypeOK == []TypeOK
\* While a request is in flight the form never reappears.
NoReopenWhileBusy == [][dialog = "submitting" => dialog' # "open"]_dialog
\* An error is shown only right after a request.
ErrorOnlyAfterSubmit == [][dialog' = "error" => dialog = "submitting"]_dialog
\* Once closed, the dialog stays closed (a wrong claim, for comparison).
ClosedIsFinal == [][dialog = "closed" => dialog' = "closed"]_dialog
=============================================================================

Here are four behaviors taken from bug reports and tests. Each one continues by stuttering forever after its last state.

  1. For each of B1 to B4, decide whether it satisfies Spec, AlwaysTypeOK and NoReopenWhileBusy.
  2. Is the formula Spec => NoReopenWhileBusy true on B2? On B3?
  3. Check the contract with TLC using the cfg below. Then add PROPERTY ClosedIsFinal and run it again. Report both results.
SPECIFICATION Spec
INVARIANT TypeOK
PROPERTY NoReopenWhileBusy
PROPERTY ErrorOnlyAfterSubmit

B2 violates NoReopenWhileBusy. What is the value of Spec => NoReopenWhileBusy on B2?

Hint

A state formula such as Init, used as a temporal formula, is about the first state only. [][A]_dialog is about every step, and a step where dialog doesn't change satisfies it whatever A says.

Solution

1.

BehaviorSpecAlwaysTypeOKNoReopenWhileBusy
B1TRUETRUETRUE
B2FALSE: submitting → open is no action of NextTRUEFALSE: that same step
B3FALSE: Init fails on the first stateTRUETRUE
B4TRUE: every step is stutteringTRUETRUE

B3 shows that a property can hold on a behavior the spec rejects. Only B2 breaks the rule QA cares about, and it's the real double-submit bug: a failed request should go to "error", not reopen the form. These values were confirmed by replaying each behavior in TLC.

2. TRUE on B2 and TRUE on B3. Neither satisfies Spec, so the implication asserts nothing about them. The implication fails only on a behavior that satisfies Spec and breaks the property. TLC's run in task 3 shows there is none.

3. No error, 4 distinct states, with TypeOK invariant and both action properties holding. With ClosedIsFinal added, TLC reports it violated after 2 states: closed → open by Open. That's a step of Spec that changes dialog away from "closed", which is exactly what the property forbids. Having a deliberately wrong property fail is a cheap check that TLC is reading your properties the way you meant them.

Problem 3●●○Databases

Does the cache implement the store?

Draws on {{ref:implementation}}, {{ref:temporal}}, {{ref:sets}} and {{ref:paxos-commit}}.

Clients of a key-value store see two operations: put a value, and get the current value of a key. The platform team's spec of what clients may observe records in out what the last get returned:

------------------------------ MODULE PSl8_KV -------------------------------
\* What clients of the key-value store may observe. out is the value the
\* most recent Get returned ("none" before the first Get).
CONSTANTS Key, Val
VARIABLES store, out
KVInit == /\ store \in [Key -> Val]
          /\ out = "none"
Put(k, v) == /\ store' = [store EXCEPT ![k] = v]
             /\ out' = out
Get(k) == /\ out' = store[k]
          /\ store' = store
KVNext == \E k \in Key : Get(k) \/ \E v \in Val : Put(k, v)
KVSpec == KVInit /\ [][KVNext]_<<store, out>>
=============================================================================

To cut database load, the team puts a cache in front of the store. Reads use the cached copy if there is one. Writes are write-through: the database and the cache change together. Fill and Evict are background work. A refactor accidentally replaced Put with PutNoInvalidate, which writes the database and leaves the cache alone.

----------------------------- MODULE PSl8_Cache -----------------------------
\* The same store with a cache in front of it. cache[k] is "miss" or a copy.
CONSTANTS Key, Val
VARIABLES store, out, cache
vars == <<store, out, cache>>
Init == /\ store \in [Key -> Val]
        /\ out = "none"
        /\ cache = [k \in Key |-> "miss"]
\* Write-through: the database and the cache change in one step.
Put(k, v) == /\ store' = [store EXCEPT ![k] = v]
             /\ cache' = [cache EXCEPT ![k] = v]
             /\ out' = out
\* The bug: write to the database and forget the cached copy.
PutNoInvalidate(k, v) == /\ store' = [store EXCEPT ![k] = v]
                         /\ UNCHANGED <<cache, out>>
Fill(k)  == /\ cache[k] = "miss"
            /\ cache' = [cache EXCEPT ![k] = store[k]]
            /\ UNCHANGED <<store, out>>
Evict(k) == /\ cache[k] # "miss"
            /\ cache' = [cache EXCEPT ![k] = "miss"]
            /\ UNCHANGED <<store, out>>
Get(k) == /\ out' = IF cache[k] = "miss" THEN store[k] ELSE cache[k]
          /\ UNCHANGED <<store, cache>>
Next == \E k \in Key : \/ Get(k) \/ Fill(k) \/ Evict(k)
                       \/ \E v \in Val : Put(k, v)
BugNext == \E k \in Key : \/ Get(k) \/ Fill(k) \/ Evict(k)
                          \/ \E v \in Val : PutNoInvalidate(k, v)
Spec == Init /\ [][Next]_vars
BugSpec == Init /\ [][BugNext]_vars

KV == INSTANCE PSl8_KV
KVSpec == KV!KVSpec
THEOREM Spec => KVSpec
=============================================================================
SPECIFICATION Spec
CONSTANTS Key = {"k1", "k2"}
          Val = {"v1", "v2"}
PROPERTY KVSpec
  1. For each action of Next (Put, Get, Fill, Evict), say whether its steps are KVNext steps or stuttering steps of KVSpec.
  2. Run the cfg as shown and report the result.
  3. Change the specification to BugSpec. Report the trace, and for each step in it say what KVSpec makes of it.
  4. Another team builds a write-back cache: Put writes only the cache, and a later Flush copies it to the database. Without running it, predict whether TLC would accept PROPERTY KVSpec for that design. Does the answer mean the write-back cache is wrong?

To KVSpec, an Evict step is

Hint

KVSpec sees only store and out. A Get step is a KVNext step only if the new out equals store[k]. When can cache[k] differ from store[k]?

Solution

1. Put(k, v) is a KV!Put(k, v) step: store changes the same way and out is unchanged. Fill and Evict change only cache, so they're stuttering steps. Get(k) sets out to the cached copy or to store[k]. It's a KV!Get(k) step as long as every cached copy equals the stored value, which holds in every reachable state of Spec, because Put updates both.

2. No error, 48 distinct states: 4 stores × 4 consistent caches (each key missing or equal to the store) × 3 values of out.

3. TLC reports the action property of KVSpec violated after 4 states:

Fill("k1") copies "v2": stuttering. PutNoInvalidate("k1","v1") sets the store to "v1": a KV!Put step, still fine. Get("k1") returns the cached "v2" while store["k1"] is "v1", so out changes to a value KV!Get doesn't allow. The bug happens in step 2, and the client sees it in step 3. That's typical: the high-level spec flags a problem only when it becomes observable.

4. TLC would reject it. A write-back Put leaves store and out unchanged, so KVSpec treats it as stuttering. The next Get returns the new value while store still holds the old one, and that's not a KV!Get step. A hidden run of this design gives exactly that 3-state trace. But the design may be perfectly correct: what a client observes as "the store" is the cached value when it is dirty, not the database row. The check failed because the implementation's variable store isn't the right thing to compare with the spec's store. Lecture 10 shows how to state that comparison with an expression in place of a variable of the same name.

Problem 4●●●Databases

Synthesis: the operator's rollback button

Draws on {{ref:implementation}}, {{ref:transactions}}, {{ref:tcommit}}, {{ref:ps-l5}}, {{ref:ps-l6}} and {{ref:ps-l7}}.

The trip booking (flight, hotel, car) still runs two-phase commit. After the coordinator outage in {{ref:ps-l7}}, operations wrote a runbook step: "If a reservation has been prepared for more than ten minutes, roll it back by hand." Some transaction managers offer exactly this escape hatch for in-doubt participants, often called a heuristic decision. Your job is to check it against all-or-nothing agreement, written in the style of TCommit as in {{ref:ps-l5}}, and now as one formula.

--------------------------- MODULE PSl8_Agreement ---------------------------
\* All-or-nothing agreement, TCommit with its spec written as one formula.
CONSTANT RM
VARIABLE rmState
AInit == rmState = [r \in RM |-> "working"]
canCommit == \A r \in RM : rmState[r] \in {"prepared", "committed"}
notCommitted == \A r \in RM : rmState[r] # "committed"
Prepare(r) == /\ rmState[r] = "working"
              /\ rmState' = [rmState EXCEPT ![r] = "prepared"]
Decide(r) == \/ /\ rmState[r] = "prepared"
                /\ canCommit
                /\ rmState' = [rmState EXCEPT ![r] = "committed"]
             \/ /\ rmState[r] \in {"working", "prepared"}
                /\ notCommitted
                /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
ANext == \E r \in RM : Prepare(r) \/ Decide(r)
ASpec == AInit /\ [][ANext]_rmState
=============================================================================

The booking module extends the lesson's TwoPhase. It defines its spec as a formula and adds the operator's action. Because PSl8_Agreement has the same variable rmState and constant RM, INSTANCE matches them by name.

---------------------------- MODULE PSl8_Booking ----------------------------
\* Two-phase commit for the trip booking, plus the operator's escape hatch:
\* a participant stuck in "prepared" can be forced to roll back by hand.
EXTENDS TwoPhase
BookSpec == TPInit /\ [][TPNext]_vars

HeuristicAbort(r) == /\ rmState[r] = "prepared"
                     /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
                     /\ UNCHANGED <<tmState, tmPrepared, msgs>>
OpsNext == TPNext \/ \E r \in RM : HeuristicAbort(r)
OpsSpec == TPInit /\ [][OpsNext]_vars

AG == INSTANCE PSl8_Agreement
Agreement == AG!ASpec
THEOREM BookSpec => Agreement
=============================================================================
SPECIFICATION BookSpec
CONSTANT RM = {"flight", "hotel", "car"}
PROPERTY Agreement
  1. Run the cfg as shown. Report the result, and say one thing the theorem guarantees and one thing it doesn't.
  2. Without TLC: all three RMs are prepared and nothing has been decided. Is a HeuristicAbort("flight") step from there an ANext step?
  3. Change the specification to OpsSpec. Report the trace length and the first step that is neither an ANext step nor stuttering for Agreement.
  4. A reviewer suggests a guard: allow HeuristicAbort only while no Commit message has been sent. Would that make OpsSpec implement Agreement? What guard would, and who can check it?

Which step does Agreement reject in TLC's trace?

Hint

Write out Decide(r)'s abort branch and evaluate it on the state in task 2. For task 4, ask whether the TM could still send Commit after the guard was checked. What has the TM already recorded?

Solution

1. No error, 288 distinct states: BookSpec => Agreement holds on this model. It guarantees that every step the protocol takes changes rmState in a way agreement allows. It doesn't guarantee that anything is ever decided. A behavior that stutters forever satisfies both sides, and the coordinator crash of {{ref:ps-l7}} is still possible.

2. Yes. The abort branch of Decide("flight") needs rmState["flight"] \in {"working", "prepared"} and notCommitted, and both hold. Taken alone, the operator's step looks like a legal abort.

3. TLC reports the action property of Agreement violated after 10 states. The run here:

States 2 to 5: hotel and flight prepare and the TM records both. State 6: HeuristicAbort("flight"), an allowed abort. States 7 to 9: car prepares, the TM records it, and TMCommit sends Commit, because tmPrepared = RM no matter what flight did afterwards. That's stuttering for Agreement. State 10: RMRcvCommitMsg("flight") moves flight from aborted to committed. TwoPhase's receive action has no guard on the RM's state, since in the real protocol a prepared RM can't have aborted. Your run may end instead with hotel or car committing while flight is aborted. Either way, the step that breaks the high-level spec is a commit receipt, three steps after the cause.

4. No. TLC rejects the guarded version too, again in 10 states. The TM recorded flight's Prepared before the operator acted, and nothing tells it to forget. The only safe guard is that the TM has decided Abort, and then the heuristic is just RMRcvAbortMsg. In other words, the decision has to be made at the coordinator, which is the process that's down. The check shows why the runbook step is dangerous: once you allow it, all-or-nothing is no longer a property of the system, and any mixed outcome has to be found and repaired by hand.
