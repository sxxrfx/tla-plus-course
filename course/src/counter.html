Run a spec, meet deadlock, then write your own.

With TLC installed from {{lesson:tools}}, you run the tiny program's spec exactly as the lecture does. TLC reports an error, and understanding why teaches you what TLC can and can't know. Then you write a small spec of your own and break it.

Run SimpleProgram

Create SimpleProgram.tla with the module from {{lesson:logic}}, and next to it a config file, SimpleProgram.cfg. A config file is the text form of a model. These two lines name the formulas TLC should treat as the initial-state and next-state formulas:

INIT Init
NEXT Next

In the Toolbox, you create a model from the TLC Model Checker menu instead, and it fills these in for you. Run TLC. It stops with an error:

Error: Deadlock reached.
Error: The behavior up to this point is:
State 1: <Initial predicate>
/\ i = 0
/\ pc = "start"
State 2: ...
/\ i = 0
/\ pc = "middle"
State 3: ...
/\ i = 1
/\ pc = "done"

That output is a behavior, printed one state at a time. Which number it picks at State 2 can differ between runs. Follow it through the diagram: start, then middle, then done. The dashed red arrow is what TLC noticed: from pc = "done", no next state exists.

Deadlock and termination

Lamport's distinction is simple. Deadlock means execution stopped when it wasn't supposed to. Termination means it stopped when it was supposed to. Here the program is supposed to stop, so this is termination. But nothing in the spec says whether an execution should stop, so TLC can't tell them apart, and since most systems should not stop, it reports any stop as deadlock.

When stopping is intended, turn the check off. In the Toolbox, it is the Deadlock checkbox on the Model Overview page. In a config file, add a line:

CHECK_DEADLOCK FALSE

Now TLC reports Model checking completed. No error has been found. and 2003 distinct states found. The diagram accounts for that number: 1 start state, 1001 middle states, and 1001 done states. Disable the check only when you know stopping is correct. Otherwise you are switching off a real alarm.

Your turn: a counter

Write a spec without a C program to start from. This one describes a counter that starts at 0 and increments up to a bound. Save it as Counter.tla, since the module name and file name must match.

---------------- MODULE Counter ----------------
EXTENDS Integers
VARIABLE x

Max == 3

Init == x = 0

Next == /\ x < Max
        /\ x' = x + 1

Safe == x =< Max
================================================

In ASCII, “less than or equal” is =<. The first line of Next has no prime, so it is a condition on the current state alone. A step can happen only when it is true. Such a condition is called a guard, and {{lesson:actions}} says more about it. Compare it with pc = "start" in SimpleProgram, which plays the same role.

Safe is a formula you claim is always true. A state that occurs in some behavior is reachable, and a formula true in every reachable state is an invariant. A claimed invariant goes in the config, and TLC tests it in every state it finds:

INIT Init
NEXT Next
INVARIANT Safe
CHECK_DEADLOCK FALSE

TLC finishes with no error and 4 distinct states. As with SimpleProgram, the deadlock check has to be off, or TLC stops at x = 3, because this counter is designed to stop there.

Explore the bounded model

Changing Max in the lab is like editing the definition Max == 3. “Explore all states” does a breadth-first search of a tiny JavaScript model: all states one step away, then two, and so on. It is not TLC. Now tick the box to weaken the guard, and predict what the search will find before you press the button.

The diagram compares the two guards. We ran the broken one, with x =< Max, through real TLC. It reports Invariant Safe is violated with a 5-state behavior, 0 through 4, which matches the bottom row. You can reason backward too: to reach the bad state x = 4, the predecessor must be x = 3, and the step must be allowed there. So the guard is the culprit, and you found that without reading a long trace.

Retrieve: what are the two formulas TLC needs, and what is a third thing you can ask it to check?

The initial-state formula and the next-state formula. On top of those you can name invariants. You can also decide whether a stop counts as deadlock. Later lessons add more, but this is the whole model so far.

Transfer: a retry budget

A file-upload client allows at most three attempts. Let attempts count those already started, not those remaining.

Next == /\ attempts < 3
        /\ attempts' = attempts + 1

BudgetOK == attempts \in 0..3

In the diagram, the guard reads the old value. At 2 it allows a step to 3, and at 3 it blocks the dashed arrow. That is why “allow three attempts” uses a strict comparison on attempts already used. Running this module through TLC gives 4 distinct states and no error. Writing the sentence out as a trace saves you from guessing whether the comparison should include equality.

Now imagine resetting attempts to zero whenever the user taps Retry. Each session still passes this check, but one logical upload can now trigger unlimited attempts. If the requirement concerns one logical request, the count must belong to that request, and every way of resetting it must appear in Next.

Exercise: instead count attempts remaining, initially 3. What would you write?

remaining > 0 /\ remaining' = remaining - 1 and the invariant remaining \in 0..3. Decide whether the first attempt consumes the budget. The variable's name can't settle that for you.
