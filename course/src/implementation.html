To implement a spec is to imply it.

The previous lesson made each spec a formula. Two-phase commit was supposed to implement transaction commit, and now that claim has a one-line statement: every behavior satisfying TPSpec also satisfies TCSpec. The surprise is what must be true of states and steps for that line to make sense.

The theorem

Module TCommit has one variable, so its spec has a simpler subscript: TCSpec == TCInit /\ [][TCNext]_rmState. At the end of module TwoPhase, INSTANCE imports every definition from TCommit, and a theorem follows:

INSTANCE TCommit

THEOREM TPSpec => TCSpec

Checking it follows the recipe you just learned: behavior spec on the left, property on the right.

SPECIFICATION TPSpec
CONSTANT RM = {r1, r2, r3}
PROPERTY TCSpec

TLC finds no error, with 288 distinct states: the same states as before, since only the question changed.

How can that formula even make sense?

TPSpec talks about four variables and TCSpec about one. The theorem looks like apples implying oranges. The answer is a fact held back until now: a state does not assign values only to the variables of your module. It assigns a value to every possible variable, infinitely many of them.

So one state may have Mozart = <<-37, {14}>> and tmState = "ouch" alongside rmState. TCInit is true on it if rmState maps each element of RM to "working", whatever else is there. A behavior of TCSpec may even have tmPrepared changing wildly from state to state, since TCSpec is silent on it.

This feels odd only if you read a spec as a program. It is a formula. x + y = 7 does not claim there is no variable z. A useful picture: a spec describes a history of the universe in which the system and its environment behave correctly. It mentions the parts it depends on (msgs might stand for a real transport underneath the protocol), and says nothing about the rest.

Why stuttering has to be there

Both formulas now apply to the same behaviors. But how can the implication be true? TMAbort leaves rmState unchanged, while every TCNext step changes it. So a TMAbort step is not a TCNext step.

The subscript from {{lesson:temporal}} is the answer. TCSpec requires only that every step satisfies TCNext or leaves rmState unchanged, and TMAbort does the second. In the first figure, each stutter cell is exactly that.

Predict: narrow what counts as stuttering, so only a step that leaves all four TwoPhase variables unchanged is excused. Property: [][TCNext]_<<rmState, tmState, tmPrepared, msgs>>. What does TLC find?

An error, immediately. TLC reports the action property violated after two states, with a TMAbort step, as the figure below shows. The property is the formula you would effectively have if specs could not stutter on variables they don't mention.

Without stuttering, TPSpec would also forbid the Timbuktu Starbucks customer count from changing except when the protocol took a step. That is one reason all TLA+ specs allow it. The most important reason is the theorem itself: because of stuttering, implementation is simply implication. There is no separate notion of implementing to define.

A check that can fail

A theorem that TLC confirms tells you more if you've seen it fail. In a copy of TwoPhase, delete one line from TMCommit, the conjunct tmPrepared = RM, so the manager can commit without hearing from anyone. Then check PROPERTY TCSpec again with two resource managers.

TLC reports the action property on the [][TCNext]_rmState part of TCSpec as violated, with the three-state trace above. The buggy step changes only tmState and msgs, so TCSpec lets it pass as stuttering. Only when r1 acts on the message does rmState do something no TCNext step allows, because Decide commits only from "prepared". A violation in the high-level view may show up later than its cause.

Should TCSpec => TPSpec also hold?

Termination, and stopping too soon

Return to SimpleProgram: Init /\ [][Next]_<<pc, i>>. Its formula allows stuttering between real steps, and after the last one, forever. That is how TLA+ represents a terminating execution: a behavior ending in infinitely many stuttering steps. The universe keeps going after your system finishes. As a result, all behaviors are infinite, and finite ones never need separate treatment.

Look at the bottom row. It also satisfies the formula: it takes one step, then stutters forever. Everything you've written so far allows the system to stop at any time. These specs say what a system may do, not what it must do. That is not a defect to patch inside the next-state formula. They are very different requirements and should be stated separately, by conjoining a further temporal formula L:

Init /\ [][Next]_vars /\ L

Writing L is the main business of the next lecture, starting at {{lesson:fairness}}. It is the tiny part of a spec. The may part is much larger, usually more important, and already enough for useful specs.

Predict: TLC checks TPSpec => TCSpec and finds no error. Does that show two-phase commit ever commits anything?

No. A behavior that stutters forever from the initial state satisfies both formulas. The theorem says each step TwoPhase takes is one TCommit permits. Nothing here says a step must be taken.
