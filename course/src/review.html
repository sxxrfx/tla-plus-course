Rebuild without looking

  1. Write Counter from memory, including vars and Spec. Introduce a bug and predict the first bad state.
  2. Write the inventory conservation invariant and explain what makes Reserve atomic.
  3. Draw a retry trace that duplicates an effect; repair it without pretending two independent stores share a transaction.
  4. Explain a weak-fairness counterexample involving an intermittently enabled action.
  5. Map a multi-step queue implementation to an abstract enqueue/dequeue operation. Identify its linearization point and its stuttering steps.
  6. Propose a cross-shard payment invariant and name the exact durable state needed after a coordinator crash.

A working vocabulary

TermMeaning
EnabledAn action has a suitable successor; fairness typically considers a non-stuttering successor.
InvariantA state predicate true in every reachable state.
SafetyA violation has a finite bad prefix. Invariants are a common special case.
LivenessEvery finite prefix can still be extended to satisfy the property; the violation requires an infinite behavior.
RefinementA detailed behavior satisfies an abstract contract under a mapping and the stated assumptions.
LinearizabilityConcurrent operations appear to take effect in a legal sequential order that respects real-time order of non-overlapping operations.
AssumptionA restriction on the behaviors for which a guarantee is claimed.
ConstraintA model-checking search restriction, which can hide behaviors.
History variableAuxiliary state recording past events to express or prove a property.
Prophecy variableAuxiliary machinery that predicts a future choice when a simple refinement mapping cannot otherwise express the relationship.
Fencing tokenAn ordered authority token the protected resource checks to reject superseded writers.

A final exercise that connects the course

Explain a photo-sharing app’s “Upload complete” message. The phone may retry, the object store may contain the bytes before the metadata row exists, a thumbnail worker may run twice, and a stale CDN response may arrive after replacement. Mark each boundary in the diagram before choosing your variables.

Retrieve five ideas without looking: a state versus an action; an invariant versus a progress claim; an atomic boundary versus a sequence of steps; a simulation versus an exhaustive finite check; and a refinement mapping versus a copied implementation detail. Then give one failure trace for each red edge.

Compare with a possible modeling answer

Use a stable upload ID, immutable content identity, durable object existence, metadata state, thumbnail effect count, and cached version. Require that “complete” implies the chosen durable evidence, a retry does not create another logical photo, and an old thumbnail cannot replace a newer one. Ask separately whether upload and processing eventually finish under recovery and delivery assumptions. A model can be safe while the phone waits forever.

For efficient review, alternate examples: apply the inventory guard idea to authorization, the request-identity idea to uploads, and the delayed-message idea to cache invalidation. If you can only repeat the original example, revisit its underlying state and transition rule before advancing.

Evidence to keep with every model

Write down the property, the abstraction boundary, the allowed failures, the constants and bounds, the invariants and temporal properties actually checked, the tool version, and whether the search completed. Preserve at least one known-bad mutation. A useful model is one another engineer can challenge and rerun.

To carry this into daily work, choose one small uncertainty in a real design: a retry boundary, a stale lease, or a race during failover. Model that uncertainty first. The next useful milestone is a counterexample that teaches your team something it did not already know.
