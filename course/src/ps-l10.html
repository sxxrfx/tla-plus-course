Problem set 10: say what stands for what.

Four refinement problems. Each gives you an implementation with more machinery than its spec, such as shards, files on disk, replicas or an optimistic screen. You write the refinement mapping, check it with TLC, and decide what a failed check means. You'll use RECURSIVE and INSTANCE … WITH from lecture 10. The last problem adds the message sets of lecture 6 and the fairness of lecture 9.

Every module below was checked with TLC exactly as shown. To check a refinement, do what {{lesson:refinement}} did: put the implementation's Spec under SPECIFICATION, and the instantiated abstract spec under PROPERTY. Keep the abstract module in the same folder, because INSTANCE looks for it there. Counts like "distinct states" only match if your copy is identical.

Problem 1●○○Infrastructure

A sharded like counter is still a counter

Draws on {{ref:refinement}}, {{ref:impl-general}} and {{ref:implementation}}.

A social app keeps the like count of each post in one database row. A popular post turns that row into a hot spot: every like is an update of the same row, and concurrent updates of one row wait for each other. The team splits the counter into shards. Each like increments one shard, chosen at random, and the page shows the sum of the shards. The product promise is unchanged: the number on the page goes up by one per like and never goes down.

That promise is this spec:

---------------- MODULE PSl10_Counter ----------------
EXTENDS Naturals
VARIABLE count
Init == count = 0
Inc == count' = count + 1
Spec == Init /\ [][Inc]_count
======================================================

Here is the implementation. MaxPerShard only keeps the model finite.

---------------- MODULE PSl10_Sharded ----------------
EXTENDS Naturals
CONSTANTS Shards, MaxPerShard
VARIABLE shard
Init == shard = [s \in Shards |-> 0]
Inc(s) == /\ shard[s] < MaxPerShard
          /\ shard' = [shard EXCEPT ![s] = shard[s] + 1]
Next == \E s \in Shards : Inc(s)
Spec == Init /\ [][Next]_shard
======================================================
SPECIFICATION Spec
CONSTANTS Shards = {s1, s2, s3}
          MaxPerShard = 2
PROPERTY CounterSpec
CHECK_DEADLOCK FALSE
  1. Add a recursive operator SumOver(f, S), the sum of f[s] over all s in a finite set S. Then add the refinement mapping as an instance C of PSl10_Counter, define CounterSpec == C!Spec, and run the model above.
  2. To keep reads cheap, a job periodically folds a shard into a stored base value: it adds the shard's count to base and resets the shard to 0. Add a base variable and a Fold(s) action, map count to base plus the shard sum, and check again. You'll need a state constraint, because shards can now refill forever.
  3. The shards are moved to an in-memory cache without persistence. Model a cache restart as Restart(s), which sets one shard back to 0. What does TLC report?
  4. A teammate maps count <- shard[Home], where Home is the shard their app server writes to. TLC finds no error. Why is that result worthless as evidence for the product promise?

Under the mapping count <- base + sum of shards, what abstract step does a Fold(s) step with shard[s] = 3 correspond to?

Hint

Write SumOver like RemoveX in {{lesson:impl-general}}: an empty set sums to 0, and otherwise pick one element with CHOOSE, add its value, and recurse on the rest. For the restart, ask what happens to the mapped count, and whether any step of PSl10_Counter can do that.

Solution

(a) The completed module. TLC finds no error, with 55 states generated and 27 distinct states.

---------------- MODULE PSl10_Sharded ----------------
EXTENDS Naturals
CONSTANTS Shards, MaxPerShard
VARIABLE shard
Init == shard = [s \in Shards |-> 0]
Inc(s) == /\ shard[s] < MaxPerShard
          /\ shard' = [shard EXCEPT ![s] = shard[s] + 1]
Next == \E s \in Shards : Inc(s)
Spec == Init /\ [][Next]_shard

RECURSIVE SumOver(_, _)
SumOver(f, S) == IF S = {} THEN 0
                 ELSE LET s == CHOOSE x \in S : TRUE
                      IN  f[s] + SumOver(f, S \ {s})
Total == SumOver(shard, Shards)

C == INSTANCE PSl10_Counter WITH count <- Total
THEOREM Spec => C!Spec
CounterSpec == C!Spec
======================================================

The cfg line CHECK_DEADLOCK FALSE matters here: once every shard reaches MaxPerShard no step is enabled, which is the end of the model, not a bug. CHOOSE is safe in SumOver because addition doesn't care which element comes first. Every Inc(s) raises the sum by exactly one, so it is an Inc step of the counter.

(b) With a base value and a fold:

---------------- MODULE PSl10_ShardedFold ----------------
EXTENDS Naturals
CONSTANTS Shards, MaxPerShard
VARIABLES shard, base
vars == <<shard, base>>
Init == /\ shard = [s \in Shards |-> 0]
        /\ base = 0
Inc(s) == /\ shard[s] < MaxPerShard
          /\ shard' = [shard EXCEPT ![s] = shard[s] + 1]
          /\ UNCHANGED base
Fold(s) == /\ shard[s] > 0
           /\ base' = base + shard[s]
           /\ shard' = [shard EXCEPT ![s] = 0]
Next == \E s \in Shards : Inc(s) \/ Fold(s)
Spec == Init /\ [][Next]_vars

RECURSIVE SumOver(_, _)
SumOver(f, S) == IF S = {} THEN 0
                 ELSE LET s == CHOOSE x \in S : TRUE
                      IN  f[s] + SumOver(f, S \ {s})
Total == base + SumOver(shard, Shards)
Bound == Total <= 4

C == INSTANCE PSl10_Counter WITH count <- Total
CounterSpec == C!Spec
==========================================================
SPECIFICATION Spec
CONSTANTS Shards = {s1, s2, s3}
          MaxPerShard = 2
CONSTRAINT Bound
PROPERTY CounterSpec
CHECK_DEADLOCK FALSE

TLC finds no error: 220 states generated, 55 distinct. A fold changes the implementation's state but not the mapped count, so it maps to stuttering, as the quiz says. This is the same move as TMAbort in {{lesson:implementation}} and as the ARcv of a corrupted message in {{lesson:refinement}}: internal work is invisible in the abstract spec.

(c) Add Restart(s) == shard[s] > 0 /\ shard' = [shard EXCEPT ![s] = 0] as a disjunct of Next (module PSl10_ShardedRestart). TLC reports that the action property of PSl10_Counter is violated, with three states: shards all 0; Inc(s1), so the count is 1; Restart(s1), so the count is 0 again. The figure shows a longer behavior of the same module. The count fell, and the abstract spec only allows count' = count + 1 or no change. The product consequence is that a like disappears from the page. A cache restart that forgets data is exactly a step the contract forbids, so the shards need persistence, or a recovery step that restores them.

(d) With Home = s1, TLC finds no error (27 distinct states). Every step either raises shard[s1] by one or leaves it alone, so every step is an Inc or a stutter. The check is correct; the claim is just weak. Under this mapping the abstract "count" ignores two thirds of the likes. A refinement theorem is only as meaningful as its mapping: the mapping says what the implementation's state means, and here it means the wrong thing. TLC can tell you a mapping works, but not that it is the one your users read.

Problem 2●●○Databases

An LSM tree implements a map

Draws on {{ref:refinement}}, {{ref:impl-general}}, {{ref:abspec}} and {{ref:sets}}.

Storage engines such as LevelDB and RocksDB are log-structured merge trees. A write goes into an in-memory table, the memtable. When the memtable is big enough, it is flushed to disk as an immutable file. Compaction later merges files, keeping the newer value of each key. A read checks the memtable first, then the files from newest to oldest. The application sees none of this. It sees a map from keys to values:

---------------- MODULE PSl10_KV ----------------
CONSTANTS Keys, Vals, NoVal
VARIABLE store
Init == store = [k \in Keys |-> NoVal]
Put(k, v) == store' = [store EXCEPT ![k] = v]
Next == \E k \in Keys, v \in Vals : Put(k, v)
Spec == Init /\ [][Next]_store
=================================================

The engine, with tables[1] the oldest file and at most MaxTables files:

---------------- MODULE PSl10_LSM ----------------
EXTENDS Naturals, Sequences
CONSTANTS Keys, Vals, NoVal, MaxTables
VARIABLES mem, tables
vars == <<mem, tables>>
Empty == [k \in Keys |-> NoVal]
Init == /\ mem = Empty
        /\ tables = <<>>              \* tables[1] is the oldest
Put(k, v) == /\ mem' = [mem EXCEPT ![k] = v]
             /\ UNCHANGED tables
Flush == /\ mem # Empty
         /\ Len(tables) < MaxTables
         /\ tables' = Append(tables, mem)
         /\ mem' = Empty
Merge(older, newer) ==
    [k \in Keys |-> IF newer[k] # NoVal THEN newer[k] ELSE older[k]]
Compact == /\ Len(tables) >= 2
           /\ tables' = <<Merge(tables[1], tables[2])>> \o Tail(Tail(tables))
           /\ UNCHANGED mem
Next == \/ \E k \in Keys, v \in Vals : Put(k, v)
        \/ Flush
        \/ Compact
Spec == Init /\ [][Next]_vars
==================================================
SPECIFICATION Spec
CONSTANTS Keys = {k1, k2}
          Vals = {v1, v2}
          NoVal = NoVal
          MaxTables = 2
PROPERTY KVSpec
CHECK_DEADLOCK FALSE
  1. Write Get(k), the value a read returns, using a recursive helper that searches the files from newest to oldest. Then add the mapping KV == INSTANCE PSl10_KV WITH store <- … and KVSpec == KV!Spec, and check it.
  2. Which actions of the engine map to stuttering? Say why for each.
  3. A refactoring swaps the arguments of Merge in Compact, so the older file wins. Check the buggy engine with Keys = {k1, k2}, and then with Keys = {k1}.
  4. Explain the difference between the two runs. What does it say about how strong PSl10_KV is as a contract?

With Keys = {k1}, what does TLC report for the buggy compaction?

Hint

Give the helper the index of the file to look at: Find(k, i) looks in tables[i] and, if the key isn't there, in tables[i - 1]. Start it at Len(tables); index 0 means "not found". For (d), ask which steps of PSl10_KV could explain a one-key rollback.

Solution

(a) The added definitions:

RECURSIVE Find(_, _)
Find(k, i) == IF i = 0 THEN NoVal
              ELSE IF tables[i][k] # NoVal THEN tables[i][k]
              ELSE Find(k, i - 1)
Get(k) == IF mem[k] # NoVal THEN mem[k] ELSE Find(k, Len(tables))

KV == INSTANCE PSl10_KV WITH store <- [k \in Keys |-> Get(k)]
THEOREM Spec => KV!Spec
KVSpec == KV!Spec

TLC finds no error: 3277 states generated, 657 distinct.

(b) Flush and Compact map to stuttering. A flush moves the memtable into the newest file, and a read finds the same values there, because nothing newer exists. A correct compaction replaces the two oldest files by one in which the newer value of each key wins, which is what a read of those two files returned anyway. So does a Put of the value a read already returns.

(c) With two keys, TLC reports the action property of PSl10_KV violated after eight states. The figure shows the important ones: Put(k1, v1), Put(k2, v1), Flush, Put(k1, v2), Put(k2, v2), Flush, and then Compact, which leaves only <<(k1 :> v1 @@ k2 :> v1)>>. The mapped store went from both keys at v2 to both at v1 in one step. Each Put changes one key, so no step of the map spec can do that.

(d) With one key, TLC finds no error, in 21 distinct states. The rollback of k1 from v2 to v1 is the same pair of mapped states as Put(k1, v1), and the map spec lets anyone put any value at any time. The bug was real in both runs; the refinement check could only see it when no abstract step explained it. PSl10_KV says nothing about who writes or which value, so data loss that looks like a write passes. To catch it with one key, put the client into the model, for example a variable recording the last value the client wrote, and require each mapped change to equal it. A weak abstract spec makes refinement easy to pass, and so says less.

Problem 3●●○Distributed systems

A replicated log's commit index

Draws on {{ref:refinement}}, {{ref:replication}}, {{ref:consensus}} and {{ref:abspec}}.

In Raft-style replication, clients send commands to a leader, which appends them to its log and copies them to followers. An entry counts as committed once a majority of servers store it, and the leader's commit index says how far that goes. The guarantee to clients is an append-only log: committed entries appear one after another and never change.

---------------- MODULE PSl10_Log ----------------
EXTENDS Sequences
CONSTANT Vals
VARIABLE log
Init == log = <<>>
Next == \E v \in Vals : log' = Append(log, v)
Spec == Init /\ [][Next]_log
==================================================

The model has one fixed leader and two followers, so a majority is two of three. Its mapping says the abstract log is the leader's log up to the commit index:

---------------- MODULE PSl10_RLog ----------------
EXTENDS Naturals, Sequences, FiniteSets
CONSTANTS Vals, Followers, MaxLen
VARIABLES llog, flog, commit
vars == <<llog, flog, commit>>
Init == /\ llog = <<>>                       \* the leader's log
        /\ flog = [f \in Followers |-> <<>>]   \* each follower's log
        /\ commit = 0                         \* the leader's commit index
Request(v) == /\ Len(llog) < MaxLen
              /\ llog' = Append(llog, v)
              /\ UNCHANGED <<flog, commit>>
Replicate(f) == /\ Len(flog[f]) < Len(llog)
                /\ flog' = [flog EXCEPT ![f] =
                              Append(flog[f], llog[Len(flog[f]) + 1])]
                /\ UNCHANGED <<llog, commit>>
\* Entry n is on a majority: the leader plus at least half the followers.
OnMajority(n) == 2 * (1 + Cardinality({f \in Followers : Len(flog[f]) >= n}))
                   > 1 + Cardinality(Followers)
AdvanceCommit == /\ \E n \in (commit + 1)..Len(llog) :
                       /\ OnMajority(n)
                       /\ commit' = n
                 /\ UNCHANGED <<llog, flog>>
Next == \/ \E v \in Vals : Request(v)
        \/ \E f \in Followers : Replicate(f)
        \/ AdvanceCommit
Spec == Init /\ [][Next]_vars

Committed == [i \in 1..commit |-> llog[i]]
L == INSTANCE PSl10_Log WITH log <- Committed
LogSpec == L!Spec
===================================================
SPECIFICATION Spec
CONSTANTS Vals = {a, b}
          Followers = {f1, f2}
          MaxLen = 3
PROPERTY LogSpec
CHECK_DEADLOCK FALSE
  1. Run it. TLC reports a violation. Is any committed entry lost or changed in the trace? Say exactly which abstract step is missing.
  2. Fix it in two ways: change AdvanceCommit to move the index by one, and, separately, keep the implementation and weaken the abstract spec so one step may append several entries. Check both.
  3. Add a failover step: a new leader that holds only the committed prefix takes over, and uncommitted entries are discarded everywhere. (Real Raft is subtler; this is the part that matters here.) Check the mapping again, and then the mapping log <- llog.

Under the mapping Committed, what is a Replicate(f) step?

Hint

A refinement maps each implementation step to one abstract step or to a stutter. For the weaker spec, say "the new log is longer and keeps every old entry" with a quantifier over 1..Len(log), and use log' \in Seq(Vals) rather than an existential over Seq(Vals), which TLC can't enumerate.

Solution

(a) TLC's shortest trace has six states, shown in the figure: two Request(a) steps, two Replicate(f1) steps, and AdvanceCommit setting commit from 0 to 2. Both entries are on a majority, the leader and f1, so committing them is safe, and nothing is lost or changed. But the mapped log went from <<>> to <<a, a>> in one step, and PSl10_Log appends one entry per step. Refinement doesn't let one implementation step stand for two abstract steps. The implementation isn't wrong; the abstract spec's steps are finer than the implementation's.

(b) First fix, in the implementation (module PSl10_RLogOne):

AdvanceCommit == /\ commit < Len(llog)
                 /\ OnMajority(commit + 1)
                 /\ commit' = commit + 1
                 /\ UNCHANGED <<llog, flog>>

Second fix, in the spec. The model keeps the jumping AdvanceCommit and maps to this module instead (PSl10_RLogBatch):

---------------- MODULE PSl10_LogBatch ----------------
EXTENDS Naturals, Sequences
CONSTANT Vals
VARIABLE log
Init == log = <<>>
\* One step may append one or more entries; earlier entries never change.
Extend == /\ log' \in Seq(Vals)
          /\ Len(log') > Len(log)
          /\ \A i \in 1..Len(log) : log'[i] = log[i]
Spec == Init /\ [][Extend]_log
=======================================================

TLC finds no error with either: 1197 states generated and 503 distinct for the one-at-a-time commit, 1425 and 503 for the batch spec. Which fix is right depends on what clients can observe. If a client can watch the committed log grow, the batch spec is honest about what it will see. If the abstract spec is shared with other components that assume one entry at a time, change the implementation.

(c) The failover step, together with the one-at-a-time commit (module PSl10_RLogFix):

Prefix(s, n) == [i \in 1..n |-> s[i]]
Failover == /\ Len(llog) > commit
            /\ llog' = Prefix(llog, commit)
            /\ flog' = [f \in Followers |->
                          IF Len(flog[f]) > commit THEN Prefix(flog[f], commit)
                          ELSE flog[f]]
            /\ UNCHANGED commit

With the Committed mapping, TLC finds no error: 1617 states generated, 503 distinct. Failover discards only entries past commit, so the mapped log doesn't change, and it is a stutter. With log <- llog (module PSl10_RLogLeader), TLC reports a violation in three states: Request(a) makes the leader's log <<a>>, and Failover empties it. Without failover, log <- llog passes too (module PSl10_RLogOneLeader, 503 distinct states), because a single leader's log only grows. That's the real reason the commit index exists: it marks the part of the log that survives a change of leader.

Problem 4●●●UI design system

Which list does an optimistic tag input refine?

Draws on {{ref:refinement}}, {{ref:messages}}, {{ref:fairness}}, {{ref:implementation}} and {{ref:ps-l9}}.

A design system ships a tag input, used to put labels on issues. When the user adds a tag, it appears at once, greyed out as pending, and a request goes to the server. If the server accepts, the tag turns solid. If it rejects, for example because the user may not use that label, the tag disappears and a toast explains why. The server's own contract is simple: an issue's tags are only ever added. Messages are a set that only grows, as in {{lesson:messages}}, so the model allows any delay, reordering and duplicate delivery.

---------------- MODULE PSl10_TagSet ----------------
CONSTANT Tags
VARIABLE tags
Init == tags = {}
Add(t) == /\ t \notin tags
          /\ tags' = tags \cup {t}
Next == \E t \in Tags : Add(t)
Spec == Init /\ [][Next]_tags
=====================================================
---------------- MODULE PSl10_TagList ----------------
CONSTANT Tags
VARIABLES pending, confirmed, server, msgs
vars == <<pending, confirmed, server, msgs>>
Msgs == [type : {"add", "ok", "rejected"}, tag : Tags]
TypeOK == /\ pending \subseteq Tags
          /\ confirmed \subseteq Tags
          /\ server \subseteq Tags
          /\ msgs \subseteq Msgs
Init == /\ pending = {}      \* shown greyed out, waiting for the server
        /\ confirmed = {}    \* shown normally
        /\ server = {}       \* the server's stored tags
        /\ msgs = {}
Sent(t) == \E m \in msgs : m.tag = t
\* The user types a tag; it appears at once, marked pending.
UserAdd(t) == /\ ~Sent(t)
              /\ pending' = pending \cup {t}
              /\ msgs' = msgs \cup {[type |-> "add", tag |-> t]}
              /\ UNCHANGED <<confirmed, server>>
Answered(t) == \E m \in msgs : m.tag = t /\ m.type \in {"ok", "rejected"}
ServerAccept(t) == /\ [type |-> "add", tag |-> t] \in msgs
                   /\ ~Answered(t)
                   /\ server' = server \cup {t}
                   /\ msgs' = msgs \cup {[type |-> "ok", tag |-> t]}
                   /\ UNCHANGED <<pending, confirmed>>
ServerReject(t) == /\ [type |-> "add", tag |-> t] \in msgs
                   /\ ~Answered(t)
                   /\ msgs' = msgs \cup {[type |-> "rejected", tag |-> t]}
                   /\ UNCHANGED <<pending, confirmed, server>>
ClientOk(t) == /\ [type |-> "ok", tag |-> t] \in msgs
               /\ t \in pending
               /\ pending' = pending \ {t}
               /\ confirmed' = confirmed \cup {t}
               /\ UNCHANGED <<server, msgs>>
ClientRollback(t) == /\ [type |-> "rejected", tag |-> t] \in msgs
                     /\ t \in pending
                     /\ pending' = pending \ {t}
                     /\ UNCHANGED <<confirmed, server, msgs>>
Next == \E t \in Tags : \/ UserAdd(t)
                        \/ ServerAccept(t) \/ ServerReject(t)
                        \/ ClientOk(t) \/ ClientRollback(t)
Spec == Init /\ [][Next]_vars
Fairness == \A t \in Tags :
              /\ WF_vars(ServerAccept(t) \/ ServerReject(t))
              /\ WF_vars(ClientOk(t) \/ ClientRollback(t))
FairSpec == Spec /\ Fairness

Shown == pending \cup confirmed
ByShown     == INSTANCE PSl10_TagSet WITH tags <- Shown
ByConfirmed == INSTANCE PSl10_TagSet WITH tags <- confirmed
ByServer    == INSTANCE PSl10_TagSet WITH tags <- server
ShownRefines     == ByShown!Spec
ConfirmedRefines == ByConfirmed!Spec
ServerRefines    == ByServer!Spec
ConfirmedOnServer == confirmed \subseteq server
Settles == \A t \in Tags : (t \in pending) ~> (t \notin pending)
Converges == <>[](Shown = server)
======================================================
SPECIFICATION FairSpec
CONSTANT Tags = {t1, t2}
INVARIANT TypeOK ConfirmedOnServer
PROPERTY ConfirmedRefines ServerRefines Settles Converges
CHECK_DEADLOCK FALSE
  1. Check the three mappings: what the user sees (ShownRefines), the solid tags (ConfirmedRefines), and the server's tags (ServerRefines). Which ones hold? For any that fails, describe TLC's trace as the user would see it.
  2. Is the failing one a bug in the component? Say which abstract spec the screen does refine, in one sentence.
  3. {{ref:ps-l9}} asked whether every request is eventually decided. Ask it here: check Settles with Spec instead of FairSpec, and explain the result. Then replace Fairness by two conditions: weak fairness of "the server answers some tag" and of "the client processes some reply". Is that enough here? Would it be enough for a lock that two processes take over and over?
  4. Explain why UserAdd needs the guard ~Sent(t). What could an old rejected message do if the user re-added the same tag?

Which mapping fails?

Hint

Run each mapping in its own model with one PROPERTY line. For (c), the aggregate condition only forces some enabled step. Ask whether any tag can be passed over forever when each tag needs just one answer and one reply.

Solution

(a) With the cfg as given, TLC finds no error: ConfirmedRefines, ServerRefines, Settles and Converges all hold, as do TypeOK and ConfirmedOnServer, in 36 distinct states. With PROPERTY ShownRefines, TLC reports the action property of PSl10_TagSet violated in four states: UserAdd(t1), ServerReject(t1), ClientRollback(t1). The user typed t1, saw it greyed out, then saw it vanish, as in the figure. The last step removes t1 from Shown, which no Add step can do.

(b) It's not a bug. It is the speculative-display contract from the editor example in {{lesson:refinement}}: the screen shows a guess, and a guess can be withdrawn. The screen refines "tags are added, and pending ones may be withdrawn", a different spec with a Withdraw action. What must not happen is a solid tag disappearing, and ConfirmedRefines together with ConfirmedOnServer rules that out. The design-system rule that follows is "only solid tags are promises". So pending tags need a visibly different style, and anything that copies the list, such as an export, should read confirmed.

(c) With SPECIFICATION Spec, TLC reports Settles violated. Its counterexample has both tags accepted by the server, t2's reply received, and then stuttering forever with t1 still pending, although the ok for t1 is in msgs. TLC also warns that the stuttering counterexample may be caused by a missing fairness constraint. Without fairness, nothing requires the client to process a reply. FairSpec asks for weak fairness of "answer t" and "process the reply to t" for each tag t. That suffices: once t's request is in msgs, answering it stays enabled until it happens, and so does processing the reply while t is pending.

The aggregate version also suffices here (module PSl10_TagListAgg):

AggFairness == /\ WF_vars(\E t \in Tags : ServerAccept(t) \/ ServerReject(t))
               /\ WF_vars(\E t \in Tags : ClientOk(t) \/ ClientRollback(t))
AggSpec == Spec /\ AggFairness

With SPECIFICATION AggSpec, TLC finds that Settles and Converges hold, in the same 36 states. Each tag is answered once and its reply processed once, and each such step disables itself. So "some answer happens" can only pick a different tag each time, and with finitely many tags every one gets its turn. A lock is different: if B can acquire, release and acquire again forever, "some process acquires" is satisfied by B alone, and A may wait forever. Per-item fairness is still the safer habit, because it keeps working if you later add retries that make an item's steps repeat.

(d) Messages are never removed, so after a rejection [type |-> "rejected", tag |-> t1] stays in msgs. If the user could add t1 again, ClientRollback(t1) would be enabled at once by the old message, and the new attempt would be rolled back before the server saw it. This is the stale-response problem: replies need to identify the request they answer, not just the tag. A real component would put a request id in each message, and the guard would compare ids.
