Find the design error before there is code to debug.

The upload example in {{lesson:orientation}} went wrong in the design, not in any line of code. TLA+ exists to catch that kind of error, by letting you model a system above the code level and check the model.

The diagram shows the argument of this lesson. A design error can sit in a system whose every function is correct. On the top route, you find it only if a test happens to hit the right circumstances, and the errors TLA+ aims at are the ones that are extremely hard to hit by testing. On the bottom route, you write the design down precisely and a tool checks it, so the dashed arrow takes you back to the design before you have written any code.

What TLA+ is

TLA+ is a language for high-level modeling of digital systems, and it comes with tools for checking those models. The tools you will hear about in the lecture are:

  • TLC, the model checker. A model checker explores the states a model can reach and tests your claims about them. This is the most important tool, and the one you will use.
  • TLAPS, the TLA+ proof system. Writing and checking proofs is a lot of work, and few engineers will use it.
  • The Toolbox, an IDE for writing specs and running the tools. {{lesson:tools}} also covers the VS Code extension.

“Digital systems” includes algorithms, programs, and computer systems. “High-level” means at the design level, above the code. You can't generate code from a TLA+ spec, and that is a choice about what the language is for, as you will see below.

TLA+ was designed for concurrent and distributed systems. Lamport's advice is direct: if you design such systems and care whether they work, use TLA+ or some other method to specify and check the design precisely. For other programming, he says plainly that he doesn't know exactly how useful it is. In his own small programs it sometimes helps and sometimes doesn't. His broader claim is that it gives most engineers a new way of thinking, which helps even when the language and tools don't apply.

Abstraction is the skill you are learning

Abstraction means simplifying by removing irrelevant details. Lamport calls it perhaps the most important part of engineering, since you can't get a complex system right unless you understand it, and you understand it only through abstraction. He credits his best-known work to this ability: stating important problems that details had hidden.

In the diagram, a model keeps the left region and drops both right regions: the parts that matter less, and the lower-level details of how things are implemented. Choosing that boundary is the hard part. The former Intel engineer quoted in the lecture says the same thing: the difficulty in learning TLA+ is learning to think abstractly about the system, and doing so improves the design process.

What engineers report

The lecture gives two pieces of evidence. Treat them as reports from specific teams, not as promises.

WhoWhat they reported
Amazon Web Services, in the 2015 Communications of the ACM paperUsed on 10 large, complex systems when written (14 by some time in 2014, per Lamport), by 7 teams. It added significant value in each: subtle bugs they were sure they wouldn't otherwise have found, or the confidence to make aggressive optimizations. Engineers from entry level to principal got useful results in 2 to 3 weeks.
A real-time operating system team led by Eric VerhulstThe TLA+ abstraction led to a much cleaner architecture. The code was about 10 times smaller than the previous version, which flew on the Rosetta spacecraft.

The second result answers a question you may already have. If a spec doesn't produce code, why not spend the time improving the code? Because you don't get a factor of 10 from better coding. You get it from a cleaner architecture, and an architecture is a specification above the code level. That team described theirs as a TLA+ spec and debugged it with the tools. Don't expect a tenfold reduction yourself: it is one case.

What you can check

“Works right” has to become something a tool can test. The properties TLA+ can check are conditions on individual executions. A system satisfies such a property if and only if every possible execution does.

Read the diagram one row at a time. “Doesn't produce a wrong answer” can be judged by looking at one row, and execution 3 fails it, so the system fails it. “99% of executions produce the right answer” can't be judged from any single row. It describes the collection, so TLA+ can't check it.

Predict: can TLC check “95% of requests finish successfully”? What about “no request is charged twice”?

The first is a statistic over many executions, so no. The second can be judged by examining one execution: did any request get charged twice in it? So yes, once you have modeled requests and charges. When a requirement is statistical, look for the per-execution rule underneath it.
