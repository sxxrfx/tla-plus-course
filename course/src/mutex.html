Separate exclusive access from eventual access.

{{lesson:fairness}} separated safety from liveness, and {{lesson:abp}} introduced strong fairness. A lock needs all of it: no two owners at once, and waiters eventually served. One can hold without the other, and the second depends on which fairness you assume.

Begin with an abstract owner variable. Acquire assumes an atomic primitive that claims an unowned lock.

---------------- MODULE Lock ----------------
EXTENDS Naturals, FiniteSets
CONSTANTS Processes, NoOwner
ASSUME NoOwner \notin Processes
VARIABLES owner, pc
vars == <<owner, pc>>
Init == /\ owner = NoOwner
        /\ pc = [p \in Processes |-> "outside"]
Request(p) ==
    /\ pc[p] = "outside"
    /\ pc' = [pc EXCEPT ![p] = "waiting"]
    /\ UNCHANGED owner
Acquire(p) ==
    /\ owner = NoOwner
    /\ pc[p] = "waiting"
    /\ owner' = p
    /\ pc' = [pc EXCEPT ![p] = "critical"]
Release(p) ==
    /\ owner = p
    /\ owner' = NoOwner
    /\ pc' = [pc EXCEPT ![p] = "outside"]
Next == \E p \in Processes: Request(p) \/ Acquire(p) \/ Release(p)
Spec == Init /\ [][Next]_vars
MutualExclusion ==
    Cardinality({p \in Processes : pc[p] = "critical"}) <= 1
OwnerAgrees == \A p \in Processes: pc[p] = "critical" => owner = p
\* Three fairness assumptions, weakest first.
ReleaseFair == \A p \in Processes: WF_vars(Release(p))
AggregateWF == ReleaseFair
    /\ WF_vars(\E p \in Processes: Acquire(p))
PerProcessWF == ReleaseFair
    /\ \A p \in Processes: WF_vars(Acquire(p))
PerProcessSF == ReleaseFair
    /\ \A p \in Processes: SF_vars(Acquire(p))
SpecAggregate == Spec /\ AggregateWF
SpecWF == Spec /\ PerProcessWF
SpecSF == Spec /\ PerProcessSF
NoStarvation ==
    \A p \in Processes: (pc[p] = "waiting") ~> (pc[p] = "critical")
=============================================

With Processes = {A, B}, TLC finds 8 distinct states and both safety invariants hold on Spec. Those are the grid’s 8 nodes. The corner where both are critical has no incoming edge, because Acquire requires owner = NoOwner. The useful invariant is the relation OwnerAgrees: a process in the critical section must be the owner.

Now the liveness question

Safety says nothing about the red cycle. A waits; B requests, acquires and releases; B requests again. NoStarvation uses leads-to from {{lesson:fairness}}, so it asks about every waiter. Here are TLC’s answers:

SpecificationAssumption addedNoStarvation
SpecAggregateWeak fairness of “some process acquires”Violated
SpecWFWeak fairness of each process’s AcquireViolated
SpecSFStrong fairness of each process’s AcquireHolds
Predict: why is per-process weak fairness not enough here?

Weak fairness only forces an action that stays enabled continuously. On the red cycle, Acquire(A) is enabled in “A wait, B wait” but disabled in “A wait, B crit”, so it is never continuously enabled and A can be skipped forever. Strong fairness also forces an action that is enabled again and again, which is the case here.

Strong fairness here is an assumption about the lock. It does not build anything. A real system earns it with a queueing discipline, or with an algorithm that does the work itself.

Without the primitive

Suppose the lock is just a shared value, checked in one step and written in the next. This is Look and Take in place of Acquire:

Look(p) ==
    /\ pc[p] = "outside"
    /\ owner = NoOwner
    /\ pc' = [pc EXCEPT ![p] = "saw-free"]
    /\ UNCHANGED owner
Take(p) ==
    /\ pc[p] = "saw-free"
    /\ owner' = p
    /\ pc' = [pc EXCEPT ![p] = "critical"]

It is the {{lesson:inventory}} race again, and TLC reports it after 4 steps. Peterson’s algorithm gets mutual exclusion with only single reads and writes, using a flag for each process and a shared turn. Written in PlusCal from {{lesson:pluscal}}:

---------------- MODULE Peterson ----------------
EXTENDS Integers
(*--algorithm Peterson
variables flag = [p \in {0, 1} |-> FALSE], turn = 0;
define
    MutualExclusion == ~(pc[0] = "cs" /\ pc[1] = "cs")
    NoStarvation == \A p \in {0, 1}: (pc[p] = "wait") ~> (pc[p] = "cs")
end define;
fair process P \in {0, 1}
begin
ncs:  while TRUE do
setf:   flag[self] := TRUE;
sett:   turn := 1 - self;
wait:   await ~flag[1 - self] \/ turn = self;
cs:     skip;
exit:   flag[self] := FALSE;
      end while;
end process;
end algorithm; *)
=================================================

TLC finds 42 distinct states; MutualExclusion holds, and NoStarvation holds with just the weak fairness of fair process. The strong fairness that the abstract lock had to assume is unnecessary here, because turn stops one process winning forever. The order of the writes matters. Swap the setf and sett steps and TLC reports a violation after 8 steps with both processes at cs.

Worked architecture: concurrent checkout

Two browser requests try to reserve the final concert seat. Request A acquires the lock, reads stock = 1, and pauses. Request B arrives. A lock contract must disable B’s Acquire until A releases, and must not merely discourage it by convention.

The guard on owner proves nothing about writes that bypass the protocol. In the diagram every arrow to Stock comes from whoever holds the lock, and every stock-changing action in your system must obey that rule.

Now put A and B on different application servers. A process-local mutex on server 1 does not exclude server 2. Represent that as two owner variables and both requests can enter. Either put ownership in a shared authority with the necessary atomic semantics, or use a storage operation that directly enforces the inventory constraint. The model should describe the shared resource you actually use.

The failure model comes next. If the owner crashes, owner stays set and everyone waits forever. Clearing it on a timeout is unsafe if the old process can still reach the resource, because a paused process is not a dead one. {{lesson:fencing}} takes this up with leases and fencing tokens.

Predict: can we recover from A crashing by unconditionally clearing owner?

Only under assumptions that ensure A cannot continue writing under its old authority. A delayed or paused process is not necessarily dead. Model the resumed write explicitly; otherwise the recovery action may conceal the violation.
