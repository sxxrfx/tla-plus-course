Claim the puzzle is unsolvable, and TLC shows you the solution.

You have the jugs' variables from {{lesson:diehard}} and their actions from {{lesson:actions}}. Now run them. The trick for saving the heroes is one line: tell TLC that the big jug never holds 4 gallons, and let it prove you wrong.

Run the module

Save the module as DieHard.tla. It contains complete definitions of SmallToBig and BigToSmall, so keep your own solutions from {{lesson:actions}} handy and don't study these until you have seen the error trace.

The complete DieHard module (open to copy; contains the pour solutions) 
------------------------------ MODULE DieHard ------------------------------
EXTENDS Integers

VARIABLES small, big

TypeOK == /\ small \in 0..3
          /\ big   \in 0..5

Init == /\ big   = 0
        /\ small = 0

FillSmall == /\ small' = 3
             /\ big'   = big

FillBig == /\ big'   = 5
           /\ small' = small

EmptySmall == /\ small' = 0
              /\ big'   = big

EmptyBig == /\ big'   = 0
            /\ small' = small

SmallToBig == IF big + small =< 5
                THEN /\ big'   = big + small
                     /\ small' = 0
                ELSE /\ big'   = 5
                     /\ small' = small - (5 - big)

BigToSmall == IF big + small =< 3
                THEN /\ big'   = 0
                     /\ small' = big + small
                ELSE /\ big'   = small - (3 - big)
                     /\ small' = 3

Next == \/ FillSmall
        \/ FillBig
        \/ EmptySmall
        \/ EmptyBig
        \/ SmallToBig
        \/ BigToSmall

NotSolved == big /= 4
=============================================================================

First run it with only INIT Init and NEXT Next in the config. TLC reports no error and 16 distinct states. No error means little here, because you asked it to check nothing. It shows that TLC could run the spec. The 16 are the filled cells in the grid above, the states reachable in some behavior, the same circles you saw in the lab.

Next, check type correctness by adding INVARIANT TypeOK. Remember from {{lesson:counter}} that an invariant must hold in every reachable state. Still no error, so every filled cell has values in range.

Saving our heroes

The 4 gallons must be in the big jug, since the small one holds only 3. So claim that it never happens. “Not equal” is /= or # in ASCII.

INIT Init
NEXT Next
INVARIANT TypeOK
INVARIANT NotSolved

In the Toolbox, you can type big /= 4 directly under Invariants. A config file needs a named formula, which is why the module defines NotSolved. Run it, and TLC reports Invariant NotSolved is violated, along with this behavior:

That is the answer, in 7 states: fill the big jug; pour into the small one, leaving 2; empty the small one; pour the 2 across; fill the big jug again; and top up the small one, which holds 2 and takes exactly 1. That leaves 4. Each state in TLC's output names its action, as in State 3: <BigToSmall ...>, which is the label above each arrow in the diagram. In the Toolbox, double-clicking an action in the trace jumps to the part of Next that allowed it.

Run with one worker for the shortest trace. With -workers 1, TLC searches in strict breadth-first order, and we got the lecture's 7-state trace in each run. With several workers, states may be processed out of order. One of our runs reported a longer, 9-state trace ending at small 0, big 4. That trace is valid, but it isn't the shortest.

Predict: there are two red cells in the grid. Why does the lecture's trace end at small 3, big 4 and not small 0, big 4?

TLC searches breadth-first, so with one worker it finds a nearest violation first. Small 3, big 4 is 7 states from the start. Small 0, big 4 is further: at best you empty the small jug after reaching small 3, big 4, which takes 8 states. The 9-state trace in the callout got there by a different route.

Reading SmallToBig and BigToSmall

Now compare your definitions. Look at the ELSE of SmallToBig. The big jug is filled, so the amount poured is 5 - big, and that is what comes out of the small jug. Someone new to TLA+ might say this is wrong, since big was set to 5 on the line above. But you know better from {{lesson:logic}}: /\ is commutative, and all these values of big are from the current state.

A warning follows. = is commutative too, so small' = 0 and 0 = small' are equivalent formulas, and the specs are equivalent. TLAPS treats them the same, but TLC does not. We ran the flipped version, and it stopped with:

In evaluation, the identifier small is either undefined or not an operator.

TLC can almost always handle the ways engineers naturally write specs, and later lectures explain why. For now, follow the lecture's rule: use a primed variable v' only in formulas of the form v' = ... or v' \in ..., where the right side has no primes.

Check your definitions

Comment out the module's two pour definitions by placing (* and *) around them, and add your own. Fix what the parser finds, then run TLC. Your definitions are probably correct if TLC finds no execution errors, no violation of TypeOK, and a violation of big /= 4. To be sure, remove NotSolved and run again with only TypeOK, since the search stops at the first violation. If it all passes, try writing the definitions a different way. You learn most from your mistakes.

With no invariants listed, TLC reports no error and 16 states. What does that show?

A good experiment can fail. The lecture's test expects a violation of big /= 4. A check you expect to fail shows that your setup reaches the interesting states. If a deliberately false claim passes, investigate the setup before you trust anything else.

Transfer: ask for a path through a product

The trick works on any “can this happen?” question. Here is the whole cart module from {{lesson:logic}}, now with a Checkout action that you can read after {{lesson:actions}}. It starts with both unknowns free: \in lets a variable begin with either value of a set, so there are 4 initial states.

---------------- MODULE Cart ----------------
EXTENDS Integers
VARIABLES items, termsAccepted, inStock, ordered

Init == /\ items = 2
        /\ termsAccepted \in {TRUE, FALSE}
        /\ inStock \in {TRUE, FALSE}
        /\ ordered = FALSE

Eligible == /\ items > 0
            /\ termsAccepted

CanCheckout == /\ Eligible
               /\ inStock

Checkout == /\ CanCheckout
            /\ ~ordered
            /\ ordered' = TRUE
            /\ items' = items
            /\ termsAccepted' = termsAccepted
            /\ inStock' = inStock

Next == Checkout

OrderOK == ordered => termsAccepted
NeverOrdered == ~ordered
=============================================

With INVARIANT OrderOK and the deadlock check off, TLC finds no error in 5 distinct states. Now claim INVARIANT NeverOrdered. TLC reports a violation with a 2-state trace: a cart with the terms accepted and goods in stock, then Checkout. You now have a concrete example of a successful order, and evidence that the implication in that lesson wasn't vacuous. To reach a harder state, you state that it is unreachable and let TLC produce the steps.
