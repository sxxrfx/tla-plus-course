Problem set 2: write the next-state formula.

These problems practice Lecture 2: an initial-state formula, a next-state formula with primed variables, evaluating a formula on a pair of states, and splitting Next into named cases joined by \/. They draw on {{ref:program}} and {{ref:logic}}, and on the models you built in {{ref:ps-l1}}.

You run TLC in the next chapter, so for now check your formulas by evaluating them on pairs of states, as {{ref:program}} did. One consequence of reading Next as a formula matters in every problem. A case that says nothing about x' is true whatever the next value of x is, so it allows x to change arbitrarily. Until a later lesson gives a shorthand, write x' = x for each variable a case leaves alone. Some solutions also count states: a state that occurs in at least one behavior is called reachable.

Problem 1●○○Networking

An HTTP client's retry loop as Init and Next

Draws on {{ref:states}}, {{ref:program}} and {{ref:logic}}.

A mobile app's HTTP client makes up to three attempts to send a request, stopping at the first success. Simplified, its code is:

bool ok = false;
int attempts = 0;
void fetchWithRetry()
{ while (!ok && attempts < 3) {   // test
    ok = send();                   // send
    attempts = attempts + 1;       // count
  }
}                                  // done

send() returns true on success and false on failure, and any call can do either, just as someNumber() in {{ref:states}} could return any number. Model the program the way that lesson modeled the tiny C program, with three variables: attempts, ok, and pc, which is "test", "send", "count" or "done" according to which statement runs next. Testing the loop condition is one step. The figure shows the control flow you are writing down.

  1. Write Init.
  2. Write Next as Test \/ Exit \/ Send \/ Count, defining each case as a bulleted /\ list, one case per arrow in the figure. Each case must say what the next value of every variable is.
  3. Evaluate your Next on two pairs of states. First: attempts = 2, ok = FALSE, pc = "count" and attempts' = 3, ok' = FALSE, pc' = "test". Second: attempts = 3, ok = FALSE, pc = "test" and attempts' = 3, ok' = FALSE, pc' = "send".
  4. List every state in which the program can be when pc = "done".
Which formula is the guard of Exit?

Hint

In Send, the next value of ok is TRUE or FALSE, and you have no set to put it in. “Or” is \/, so write two equalities joined by it, in parentheses. Exit applies when the while condition is false: negate it with ~.

Solution 
------------------ MODULE PSl2_Retry ------------------
EXTENDS Integers
VARIABLES attempts, ok, pc

Init == /\ attempts = 0
        /\ ok = FALSE
        /\ pc = "test"

Test == /\ pc = "test"
        /\ ~ok
        /\ attempts < 3
        /\ pc' = "send"
        /\ attempts' = attempts
        /\ ok' = ok

Exit == /\ pc = "test"
        /\ (ok \/ ~(attempts < 3))
        /\ pc' = "done"
        /\ attempts' = attempts
        /\ ok' = ok

Send == /\ pc = "send"
        /\ (ok' = TRUE \/ ok' = FALSE)
        /\ pc' = "count"
        /\ attempts' = attempts

Count == /\ pc = "count"
         /\ attempts' = attempts + 1
         /\ pc' = "test"
         /\ ok' = ok

Next == Test \/ Exit \/ Send \/ Count

BudgetOK == attempts \in 0..3
DoneOK == pc = "done" => (ok \/ attempts = 3)
=======================================================

The four cases match the four arrows. Send is where the nondeterminism lives: (ok' = TRUE \/ ok' = FALSE) plays the role that i' \in 0..1000 played for someNumber(). Exit's guard is the negation of the while condition, so in every "test" state exactly one of Test and Exit applies. BudgetOK and DoneOK are two claims about every reachable state that you will check with TLC in the next problem set.

(c) The first pair satisfies Next through Count: pc is "count", 3 = 2 + 1, pc' is "test" and ok keeps its value. The second pair doesn't. Its pc is "test", so only Test or Exit could be true. Test needs attempts < 3, which is false, and Exit needs pc' = "done". The client has used its three attempts and can't send again.

(d) 4 states: ok = TRUE with attempts equal to 1, 2 or 3, and ok = FALSE with attempts = 3. In each, no case of Next applies, so the program halts, as {{ref:program}}'s tiny program did when pc was "done". We checked this module with TLC, which you install in the next chapter. It has 20 reachable states, and BudgetOK and DoneOK are true in all of them.

Problem 2●●○Algorithms

Binary search with git bisect: which steps does Next allow?

Draws on {{ref:program}} and {{ref:logic}}.

A performance regression slipped into one of 16 commits, numbered 1 to 16 in order. Commit 16 is known to be bad, the commit before commit 1 is known to be good, and once a commit is bad every later one is bad too. git bisect finds the first bad commit by binary search: you test a commit in the suspect range, mark it good or bad, and the range shrinks. Git checks out the middle commit for you, but you can test any commit you like, for example when the middle one doesn't build, and mark it with git bisect good <rev> or git bisect bad <rev>.

This module models only the suspect range: the first bad commit is somewhere in lo..hi.

------------------ MODULE PSl2_Bisect ------------------
EXTENDS Integers
VARIABLES lo, hi

Init == /\ lo = 1
        /\ hi = 16

MarkBad == /\ lo < hi
           /\ hi' \in lo..(hi - 1)
           /\ lo' = lo

MarkGood == /\ lo < hi
            /\ lo' \in (lo + 1)..hi
            /\ hi' = hi

Next == MarkBad \/ MarkGood
========================================================

In MarkBad, the tested commit is hi' and it was bad, so the range now ends there. In MarkGood, the tested commit is lo' - 1 and it was good, so the range now starts just after it. Neither case says which commit to test. Binary search tests the middle; this Next allows every choice, so it describes binary search along with every other way of bisecting.   1. For each pair in the table, decide whether it satisfies Next, and if it does, through which case. Say in words what the step means for the person bisecting.
  2. How many next states does the initial state have?
  3. An implementer writes MarkBad with hi' \in lo..hi instead. Which pair in the table does this version allow that the original doesn't? What does that step mean, and why could a program built on it loop forever?
  4. Next has no case that applies when lo = hi. What does it mean when the state machine halts?

Hint

Each case is a conjunction, so every line must be true. In MarkBad, lo must stay the same and hi' must be in lo..(hi - 1), which you can write out for the given lo and hi. A pair satisfies Next if either case is true.

Solution

(a) a: MarkBad; commit 8 was bad, so the first bad commit is in 1..8. b: MarkGood; commit 8 was good, so it is in 9..16. c: no. MarkBad needs hi' in 9..15 and MarkGood needs lo' in 10..16, and here neither end moved. d: no; both cases keep one end fixed, and here both moved. e: no; the guard lo < hi is false, since the answer is already known. f: MarkBad; commit 5 was bad, so commit 5 is the answer. g: MarkGood; commit 3 was good, so commit 4 is the answer. Four pairs satisfy Next.

(b) 30: 15 from MarkBad, one for each hi' in 1..15, and 15 from MarkGood, one for each lo' in 2..16. Binary search would choose one of these 30; the spec describes them all, as i' \in 0..1000 described every value someNumber() might return.

(c) Pair c. With hi' \in lo..hi, MarkBad allows hi' = hi: “test commit 16, find it bad.” Commit 16 was already known to be bad, so the step teaches nothing and leaves the state unchanged. It is the classic off-by-one in binary search. Code that computes the middle as (lo + hi + 1) / 2, rounding up, and sets hi = mid when the test is bad, picks mid = hi once lo + 1 = hi. If that commit is bad, nothing changes, and the loop repeats the same step forever. We ran both modules through TLC: each reaches the same 136 states, every range with 1 ≤ lo ≤ hi ≤ 16. The bug adds no new state, only a step from a state to itself, so you can't find it by asking which states are reachable. You find it by reading Next.

(d) The state machine halts when lo = hi: the range holds one commit, which is the first bad one. Here halting is the intended end, as it was for the tiny program in {{ref:program}}.

Problem 3●●○Databases

Find the step a buggy connection pool allows

Draws on {{ref:program}} and {{ref:logic}}.

A web service talks to Postgres through a connection pool capped at 3 connections, because each Postgres connection is a separate server process and costs memory. The pool starts empty and opens connections only when needed. It counts idle connections (open, not in use) and busy ones (checked out by a request). Four things can happen:

  • Open: if fewer than 3 connections exist, the pool opens one; it starts idle.
  • Acquire: a request checks out an idle connection.
  • Release: a request returns its connection, which becomes idle.
  • Evict: the pool closes an idle connection that has been unused for too long.

The figure shows part of the state graph the authors have in mind. A teammate wrote this module. PoolOK is the pool's promise: no count is negative, and there are never more than Max connections.

----------------- MODULE PSl2_PoolBug -----------------
EXTENDS Integers
VARIABLES idle, busy

Max == 3

Init == /\ idle = 0
        /\ busy = 0

Open    == /\ idle + busy < Max
           /\ idle' = idle + 1
           /\ busy' = busy

Acquire == /\ busy < Max
           /\ idle' = idle - 1
           /\ busy' = busy + 1

Release == /\ busy > 0
           /\ busy' = busy - 1
           /\ idle' = idle + 1

Evict   == /\ idle > 0
           /\ idle' = idle - 1
           /\ busy' = busy

Next == Open \/ Acquire \/ Release \/ Evict

PoolOK == /\ idle \in 0..Max
          /\ busy \in 0..Max
          /\ idle + busy \in 0..Max
=======================================================
  1. For each of the four cases, name its guard and say which variables change.
  2. Find a pair of states that satisfies this Next, where the first state satisfies PoolOK and the second doesn't. Start from the initial state.
  3. Which case is wrong? Describe the real bug it stands for in the pool's code, and fix the case.
  4. With your fix, argue case by case that if a state satisfies PoolOK, every next state allowed by Next does too.
Which case is wrong?

Hint

A guard should test exactly what the change needs. A case that subtracts 1 from a count needs that count to be above 0 first. Compare each case's guard with the variable it decreases.

Solution

(a) Open: guard idle + busy < Max; idle goes up by 1. Acquire: guard busy < Max; idle goes down and busy up. Release: guard busy > 0; busy goes down and idle up. Evict: guard idle > 0; idle goes down.

(b) idle = 0, busy = 0 and idle' = -1, busy' = 1. The initial state satisfies PoolOK. Acquire's guard busy < Max is true, so Acquire, and therefore Next, is true for this pair, and the second state has idle = -1. We ran the module through TLC: it reports PoolOK violated by exactly this two-state behavior.

(c) Acquire checks whether the pool has room (busy < Max) when it should check whether an idle connection exists. In code, this is a pool that tests “not at capacity” before taking from the idle list, and on an empty list gets nothing, or a connection another request already holds. The fix:

Acquire == /\ idle > 0
           /\ idle' = idle - 1
           /\ busy' = busy + 1

When the pool is empty, a request now has to wait for Open first, as in the figure, where the only arrow out of the initial state is Open.

(d) Suppose a state satisfies PoolOK. Open raises idle + busy by 1, but only when it is below Max, so it stays in 0..Max. Acquire and Release move one connection between the counts, so the total is unchanged, and each decreases a count only when its guard says that count is above 0. Evict lowers idle only when it is above 0, and lowers the total. So every case keeps every conjunct of PoolOK true. Arguing one step at a time like this, without listing behaviors, is how you will later show that a claim holds in every reachable state. TLC agrees: with the fix it finds 10 reachable states and no violation.

Problem 4●●●Design systems

The design-system Button as Init and Next

Synthesis. Draws on {{ref:ps-l1}} (the Button problem), {{ref:orientation}}, {{ref:states}}, {{ref:program}} and {{ref:logic}}.

In {{ref:ps-l1}}, problem 3, you chose variables for the design system's Button: phase, disabled, and inflight, the number of requests started and not yet finished. Now write its spec. The rules, as the design system's documentation should state them:

  • Initially the phase is idle and no request is in flight. The page may have set disabled either way.
  • Click: possible only when the button isn't disabled and the phase is idle or error. It starts a request and the phase becomes loading.
  • Resolve and Reject: the request of a loading button finishes, and the phase becomes success or error.
  • Reset: from success, back to idle (the two seconds are left out).
  • Toggle: the page flips disabled, at any time.

The figure shows four sequences of states that people on the team wrote down while discussing the double-charge ticket.

  1. Write a module with Init and Next == Click \/ Resolve \/ Reject \/ Reset \/ Toggle. Use TRUE and FALSE for disabled.
  2. Check every step of A to D against your Next, and each first state against Init. For each sequence that is not a behavior, name the first step that fails and the case that would have to change to allow it.
  3. Define OneRequest (inflight is 0 or 1) and LoadingOK (if the phase is loading, exactly one request is in flight). Explain what LoadingOK would tell you in a model where Click could never happen.
  4. Sequence C is the double charge. Write the change to Click that would make C a behavior.

Hint

“Either way” in Init is a disjunction: (disabled = TRUE \/ disabled = FALSE). “Idle or error” in Click's guard is one too. Remember x' = x for every variable a case leaves alone: Toggle leaves two of them alone.

Solution 
----------------- MODULE PSl2_Button -----------------
EXTENDS Integers
VARIABLES phase, disabled, inflight

Init == /\ phase = "idle"
        /\ (disabled = TRUE \/ disabled = FALSE)
        /\ inflight = 0

Click   == /\ ~disabled
           /\ (phase = "idle" \/ phase = "error")
           /\ phase' = "loading"
           /\ inflight' = inflight + 1
           /\ disabled' = disabled

Resolve == /\ phase = "loading"
           /\ phase' = "success"
           /\ inflight' = inflight - 1
           /\ disabled' = disabled

Reject  == /\ phase = "loading"
           /\ phase' = "error"
           /\ inflight' = inflight - 1
           /\ disabled' = disabled

Reset   == /\ phase = "success"
           /\ phase' = "idle"
           /\ inflight' = inflight
           /\ disabled' = disabled

Toggle  == /\ disabled' = ~disabled
           /\ phase' = phase
           /\ inflight' = inflight

Next == Click \/ Resolve \/ Reject \/ Reset \/ Toggle

OneRequest == inflight \in 0..1
LoadingOK  == (phase = "loading") => (inflight = 1)
======================================================

(b) A is a behavior: Click, Reject, Click again from error (the retry), then Resolve. B is a behavior: Click, then Toggle while loading, then Resolve, then Reset. Nothing in Resolve or Reset depends on disabled, so the response still lands, as you predicted in {{ref:ps-l1}}. C fails at step 2: the phase stays loading while inflight goes from 1 to 2, which only Click could do, and Click requires idle or error. D fails at step 3: success to loading is again a Click, from a phase Click doesn't allow. To allow D you would change Click's guard; whether a click on the check mark should start a new request is a design decision the documentation must state.

(c) Both definitions are in the module. LoadingOK is an implication, and {{ref:logic}} warned about it: if Click could never happen, the phase would never be loading, so LoadingOK would be true in every state without saying anything. Here it isn't vacuous, because A and B pass through loading states. We checked the module with TLC: it has 8 reachable states, 4 phases times 2 values of disabled, with inflight fixed by the phase, and OneRequest and LoadingOK hold in all of them.

(d) Replace the phase condition so that it allows loading, for example /\ ~(phase = "success"). Then C's second step satisfies Click. We ran that variant through TLC as well: OneRequest fails in a three-state behavior, idle with 0, loading with 1, loading with 2, which is exactly C. The spec turns the support ticket into a one-line difference in a guard, and the design-system documentation can now say precisely what the Button guarantees: at most one request per Button at a time. As in {{ref:ps-l1}}, the server still has to recognise a repeated payment that arrives some other way, such as a retry after a lost reply.
