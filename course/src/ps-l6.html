Problem set 6: what a commit protocol promises, and what it doesn't.

Lecture 6 turned TCommit into a protocol: records as messages, a grow-only set of messages as the network, and UNCHANGED for frames. These problems change TwoPhase the way real teams do, adding a business rule, a crash, a side effect, and see what breaks. They reuse functions and quantifiers from {{ref:sets}}, the agreement spec of {{ref:ps-l5}}, and TLC's deadlock check from {{lesson:counter}}.

Most modules here are the lesson's TwoPhase with a few lines changed, and they end with INSTANCE TCommit, so keep TCommit.tla from {{lesson:tcommit}} in the same folder. For trace lengths, run TLC with -workers 1.

Problem 1●○○Travel booking

A trip where the car is optional

Draws on {{ref:transactions}}, {{ref:tcommit}} and {{ref:sets}}.

A travel site sells trips: a flight, a hotel and a rental car, each booked in a different supplier's system. The booking service runs two-phase commit exactly as the TwoPhase spec in {{lesson:transactions}} describes. It is the TM, and the three suppliers are RMs. Preparing means a supplier holds the seat, room or car. A product manager asks for a change: “The car is optional. If the car supplier can't confirm, book the trip without it.” A developer implements it with one line in TMCommit:

TMCommit ==
  /\ tmState = "init"
  /\ {"flight", "hotel"} \subseteq tmPrepared   \* the car is optional
  /\ tmState' = "done"
  /\ msgs' = msgs \cup {[type |-> "Commit"]}
  /\ UNCHANGED <<rmState, tmPrepared>>

Everything else is the lesson's TwoPhase, renamed PSl6_Booking. The config uses CONSTANT RM = {"flight", "hotel", "car"}, the invariants TPTypeOK and TCConsistent, and CHECK_DEADLOCK FALSE.

  1. Run the unchanged TwoPhase with these three RMs first. What do you expect for the state count, and why?
  2. Make the change and run TLC. Explain the trace.
  3. Add this invariant, which says that an RM commits only after it prepared, and run again with it as the only invariant besides TPTypeOK. What does TLC find? Why does the lesson's TwoPhase get away with no guard in RMRcvCommitMsg? 
    CommitAfterPrepare == \A r \in RM : rmState[r] = "committed"
                         => [type |-> "Prepared", rm |-> r] \in msgs
  4. Propose a design that meets the product manager's request and keeps TCConsistent true.

Why can RMRcvCommitMsg in the lesson's spec omit a guard on rmState[r]?

Hint

Once the Commit message is in msgs, what can the car do while it is still working? Look at the guards of RMChooseToAbort and RMRcvCommitMsg.

Solution

(a) No error and 288 distinct states, the lesson's count. The RMs' names don't matter, only how many there are.

(b) TLC reports Invariant TCConsistent is violated with an 8-state trace:

The flight and hotel prepare and the TM records both. That is enough for the new guard, so the TM commits, and the flight receives Commit. The car never prepared, so RMChooseToAbort("car") is still enabled, and it aborts. One RM committed and another aborted, which TCommit forbids. In business terms this might even be the outcome the product manager wanted. But the spec claimed all or nothing for three RMs, and the code now does something else. The problem is the mismatch.

(c) TLC reports Invariant CommitAfterPrepare is violated with a 7-state trace that ends in RMRcvCommitMsg("car"): the car, still working, receives Commit and becomes committed without ever having held a car. In the lesson's spec the invariant holds (TLC: no error, 288 states, module PSl6_BookingOrig), because a Commit message can only exist once every RM is in tmPrepared. RMRcvCommitMsg relies on TMCommit's guard. Change that guard and every receive action becomes wrong too, even though nobody touched it.

(d) Make the transaction say what the business means. Run two-phase commit over RM = {"flight", "hotel"}, the parts that must succeed together. TLC: no error in 56 states. Then book the car as a separate step after the trip commits, and if that fails, tell the customer. If the car really must be all-or-nothing with the rest, it has to stay an RM, and the trip aborts when the car can't be held. Either way the spec and the code agree on which RMs share a fate.

Problem 2●●○Databases

Postgres prepared transactions and a dead coordinator

Draws on {{ref:transactions}}, {{ref:messages}} and {{ref:counter}}.

An app server writes an order to one Postgres database and a payment to another, using Postgres's own two-phase commit. On each database it runs PREPARE TRANSACTION 'tx42', then COMMIT PREPARED 'tx42' on both, or ROLLBACK PREPARED 'tx42'. A prepared transaction is stored on disk, survives a database restart, and keeps every lock it holds until one of those two commands arrives. If the app server's session drops before PREPARE TRANSACTION, Postgres rolls the transaction back. Meanwhile a nightly report session wants to update a row the payment locked.

The model is TwoPhase with the app server as the TM and three changes. The TM can crash and stay down (TMCrash), and an RM can prepare only while the TM is up. A report variable models the waiting session. A Finished action marks the intended end, so that the deadlock check can stay on. A constant DBA picks what a database administrator may do by hand while the app server is down.

The module (open to copy) 
---------------------------- MODULE PSl6_Prepared ----------------------------
CONSTANTS RM,            \* the Postgres databases in the transaction
          DBA            \* the DBA's rule: "never", "blind", or "checklog"
VARIABLES
  rmState,               \* rmState[r] is the state of r's transaction
  tmState,               \* the app server: "init", "done", or "down"
  tmPrepared,            \* the databases the app server knows are prepared
  msgs,                  \* every message ever sent
  report                 \* a session on "payments" blocked on a row lock
vars == <<rmState, tmState, tmPrepared, msgs, report>>

Messages == [type : {"Prepared"}, rm : RM] \cup [type : {"Commit", "Abort"}]

TypeOK ==
  /\ rmState \in [RM -> {"working", "prepared", "committed", "aborted"}]
  /\ tmState \in {"init", "done", "down"}
  /\ tmPrepared \subseteq RM
  /\ msgs \subseteq Messages
  /\ report \in {"waiting", "done"}

Init ==
  /\ rmState = [r \in RM |-> "working"]
  /\ tmState = "init"
  /\ tmPrepared = {}
  /\ msgs = {}
  /\ report = "waiting"
-----------------------------------------------------------------------------
TMRcvPrepared(r) ==
  /\ tmState = "init"
  /\ [type |-> "Prepared", rm |-> r] \in msgs
  /\ tmPrepared' = tmPrepared \cup {r}
  /\ UNCHANGED <<rmState, tmState, msgs, report>>

TMCommit ==                                  \* COMMIT PREPARED on each database
  /\ tmState = "init"
  /\ tmPrepared = RM
  /\ tmState' = "done"
  /\ msgs' = msgs \cup {[type |-> "Commit"]}
  /\ UNCHANGED <<rmState, tmPrepared, report>>

TMAbort ==                                   \* ROLLBACK PREPARED on each database
  /\ tmState = "init"
  /\ tmState' = "done"
  /\ msgs' = msgs \cup {[type |-> "Abort"]}
  /\ UNCHANGED <<rmState, tmPrepared, report>>

TMCrash ==                                   \* the app server dies and stays down
  /\ tmState # "down"
  /\ tmState' = "down"
  /\ UNCHANGED <<rmState, tmPrepared, msgs, report>>

RMPrepare(r) ==                \* the app server's PREPARE TRANSACTION succeeds
  /\ tmState = "init"
  /\ rmState[r] = "working"
  /\ rmState' = [rmState EXCEPT ![r] = "prepared"]
  /\ msgs' = msgs \cup {[type |-> "Prepared", rm |-> r]}
  /\ UNCHANGED <<tmState, tmPrepared, report>>

RMChooseToAbort(r) ==          \* an error, or the app server's session is lost
  /\ rmState[r] = "working"
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ UNCHANGED <<tmState, tmPrepared, msgs, report>>

RMRcvCommitMsg(r) ==
  /\ [type |-> "Commit"] \in msgs
  /\ rmState' = [rmState EXCEPT ![r] = "committed"]
  /\ UNCHANGED <<tmState, tmPrepared, msgs, report>>

RMRcvAbortMsg(r) ==
  /\ [type |-> "Abort"] \in msgs
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ UNCHANGED <<tmState, tmPrepared, msgs, report>>

\* The report's UPDATE waits for the row lock until the transaction ends.
ReportRuns ==
  /\ report = "waiting"
  /\ rmState["payments"] \in {"committed", "aborted"}
  /\ report' = "done"
  /\ UNCHANGED <<rmState, tmState, tmPrepared, msgs>>

\* ROLLBACK PREPARED by hand while the app server is down. "blind": anything
\* still prepared. "checklog": only if the app server's log has no Commit.
DBARollback(r) ==
  /\ \/ DBA = "blind"
     \/ DBA = "checklog" /\ [type |-> "Commit"] \notin msgs
  /\ tmState = "down"
  /\ rmState[r] = "prepared"
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ UNCHANGED <<tmState, tmPrepared, msgs, report>>

\* An intended stop: every transaction has ended and the report has run.
Finished ==
  /\ \A r \in RM : rmState[r] \in {"committed", "aborted"}
  /\ report = "done"
  /\ UNCHANGED vars
-----------------------------------------------------------------------------
Next ==
  \/ TMCommit \/ TMAbort \/ TMCrash \/ ReportRuns \/ Finished
  \/ \E r \in RM : \/ TMRcvPrepared(r) \/ RMPrepare(r) \/ RMChooseToAbort(r)
                   \/ RMRcvCommitMsg(r) \/ RMRcvAbortMsg(r) \/ DBARollback(r)
-----------------------------------------------------------------------------
INSTANCE TCommit
=============================================================================

The config, with the deadlock check on:

INIT Init
NEXT Next
CONSTANTS RM = {"orders", "payments"}
          DBA = "never"
INVARIANT TypeOK
INVARIANT TCConsistent
  1. Why is Finished needed for the deadlock check to mean anything here? (Compare the terminating counter in {{lesson:counter}}.)
  2. Run TLC with DBA = "never". What does it report? Describe the final state in Postgres terms: what holds locks, and who waits?
  3. The on-call DBA's runbook says: “If the app server is down, run ROLLBACK PREPARED on anything still prepared.” Run with DBA = "blind". What breaks, and why can't the payments database alone tell the DBA what to do?
  4. Run with DBA = "checklog", where the DBA rolls back only if the app server's log contains no Commit decision. What does TLC report?

Hint

In TwoPhase, after the TM decides, RMRcvCommitMsg or RMRcvAbortMsg stays enabled forever, so TLC never sees a stop. Here, which states have no enabled action? For (c), remember that a message in msgs may never be received: that is how the model says it was lost.

Solution

(a) A run in which both transactions end and the report finishes is supposed to stop. Without Finished, TLC would report that intended stop as a deadlock, and you would have to turn the check off, which also hides the stops you care about. Finished is enabled exactly in the good final states and changes nothing, so any deadlock TLC reports is a state where work is left undone.

(b) TLC reports Deadlock reached with a 4-state trace:

Both databases prepared, and then the app server died before deciding. Each database holds a prepared tx42 with its row locks. Nothing in Postgres will resolve it: the protocol gives a prepared participant no step of its own. The report's UPDATE waits on the payment row, indefinitely. Postgres's documentation warns against leaving transactions prepared for long, because they also stop VACUUM from reclaiming storage. You can list them in the pg_prepared_xacts view. This is the blocking problem the lab in {{lesson:transactions}} showed, now as a TLC trace.

(c) TLC reports Invariant TCConsistent is violated with a 9-state trace. Both databases prepare, the app server commits and sends Commit, then crashes. Orders receives Commit and commits. Payments never gets its Commit (in the model, that message is never received), and the DBA, following the runbook, rolls it back. An order with no payment. From inside the payments database, “prepared and the coordinator is down” looks the same whether or not a Commit decision exists. The information the DBA needs is the decision, and that lives in the coordinator's log, not in this database.

(d) No error and 194 distinct states, and no deadlock. If the log has no Commit, nobody can have committed, so a rollback is safe. If it does, the Commit message stays in msgs, and receiving it models the DBA running COMMIT PREPARED. Resolving a prepared transaction by hand is safe only with the decision in hand. Real transaction managers write their decision to durable storage before sending it, so that they, or a person, can finish the job after a crash.

Problem 3●●○Messaging

Receipt emails over an at-least-once queue

Draws on {{ref:messages}}, {{ref:transactions}} and {{ref:sets}}.

After an order commits, the order service publishes a “send receipt” message to a queue, and an email worker consumes it. The queue behaves like Amazon SQS standard queues: delivery is at least once, ordering is best effort, and a message that isn't acknowledged within its visibility timeout is delivered again. The model below uses the grow-only msgs from {{lesson:messages}}. The constant Mode picks how the worker handles a delivery. emailed is the worker's table of orders it has emailed.

The module (open to copy) 
----------------------------- MODULE PSl6_Receipts -----------------------------
EXTENDS Integers
CONSTANT Mode            \* how the email worker handles a delivery:
                         \* "naive", "atomic", or "twostep"
Orders == {"o1", "o2"}   \* o1 is placed before o2
Receipt(o) == [type |-> "receipt", order |-> o]
VARIABLES
  msgs,                  \* every message ever published to the queue
  sent,                  \* sent[o]: receipt emails sent for order o
  emailed                \* orders the worker's table records as emailed
vars == <<msgs, sent, emailed>>

TypeOK == /\ msgs \subseteq [type : {"receipt"}, order : Orders]
          /\ sent \in [Orders -> 0..2]
          /\ emailed \subseteq Orders

Init == /\ msgs = {}
        /\ sent = [o \in Orders |-> 0]
        /\ emailed = {}

\* The order service publishes after each order commits, o1 first.
Publish(o) == /\ Receipt(o) \notin msgs
              /\ o = "o2" => Receipt("o1") \in msgs
              /\ msgs' = msgs \cup {Receipt(o)}
              /\ UNCHANGED <<sent, emailed>>

SendEmail(o) == sent' = [sent EXCEPT ![o] = sent[o] + 1]

\* The queue hands o's receipt message to the worker (again, possibly).
Deliver(o) ==
  /\ Receipt(o) \in msgs
  /\ sent[o] < 2                          \* keeps the model finite
  /\ \/ /\ Mode = "naive"
        /\ SendEmail(o)
        /\ UNCHANGED emailed
     \/ /\ Mode = "atomic"                \* check, send, record: one step
        /\ o \notin emailed
        /\ SendEmail(o)
        /\ emailed' = emailed \cup {o}
     \/ /\ Mode = "twostep"               \* check and send; record later
        /\ o \notin emailed
        /\ SendEmail(o)
        /\ UNCHANGED emailed
  /\ UNCHANGED msgs

\* twostep only: the worker writes "emailed" after the provider accepts.
Record(o) == /\ Mode = "twostep"
             /\ sent[o] > 0
             /\ o \notin emailed
             /\ emailed' = emailed \cup {o}
             /\ UNCHANGED <<msgs, sent>>

Next == \E o \in Orders : Publish(o) \/ Deliver(o) \/ Record(o)

OneEmail == \A o \in Orders : sent[o] =< 1
InOrder  == sent["o2"] > 0 => sent["o1"] > 0
=============================================================================

The config for the first run:

INIT Init
NEXT Next
CONSTANT Mode = "naive"
INVARIANT TypeOK
INVARIANT OneEmail
CHECK_DEADLOCK FALSE

Notice what is not in the module: no action duplicates, delays or reorders messages. Deliver(o) only requires the message to be in msgs.

  1. Run with Mode = "naive". Where in the module does the duplicate come from?
  2. Run with Mode = "atomic". What does TLC report? What does putting the check, the email and the record in one step claim about the real worker?
  3. Run with Mode = "twostep", the honest version: the worker checks the table, calls the email API, and records the order afterwards. What happens?
  4. With Mode = "atomic", add INVARIANT InOrder. What does TLC find? Does a receipt service need to care?

Which of these can't happen in this model of the queue?

Hint

Look for what removes a message from msgs, or disables Deliver(o) once it has run. In "twostep", which action has to happen between the two deliveries to prevent the second email?

Solution

(a) TLC reports Invariant OneEmail is violated with a 4-state trace: Publish("o1"), Deliver("o1"), Deliver("o1"). Nothing removes a message from msgs, so Deliver("o1") stays enabled. That is the lesson's point about one reader and many receipts, with an effect, an email, that isn't harmless to repeat. You got duplicate delivery without writing a line for it.

(b) No error, 7 distinct states. The second delivery finds "o1" \in emailed and is disabled. But the step claims that checking the table, calling the email API, and writing the table happen as one indivisible event. A database transaction can make the check and the write atomic. It can't include a call to an external email service.

(c) TLC reports OneEmail violated, again in 4 states: Publish, then Deliver("o1") twice, before Record("o1") ever runs.

In SQS terms, the worker took longer than the visibility timeout, or crashed after sending and before recording, and the queue handed the message to another delivery. Your table can make duplicates rarer. It can't rule them out, because the gap between the external effect and the record is real. The usual way out is to give the email provider an idempotency key such as the order id and let it deduplicate, or to accept that a customer may occasionally get two receipts. Which one is right is a product decision, and the model has made it a visible one.

(d) TLC reports InOrder violated with a 4-state trace: Publish("o1"), Publish("o2"), Deliver("o2"). The set model includes reordering for free, which matches the queue's best-effort ordering. Receipts don't need order, so you'd delete the invariant. A consumer that applies successive updates to the same record would care. It would need a sequence and an ordered channel, which the course models with the alternating bit protocol in Lecture 9.

Problem 4 · Synthesis●●●Databases

Reserving stock in two warehouses

Draws on {{ref:transactions}}, {{ref:messages}}, {{ref:sets}}, {{ref:actions}}, and the schema-agreement problem in {{ref:ps-l5}}.

An online shop fulfils an order from two warehouses, east and west, one unit from each. Each warehouse's inventory database is an RM in two-phase commit, and the order service is the TM. Preparing reserves a unit: it leaves the shelf count and is held for this order. Committing ships the held unit. Aborting must cancel the reservation and put the unit back. A developer adds a stock variable to TwoPhase, with these changes:

RMPrepare(r) ==
  /\ rmState[r] = "working"
  /\ stock[r] > 0
  /\ rmState' = [rmState EXCEPT ![r] = "prepared"]
  /\ stock' = [stock EXCEPT ![r] = stock[r] - 1]
  /\ msgs' = msgs \cup {[type |-> "Prepared", rm |-> r]}
  /\ UNCHANGED <<tmState, tmPrepared>>

RMRcvAbortMsg(r) ==
  /\ [type |-> "Abort"] \in msgs
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ stock' = [stock EXCEPT ![r] = stock[r] + 1]
  /\ UNCHANGED <<tmState, tmPrepared, msgs>>

Every other action has stock in its UNCHANGED list, TypeOK requires stock \in [RM -> 0..Stock0] with Stock0 == 1, and the module ends with INSTANCE TCommit. The fixed module is in the solution; the developer's version differs only in RMRcvAbortMsg.

  1. Write Conservation: for every warehouse, the units on the shelf plus the units held or shipped for this order equal Stock0. A helper Held(w), which is 1 when w is prepared or committed and 0 otherwise, makes it short.
  2. Run TLC with CONSTANT RM = {"east", "west"}, listing INVARIANT Conservation first, then TypeOK and TCConsistent, with CHECK_DEADLOCK FALSE. Explain the trace.
  3. Compare with the schema-agreement problem in {{ref:ps-l5}}, where Agreement and ReadersReady were the requirements. Does TCConsistent catch this bug?
  4. A reviewer suggests releasing stock only if rmState[r] # "working". Try it. Then write a fix that works, and check it with two and with three warehouses.

Does TCConsistent catch the bug?

Hint

Which RMs can receive an Abort message? In TwoPhase, receiving the same message twice was harmless because setting rmState[r] to "aborted" again changes nothing. Is stock[r] + 1 like that? The release should depend on what this particular step undoes.

Solution

(a)

Held(w) == IF rmState[w] \in {"prepared", "committed"} THEN 1 ELSE 0

Conservation == \A w \in RM : stock[w] + Held(w) = Stock0

(b) TLC reports Invariant Conservation is violated with a 3-state trace: TMAbort, then RMRcvAbortMsg("east") while east is still working. East never reserved anything, but the release adds a unit, so its shelf shows 2. TLC checks the invariants in the order the config lists them. With TypeOK listed first it reports TypeOK violated in the same 3 states, since 2 isn't in 0..Stock0. In TwoPhase, an Abort can reach any RM, prepared or not, and any number of times. Those receives were safe only because they had no effect beyond setting rmState.

(c) No. TCConsistent mentions only rmState, and this change never affects rmState. With shelf counts bounded at 4, TLC confirms it: no error in 245 states. The decision was abort and nobody committed, so agreement holds, and the inventory is wrong anyway. In the schema problem of {{ref:ps-l5}}, agreement wasn't enough either, and ReadersReady was the requirement that mattered. Here it is Conservation. A commit protocol guarantees agreement on the decision, and the effects you attach to the decision need their own invariant.

(d) The reviewer's guard isn't enough. TLC finds a 4-state trace: TMAbort, east aborts on its own with RMChooseToAbort, then receives Abort and releases a unit it never reserved.

A duplicate delivery to a prepared warehouse is a third route: prepare, TM aborts, receive Abort (correct release), receive it again (second release). The fix releases exactly when this step undoes a reservation, that is, when the RM is prepared:

------------------------------ MODULE PSl6_StockFixed ------------------------------
EXTENDS Integers
CONSTANT RM              \* the warehouses; the order needs one unit from each
Stock0 == 1              \* units each warehouse has on the shelf at the start
VARIABLES rmState, tmState, tmPrepared, msgs,
          stock          \* stock[w]: units on the shelf at w, not reserved
vars == <<rmState, tmState, tmPrepared, msgs, stock>>

Messages == [type : {"Prepared"}, rm : RM] \cup [type : {"Commit", "Abort"}]

TypeOK ==
  /\ rmState \in [RM -> {"working", "prepared", "committed", "aborted"}]
  /\ tmState \in {"init", "done"}
  /\ tmPrepared \subseteq RM
  /\ msgs \subseteq Messages
  /\ stock \in [RM -> 0..Stock0]

Init ==
  /\ rmState = [r \in RM |-> "working"]
  /\ tmState = "init"
  /\ tmPrepared = {}
  /\ msgs = {}
  /\ stock = [r \in RM |-> Stock0]
-----------------------------------------------------------------------------
TMRcvPrepared(r) ==
  /\ tmState = "init"
  /\ [type |-> "Prepared", rm |-> r] \in msgs
  /\ tmPrepared' = tmPrepared \cup {r}
  /\ UNCHANGED <<rmState, tmState, msgs, stock>>

TMCommit ==
  /\ tmState = "init"
  /\ tmPrepared = RM
  /\ tmState' = "done"
  /\ msgs' = msgs \cup {[type |-> "Commit"]}
  /\ UNCHANGED <<rmState, tmPrepared, stock>>

TMAbort ==
  /\ tmState = "init"
  /\ tmState' = "done"
  /\ msgs' = msgs \cup {[type |-> "Abort"]}
  /\ UNCHANGED <<rmState, tmPrepared, stock>>

\* Prepare = reserve: take a unit off the shelf and hold it for this order.
RMPrepare(r) ==
  /\ rmState[r] = "working"
  /\ stock[r] > 0
  /\ rmState' = [rmState EXCEPT ![r] = "prepared"]
  /\ stock' = [stock EXCEPT ![r] = stock[r] - 1]
  /\ msgs' = msgs \cup {[type |-> "Prepared", rm |-> r]}
  /\ UNCHANGED <<tmState, tmPrepared>>

RMChooseToAbort(r) ==
  /\ rmState[r] = "working"
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ UNCHANGED <<tmState, tmPrepared, msgs, stock>>

\* Commit = ship the held unit. The shelf count doesn't change.
RMRcvCommitMsg(r) ==
  /\ [type |-> "Commit"] \in msgs
  /\ rmState' = [rmState EXCEPT ![r] = "committed"]
  /\ UNCHANGED <<tmState, tmPrepared, msgs, stock>>

\* Abort = cancel the reservation and put the unit back on the shelf.
RMRcvAbortMsg(r) ==
  /\ [type |-> "Abort"] \in msgs
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ stock' = IF rmState[r] = "prepared"
                THEN [stock EXCEPT ![r] = stock[r] + 1]
                ELSE stock
  /\ UNCHANGED <<tmState, tmPrepared, msgs>>
-----------------------------------------------------------------------------
Next ==
  \/ TMCommit \/ TMAbort
  \/ \E r \in RM : TMRcvPrepared(r) \/ RMPrepare(r) \/ RMChooseToAbort(r)
                     \/ RMRcvCommitMsg(r) \/ RMRcvAbortMsg(r)
-----------------------------------------------------------------------------
INSTANCE TCommit

Held(w) == IF rmState[w] \in {"prepared", "committed"} THEN 1 ELSE 0

\* Every unit is on the shelf, or held or shipped for this order.
Conservation == \A w \in RM : stock[w] + Held(w) = Stock0
=============================================================================

TLC finds no error: 56 distinct states with two warehouses and 288 with three. These are exactly TwoPhase's counts for two and three RMs. In the fixed model, stock[w] always equals Stock0 - Held(w), which is what Conservation says, so the extra variable adds no states. When adding a variable doesn't change the count, it is a function of the others, and it is worth asking whether you need to store it at all. The general lesson: an effect attached to a receive action must be idempotent, because the network may deliver the message to any RM, any number of times.
