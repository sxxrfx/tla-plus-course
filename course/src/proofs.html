The hard part is usually finding the invariant that carries the design argument, which you did with TLC in the previous lessons. What remains is the structure in the diagram: a claim, split into smaller claims, until each one is small enough to check on its own.

A worked proof

Return to Inventory. Let Inv combine TypeOK and Conservation. Initially remaining = 1 and booked is empty. In Reserve(b), the guard ensures b is not already in booked, so adding b raises its cardinality by exactly one. The action lowers remaining by one, preserving the sum, and its positive-stock guard preserves the lower bound. Stuttering preserves both. Inv implies NoOverselling because remaining is nonnegative.

That is the informal outline. Written as a TLA+ hierarchical proof, the same argument has numbered steps. <1>2 is a top-level step, and its <2> steps are the children that prove it:

---------------- MODULE InventoryProof ----------------
EXTENDS Inventory, TLAPS
Inv == /\ TypeOK
       /\ IsFiniteSet(booked)
       /\ Conservation
LEMMA CardEmpty == IsFiniteSet({}) /\ Cardinality({}) = 0
    PROOF OMITTED
LEMMA CardNat == \A S : IsFiniteSet(S) => Cardinality(S) \in Nat
    PROOF OMITTED
LEMMA CardAdd == \A S, x : IsFiniteSet(S) /\ x \notin S =>
    /\ IsFiniteSet(S \cup {x})
    /\ Cardinality(S \cup {x}) = Cardinality(S) + 1
    PROOF OMITTED
THEOREM Safety == Spec => []NoOverselling
<1>1. Init => Inv
    BY CardEmpty DEF Init, Inv, TypeOK, Conservation
<1>2. Inv /\ [Next]_vars => Inv'
    <2> SUFFICES ASSUME Inv, [Next]_vars PROVE Inv'
        OBVIOUS
    <2>1. ASSUME NEW b \in Buyers, Reserve(b) PROVE Inv'
        BY <2>1, CardAdd, CardNat
        DEF Reserve, Inv, TypeOK, Conservation
    <2>2. CASE UNCHANGED vars
        BY <2>2 DEF vars, Inv, TypeOK, Conservation
    <2>3. QED
        BY <2>1, <2>2 DEF Next
<1>3. Inv => NoOverselling
    BY CardNat DEF Inv, TypeOK, Conservation, NoOverselling
<1>4. QED
    BY <1>1, <1>2, <1>3, PTL DEF Spec
=======================================================

How far this was checked: the module parses under SANY with a stand-in for the TLAPS module, and TLC confirms Inv is inductive for Buyers = {A, B}, with 3 states and NoOverselling holding. It has not been run through TLAPS, so a prover may ask for more detail in some steps. Treat it as the shape of a proof. The three OMITTED lemmas are facts about finite sets that a complete proof must import or prove.

BY lists the facts a step may use and DEF lists the definitions it may expand. Nothing else is visible, which is the point: every use of an assumption is on the page. PTL names propositional temporal logic, the reasoning that gets from “preserved by every step” to [].

Exercise: remove b \notin booked from Reserve. Is the one-ticket model enough to expose a bug?

Not in this one-ticket model. TLC still finds 3 states and no error. Inv plus remaining > 0 implies booked is empty, so the membership guard is redundant here and the proof can recover that fact. With more tickets, the same buyer could reserve twice: adding that buyer again does not increase the cardinality while remaining decreases. The broader conservation proof then needs the guard or a different booking representation. Test assumptions at the size where they become relevant.

Where TLAPS helps

TLAPS checks hierarchical proofs by sending each step’s obligation to backend provers. Break large obligations into named claims, and expose the definitions each one needs. An informal outline is not a checked proof. Consult the supported-feature list: the documented system focuses on safety reasoning and does not generally discharge arbitrary temporal liveness arguments.

Use TLC to attack a candidate invariant before you spend time proving it, as in {{lesson:invariants}}. A finite run can refute a candidate quickly. It cannot prove the unbounded theorem.

Worked example: prove a cache cannot roll back a version

An app fetches a product description twice. Version 5 and version 4 are in flight, and the network delivers 5 first. A naive cache that accepts every response replaces the fresh value with the old one.

---------------- MODULE CacheVersion ----------------
EXTENDS Naturals
VARIABLES cacheVersion, pending
vars == <<cacheVersion, pending>>
Init == cacheVersion = 3 /\ pending = {4, 5}
Accept(v) == /\ v \in pending
             /\ v >= cacheVersion
             /\ cacheVersion' = v
             /\ pending' = pending \ {v}
Reject(v) == /\ v \in pending
             /\ v < cacheVersion
             /\ pending' = pending \ {v}
             /\ UNCHANGED cacheVersion
Next == \E v \in pending: Accept(v) \/ Reject(v)
Spec == Init /\ [][Next]_vars
Monotonic == [][cacheVersion' >= cacheVersion]_vars
=====================================================

This time the property is about steps, not states: Monotonic says every step keeps or raises the version. TLC finds 4 distinct states and no error. Delete the guard v >= cacheVersion and it reports the bottom row of the diagram.

The proof is short. For Accept, the guard gives cacheVersion' >= cacheVersion directly. For Reject and stuttering, cacheVersion is unchanged. An action that resets cacheVersion must join this case split, even if it lives in another component, and this is where a proof tends to find what a design forgot.

It assumes one key, one monotonically increasing version scheme, and immutable content for a given version. Incomparable version vectors or reused version numbers need a different model.

What the proof forces you to decide

Split cacheVersion into what is in memory and what is on disk, with Persist and Restart actions. Now there is a new case to prove, and it fails:

Restart == /\ volatile # durable
           /\ volatile' = durable
           /\ UNCHANGED <<durable, pending>>

TLC reports Monotonic violated in 2 steps. You must either persist the accepted version before showing it, weaken the contract to permit rollback after restart, or hold back older data until resynchronization. The proof makes that a design choice instead of a surprise.

A proof of one property establishes exactly that property. A server could send version 100 with the wrong product’s text and Accept would take it. Add a key-match property and a mapping from version to content if you need them. And checking versions 3 to 5 with TLC can reveal a counterexample, but does not establish the claim for all numbers: the argument above does, because no step of it depends on which numbers they are.

Transfer exercise: can a cache safely delete its version record on logout?

It depends on the contract and scope. If the next login begins a new cache epoch with no promised cross-session monotonicity, clearing it may be valid. If old responses can still arrive and populate the new session, include session identity in the acceptance guard; otherwise an old authenticated response can cross the reset boundary.
