Reuse definitions without hiding assumptions.

In {{lesson:implementation}} you read a specification as a formula, and used INSTANCE to compare two of them. Formulas can also be conjoined. That is how you combine components, and it behaves differently from what you might expect from running programs.

Composition needs a shared step convention

Writing SpecA /\ SpecB intersects the allowed behaviors. It is not a request to interleave two programs. Here is the experiment behind the diagram, with each component written first as if it owned the whole state:

---------------- MODULE Frames ----------------
VARIABLES x, y
vars == <<x, y>>
Init == x = 0 /\ y = 0
\* Each component written as if it owned the whole state:
A == x = 0 /\ x' = 1 /\ y' = y
B == y = 0 /\ y' = 1 /\ x' = x
SpecA == Init /\ [][A]_vars
SpecB == Init /\ [][B]_vars
Conjoined == [A]_vars /\ [B]_vars
Interleaved == A \/ B
\* Each component constrains only its own variable:
OwnX == x = 0 /\ x' = 1
OwnY == y = 0 /\ y' = 1
OwnVars == [OwnX]_x /\ [OwnY]_y
===============================================
Next-state relationDistinct statesSteps allowed
Conjoined (what SpecA /\ SpecB means)1Only stuttering
Interleaved (A \/ B)4The solid arrows
OwnVars4The solid and dashed arrows

The first row is the trap: A requires y unchanged and B requires y to change, so no step satisfies both, and all the system can do is stutter. TLC reports no error, because a system that does nothing violates no safety property. For an interleaving composition, write global actions with compatible frames. If you want simultaneous steps, each component must constrain only the variables it owns.

Assume-guarantee reasoning says a component guarantees G provided its environment satisfies A. Check that the other components establish A. Two components that each assume the other eventually responds may prove nothing useful when combined: circular progress assumptions need an actual argument.

Predict: is the Conjoined run’s clean TLC result good news?

No. It found no error in 1 state. A state count far below what you expected is a result to investigate. A liveness property would have failed here.

Module tools you have not needed yet

You know EXTENDS and named instances. Substituting parameters lets you reuse a whole model. This puts the queue from {{lesson:fifo}} into a job system:

---------------- MODULE JobQueue ----------------
CONSTANT Jobs
VARIABLE pending
Queue == INSTANCE BoundedFIFO
    WITH Values <- Jobs, Capacity <- 2, q <- pending
Spec == Queue!Spec
QueueSafe == Queue!TypeOK
=================================================

TLC finds the same 7 states as before, since only the names changed. Queue!TypeOK is the qualified name for a definition in that instance.

You have also met LET, CHOOSE and RECURSIVE in the lectures. Two more belong beside them. This module runs under TLC, and its ASSUME lines pass:

---------------- MODULE LangTools ----------------
EXTENDS Naturals
Outcome(x) == CASE x = 0 -> "empty"
                [] x > 0 -> "ready"
Pick == CHOOSE x \in {"A", "B"}: TRUE
RECURSIVE Fact(_)
Fact(n) == IF n = 0 THEN 1 ELSE n * Fact(n-1)
LOCAL Helper == 41
Exported == Helper + 1
ASSUME Outcome(0) = "empty" /\ Outcome(3) = "ready"
ASSUME Pick = Pick /\ Pick \in {"A", "B"}
ASSUME Fact(4) = 24 /\ Exported = 42
VARIABLE v
Spec == v = Pick /\ [][v' = Pick]_v
Stable == v = Pick
==================================================

LOCAL keeps a helper from being exported to modules that use this one. It does not make state thread-local. CASE chooses a branch whose guard is true. Do not rely on branch order when guards overlap, and add OTHER if no guard might be true, because otherwise TLC stops with “Attempted to evaluate a CASE with no conditions true”.

\EE h : F, temporal existential quantification, hides a variable at the level of whole behaviors: a behavior satisfies it if some sequence of values for h makes F true. That differs from the state-level \E. It is how you state a specification with internal variables hidden, but TLC does not accept it (“TLC cannot handle the temporal formula”).

Predict: does CHOOSE x \in {"A","B"}: TRUE mean TLC will try both at every step?

No. It denotes one unspecified value, the same every time, which is why Stable holds above and TLC finds 1 state. To explore both, write \E x \in S: Action(x).

Worked example: compose search, selection, and caching

A search screen has query text, an asynchronous request, displayed results, and a selected result. You could verify each alone: the service returns matches, the cache stores responses, and selection picks an existing row. The composition can still be wrong when responses arrive out of order.

---------------- MODULE SearchUI ----------------
EXTENDS Naturals
CONSTANTS MaxGen, NoSelection
VARIABLES generation, inflight, shownGen, results, selected
vars == <<generation, inflight, shownGen, results, selected>>
Rows(g) == {<<g, 1>>, <<g, 2>>}
Init == /\ generation = 0
        /\ inflight = {}
        /\ shownGen = 0
        /\ results = {}
        /\ selected = NoSelection
Input ==
    /\ generation < MaxGen
    /\ LET g == generation + 1 IN
         /\ generation' = g
         /\ inflight' = inflight \cup {[gen |-> g, rows |-> Rows(g)]}
    /\ UNCHANGED <<shownGen, results, selected>>
ShowResponse(r) ==
    /\ r \in inflight
    /\ r.gen = generation
    /\ shownGen' = r.gen
    /\ results' = r.rows
    /\ selected' = NoSelection
    /\ inflight' = inflight \ {r}
    /\ UNCHANGED generation
DropStale(r) ==
    /\ r \in inflight
    /\ r.gen # generation
    /\ inflight' = inflight \ {r}
    /\ UNCHANGED <<generation, shownGen, results, selected>>
Select(row) ==
    /\ row \in results
    /\ selected' = row
    /\ UNCHANGED <<generation, inflight, shownGen, results>>
Next == \/ Input
        \/ \E r \in inflight: ShowResponse(r) \/ DropStale(r)
        \/ \E row \in results: Select(row)
Spec == Init /\ [][Next]_vars
Status == CASE shownGen = 0 -> "empty"
            [] shownGen = generation -> "ready"
            [] shownGen < generation -> "loading"
SelectionValid == selected = NoSelection \/ selected \in results
SettlesOnLatest ==
    inflight = {} /\ generation > 0 => shownGen = generation
StatusKnown == Status \in {"empty", "ready", "loading"}
=================================================
SPECIFICATION Spec
CONSTANTS MaxGen = 2
          NoSelection = NoSelection
INVARIANT SelectionValid SettlesOnLatest StatusKnown
CHECK_DEADLOCK FALSE

TLC finds 16 distinct states and all three invariants hold. Status uses CASE and needs no OTHER because the guards cover every reachable state, which StatusKnown confirms. SettlesOnLatest says that once nothing is in flight, the screen shows the latest generation.

Two one-line mutations each break a different contract:

  • Delete the guard r.gen = generation, and TLC reports SettlesOnLatest violated after 4 steps: the red arrow in the diagram.
  • Replace selected' = NoSelection with UNCHANGED selected, and SelectionValid fails after 5 steps: the user picks a row from gen 1, gen 2 arrives, and the selection names a row no longer on screen.

The request component’s guarantee is “every response carries its original generation”. The display relies on that and guarantees it never accepts an obsolete one. The cache must preserve the relevant key too: if results depend on query, tenant, locale and permissions, caching by query alone breaks the composition, even though each lookup is consistent with its own incomplete key.

If the UI intentionally keeps old results while loading, the "loading" status above says so. That is better than asserting a stricter invariant and then hiding its violations. A policy is part of the model.

Transfer exercise: why might a query-only cache expose another account’s results?

Two accounts can issue the same query with different authorized result sets. If account identity or an equivalent authorization scope is missing from the key, one account’s cached response may be reused for the other. Model two accounts, one shared query, and two distinct expected result sets to expose the missing key component.
