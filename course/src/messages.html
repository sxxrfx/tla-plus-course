A network can be one set that only grows.

In TwoPhase, sending adds a record to msgs, and receiving removes nothing. That choice looks odd, and it's the most reusable modeling idea in lecture 6. This lesson explains why it works, then uses it to model loss, delay, and duplicates without new machinery.

Follow both rows left to right. The top row is the obvious model: msgs is what's in transit, and receiving takes a message out. In the last column r1 has consumed the only Commit, so r2 can never get it. The bottom row is the lecture's: msgs is everything ever sent, and both RMs can read the same record.

What the spec needs from the network

A spec should describe only what the algorithm requires of message passing. Two-phase commit needs no ordering between messages, so a set is enough. Lamport compares two methods:

  • Simple: msgs is the set of messages in transit. Receiving removes one.
  • Simpler: msgs is the set of all messages ever sent. A receive action merely requires the message to be there.

Here is what TLC finds for both, with three RMs, plus a repaired version of the first.

Model of msgsDistinct statesCan all three RMs commit?
Ever sent (the lecture's TwoPhase)288Yes
In transit, one Commit record265No: ~\A r : committed holds as an invariant
In transit, one addressed copy per RM415Yes: TLC finds the run, 11 states long

The second row is a warning: TLC reports no error on TCConsistent, yet the model can't do its job. It's the kind of success to be suspicious of. The third row works, but it adds a to field and more states. It also says each copy is received at most once, which real networks don't promise.

Receiving twice is harmless, here

Since a message stays in msgs, TMRcvPrepared(r) stays enabled after it runs. A later step does tmPrepared' = tmPrepared \cup {r} with r already in the set. A set can't contain two copies of r, so nothing changes. A step that leaves every variable unchanged is a stuttering step, and it makes no difference; {{lesson:temporal}} explains why such steps are always allowed. This matters because a real process can receive one message twice.

The set is doing real work. In the diagram, the top row is TwoPhase, and the bottom row is a variant where the TM keeps a count instead and commits when the count reaches the number of RMs. TLC finds a TCConsistent violation in a 7-state trace, with two RMs: r1 prepares, the TM counts r1's message twice, commits, r1 commits, and r2, still working, aborts on its own. A message read twice made one vote look like two.

Predict: does the grow-only set break when the TM's rule is "commit once I've seen any Prepared from r1 and r2"?

No, and it's exactly what TMCommit with tmPrepared = RM says. A rule about which messages exist is automatically immune to duplicates. A rule about how many receipts happened isn't.

Extending the model: the network's freedoms

Nothing in msgs forces a process to act on a message. That one fact covers most of what a network can do, as long as you're checking safety (what can happen, not what must).

Network behaviorIn the grow-only model
DelayThe message sits in msgs while other steps happen
ReorderingAny message in the set may be read next
Duplicate deliveryThe receive action can run again
LossThe receive action never runs for that message
Timeout and retryA new message or attempt; nothing proves the first was lost

A permanently lossy channel still satisfies every safety property, because nothing happens. Saying that something must eventually be delivered is a liveness assumption, the subject of {{lesson:fairness}}. And if an algorithm needs ordering, a set is too weak and you'd use a sequence, as {{lesson:abp}} does.

Worked trace: the uncertain checkout response

A checkout client sends request r7. The server creates an order, but the reply is lost, and the browser times out.

At the X in the diagram the client knows nothing and the server has an order. A timeout only shows no reply arrived in time; it doesn't show the server did nothing. The dashed retry is what makes a double order possible. Here's the model. Attempts are records with both the logical request and the transport attempt:

------------------------------ MODULE CheckoutRetry ---------------------------
EXTENDS Integers
CONSTANTS Attempt,          \* the attempts the client may send for request r7
          KeyField          \* the message field the server deduplicates on
VARIABLES
  msgs,                     \* every attempt ever sent; never shrinks
  applied,                  \* what the server has recorded as already done
  orders,                   \* orders the server created
  replied,                  \* the server has sent a reply
  client                    \* "waiting" or "knows"
vars == <<msgs, applied, orders, replied, client>>

CInit == /\ msgs = {} /\ applied = {} /\ orders = 0
         /\ replied = FALSE /\ client = "waiting"

\* First try, or a retry after a timeout. Nothing forces a reply to come first.
Send(a) == /\ client = "waiting"
           /\ [req |-> "r7", try |-> a] \notin msgs
           /\ msgs' = msgs \cup {[req |-> "r7", try |-> a]}
           /\ UNCHANGED <<applied, orders, replied, client>>

\* The client learns the result only if it reads a reply.
Hear == /\ replied
        /\ client' = "knows"
        /\ UNCHANGED <<msgs, applied, orders, replied>>

\* Creates an order unless this message's key is recorded. Delivery leaves m
\* in msgs, so m can be delivered again; one never delivered has been lost.
Deliver ==
  \E m \in msgs :
    /\ m[KeyField] \notin applied
    /\ orders < 2
    /\ orders' = orders + 1
    /\ applied' = applied \cup {m[KeyField]}
    /\ replied' = TRUE
    /\ UNCHANGED <<msgs, client>>

\* A repeat of work already done: just send the reply again.
Repeat ==
  \E m \in msgs :
    /\ m[KeyField] \in applied
    /\ replied' = TRUE
    /\ UNCHANGED <<msgs, applied, orders, client>>

CNext == \/ \E a \in Attempt : Send(a)
         \/ Deliver \/ Repeat \/ Hear

OneOrder == orders <= 1
KnowsTruth == client = "knows" => orders >= 1
=============================================================================
INIT CInit
NEXT CNext
CONSTANTS Attempt = {"e1", "e2"}
          KeyField = "req"
INVARIANT OneOrder
INVARIANT KnowsTruth
CHECK_DEADLOCK FALSE

The constant KeyField picks what the server deduplicates on. m[KeyField] works because a record is a function. With KeyField = "req", TLC reports no error, 10 distinct states. With KeyField = "try", OneOrder is violated in 5 states: send e1, send e2, deliver each, two orders. The retry looks like a new purchase because its transport identity is new.

Predict: the client gives every retry a fresh request ID. Is it protected?

No. That is the "try" run again: a fresh ID makes each retry a distinct purchase. The ID has to survive the ambiguous response, so it must belong to the customer's intent, not to the attempt.
