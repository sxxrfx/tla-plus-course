Problem 1●○○Databases

Two doctors go off call: write skew under snapshot isolation

Draws on {{ref:states}}, {{ref:sets}}, {{ref:tcommit}}, {{ref:inventory}} and {{ref:pluscal}}.

A hospital's on-call app keeps one row per doctor per shift in Postgres, at the REPEATABLE READ isolation level, which Postgres implements as snapshot isolation. The rule is that at least one doctor stays on call. To go off call, the app runs one transaction: count the doctors on call in the shift; if there are at least two, set your own row to off call; commit. Alice and Bob both feel unwell and press the button at the same moment. Both transactions commit, and nobody is on call. Kleppmann's Designing Data-Intensive Applications uses this example.

Under snapshot isolation each transaction reads from a snapshot taken when it starts, and two transactions conflict only if they write the same row. The PlusCal model has one process per doctor's transaction. snap is the transaction's snapshot and version counts commits per row. With Isolation = "Serializable", a transaction aborts at commit if any row it read has changed since its snapshot. Translate the algorithm with pcal.trans before running TLC; the translation is omitted below.

---------------- MODULE PSfinal_OnCall ----------------
EXTENDS Naturals, FiniteSets
CONSTANTS Doctors, Isolation
ASSUME Isolation \in {"Snapshot", "Serializable"}
(*--algorithm OnCall
variables onCall = [d \in Doctors |-> TRUE],  \* committed rows
          version = [d \in Doctors |-> 0];     \* committed row versions
define
    AtLeastOneOnCall == \E d \in Doctors : onCall[d]
end define;
process Tx \in Doctors
variables snap = [d \in Doctors |-> TRUE],     \* this transaction's snapshot
          snapVersion = [d \in Doctors |-> 0];
begin
Begin:
    snap := onCall;
    snapVersion := version;
Check:
    if Cardinality({d \in Doctors : snap[d]}) >= 2 then
Commit:
        if Isolation = "Serializable" /\ version # snapVersion then
            skip;   \* abort: a row it read has changed since its snapshot
        else
            onCall[self] := FALSE;
            version[self] := version[self] + 1;
        end if;
    end if;
end process;
end algorithm; *)
=======================================================

CONSTANTS Doctors = {alice, bob}
          Isolation = "Snapshot"

  2. Run Isolation = "Snapshot" and report TLC's trace.
  3. Snapshot isolation does detect a write-write conflict, and the first transaction to commit wins. Why does that not stop this anomaly?
  4. Run Isolation = "Serializable". Report the distinct states. Then explain how the model's rule relates to Postgres's SERIALIZABLE level, and what the application must do when a transaction is aborted.

Which conflict does write skew consist of?

Hint

{{ref:inventory}} had the same structure: a check, then an action based on it, with another process changing the facts in between. Here the database itself keeps the check's facts frozen, inside the snapshot.

Solution

1. Only interleavings. Run alone, either transaction sees two doctors on call and leaves one. A bad behavior needs both checks to happen before either change becomes visible to the other.

2. AtLeastOneOnCall fails after 7 states: Begin(alice), Check(alice) (2 on call), Begin(bob), Commit(alice), Check(bob), Commit(bob). Bob checks after Alice has committed, but he reads his snapshot, which was taken before her commit. The diagram shows the two snapshots disagreeing with the database.

3. The writes go to different rows, Alice's and Bob's, so first-committer-wins never fires. What makes the outcome wrong is that each transaction's decision depended on a row the other one changed. That read-write dependency is not something snapshot isolation tracks.

4. No error, 21 distinct states. In every interleaving where both have read the other's row before either commits, the second commit sees a changed version and aborts. The model's rule, validating the read set at commit, is a simple optimistic scheme, not Postgres's algorithm. Postgres's SERIALIZABLE uses serializable snapshot isolation: it tracks read-write dependencies among concurrent transactions and aborts one when they could form a cycle. In this example the effect is the same, one of the two fails with a serialization error. The application must be ready to retry the transaction from the start, and the retry will see one doctor on call and refuse. Another fix keeps REPEATABLE READ and makes the conflict a write conflict, for example by locking the shift's row before counting. This model does not check that variant.

Note what the model left out: the number of doctors, other shifts, retries. Two processes and one invariant were enough to produce the bug, which is the reduction argument of {{ref:scaling}}.

Problem 2●●○Microservices

An order saga that refunds a charge that hasn't happened yet

Draws on {{ref:diehard-tlc}}, {{ref:transactions}}, {{ref:paxos-commit}}, {{ref:messages}}, {{ref:fairness}} and {{ref:idempotency}}.

An order service runs a saga, a sequence of local transactions in different services, each with a compensating action that undoes it if a later step fails. Step 1 reserved the stock. Step 2 asks the payment service to charge the card. If the charge is declined, the compensation releases the stock and the order is cancelled. The payment service is sometimes slow, so after 30 seconds the order service gives up on the reply and compensates. Customers complain about being charged for cancelled orders.

The team tries three designs for the timeout. "ReleaseOnly" releases the stock and cancels. "Refund" also sends a refund request. "RefundTombstone" sends the refund too, and the payment service records a refund for a charge it has not seen yet. That record makes a late charge request for the same order fail. The network is a set of messages that can arrive in any order. Timeout has no fairness: it may or may not happen, which is the environment's choice.

---------------- MODULE PSfinal_Saga ----------------
CONSTANT Design
ASSUME Design \in {"ReleaseOnly", "Refund", "RefundTombstone"}
VARIABLES stock,  \* inventory service: "reserved" or "released"
          pay,    \* payment service: "none", "charged", "declined",
                  \*   "refunded" or "blocked" (a refund came first)
          orch,   \* orchestrator: "charge", "wait", "done", "cancelled"
          msgs    \* messages in flight
vars == <<stock, pay, orch, msgs>>

Init == /\ stock = "reserved"     \* step 1 of the saga has completed
        /\ pay = "none"
        /\ orch = "charge"
        /\ msgs = {}

\* Step 2: ask the payment service to charge the card.
SendCharge == /\ orch = "charge"
              /\ orch' = "wait"
              /\ msgs' = msgs \cup {"charge"}
              /\ UNCHANGED <<stock, pay>>

\* The payment service handles the charge request.
Reply(m) == msgs' = (msgs \ {"charge"}) \cup {m}
Charge == /\ "charge" \in msgs
          /\ \/ pay = "none" /\ pay' = "charged" /\ Reply("charged")
             \/ pay = "none" /\ pay' = "declined" /\ Reply("declined")
             \/ pay = "blocked" /\ UNCHANGED pay /\ Reply("declined")
          /\ UNCHANGED <<stock, orch>>

\* The orchestrator gets the outcome.
Charged  == /\ "charged" \in msgs
            /\ msgs' = msgs \ {"charged"}
            /\ orch' = IF orch = "wait" THEN "done" ELSE orch
            /\ UNCHANGED <<stock, pay>>
Declined == /\ "declined" \in msgs
            /\ msgs' = msgs \ {"declined"}
            /\ IF orch = "wait"
                  THEN orch' = "cancelled" /\ stock' = "released"
                  ELSE UNCHANGED <<orch, stock>>
            /\ UNCHANGED pay

\* No reply yet: the orchestrator gives up and compensates.
Timeout == /\ orch = "wait"
           /\ orch' = "cancelled"
           /\ stock' = "released"
           /\ msgs' = IF Design = "ReleaseOnly" THEN msgs
                      ELSE msgs \cup {"refund"}
           /\ UNCHANGED pay

\* The payment service handles a refund for this order.
Refund == /\ "refund" \in msgs
          /\ msgs' = msgs \ {"refund"}
          /\ pay' = CASE pay = "charged" -> "refunded"
                      [] pay = "none" /\ Design = "RefundTombstone" -> "blocked"
                      [] OTHER -> pay
          /\ UNCHANGED <<stock, orch>>

FairSpec == /\ Spec
            /\ WF_vars(SendCharge) /\ WF_vars(Charge) /\ WF_vars(Charged)
            /\ WF_vars(Declined) /\ WF_vars(Refund)

\* What a finished order must look like.
Settled == \/ orch = "done" /\ stock = "reserved" /\ pay = "charged"
           \/ orch = "cancelled" /\ stock = "released" /\ pay # "charged"
EventuallySettled == <>[]Settled
\* A search goal: a quiet system with a paid, cancelled order.
NoPaidCancelled == ~(orch = "cancelled" /\ pay = "charged" /\ msgs = {})
\* "Never charged while the stock is released" (true of 2PC's outcome).
NoChargedRelease == ~(pay = "charged" /\ stock = "released")

  2. Run "Refund". Why didn't the refund help?
  3. Run "RefundTombstone" and report the distinct states.
  4. Check INVARIANT NoChargedRelease on "RefundTombstone". It fails. Is that a bug? Compare with what two-phase commit, as in {{ref:transactions}}, would guarantee, and say what it would cost here.

Which earlier idea does the payment service's "blocked" state implement?

Hint

A timeout does not mean the request failed. It means the reply did not arrive in time. Ask what the request can still do after the timeout, and who can stop it.

Solution

1. EventuallySettled fails: SendCharge, Charge (succeeds), Timeout (the reply is in flight; stock released), Charged (ignored, since the order is cancelled), then stuttering forever in a state with a paid, cancelled order. The invariant NoPaidCancelled describes that end state as a safety goal. TLC finds it in 5 states with the same steps, under Spec, with no fairness. Turning "this must not happen eventually" into "this state is never reached" made the check simpler, which is the trick of {{ref:diehard-tlc}}. It works when the bad outcome is a state the system cannot leave.

2. "Refund" fails differently: SendCharge, Timeout (refund sent while the charge request is still on the network), Refund (nothing to refund yet), Charge (succeeds), Charged. The refund and the charge were reordered, as {{ref:messages}} allows, and the refund of a charge that did not exist yet did nothing. The diagram draws this trace.

3. No error, 17 distinct states. The refund leaves a durable record, "blocked", so the late charge is declined. In a real payment service, the charge and the refund both carry the order's ID, and the service keeps the ID's state, which is the idempotency record of {{ref:idempotency}}.

4. It fails after 4 states: SendCharge, Charge, Timeout. The card is charged while the stock is released, and the refund is still on its way. That is not a bug in a saga: a saga gives up isolation, so other observers can see intermediate states, and promises only that compensations eventually bring it to a consistent end. EventuallySettled states that promise. Two-phase commit would rule the intermediate state out. Both services would prepare and hold their resources, and a coordinator would decide. The cost is what {{ref:transactions}} and {{ref:paxos-commit}} showed: every participant must support a prepared state, resources stay locked while the decision is pending, and a coordinator failure can block them. An external payment provider is usually not a participant you can enlist in your own two-phase commit, which is one reason payment flows are often built as sagas.

Problem 3●●○Distributed data

A like counter on three continents

Draws on {{ref:sets}}, {{ref:temporal}}, {{ref:fairness}}, {{ref:refinement}} and {{ref:composition}}.

A social app runs active replicas in three regions, and each region accepts likes locally. Replicas periodically send their whole state to each other and merge what they receive. The first design keeps one integer per region and merges with max, "because max never loses the bigger number". The second merges by adding. The third is a G-counter, a grow-only counter from the literature on conflict-free replicated data types (CRDTs). Each replica keeps a vector with one entry per replica, increments only its own entry, merges by taking the maximum of each entry, and displays the sum.

---------------- MODULE PSfinal_NaiveCounter ----------------
EXTENDS Naturals
CONSTANTS Replicas, MaxLikes, MergeRule
ASSUME MergeRule \in {"Max", "Add"}
VARIABLES n,      \* n[r]: the single number replica r stores
          likes   \* history: likes actually taken, anywhere
vars == <<n, likes>>
Init == n = [r \in Replicas |-> 0] /\ likes = 0
Like(r) == /\ likes < MaxLikes
           /\ n' = [n EXCEPT ![r] = @ + 1]
           /\ likes' = likes + 1
Merge(r, s) == /\ r # s
               /\ n' = [n EXCEPT ![r] = IF MergeRule = "Max"
                          THEN (IF n[s] > n[r] THEN n[s] ELSE n[r])
                          ELSE n[r] + n[s]]
               /\ UNCHANGED likes
Next == \E r, s \in Replicas : Like(r) \/ Merge(r, s)
Spec == Init /\ [][Next]_vars
FairSpec == Spec /\ \A r, s \in Replicas : WF_vars(Merge(r, s))
Bounded == \A r \in Replicas : n[r] <= MaxLikes + 1   \* a CONSTRAINT for "Add"
NeverOverCount == \A r \in Replicas : n[r] <= likes
Converges == <>[](\A r \in Replicas : n[r] = likes)

---------------- MODULE PSfinal_Counter ----------------
EXTENDS Naturals

Init == count = 0
Next == count' = count + 1

---------------- MODULE PSfinal_GCounter ----------------
EXTENDS Naturals
CONSTANTS Replicas, MaxLikes
VARIABLE c   \* c[r][s]: what replica r knows of the likes taken at s
vars == c

RECURSIVE SumOver(_, _)
SumOver(f, S) == IF S = {} THEN 0
                 ELSE LET x == CHOOSE x \in S : TRUE
                      IN  f[x] + SumOver(f, S \ {x})

Like(r) == /\ Total < MaxLikes

Merge(r, s) == c' = [c EXCEPT ![r] = [x \in Replicas |->

Why does the mapping count <- Value(r) fail?

Hint

A merge function's input may include information the receiver already has. Ask what happens if the same state arrives twice, and whether the merge can tell two different likes from one like seen twice.

Solution

1. Converges fails: Like(r2), Like(r1), then stuttering, with n = (r1 :> 1 @@ r2 :> 1) and likes = 2. The replicas agree, on 1. Weak fairness forces every merge that is enabled, but a merge of 1 with 1 changes nothing, so it is a stuttering step and fairness asks for nothing more. Max cannot tell two different likes from one like seen twice. Convergence to the wrong value is not convergence.

2. NeverOverCount fails after 4 states: Like(r1), Merge(r2, r1), Merge(r2, r1), with r2 showing 2 after one like. Gossip delivers the same state many times, as messages in {{ref:messages}} could be duplicated. So a merge must be idempotent, as well as commutative and associative, because states arrive in any order and grouping. Max on each entry has all three properties. Addition is not idempotent.

3. No error, 414 distinct states. NeverOverCount and OwnEntryLargest hold, Converges holds under the merge fairness, and so does Refines. A Like(r) adds 1 to c[r][r] and so to Total: an abstract Next step. A Merge(r, s) sets c[r][r] to the larger of c[r][r] and c[s][r], which is c[r][r] because of OwnEntryLargest: only r ever increments its own entry, so no one knows more about it than r. Every own entry is unchanged, so Total is unchanged and the step stutters, as in {{ref:implementation}}. This is how refinement uses an invariant: the mapping is only correct in reachable states.

4. TLC reports the contract's action property violated after 4 states: Like(r2), Like(r2), then a Merge into the watched replica, whose display jumps from 0 to 2. The contract allows only steps of 1 (the replica TLC watches is CHOOSE r \in Replicas : TRUE, so your run may name a different one). The display is a lagging view of the counter, not the counter. A contract for it would be weaker: never more than Total, never decreasing, eventually equal.

Problem 4●●●Consensus

Why a Raft follower checks the previous entry

Draws on {{ref:replication}}, {{ref:consensus}}, {{ref:abspec}}, {{ref:scaling}} and {{ref:ps-l7}}.

A team is building a metadata service on a Raft-style replicated log. Each log entry records the term of the leader that created it. A leader sends a follower the entry at index i + 1 together with the index i and term of the entry before it, and the follower accepts only if its own entry i has that term. The Raft paper calls the resulting guarantee Log Matching: if two logs contain an entry with the same index and term, the logs are identical up to that index. A refactoring "optimizes" the follower by dropping the check.

The model abstracts elections: Elect(s, t) makes s leader of a newer term, and OneLeaderPerTerm says whether two servers can win the same term. Real Raft gets that from votes, as you saw in {{ref:ps-l7}}. AppendEntries is one atomic step from leader to follower. As a simplification, the follower always cuts its log after the new entry, where Raft deletes entries only on a conflict. That is harmless for Log Matching, but it would not be for a property about committed entries.

---------------- MODULE PSfinal_RaftLog ----------------
EXTENDS Naturals, Sequences
CONSTANTS Servers, MaxTerm, MaxLen, PrevCheck, OneLeaderPerTerm
ASSUME PrevCheck \in BOOLEAN /\ OneLeaderPerTerm \in BOOLEAN
Terms == 1..MaxTerm
VARIABLES term,     \* term[s]: the latest term server s knows
          leaders,  \* leaders[t]: servers elected leader in term t
          log       \* log[s]: the term of each entry, in index order
vars == <<term, leaders, log>>

Init == /\ term = [s \in Servers |-> 0]
        /\ leaders = [t \in Terms |-> {}]
        /\ log = [s \in Servers |-> <<>>]

\* Elections are abstracted: s wins term t, a term newer than its own.
Elect(s, t) == /\ t > term[s]
               /\ OneLeaderPerTerm => leaders[t] = {}
               /\ leaders' = [leaders EXCEPT ![t] = @ \cup {s}]
               /\ term' = [term EXCEPT ![s] = t]
               /\ UNCHANGED log

IsLeader(s) == term[s] > 0 /\ s \in leaders[term[s]]

\* A leader appends a client command, tagged with its term, to its own log.
ClientRequest(s) == /\ IsLeader(s)
                    /\ Len(log[s]) < MaxLen
                    /\ log' = [log EXCEPT ![s] = Append(@, term[s])]
                    /\ UNCHANGED <<term, leaders>>

\* Leader l sends f entry i+1, with prevLogIndex i and prevLogTerm log[l][i].
\* f accepts if l's term is not older than f's and (with PrevCheck) f's
\* entry i has that term. f keeps entries 1..i, then takes entry i+1.
AppendEntries(l, f, i) ==
    /\ l # f /\ IsLeader(l)
    /\ term[l] >= term[f]
    /\ i < Len(log[l]) /\ i <= Len(log[f])
    /\ PrevCheck => IF i = 0 THEN TRUE ELSE log[f][i] = log[l][i]
    /\ log' = [log EXCEPT ![f] = [j \in 1..(i + 1) |->
                   IF j <= i THEN log[f][j] ELSE log[l][i + 1]]]
    /\ term' = [term EXCEPT ![f] = term[l]]
    /\ UNCHANGED leaders

Next == \/ \E s \in Servers, t \in Terms : Elect(s, t)
        \/ \E s \in Servers : ClientRequest(s)
        \/ \E l, f \in Servers, i \in 0..(MaxLen - 1) : AppendEntries(l, f, i)
Spec == Init /\ [][Next]_vars

\* Log Matching: same index and term => identical logs up to that index.
LogMatching ==
    \A s, u \in Servers : \A i \in 1..MaxLen :
        (i <= Len(log[s]) /\ i <= Len(log[u]) /\ log[s][i] = log[u][i])
            => \A j \in 1..i : log[s][j] = log[u][j]
=========================================================

CONSTANTS Servers = {s1, s2, s3}
          MaxTerm = 2
          MaxLen = 2

          OneLeaderPerTerm = TRUE

With the check but two leaders per term, what breaks Log Matching?

Hint

Log Matching has two halves. An (index, term) pair must name a single entry, and the entries before it must agree. Each half is protected by a different mechanism; break one at a time.

Solution

1. No error, 793 distinct states.

2. LogMatching fails after 7 states: Elect(s1, 1), Elect(s2, 2), ClientRequest(s1) (s1's log is <<1>>), ClientRequest(s2) twice (s2's log is <<2, 2>>), then AppendEntries(s2, s1, 1). s2 sends its entry 2 with previous term 2, s1's entry 1 has term 1, and without the check s1 keeps it and appends: <<1, 2>>. Now s1 and s2 both have term 2 at index 2 but differ at index 1. The diagram shows the logs. Any later reasoning that "same index and term means same history", which Raft's commit rule depends on, is wrong for this pair.

3. LogMatching fails after 8 states: Elect(s1, 1), Elect(s2, 2), ClientRequest(s1), Elect(s1, 2) (a second leader of term 2), ClientRequest(s1) gives <<1, 2>>, and ClientRequest(s2) twice gives <<2, 2>>. No message was needed. In Raft a candidate needs votes from a majority, and each server votes at most once per term. Two majorities of the same servers intersect, as in {{ref:replication}}, so two leaders of one term would need some server to vote twice.

4. With SYMMETRY Perms: no error, 148 distinct states instead of 793.

---------------- MODULE PSfinal_RaftLogSym ----------------
EXTENDS PSfinal_RaftLog, TLC
Perms == Permutations(Servers)
============================================================

The reduction is sound here because no definition singles out a server: Init, Next and LogMatching treat every server alike, so a permuted state violates the invariant exactly when the original does. {{ref:scaling}} warns against combining symmetry with liveness checks unless your tools and reasoning explicitly support it, so run liveness checks without it.

5. Suppose Log Matching holds before a step. ClientRequest appends an entry whose term is the leader's current term at a new index. No other log has an entry with that term at that index, because one leader creates all of a term's entries and it never overwrites its own. So the new entry matches nothing yet. AppendEntries(l, f, i) gives f the prefix up to i only if f's entry i has the same term as l's. By the hypothesis, f's prefix through i equals l's. The new entry i + 1 is l's, so f's new log is a prefix of l's, and every pair involving f reduces to a pair involving l. Making this into a checked inductive invariant needs extra facts, such as that each term's entries appear in that term's leader's log. Finding them is the work {{ref:invariants}} describes.

Problem 5●●●Infrastructure

Capstone: a job scheduler that sends each invoice exactly once

Synthesis of the whole course. Draws on {{ref:fencing}}, {{ref:idempotency}}, {{ref:fairness}}, {{ref:refinement}}, {{ref:invariants}}, {{ref:capstone}} and {{ref:ps-b3}}.

A billing platform runs one job per customer each month. The job computes the invoice, writes it to storage, and queues the invoice email. A scheduler leases each job to one worker at a time and issues an increasing fencing token per job with each lease. Workers can pause past their lease's expiry, and they can crash. The worker writes the output, then runs one storage transaction that marks the job done and inserts an outbox row for the email, as in the outbox problem of {{ref:ps-b3}}. The product requirement is that every customer eventually gets exactly one invoice, built from the output of the run that committed it.

Three designs differ only in storage's checks. "LeaseOnly" trusts the lease: storage checks nothing. "DedupOnly" refuses to commit a job already done. "Fenced" also refuses a write or a commit whose token is below the job's fence, and refuses writes to a finished job. Expiries and crashes are bounded to keep the model finite. Reap frees the lease of a worker that crashed, and has fairness, because a lease always runs out eventually. The contract, PSfinal_Jobs, sends each job's invoice once, eventually.

---------------- MODULE PSfinal_Jobs ----------------
EXTENDS Naturals
CONSTANT Jobs
VARIABLE invoiced      \* invoiced[j]: invoices sent for job j
Init == invoiced = [j \in Jobs |-> 0]
\* The contract: each job's invoice goes out once, in one step.
Finish(j) == /\ invoiced[j] = 0
             /\ invoiced' = [invoiced EXCEPT ![j] = 1]
Next == \E j \in Jobs : Finish(j)
Spec == Init /\ [][Next]_invoiced /\ WF_invoiced(Next)
======================================================
---------------- MODULE PSfinal_Scheduler ----------------
EXTENDS Naturals
CONSTANTS Workers, Jobs, Design, MaxExpiries, MaxCrashes
ASSUME Design \in {"LeaseOnly", "DedupOnly", "Fenced"}
VARIABLES lease,     \* lease[j]: the worker holding j's lease, or "none"
          issued,    \* issued[j]: the last fencing token issued for j
          wpc,       \* wpc[w]: "idle", "run" or "wrote" (volatile)
          wjob,      \* wjob[w]: the job w is running
          wtok,      \* wtok[w]: the token w received with its lease
          output,    \* storage: output[j] = token of the run that wrote it
          fence,     \* storage: fence[j] = highest token accepted for j
          done,      \* storage: jobs committed as finished
          doneTok,   \* storage: doneTok[j] = token of the committing run
          invoices,  \* outbox rows: invoices[j] = invoices queued for j
          expiries,  \* lease expiries so far (the holder is still alive)
          crashes    \* worker crashes so far
vars == <<lease, issued, wpc, wjob, wtok, output, fence, done, doneTok,
          invoices, expiries, crashes>>

MaxTok == 1 + MaxExpiries + MaxCrashes  \* enough for every run allowed

Init == /\ lease = [j \in Jobs |-> "none"]
        /\ issued = [j \in Jobs |-> 0]
        /\ wpc = [w \in Workers |-> "idle"]
        /\ wjob = [w \in Workers |-> CHOOSE j \in Jobs : TRUE]
        /\ wtok = [w \in Workers |-> 0]
        /\ output = [j \in Jobs |-> 0]
        /\ fence = [j \in Jobs |-> 0]
        /\ done = {}
        /\ doneTok = [j \in Jobs |-> 0]
        /\ invoices = [j \in Jobs |-> 0]
        /\ expiries = 0
        /\ crashes = 0

Storage == <<output, fence, done, doneTok, invoices>>

\* The scheduler leases an unfinished job to an idle worker, with a token.
Acquire(w, j) == /\ wpc[w] = "idle" /\ lease[j] = "none" /\ j \notin done
                 /\ issued[j] < MaxTok
                 /\ lease' = [lease EXCEPT ![j] = w]
                 /\ issued' = [issued EXCEPT ![j] = @ + 1]
                 /\ wpc' = [wpc EXCEPT ![w] = "run"]
                 /\ wjob' = [wjob EXCEPT ![w] = j]
                 /\ wtok' = [wtok EXCEPT ![w] = issued[j] + 1]
                 /\ UNCHANGED <<Storage, expiries, crashes>>

\* The worker stops; it gives the lease back if it still holds it.
Stop(w) == /\ wpc' = [wpc EXCEPT ![w] = "idle"]
           /\ lease' = IF lease[wjob[w]] = w
                          THEN [lease EXCEPT ![wjob[w]] = "none"] ELSE lease

\* The worker writes the job's output to storage.
Write(w) == LET j == wjob[w] IN
    /\ wpc[w] = "run"
    /\ IF Design = "Fenced" /\ (j \in done \/ wtok[w] < fence[j])
          THEN /\ Stop(w)                      \* storage refused
               /\ UNCHANGED <<output, fence>>
          ELSE /\ output' = [output EXCEPT ![j] = wtok[w]]
               /\ fence' = [fence EXCEPT ![j] = IF wtok[w] > @ THEN wtok[w] ELSE @]
               /\ wpc' = [wpc EXCEPT ![w] = "wrote"]
               /\ UNCHANGED lease
    /\ UNCHANGED <<issued, wjob, wtok, done, doneTok, invoices, expiries, crashes>>

\* One storage transaction marks the job done and queues the invoice.
Commit(w) == LET j == wjob[w] IN
    /\ wpc[w] = "wrote"
    /\ Stop(w)
    /\ IF \/ Design # "LeaseOnly" /\ j \in done
          \/ Design = "Fenced" /\ wtok[w] # fence[j]
          THEN UNCHANGED <<done, doneTok, invoices>>   \* refused
          ELSE /\ done' = done \cup {j}
               /\ doneTok' = [doneTok EXCEPT ![j] = wtok[w]]
               /\ invoices' = [invoices EXCEPT ![j] = @ + 1]
    /\ UNCHANGED <<issued, wjob, wtok, output, fence, expiries, crashes>>

\* The lease runs out while its holder is alive but paused.
Expire(j) == /\ lease[j] # "none" /\ expiries < MaxExpiries
             /\ lease' = [lease EXCEPT ![j] = "none"]
             /\ expiries' = expiries + 1
             /\ UNCHANGED <<issued, wpc, wjob, wtok, Storage, crashes>>

\* A worker crashes; its lease stays until Reap.
Crash(w) == /\ wpc[w] # "idle" /\ crashes < MaxCrashes
            /\ wpc' = [wpc EXCEPT ![w] = "idle"]
            /\ crashes' = crashes + 1
            /\ UNCHANGED <<lease, issued, wjob, wtok, Storage, expiries>>

\* The lease of a worker that is no longer running the job runs out.
Reap(j) == /\ lease[j] # "none"
           /\ LET w == lease[j] IN wpc[w] = "idle" \/ wjob[w] # j
           /\ lease' = [lease EXCEPT ![j] = "none"]
           /\ UNCHANGED <<issued, wpc, wjob, wtok, Storage, expiries, crashes>>

Next == \/ \E w \in Workers, j \in Jobs : Acquire(w, j)
        \/ \E w \in Workers : Write(w) \/ Commit(w) \/ Crash(w)
        \/ \E j \in Jobs : Expire(j) \/ Reap(j)
Spec == Init /\ [][Next]_vars
FairSpec == /\ Spec
            /\ \A j \in Jobs : WF_vars(\E w \in Workers : Acquire(w, j))
                               /\ WF_vars(Reap(j))
            /\ \A w \in Workers : WF_vars(Write(w)) /\ WF_vars(Commit(w))

OneInvoice == \A j \in Jobs : invoices[j] <= 1
OutputOfCommitter == \A j \in done : output[j] = doneTok[j]
Contract == INSTANCE PSfinal_Jobs WITH invoiced <- invoices
Refines == Contract!Spec
===========================================================
SPECIFICATION FairSpec
CONSTANTS Workers = {w1, w2}
          Jobs = {j1}
          Design = "Fenced"
          MaxExpiries = 1
          MaxCrashes = 1
INVARIANT OneInvoice
INVARIANT OutputOfCommitter
PROPERTY Refines
CHECK_DEADLOCK FALSE

For task 4, this module adds a type invariant, a first guess at an inductive invariant, and a stronger candidate. It also defines a specification with no fairness for Reap.

---------------- MODULE PSfinal_SchedulerInd ----------------
EXTENDS PSfinal_Scheduler
\* Fairness without Reap: a crashed worker's lease never runs out.
NoReapSpec == /\ Spec
              /\ \A j \in Jobs : WF_vars(\E w \in Workers : Acquire(w, j))
              /\ \A w \in Workers : WF_vars(Write(w)) /\ WF_vars(Commit(w))

TypeOK == /\ lease \in [Jobs -> Workers \cup {"none"}]
          /\ issued \in [Jobs -> 0..MaxTok]
          /\ wpc \in [Workers -> {"idle", "run", "wrote"}]
          /\ wjob \in [Workers -> Jobs]
          /\ wtok \in [Workers -> 0..MaxTok]
          /\ fence \in [Jobs -> 0..MaxTok]
          /\ output \in [Jobs -> 0..MaxTok]
          /\ done \in SUBSET Jobs
          /\ doneTok \in [Jobs -> 0..MaxTok]
          /\ invoices \in [Jobs -> 0..2]
          /\ expiries \in 0..MaxExpiries
          /\ crashes \in 0..MaxCrashes
\* A first guess: the two safety properties themselves.
Guess == TypeOK /\ OneInvoice /\ OutputOfCommitter

Inv == /\ TypeOK
       /\ \A j \in Jobs : output[j] = fence[j]

Solution

1. "LeaseOnly" fails OneInvoice after 8 states. w1 acquires j1 with token 1 and writes the output. Its lease expires while it is paused. w2 acquires with token 2. w1 commits: done, one invoice. w2 writes and commits: a second invoice. Storage trusted a lease that had already ended. That is the fencing problem, and checking nothing also loses idempotency. "DedupOnly" passes OneInvoice but fails OutputOfCommitter after 7 states, the same steps up to w1's commit and then w2's write. The job is done with token 1, but the stored output now comes from run 2. The invoice email describes one computation and storage holds another. Deduplication from {{ref:idempotency}} stopped the second commit, but only fencing from {{ref:fencing}} stops the stale run's write. The diagram draws this trace. In "Fenced", w2's write is refused because the job is done; if w2 had written first, w1's commit would have been refused instead, since its token would be below the fence.

2. No error: 163 distinct states with one job, 2189 with two. Refines checks the contract's whole formula, including WF_invoiced(Next), so it checks that every invoice is eventually sent, not just that none is sent twice. "DedupOnly" also refines the contract (207 distinct states), although its invoice can describe the wrong output. The contract says nothing about which output; a passing refinement is only as strong as the contract. Either add the output to the contract or keep OutputOfCommitter as a separate checked property.

3. Refines fails. w1 acquires; its lease expires; w2 acquires, writes, and crashes, and w2's lease stays held. w1 resumes, its write is refused (token 1 is below fence 2), and then the system stutters forever: j1 is not done, no one can acquire it, and the invoice never goes out. WF_vars(Reap(j)) stands for lease expiry: a crashed holder's lease runs out because the lock service's clock keeps moving. That is the time assumption {{ref:fencing}} told you to make explicit. Safety never depended on it; liveness does.

4. Guess fails from an unreachable state: invoices[j1] = 1 while done = {} and w2 is about to commit, so Commit(w2) makes the count 2. The missing fact is that invoices and done move together, and similarly that the stored output always belongs to the fence's token. Inv says exactly that. Starting from every state that satisfies it, TLC finds no error (138,240 distinct states), so it is inductive for these constants. By hand: Init has every count, token and fence at 0 and nothing done, so it satisfies Inv. Inv gives invoices[j] <= 1 directly, and for a done job output[j] = fence[j] = doneTok[j], which is OutputOfCommitter. The step case is the one TLC checked. The fenced Write sets output and fence to the same token. Commit needs wtok[w] = fence[j], so doneTok becomes the fence. And nothing changes output or fence after the job is done. As {{ref:invariants}} says, this is a finite check, not a proof for all sizes; {{ref:proofs}} shows how to make it one.

5. Tokens increase per job and are never reused, even after the scheduler restarts. Storage checks the token and applies the write, or the commit, in one atomic step, like a conditional update in one transaction. The outbox relay and the email consumer give at-least-once delivery with deduplication, as in {{ref:ps-b3}}. Crashes and pauses happen finitely often; the bounds here stand in for that. A crashed holder's lease eventually expires. And the contract is about invoices queued, not delivered: delivery is the next layer's contract. Every one of these is either checked in some model of this course or stated as an assumption. That is what a reviewable design looks like.
