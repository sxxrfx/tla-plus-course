Keep an old response from replacing a newer choice.

A search screen can show the wrong results even when every request succeeds. Model which response is allowed to change the current view.

This builds on {{lesson:messages}}, where messages arrive in any order, and on {{lesson:fencing}}, where a resource refused superseded work. Here the resource is your screen, and the token is a request ID.

The concrete bug

A user searches for cats, then dogs. The cats request is slow; dogs returns first. A handler that displays every successful response shows dogs, then replaces it with cats.

The HTTP responses in the chart are individually correct. The screen is wrong because it has forgotten which request represents the user’s current choice. A debounce reduces how often requests start, but it does not establish response ordering.

State the contract

Use a fresh increasing request ID whenever a search begins. latest records that ID, and pending contains requests whose responses can still arrive. The UI is a tagged record: idle has no request, loading identifies the current request, and ready contains its request and result. These variants rule out combinations such as idle = TRUE with resultsLoading = TRUE.

The property is precise: whenever the UI is ready, it shows the result of latest. Compare the same delivery order with and without the guard.

The two grids differ in one cell. We also clear the old view on Start on purpose. A product that keeps previous results while loading needs a different contract, such as a separate displayedRequest field and an explicit “updating” state.

A complete bounded model

Save as AppState.tla for the real tools. There are two possible requests with fixed results. Start issues them in order, but Deliver may select either pending response. Errors, cancellation, and duplicated responses are omitted to isolate the stale-response race.

---------------- MODULE AppState ----------------
EXTENDS Naturals
VARIABLES latest, pending, ui
vars == <<latest,pending,ui>>
Requests == 1..2
Query == [r \in Requests |->
             IF r = 1 THEN "cats" ELSE "dogs"]
UIStates ==
    [tag : {"idle"}]
    \cup [tag : {"loading"}, request : Requests]
    \cup [tag : {"ready"}, request : Requests,
          value : {"cats", "dogs"}]

Init == /\ latest = 0
        /\ pending = {}
        /\ ui = [tag |-> "idle"]
Start ==
    /\ latest < 2
    /\ LET r == latest + 1 IN
           /\ latest' = r
           /\ pending' = pending \cup {r}
           /\ ui' = [tag |-> "loading", request |-> r]
Deliver(r) ==
    /\ r \in pending
    /\ pending' = pending \ {r}
    /\ UNCHANGED latest
    /\ ui' = IF r = latest
              THEN [tag |-> "ready", request |-> r,
                    value |-> Query[r]]
              ELSE ui
Next == Start \/ (\E r \in Requests: Deliver(r))
Spec == Init /\ [][Next]_vars
FairSpec == Spec /\ (\A r \in Requests: WF_vars(Deliver(r)))

TypeOK == /\ latest \in 0..2
          /\ pending \subseteq 1..latest
          /\ ui \in UIStates
CurrentView ==
    IF ui.tag = "ready"
    THEN /\ ui.request = latest
         /\ ui.value = Query[latest]
    ELSE TRUE
Settles == (ui.tag = "loading") ~> (ui.tag = "ready")
=================================================

Start’s LET names the new request number; all three primed equations describe the same step. Deliver always removes the arriving request from pending but updates ui only if the ID still equals latest. CurrentView reads the tagged record’s fields only when they exist.

SPECIFICATION FairSpec
INVARIANT TypeOK
INVARIANT CurrentView
PROPERTY Settles
CHECK_DEADLOCK FALSE

TLC completes with 7 distinct states and 9 generated, with both invariants and Settles holding. That is small enough to draw completely.

Follow the two dashed arrows: they are the only places where a stale response arrives. Each changes pending and leaves ui alone. Settles uses fairness from {{lesson:fairness}}: each pending Deliver stays enabled until executed, and only two Start steps exist, so a current request cannot be postponed forever. Real applications cannot promise this over a permanently failed network; add error and timeout outcomes for their progress contract.

Make the bug appear

Replace the entire IF expression in Deliver with the ready record, unconditionally. Check TypeOK and CurrentView under Spec.

Predict: does TLC need dogs to arrive first to break the view?

No. TLC’s trace is shorter than the story: Start, Start, Deliver(1). Cats arrives while dogs is still loading, and the screen shows ready 1 with latest = 2. The dogs-first order in the chart also fails, but the guard was never about dogs arriving. It was about any response that is not the latest.

The implementation boundary

let latest = 0;
let ui = { tag: "idle" };
async function search(query) {
  const request = ++latest;
  ui = { tag: "loading", request };
  render(ui);
  try {
    const value = await searchApi(query);
    if (request !== latest) return;
    ui = { tag: "ready", request, value };
    render(ui);
  } catch (error) {
    if (request !== latest) return;
    ui = { tag: "error", request, error };
    render(ui);
  }
}

The synchronous increment and loading update correspond to Start. The await permits arbitrary interleaving. Checking the ID and committing the view form one synchronous callback segment with no await between them, which is why one Deliver step can stand for them. The error variant extends the small module; apply the same test to failures. Cancellation can save work, but correct ID handling must not assume cancellation always prevents a response.

Predict: dogs fails, then the old cats request succeeds. Should cats replace the error?

Under this contract, no. The latest user choice is still dogs. An old success and an old failure must both be rejected. To show fallback results intentionally, model that as an explicit product rule rather than letting callback order decide.
