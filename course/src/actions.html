A step formula must describe the whole next state.

{{lesson:diehard}} left Next as six names. Writing their definitions exposes the most common beginner's mistake in TLA+, and it fixes what you need to say about every variable in every step.

A formula like the six in Next, which relates a current state to a next state and describes one kind of step, is called an action. Start with FillSmall. Most people first write this:

FillSmall == small' = 3
Predict: why is that wrong? Decide before opening this. The diagram above is a clue.

If you didn't see it, you are reading it as a command that sets small to 3. It is a formula, true for some steps and false for others. It is true for any step where small is 3 in the second state, whatever big does. In the diagram, that includes the two red arrows, where big becomes √7 or the string "abc".

Frames: say what stays the same

The correct definition also says big doesn't change:

FillSmall == /\ small' = 3
             /\ big'   = big

FillBig == /\ big'   = 5
           /\ small' = small

A line like big' = big is called a frame condition. Most engineers feel it shouldn't be needed. Lamport's answer is that “unchanged unless mentioned” would take you out of simple math and into the more complicated world of programming languages. In math, a formula that doesn't mention big' says nothing about it.

TLC enforces this in practice. We removed the frame line and ran the spec:

Error: Successor state is not completely specified by action FillSmall
of the next-state relation. The following variable is not defined: big.

Keep the two facts separate. Mathematically, omission permits any value. In TLC, omission usually produces this error. In neither case does it preserve the old value.

Exercise: write EmptySmall and EmptyBig.

EmptySmall == /\ small' = 0 /\ big' = big and EmptyBig == /\ big' = 0 /\ small' = small, each written as a two-line bulleted list. Each one has a line for each variable.

Pouring has two cases

Now SmallToBig. There are two cases, and the behavior from {{lesson:diehard}} contains both.

In the top row of the diagram, the big jug has room for all the water in the small one, so all of it moves and the small jug is empty. In the bottom row there isn't enough room, so the big jug ends up full and some water stays behind. Which case applies depends only on the total, so an IF formula fits:

SmallToBig == IF big + small =< 5
                THEN /\ big'   = big + small
                     /\ small' = 0
                ELSE ...

Stop and solve this. Write the ELSE part of SmallToBig, and then all of BigToSmall. Write them down. You can test your arithmetic against the lab in {{lesson:diehard}}.

All the lines in a list describe the same pair of states, so nothing happens first. In big' = big + small, both unprimed values are from the current state. This is what lets one step swap two values:

With x = 2 and y = 9, what next state does x' = y /\ y' = x allow?

Predict: does x' = x + 1 /\ x' = x + 2 increment x twice?

No. No integer equals both x + 1 and x + 2, so no next state satisfies the formula and this action never happens. Conjunction combines conditions. It doesn't sequence assignments.

Guards, and why the jugs have none

You saw a guard in {{lesson:counter}}: a line with no primes, which an action needs to be true of the current state. x < Max is one. An action is enabled in a state when some next state satisfies it, so a false guard disables the action.

The jug actions have no guards. Every one of the six is enabled in every state, which is why the lab never greys out a button, and why TLC will never report deadlock for this spec. The IF in SmallToBig is not a guard, since it doesn't disable anything. It chooses between two descriptions of the next state, and both are possible to satisfy.

The matrix is a mechanical check for the frame of every action: one row per action, one column per variable, no blanks. A blank cell is a question you haven't answered. A later lecture introduces UNCHANGED, a shorthand for frame lines, once specs have more variables. For now, write each one out.

Worked action: sending a chat message

A chat composer stores a draft, a count of pending messages, the last text sent, and the selected conversation. Sending should record the draft, clear it, and leave the selected conversation alone. /= means “not equal.”

Send == /\ draft /= ""
        /\ pending' = pending + 1
        /\ lastSent' = draft
        /\ draft' = ""
        /\ selected' = selected

The first line is a guard that rejects an empty draft. lastSent' = draft uses the old draft, even though the same action clears it, as the diagram shows. If you instead cleared the draft in one action and recorded it in a later one, the later action would see an empty draft unless you saved a copy. That model needs an extra variable. Where you draw the boundary of an action says whether capture and clearing are one indivisible operation or two visible steps.

Predict: Send specifies draft' but says nothing about pending'. Is pending preserved?

No. Nothing constrains its next value, and TLC would report that the successor state isn't completely specified, just as it did for FillSmall. Add the increment you want or an explicit pending' = pending.
