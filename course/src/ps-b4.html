Problem set 14: decide which answer is allowed to land.

These problems practice the fourth Beyond part: responses that arrive after the user has moved on, cache fills that arrive after the data changed, and contracts that hold across several layers. They draw on {{ref:app-state}}, {{ref:cache}} and {{ref:capstone}}, with {{ref:fencing}}, {{ref:messages}}, {{ref:fairness}} and {{ref:replication}} from earlier parts.

All the modules are complete and were checked with TLC exactly as shown. Trace lengths come from TLC with one worker (-workers 1) and count the initial state. In every problem the bug is the same shape: a result that was correct when produced arrives where something newer already decided. Look for that shape before you run anything.

Problem 1●○○Design systems

The combobox that shows options for "al" after you typed "ali"

Draws on {{ref:app-state}}, {{ref:messages}} and {{ref:fencing}}.

Your design system's Combobox loads its options asynchronously: on every keystroke it calls the product team's loadOptions(query) and renders the result in the listbox. A bug report: in the "Assign to" field, a user typed "al", then quickly "ali", pressed Enter, and assigned the ticket to Alan instead of Alice. The listbox was showing the options for "al".

The component team already aborts the previous request with an AbortController on each keystroke, and believes that rules this out. In the module, inflight holds requests still on the network, which an abort can cancel. queued holds responses whose body has already been read, so their continuation is waiting to run and an abort no longer stops it. Mode is "Plain" (render every response), "Abort" (cancel everything in flight on each keystroke) or "RequestId" (render only if the response's ID is still latest, as in {{ref:app-state}}).

Problem 2●●○Databases

Cache-aside with leases: the stale set and the write order

Draws on {{ref:cache}}, {{ref:fencing}}, {{ref:inventory}} and {{ref:scaling}}.

A product service reads prices with the cache-aside pattern. A reader does GET from a memcached-style cache; on a miss it reads the database and SETs the value. A writer updates the database and then DELETEs the key. Prices occasionally stay wrong until the key's TTL runs out. Facebook's paper "Scaling Memcache at Facebook" (NSDI 2013) describes a fix it calls leases. On a miss the cache hands the reader a lease token. A DELETE of the key invalidates the token, and a SET carrying an invalid token is refused.

In the module, versions stand for values. One reader and one writer run, and the writer makes up to two updates. Leases turns the tokens on, and DeleteFirst makes the writer delete the key before updating the database instead of after. The property allows a stale cache only while a write is in progress: once the writer is idle, a cached value must be current.

---------------- MODULE PSb4_CacheAside ----------------
EXTENDS Naturals

          wpc       \* writer: "idle", "updated" or "deleted"

        /\ rpc = "idle" /\ rtoken = 0 /\ rval = 0
        /\ wpc = "idle"

\* Reader: GET misses. With leases, the cache hands out a token.

        /\ IF Leases THEN /\ tokens' = tokens + 1
                          /\ lease' = tokens + 1
                          /\ rtoken' = tokens + 1
                     ELSE UNCHANGED <<tokens, lease, rtoken>>
        /\ rpc' = "reading"
        /\ UNCHANGED <<db, cache, rval, wpc>>
\* Reader: SELECT from the database.
Read == /\ rpc = "reading"
        /\ rval' = db
        /\ rpc' = "setting"
        /\ UNCHANGED <<db, cache, lease, tokens, rtoken, wpc>>
\* Reader: SET the value. With leases, only if the token is still valid.
Set == /\ rpc = "setting"
       /\ IF ~Leases \/ lease = rtoken
             THEN cache' = rval /\ lease' = 0

          /\ (DeleteFirst => db < MaxVersion)
          /\ cache' = 0 /\ lease' = 0
          /\ wpc' = IF DeleteFirst THEN "deleted" ELSE "idle"
          /\ UNCHANGED <<db, tokens, rpc, rtoken, rval>>

With leases on, which writer order is safe?

Hint

A lease is a fencing token issued by the cache. It protects a fill only if something invalidates it after the database has changed. Find which writer step does that in each order.

Solution

1. Miss, Read (version 1), Update (the database is now 2), Delete (the cache was already empty), Set: the cache holds 1, the writer is idle, the database holds 2. The fill began before the write and landed after the invalidation, as in {{ref:cache}}. The stale value then stays until the TTL expires or the next write.

2. No error, 70 distinct states. In the same order of events, Miss takes token 1, Delete sets lease to 0, and the final Set presents token 1 and is refused: lease # rtoken. The diagram shows this. The reader gets nothing cached and misses again next time, which is safe.

3. Without leases: Miss, Read (1), Delete, Set (1), Update (2). The stale value lands between the two writer steps, and nothing deletes it afterward. With leases it still fails, with a different trace: Delete, Miss (a fresh token, issued after the delete), Read (1), Set (accepted), Update. The token is valid because the only invalidation came before it was issued. A lease rejects a fill that overlapped a later invalidation, so the invalidation must come after the change it announces. Delete-first fails for the same reason as splitting write and invalidation in {{ref:cache}}.

4. In cache-aside, the database update and the delete are two steps in two systems. Between them the cache necessarily holds the old value, so the strong property fails in every design, including the correct one. The contract you can deliver is "fresh once the invalidation has run", which is what FreshAfterWrite says. Choosing the property is part of the design: {{ref:cache}} made the write and invalidation atomic to get the strong version, and said so.

Two readers would show the paper's second use of leases, rate-limiting how many clients may fill the same key at once. That is a performance property, not one this invariant can see.

Problem 3●●○Databases

Read your own write from an asynchronous replica

Draws on {{ref:cache}}, {{ref:app-state}}, {{ref:replication}} and {{ref:fairness}}.

A web app runs a Postgres primary with two asynchronous streaming replicas and sends reads to the replicas. A user saves their profile, the page reloads, and the old profile appears. The team's fix: after each commit, store the primary's WAL position from pg_current_wal_lsn() in the session. Then read only from a replica whose pg_last_wal_replay_lsn() is at least that value. A week later a new report: the profile flickers between two versions as the user clicks around.

In the module LSNs are small integers. OtherWrite is another user's commit, and Replay(r) advances replica r by one record. The variables last, need and before record the most recent read, so both session guarantees become invariants. Routing is "AnyReplica" (the original app), "WriteLsn" (the fix: the token is the session's last write) or "SessionLsn" (the token also rises to whatever a read has returned).

---------------- MODULE PSb4_Replica ----------------
EXTENDS Naturals
CONSTANTS Replicas, MaxLsn, Routing
ASSUME Routing \in {"AnyReplica", "WriteLsn", "SessionLsn"}
VARIABLES primary,  \* the primary's current WAL position (LSN)
          replay,   \* replay[r]: the LSN replica r has replayed
          token,    \* the LSN the session carries in its cookie
          wrote,    \* the LSN of the session's last write
          seen,     \* the highest LSN the session has read so far
          last,     \* the LSN the most recent read returned
          need,     \* ... the value of wrote at that read
          before    \* ... the value of seen just before that read
vars == <<primary, replay, token, wrote, seen, last, need, before>>

Max(a, b) == IF a >= b THEN a ELSE b

Init == /\ primary = 0
        /\ replay = [r \in Replicas |-> 0]
        /\ token = 0 /\ wrote = 0 /\ seen = 0
        /\ last = 0 /\ need = 0 /\ before = 0

\* The session commits a write on the primary.
MyWrite == /\ primary < MaxLsn
           /\ primary' = primary + 1
           /\ wrote' = primary + 1
           /\ token' = IF Routing = "AnyReplica" THEN token ELSE primary + 1
           /\ UNCHANGED <<replay, seen, last, need, before>>
\* Another session commits a write.
OtherWrite == /\ primary < MaxLsn
              /\ primary' = primary + 1
              /\ UNCHANGED <<replay, token, wrote, seen, last, need, before>>
\* Asynchronous streaming: replica r replays one more WAL record.
Replay(r) == /\ replay[r] < primary
             /\ replay' = [replay EXCEPT ![r] = @ + 1]
             /\ UNCHANGED <<primary, token, wrote, seen, last, need, before>>
\* The session reads from replica r. Except in AnyReplica, the router
\* uses a replica only if it has replayed up to the session's token.
Read(r) == /\ Routing # "AnyReplica" => replay[r] >= token
           /\ last' = replay[r]
           /\ need' = wrote
           /\ before' = seen
           /\ seen' = Max(seen, replay[r])
           /\ token' = IF Routing = "SessionLsn" THEN Max(token, replay[r])
                       ELSE token
           /\ UNCHANGED <<primary, replay, wrote>>

Under plain Spec, why does Servable fail?

Hint

Read-your-writes compares a read with the session's writes. Monotonic reads compares a read with the session's earlier reads. A token built from writes only knows about the first.

Solution

1. ReadYourWrites fails in 3 states: MyWrite (primary at 1), Read(r1) while r1 has replayed nothing. That is the stale profile after saving.

2. MonotonicReads fails after 5 states: OtherWrite (someone else commits LSN 1), Replay(r1), Read(r1) returns 1, Read(r2) returns 0. The session has not written, so its token is 0 and every replica qualifies. The page shows the newer profile and then the older one. The diagram draws the trace. Read-your-writes holds throughout; the token answers the wrong question.

3. No error, 157 distinct states. Raising the token to the highest LSN read means a later read goes only to a replica at least as fresh as anything already shown. It is the same rule as the fence in {{ref:fencing}}: accept only something not older than what you have already accepted. Here the session is the one keeping the fence.

4. Under Spec, Servable fails: MyWrite, OtherWrite, then stuttering, with no replica ever replaying. Under FairSpec it holds, again with 157 states. WF_vars(Replay(r)) says a replica that is behind keeps replaying, so once writes stop it catches up. A replica that stops streaming, or lags for minutes during a long-running query, breaks that assumption. The fix belongs in the design: wait with a timeout, then read from the primary, which always satisfies the token. That keeps safety from depending on replication speed, and makes progress depend only on the primary being up.

Problem 4●●●Design systems

An undo toast that tells the truth

Synthesis. Draws on {{ref:app-state}}, {{ref:capstone}}, {{ref:fencing}}, {{ref:messages}} and {{ref:fairness}}.

An email client deletes optimistically. The message disappears at once and a design-system Toast offers "Undo" for a few seconds. The team has tried four designs. "Deferred" sends DELETE only when the toast's timer fires, and removes Undo at that moment. "UndoWhileSending" keeps Undo on screen until the server answers, because the button looked unresponsive otherwise. "Immediate" sends DELETE at once and makes Undo send a separate RESTORE. "ImmediateSeq" does the same, but the server skips a request whose sequence number is lower than one it already applied. A request can fail with no effect when CanFail is true. When the client's latest request fails, it rolls back its optimistic change and shows an error toast.

Requests and responses travel in sets, so they can be reordered. The user deletes at most once and undoes at most once. AgreeWhenQuiet says that when nothing is in flight and no Undo is offered, the inbox shows the truth. Converges says the screen eventually agrees with the server for good.

2. Delete, Timeout (DELETE sent, Undo still shown), Undo (the message reappears), Serve (the server deletes it), Receive (success, nothing to do). 3. Without failures: Delete (DELETE 1 sent), Undo (RESTORE 2 sent), the server handles RESTORE 2 first, then DELETE 1, and both succeed. The message is shown and deleted. 4. With CanFail = FALSE, "ImmediateSeq" passes with 16 states. The server ignores DELETE 1 after applying RESTORE 2, which is a fence on request numbers. With failures it fails on the same double-failure trace as "Immediate", because the fence cannot fix the client's rollback rule. A rollback encodes an assumption about server state that the client never observed. One fix is to answer a failure with the resource's current state, or to refetch it, and render that instead of guessing. To check it you would model the refetch as another request whose response can be stale too. Then you would need the request-ID rule of {{ref:app-state}} on the client as well as the sequence fence on the server. That is a layered contract, in the sense of {{ref:capstone}}.

5. It assumes the client survives until the timer fires. If the tab closes during the toast, Timeout never happens, the DELETE is never sent, and the message is still in the inbox next time. In the model, that is a behavior allowed by Spec but excluded by FairSpec. Whether it is acceptable is a product decision. "Close the tab to undo" is often fine for email, but not for a payment. If it is not acceptable, send the request immediately and accept the problems of tasks 3 and 4, or have the server run the delay. Fairness should be a property the product actually has, not a convenience that makes TLC pass.
