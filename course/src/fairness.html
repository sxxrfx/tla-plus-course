"May happen" is not "will happen."

ABSpec's Spec allows a value to be sent and then never received, because a behavior may stutter forever, as you saw in {{lesson:implementation}}. This lesson adds what a system must do. You write the requirement as a temporal formula, then add fairness conditions that make it true.

Safety and liveness

A safety formula says what may happen. If a behavior violates it, the violation occurs at some particular point, and nothing later can undo it. Init /\ [][Next]_vars is one: it fails on a bad first state or on a step that is neither Next nor stuttering. A liveness formula says what must happen, and no point in a behavior can violate it, because the rest of the behavior could always make it true. Remember that a behavior here is any infinite sequence of states, not just one allowed by some spec.

The figure's second row uses a new operator. <>P, read eventually P, says P is true on some state. It equals ~[]~P; convince yourself of that. For a sequential program, the one liveness property is termination: <>Terminated. Concurrent systems have many others, written with these forms:

FormulaMeaning
<>PP holds at some state.
[]<>PP holds infinitely often.
<>[]PThere comes a point after which P always holds.
P ~> QP leads to Q, which abbreviates [](P => <>Q). Whenever P holds, Q holds then or later.

For the channel, we'd like every value being sent to be received. The lecture gives this formula to copy; here it has a name, defined in a small wrapper module that extends ABSpec:

Delivered == \A v \in Data \X {0, 1} : (AVar = v) ~> (BVar = v)

Eventually is not a deadline. It has no time bound at all. Also, with changing requests, the predicate must identify which request. Here the pair v plays that role, while an imprecise "some request completed" could be satisfied by an old one.

Enabled, and weak fairness

Action A is enabled in state s when some state t makes s → t an A step. A conjunct with no primes is an enabling condition, so ABSpec's A is enabled when AVar = BVar and Data is non-empty.

Weak fairness of A says: if A ever remains continuously enabled, an A step must eventually occur. Equivalently, A cannot stay enabled forever without another A step. It is written WF_vars(A), in ASCII exactly like that, and read "WF of A". It is a liveness property, because an A step or a state where A is disabled can always make it true.

Strong fairness, SF_vars(A), is stronger: if A is repeatedly enabled, even with gaps, an A step must eventually occur. The difference is the flicker shown in run 2 below.

Inspect repeating schedules

Predict: Serve is enabled every other step and never runs. Does weak fairness reject the behavior?

No. It never stays enabled continuously forever. Strong fairness rejects that particular infinite behavior. Whether strong fairness is a justified system assumption is a separate question.

What the subscript means

WF_vars(A) is weak fairness of the action A /\ (vars' # vars), a non-stuttering A step. It makes no sense to require a stuttering step, since nobody could tell whether it happened.

Adding liveness to a spec

A spec with liveness has the form Init /\ [][Next]_vars /\ Fairness. Fairness is a conjunction of WF and SF formulas, each on a subaction of Next, meaning every step of it is a Next step. Now you can read the last line of ABSpec:

FairSpec == Spec /\ WF_vars(Next)

Behaviors must keep taking Next steps while Next is enabled. The safety part never reaches a state where it isn't, so A keeps sending and B keeps receiving forever. A second possible spec says something weaker, using WF_vars(B) alone: every sent value is received, but the sender may stop. Here are the checks, with Data = {d1, d2, d3}. Worked architecture: a background upload worker

A mobile app has accepted upload U. The worker can Send(U) whenever the device is online and U is pending. Take a behavior where the phone keeps reconnecting and disconnecting before U is selected. As the figure shows, the upload was enabled many times, and weak fairness still doesn't require it to run.

For Pending(U) ~> Uploaded(U), decide what the environment promises. If the device eventually stays online, Send(U) becomes continuously enabled and weak fairness suffices. Strong fairness would let recurring opportunities suffice, but background execution limits on the platform may make that assumption false. And sending still isn't delivery: a separate assumption is needed if the network can drop every attempt.

Fairness also needs the right granularity. With uploads U and V pending, WF_vars(SendAny) can be satisfied by sending V forever while U waits. Attach fairness per request, such as \A p \in Processes : WF_vars(Serve(p)). Never add fairness merely to silence a counterexample. Fairness is not a scheduler, a response-time bound, or a delivery guarantee. It states what you assume, and permanent partitions can make the assumption false.

Predict: a worker is weakly fair, but every request is dropped. Does "pending leads to delivered" follow?

No. Worker scheduling and network delivery are different actions with different assumptions. A correct argument must connect retries, eventual delivery, acknowledgement, and durable completion instead of jumping from "worker runs" to "request succeeds".
