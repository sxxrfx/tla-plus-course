Problem set 4: write the steps, then let TLC search.

These problems practice what Lecture 4 taught: actions with guards and complete frames, and the trick of claiming that a goal is never reached so that TLC hands you the steps. They also lean on running TLC and reading its results, from {{lesson:counter}}, and the last one reuses Euclid's algorithm from {{ref:ps-l3}}.

Write every frame line out in full: UNCHANGED arrives with Lecture 6. When a problem asks for the length of a trace, run TLC with one worker (-workers 1), as {{lesson:diehard-tlc}} recommends, so that its breadth-first search returns a shortest one.

Problem 1●○○Design systems

The modal that leaves the page frozen

Draws on {{ref:actions}}, {{ref:diehard-tlc}} and {{ref:counter}}.

Your design system ships a Modal dialog component. While it is open, it keeps keyboard focus inside the dialog and locks page scrolling, so the page behind it doesn't move. It closes in two ways: the close button, or the Escape key. A bug report arrives: after someone closes a dialog with Escape, the page no longer scrolls. You write the component as a state machine with three variables. CloseButton was written carefully. PressEscape was added later by copying its first three lines.

------------------------------ MODULE PSl4_Modal ------------------------------
VARIABLES open, focus, scrollLocked

TypeOK == /\ open \in {TRUE, FALSE}
          /\ focus \in {"page", "dialog"}
          /\ scrollLocked \in {TRUE, FALSE}

Init == /\ open = FALSE
        /\ focus = "page"
        /\ scrollLocked = FALSE

OpenDialog == /\ ~open
              /\ open' = TRUE
              /\ focus' = "dialog"
              /\ scrollLocked' = TRUE

CloseButton == /\ open
               /\ open' = FALSE
               /\ focus' = "page"
               /\ scrollLocked' = FALSE

PressEscape == /\ open
               /\ open' = FALSE
               /\ focus' = "page"

Next == OpenDialog \/ CloseButton \/ PressEscape

LockMatches == scrollLocked = open
FocusInside == open => focus = "dialog"
=============================================================================

The config lists INIT Init, NEXT Next, and the invariants TypeOK, LockMatches and FocusInside.

  1. Before running anything: as a formula, what does PressEscape say about scrollLocked'? Which next states does it allow? The dashed arrow down in the diagram is your clue.
  2. Run TLC. What does it report, and after which action?
  3. A teammate makes the error go away by adding /\ scrollLocked' = scrollLocked to PressEscape. Run TLC again. What does it report now, and how long is the trace?
  4. Write the correct PressEscape. Then draw the frame matrix from {{lesson:actions}} for the three actions: one row per action, one column per variable, and the value each action gives each variable. How many distinct states does TLC find with your fix?
What does TLC report for the module as written?

Hint

A frame line is a decision about what a step does, not boilerplate. Ask what pressing Escape should do to the scroll lock, then compare with what CloseButton does.

Solution

(a) PressEscape doesn't mention scrollLocked', so as a formula it allows any value at all: TRUE, FALSE, 42, or "abc". It doesn't keep the old value.

(b) TLC stops with the error you met in {{lesson:actions}}:

Error: Successor state is not completely specified by action PressEscape
of the next-state relation. The following variable is not defined: scrollLocked.
State 1: <Initial predicate>      open = FALSE, focus = "page",   scrollLocked = FALSE
State 2: <OpenDialog ...>         open = TRUE,  focus = "dialog", scrollLocked = TRUE
State 3: <PressEscape ...>        open = FALSE, focus = "page",   scrollLocked = null

(We put each state on one line.) The null is how TLC prints the value it couldn't determine.

(c) With the copied frame line, the spec is complete and wrong. TLC reports Invariant LockMatches is violated with a 3-state trace: the initial state, OpenDialog, then PressEscape, which ends with the dialog closed and scrollLocked = TRUE. That is the red box in the diagram, and it is exactly the bug report. The error in (b) was TLC pointing at the problem. Silencing it with the first frame line that parses turned it into the bug.

(d) Escape should do what the close button does:

PressEscape == /\ open
               /\ open' = FALSE
               /\ focus' = "page"
               /\ scrollLocked' = FALSE
Actionopen'focus'scrollLocked'
OpenDialogTRUE"dialog"TRUE
CloseButtonFALSE"page"FALSE
PressEscapeFALSE"page"FALSE

With this fix (module PSl4_ModalFixed), TLC finds no error and 2 distinct states: closed and open. Two of the three cells in the bug's row of the matrix were right. The blank one was where the bug lived. In component code the same gap appears when one close path calls the cleanup and another doesn't. Many teams avoid it by routing every way of closing through one function. In the spec, the matrix makes the gap visible.

Problem 2●●○Databases

Rename a column without downtime

Draws on {{ref:actions}}, {{ref:diehard-tlc}} and {{ref:counter}}.

Your team must rename users.email to users.email_address in a production Postgres database. A plain rename would break every running server that still queries email. So you use the expand and contract pattern: add the new column, deploy app v2 that writes both columns, backfill old rows, deploy v3 that reads the new column, deploy v4 that writes only the new column, and drop the old column. Each step has a precondition in the runbook. In the model below, each precondition is a guard.

missing means some row has no value in email_address. It starts TRUE: no existing row has one. SignUp is a user registering while v1 is live, which writes only email.

The module (open to copy) 
--------------------------- MODULE PSl4_Migration ---------------------------
EXTENDS Integers

VARIABLES schema,      \* columns that exist: "old", "both", or "new"
          app,         \* deployed app version, 1..4
          backfilled,  \* the backfill job has finished
          missing      \* some row has no value in email_address

TypeOK == /\ schema \in {"old", "both", "new"}
          /\ app \in 1..4
          /\ backfilled \in {TRUE, FALSE}
          /\ missing \in {TRUE, FALSE}

Init == /\ schema = "old"
        /\ app = 1
        /\ backfilled = FALSE
        /\ missing = TRUE

OldExists == schema \in {"old", "both"}
NewExists == schema \in {"both", "new"}

\* v1 reads and writes email; v2 writes both; v3 reads email_address;
\* v4 writes only email_address.
WritesOld == app \in {1, 2, 3}
WritesNew == app \in {2, 3, 4}
ReadsNew  == app \in {3, 4}

AddColumn == /\ schema = "old"
             /\ schema' = "both"
             /\ app' = app
             /\ backfilled' = backfilled
             /\ missing' = missing

DeployV2 == /\ app = 1
            /\ NewExists
            /\ app' = 2
            /\ schema' = schema
            /\ backfilled' = backfilled
            /\ missing' = missing

Backfill == /\ ~backfilled
            /\ app = 2
            /\ backfilled' = TRUE
            /\ missing' = FALSE
            /\ schema' = schema
            /\ app' = app

DeployV3 == /\ app = 2
            /\ backfilled
            /\ app' = 3
            /\ schema' = schema
            /\ backfilled' = backfilled
            /\ missing' = missing

DeployV4 == /\ app = 3
            /\ app' = 4
            /\ schema' = schema
            /\ backfilled' = backfilled
            /\ missing' = missing

DropOld == /\ schema = "both"
           /\ app = 4
           /\ schema' = "new"
           /\ app' = app
           /\ backfilled' = backfilled
           /\ missing' = missing

\* A user signs up while v1 is live: the new row gets only email.
SignUp == /\ app = 1
          /\ missing' = TRUE
          /\ schema' = schema
          /\ app' = app
          /\ backfilled' = backfilled

Next == \/ AddColumn \/ DeployV2 \/ Backfill \/ DeployV3
        \/ DeployV4 \/ DropOld \/ SignUp

WritesOK == /\ (WritesOld => OldExists)
            /\ (WritesNew => NewExists)
ReadsOK == IF ReadsNew THEN NewExists /\ ~missing ELSE OldExists
NotDone == ~(schema = "new" /\ app = 4)
=============================================================================

The config:

INIT Init
NEXT Next
INVARIANT TypeOK
INVARIANT WritesOK
INVARIANT ReadsOK
CHECK_DEADLOCK FALSE
  1. For each of the guards NewExists in DeployV2, app = 2 in Backfill, backfilled in DeployV3, and app = 4 in DropOld, say which invariant would fail without it, and in which situation.
  2. Run TLC with the config. How many distinct states does it find? Why must the deadlock check be off here, and is the stop it would report a deadlock or termination?
  3. Add INVARIANT NotDone. What does TLC's trace give you?
  4. The backfill takes hours on a big table, so a teammate wants to start it as soon as the column exists. Change the guard app = 2 in Backfill to NewExists and run again. Which invariant fails, and why?

Hint

For (a), delete one guard at a time and run TLC. That's faster than arguing, and the trace tells you the situation. For (d), look at which action can set missing back to TRUE, and when it is enabled.

Solution

(a) Without NewExists, v2 could go live before the column exists, so it would write to a column that isn't there: WritesOK. Without app = 2, the backfill could run while v1 still writes only email: that is part (d), and ReadsOK fails later. Without backfilled, v3 would read email_address while old rows have no value there: ReadsOK. Without app = 4, you could drop email while v1, v2 or v3 still writes it: WritesOK.

(b) No error, 7 distinct states. The guards leave exactly one runbook step enabled at a time, so the state graph is a single line. SignUp adds nothing, because while v1 is live missing is already TRUE. After DropOld, no action is enabled. The migration is supposed to end there, so this is termination, as in {{lesson:counter}}. With the check on, TLC reports Deadlock reached at that final state.

(c) TLC reports Invariant NotDone is violated with a 7-state trace: AddColumn, DeployV2, Backfill, DeployV3, DeployV4, DropOld. That is the runbook, in an order every guard allows. It also shows the guards don't block each other: a runbook whose preconditions can never all be met would have no such trace.

(d) TLC reports Invariant ReadsOK is violated:

The backfill copies every row that exists at the time, and the guard NewExists allows it while v1 is live. A user signs up, and v1 writes the new row's email only. The backfill already ran, so nothing ever copies that row. v2 and v3 deploy, and v3 reads email_address, which is empty for that user. In production the user would look like they had no email address. The step the trace exposes is SignUp, and you probably never thought of it as part of the migration. The guard app = 2 says the backfill starts only once every new row gets both columns, which closes that gap.

Two limits of this model are worth knowing. It deploys each version to every server in one step, while a real rolling deploy runs two versions side by side for a while. And it has one kind of write; updates and deletes of existing rows need the same reasoning. Both would be good extensions once you have more notation.

Problem 3●●○Algorithms

Tower of Hanoi: let breadth-first search find the shortest solution

Draws on {{ref:diehard}}, {{ref:actions}} and {{ref:diehard-tlc}}.

The Tower of Hanoi is the textbook example of recursion. Disks of different sizes sit on peg 1, largest at the bottom. You must move them all to peg 3, one disk at a time, never putting a disk on a smaller one. The recursive algorithm moves n − 1 disks out of the way, moves the largest, then moves the n − 1 back on top, for 2n − 1 moves. A colleague reviewing your course notes asks whether any solution is shorter. Rather than prove it, let TLC look at every possibility for 3 disks.

Use one variable per disk: d1 (smallest), d2, d3 (largest), each holding the number of the peg the disk is on. You don't need to record the order of disks on a peg, because the rules force it: it is always by size.

  1. Write the module: TypeOK, Init, and one action per disk, MoveD1, MoveD2, MoveD3. A disk can move only if no smaller disk is on its peg, and only to a peg with no smaller disk. Remember the frame lines.
  2. Write NotSolved, the claim that the disks never all reach peg 3, and run TLC with one worker. How many states are in the trace? Compare it with the recursive algorithm's moves.
  3. Remove NotSolved and run again. How many distinct states are there, and why exactly that many?
  4. Add a fourth disk. Predict both numbers before you run TLC, then check.

Hint

If a and b are two different pegs among 1, 2 and 3, the third one is 6 - a - b. When can d2 move, and where can it go? The smallest disk is always on top and has two choices: use d1' \in with an IF that gives the set of the other two pegs.

Solution

(a)

------------------------------ MODULE PSl4_Hanoi ------------------------------
EXTENDS Integers

\* d1 is the smallest disk, d3 the largest. Each holds the peg (1, 2 or 3)
\* the disk is on. On any peg, the disks sit in size order.
VARIABLES d1, d2, d3

TypeOK == /\ d1 \in 1..3
          /\ d2 \in 1..3
          /\ d3 \in 1..3

Init == /\ d1 = 1
        /\ d2 = 1
        /\ d3 = 1

\* The smallest disk is always on top, and can go to either other peg.
MoveD1 == /\ d1' \in IF d1 = 1 THEN {2, 3}
                     ELSE IF d1 = 2 THEN {1, 3}
                     ELSE {1, 2}
          /\ d2' = d2
          /\ d3' = d3

\* d2 is on top if d1 isn't on its peg. It can't go onto d1, so it goes to
\* the one remaining peg. Pegs are 1, 2, 3, so the third one is 6 - d1 - d2.
MoveD2 == /\ d1 /= d2
          /\ d2' = 6 - d1 - d2
          /\ d1' = d1
          /\ d3' = d3

\* d3 can move only when d1 and d2 are both on the same other peg.
MoveD3 == /\ d1 = d2
          /\ d1 /= d3
          /\ d3' = 6 - d1 - d3
          /\ d1' = d1
          /\ d2' = d2

Next == MoveD1 \/ MoveD2 \/ MoveD3

NotSolved == ~(d1 = 3 /\ d2 = 3 /\ d3 = 3)
=============================================================================

The guards come from the rules. d2 is on top of its peg exactly when d1 isn't there. It can't go onto d1, so its only legal target is the third peg, 6 - d1 - d2. d3 can move only when both smaller disks are off its peg and off the target, which means they are together on the remaining peg: d1 = d2 and d1 /= d3.

(b) With INVARIANT NotSolved and one worker, TLC reports the violation with an 8-state trace: 7 moves. The diagram shows it, one column per state. It is the recursive algorithm's sequence exactly. The smallest disk moves on every other step, and the largest moves once, in the middle. Breadth-first search examined all states 1 move away, then 2, and so on, so no solution with 6 or fewer moves exists. For 3 disks, that answers your colleague.

(c) Without NotSolved, there is no error and 27 distinct states. Every way of giving three disks a peg each is a legal position, and every legal position is reachable. The state graph is connected.

(d) MoveD4 needs d1 = d2, d2 = d3 and d1 /= d4, and every other action gains the frame line d4' = d4 (module PSl4_Hanoi4). TLC finds a 16-state trace (15 moves, which is 24 − 1) and 81 = 34 distinct states. A check on 3 and 4 disks is not a proof for every n, of course. It is strong evidence for a claim that has a short proof by induction.

Problem 4 · Synthesis●●●Algorithms

A dosing station that can't measure 3 litres

Draws on {{ref:diehard-tlc}}, {{ref:counter}}, {{ref:logic}}, and the Euclid's GCD problem in {{ref:ps-l3}}.

A lab automation rig measures liquid with two fixed chambers and no level sensors: a 4-litre chamber and a 6-litre chamber. It can fill a chamber from the supply, drain a chamber, or pump from one chamber into the other until the source is empty or the destination is full. These are the Die Hard jugs in steel. A new recipe needs exactly 3 litres, and the controls engineer asks you whether any sequence of operations produces it.

Recall Euclid's algorithm from {{ref:ps-l3}}: replacing the larger of two numbers by their difference doesn't change their greatest common divisor, so it ends at gcd of the starting pair. Here gcd(4, 6) = 2.

  1. Generalize the DieHard module. Define the capacities as Small == 4 and Big == 6, the way Counter defined Max == 3, and use those names everywhere, including in the pours.
  2. Claim NoThree: neither chamber ever holds 3. Run TLC. How many distinct states does it find, and what does the result mean? Before you trust it, show that your setup can find a violation by claiming NoTwo == big /= 2.
  3. Explain the result with the gcd. Write it as an invariant Even and check it.
  4. The vendor offers a 5-litre chamber instead of the 4-litre one. Predict what changes, then change one definition and check. How many states are in the shortest trace to 3 litres?

TLC reports no violation of NoThree. What makes that a trustworthy answer?

Hint

Look at what each of the six actions does to the amounts: each one sets a chamber to 0 or to its capacity, or moves water from one chamber to the other. If both amounts are even before a step, can either be odd after it?

Solution

(a)

------------------------------- MODULE PSl4_Dosing -------------------------------
EXTENDS Integers

Small == 4    \* litres the small chamber holds
Big   == 6    \* litres the big chamber holds

VARIABLES small, big

TypeOK == /\ small \in 0..Small
          /\ big   \in 0..Big

Init == /\ small = 0
        /\ big   = 0

FillSmall == /\ small' = Small
             /\ big'   = big

FillBig == /\ big'   = Big
           /\ small' = small

EmptySmall == /\ small' = 0
              /\ big'   = big

EmptyBig == /\ big'   = 0
            /\ small' = small

SmallToBig == IF big + small =< Big
                THEN /\ big'   = big + small
                     /\ small' = 0
                ELSE /\ big'   = Big
                     /\ small' = small - (Big - big)

BigToSmall == IF big + small =< Small
                THEN /\ big'   = 0
                     /\ small' = big + small
                ELSE /\ big'   = big - (Small - small)
                     /\ small' = Small

Next == \/ FillSmall  \/ FillBig
        \/ EmptySmall \/ EmptyBig
        \/ SmallToBig \/ BigToSmall

NoThree == /\ small /= 3
           /\ big   /= 3
NoTwo   == big /= 2
Even    == /\ small \in {0, 2, 4}
           /\ big   \in {0, 2, 4, 6}
=============================================================================

(b) With INVARIANT TypeOK and INVARIANT NoThree, TLC reports no error and 10 distinct states, the filled cells of the grid. Because the model is finite and TLC examined every reachable state, “no error” here means that no sequence of operations ever puts 3 litres in either chamber. That is a real answer only if the check could have failed. Claiming NoTwo shows it could: TLC reports a violation with a 3-state trace, FillBig then BigToSmall, which leaves 2 litres in the big chamber. This is the experiment-that-fails test from {{lesson:diehard-tlc}}, used in reverse to trust a success.

(c) Each action sets a chamber to 0, to 4, or to 6, all even, or moves water between chambers so that the total stays the same and one chamber ends empty or full. Start with two even amounts, and every one of these steps leaves two even amounts. So Even is an invariant, and TLC confirms it: no error, 10 states. It is the same argument as Euclid's: a step that only adds or subtracts multiples of 2 can't produce an odd number. In general, every amount you can measure is a multiple of gcd(Small, Big). Euclid's algorithm computes exactly that number by repeated subtraction, much as the pumps subtract one chamber from the other.

(d) gcd(5, 6) = 1, so the argument no longer rules 3 out. Set Small == 5 (module PSl4_Dosing56) and TLC reports NoThree violated with a 9-state trace: fill 5, pump into 6, fill 5, pump until 6 is full (4 left), drain 6, pump the 4 across, fill 5, pump until 6 is full, which leaves 3 in the 5-litre chamber. Without NoThree, TLC finds 22 distinct states. So the engineer's answer is: not with these chambers; with a 5-litre chamber, yes, in 8 operations.

Notice what each chapter contributed. The state machine view turned a machine into variables and steps. TLC's exhaustive search made “impossible” a checkable claim. The invariant from {{ref:ps-l3}} explains why it's impossible, and tells you which chamber sizes would work before you run anything.
