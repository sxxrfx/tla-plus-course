Write an algorithm; inspect its translation.

In {{lesson:program}} you turned a small program into a state machine by hand, with a control variable pc saying what runs next. PlusCal does that translation for you. You still decide what one step is, as you just did in {{lesson:inventory}}.

PlusCal is an algorithm language written inside a comment in a TLA+ module. Its translator generates ordinary TLA+ after the comment: Init, Next, Spec, and a pc function for processes. The language is convenient for algorithms that read as sequential steps. It does not replace the state machine, and the diagram above is the state machine you get from the source below.

---------------- MODULE TicketPC ----------------
EXTENDS Integers, FiniteSets
CONSTANT Buyers
(*--algorithm Ticket
variables remaining = 1, booked = {};
define
    Safe == Cardinality(booked) <= 1
end define;
process Buyer \in Buyers
begin
Reserve:
    if remaining > 0 then
        remaining := remaining - 1;
        booked := booked \cup {self};
    end if;
end process;
end algorithm; *)
=================================================
SPECIFICATION Spec
CONSTANT Buyers = {A, B}
INVARIANT Safe

That is the source before translation. To translate, run java -cp tla2tools.jar pcal.trans -nocfg TicketPC.tla or use your editor’s translate command. -nocfg keeps the translator from writing its own config file over yours. The generated text appears between translation markers before the closing line. TLC then finds 5 distinct states and no error.

self identifies the current process. Each label starts an atomic step, and everything up to the next label runs in that one step. So the if and both assignments under Reserve are one edge in the diagram. Inside a step, := runs in order, so a later statement sees an earlier statement’s value. Do not confuse this with the simultaneous primed equations in raw TLA+.

Move a label, change the model

Add one label, Take:, in front of the decrement, and rename the first label Check. The translator now produces two actions for each buyer. This is its real output for that change:

Check(self) == /\ pc[self] = "Check"
               /\ IF remaining > 0
                     THEN /\ pc' = [pc EXCEPT ![self] = "Take"]
                     ELSE /\ pc' = [pc EXCEPT ![self] = "Done"]
               /\ UNCHANGED << remaining, booked >>
Take(self) == /\ pc[self] = "Take"
              /\ remaining' = remaining - 1
              /\ booked' = (booked \cup {self})
              /\ pc' = [pc EXCEPT ![self] = "Done"]

The diagram is pc[self] for one buyer. You could have written this translation yourself: it is the same pattern as {{lesson:program}}. Between the two actions, the other buyer can run, so TLC now reports Safe violated after 4 steps, the same race as InventorySplit. When reading an error trace, look at pc first. It tells you which labeled step each process is about to run.

Three more statements cover most algorithms. await P blocks a step until P holds, but does not promise P ever will. either … or … is a choice among alternatives. with x \in S do … picks a value nondeterministically. Each of these translates into guards and existential quantifiers you already know.

Predict: where does the deadlock go when both buyers finish?

Nowhere. The translator adds a Terminating action that stutters once every process is at Done, so TLC does not report termination as deadlock. A process stuck on an await is still reported.

Worked interleaving: two event handlers increment a count

Consider two workers that each read a shared notification count, compute one more, and write it back. In a single JavaScript event loop, a synchronous increment has no await inside it. But reading the value, awaiting remote work, and later writing the captured value does let another handler intervene. So it gets two labels, and the captured value becomes a per-process variable.

---------------- MODULE LostUpdate ----------------
EXTENDS Naturals
CONSTANT Workers
(*--algorithm LostUpdate
variables count = 0;
define
    AllDone == \A w \in Workers: pc[w] = "Done"
    NoLostUpdate == AllDone => count = 2
end define;
process Worker \in Workers
variable local = 0;
begin
Read:
    local := count;
Write:
    count := local + 1;
end process;
end algorithm; *)
===================================================
SPECIFICATION Spec
CONSTANT Workers = {A, B}
INVARIANT NoLostUpdate

Read the graph from the left. If one worker gets both of its steps in before the other reads, the top and bottom paths, the count reaches 2. If both read first, the middle node, both write 1. TLC finds the 13 states and reports NoLostUpdate violated.

For an atomic abstraction, replace the two labels with one, Increment: count := count + 1;. TLC then finds 4 states and no error. This is correct only if the actual operation has that guarantee, such as a synchronous local update or a suitable atomic database update.

To find a real async boundary, annotate the implementation: what is captured before an await, what can change during the wait, and what is rechecked after it? Captured values become local variables. Each interaction point becomes a label. A familiar callback race is now a state machine.

Predict: will making the whole process fair repair the lost update?

No. PlusCal’s fair process asks for the fairness from {{lesson:fairness}}. With it, TLC confirms <>AllDone: both workers do finish. But NoLostUpdate still fails in the same 13-state graph. Fairness rules out stopping early. It removes no order of steps, and this is a safety failure.
