Problem set 7: count on the overlap.

Four problems on quorums, consensus and Paxos Commit. You'll use the set operators and the overlap property from lecture 7 to find a stale read and to choose where cluster members live. Then you'll break a leader election by losing one field in a restart, and compare Paxos Commit with the two-phase commit booking from {{ref:ps-l6}}. Every problem ends in a TLC run.

Each module below is complete and was checked with TLC exactly as shown. Type it in yourself or copy it into a file of the same name. Counts like "distinct states" only match if your module is identical, so use those numbers to test your copy.

Problem 1●○○Databases

Find the stale read in a Dynamo-style store

Draws on {{ref:replication}}, {{ref:paxos-commit}} and {{ref:counter}}.

A shopping-cart service keeps each cart in a key-value store built on the design of Amazon's Dynamo paper. Every key lives on N replicas. A write counts as successful once W replicas have stored it, and a read asks R replicas and returns the newest version it hears. The team runs N = 5 with W = 3. To cut read latency, someone proposes R = 2: "three of the five replicas have every acknowledged write, so asking two will nearly always find one." Customers then report carts that lose the item they just added.

The module models one key. Every replica starts at version 1, a client writes version 2, and once the write is acknowledged a single read happens. Maximum is the definition from Paxos Commit.

---------------------------- MODULE PSl7_Quorum -----------------------------
\* One key of a Dynamo-style store with replication factor N = |Replica|.
\* Every replica holds version 1. A client writes version 2: the coordinator
\* stores it replica by replica and reports success once W replicas have it.
\* A later read asks R replicas and returns the highest version it hears.
EXTENDS Integers, FiniteSets
CONSTANTS Replica, W, R
VARIABLES version,   \* version[n]: the version replica n stores
          acked,     \* the coordinator has told the client "write succeeded"
          seen       \* what the read returned (0 = no read yet)
vars == <<version, acked, seen>>

Maximum(S) == IF S = {} THEN -1
                        ELSE CHOOSE n \in S : \A m \in S : n >= m
WriteSets == {Q \in SUBSET Replica : Cardinality(Q) = W}
ReadSets  == {Q \in SUBSET Replica : Cardinality(Q) = R}

Init == /\ version = [n \in Replica |-> 1]
        /\ acked = FALSE
        /\ seen = 0

Store(n) == /\ version[n] = 1
            /\ version' = [version EXCEPT ![n] = 2]
            /\ UNCHANGED <<acked, seen>>

Ack == /\ ~acked
       /\ \E Q \in WriteSets : \A n \in Q : version[n] = 2
       /\ acked' = TRUE
       /\ UNCHANGED <<version, seen>>

Read == /\ acked
        /\ seen = 0
        /\ \E Q \in ReadSets : seen' = Maximum({version[n] : n \in Q})
        /\ UNCHANGED <<version, acked>>

Next == Ack \/ Read \/ \E n \in Replica : Store(n)

ReadsLatest == seen \in {0, 2}
Overlap == \A Wq \in WriteSets, Rq \in ReadSets : Wq \cap Rq # {}
=============================================================================
INIT Init
NEXT Next
CONSTANTS Replica = {"A", "B", "C", "D", "E"}
          W = 3
          R = 2
INVARIANT ReadsLatest
CHECK_DEADLOCK FALSE
  1. Before running anything, use the R + W > N rule to say which values of R from 1 to 5 make every read set meet every write set.
  2. Run TLC with R = 1, R = 2 and R = 3. For each, report whether ReadsLatest holds, and for failures, the length of the trace and which replicas the read asked.
  3. Add the line ASSUME Overlap after the definition of Overlap, and run it with R = 2 and with R = 3. What changes in TLC's output, and why does it appear before any state is explored?
  4. Say in one sentence why Read takes the maximum of the versions it hears instead of the version of whichever replica answers first.

Keep R = 3, but change the read to \E n \in Q : seen' = version[n]: it returns the version of any one replica it asked. Does ReadsLatest still hold?

Hint

A read set of size R and a write set of size W must share an element when R + W elements can't fit into N places without repeating one. For task 3, remember that a constant formula doesn't depend on any state.

Solution

1. R + W > N means R + 3 > 5, so R ≥ 3. R = 3, 4 and 5 force overlap; R = 1 and R = 2 don't. With R = 2 the write set {A, C, D} and the read set {B, E} are disjoint.

2. R = 1 and R = 2 both violate ReadsLatest with a 6-state trace. In the R = 2 run, the trace went Store("A"), Store("C"), Store("D"), Ack, Read, ending with seen = 1. The read set must have been {B, E}, the only pair whose maximum is 1 there, as the diagram shows. Your run may store a different three replicas first. R = 3 gives no error, with 64 distinct states. That count is easy to check by hand: 32 version maps before the ack, then for each of the 16 maps with at least three 2s, one state before the read and one after it, which returns 2.

3. With R = 2 TLC stops at once with "Assumption … is false" and explores no states. With R = 3 the assumption holds, and the run is the same as before. Overlap mentions no variable, so it is a constant formula, and TLC evaluates assumptions before it computes the initial states. That's why Paxos Commit puts its Majority condition in an ASSUME: a bad configuration is rejected before any behavior is checked.

4. The overlap only promises that some replica asked has version 2. The read has to recognize that replica among its answers, and taking the highest version is how it does that. The quiz shows the same read with no such rule failing at R = 3. Real stores also need versions that order concurrent writes, which this one-writer model avoids.

The team's "nearly always" was correct as a probability and wrong as a guarantee. TLC doesn't weigh how likely a behavior is: it reports the one bad read that is allowed.

Problem 2●○○Infrastructure

Place five cluster members across data centres

Draws on {{ref:replication}}, {{ref:consensus}} and {{ref:sets}}.

Your company's configuration store is a five-member cluster that uses Raft, like etcd. A write needs a quorum of three members. The cluster must keep accepting writes when a whole data centre (DC) goes dark. The infrastructure team has three proposals:

  • Two DCs, three members in one and two in the other.
  • Three DCs, with two, two and one members.
  • Save a machine: four members in two DCs, two in each, with a quorum of just two "so either DC can carry on alone."

In the module below DCs is a set of sets: each element is the set of members in one DC. The single variable lost is the DC that has gone dark, and Init lets TLC try every choice. Because Next changes nothing, each state is one "what if". The cfg shows the first proposal.

--------------------------- MODULE PSl7_Placement ---------------------------
\* Where to put the members of a quorum-based cluster. DCs is a set of sets:
\* each element is the set of nodes in one data centre. The variable lost is
\* the one data centre that has gone dark; Init lets TLC try each in turn.
EXTENDS Integers, FiniteSets
CONSTANTS Node, DCs, QSize
ASSUME \A d1, d2 \in DCs : d1 # d2 => d1 \cap d2 = {}   \* no node in two DCs
ASSUME \A n \in Node : \E d \in DCs : n \in d           \* every node placed
VARIABLE lost
Quorum == {Q \in SUBSET Node : Cardinality(Q) >= QSize}
\* The property Paxos and Raft rely on, checked before any state is explored.
QuorumsOverlap == \A Q1, Q2 \in Quorum : Q1 \cap Q2 # {}
ASSUME QuorumsOverlap

Init == lost \in DCs
Next == UNCHANGED lost

\* Some quorum is made only of nodes outside the lost data centre.
QuorumSurvives == \E Q \in Quorum : Q \cap lost = {}
=============================================================================
INIT Init
NEXT Next
CONSTANTS Node = {"n1", "n2", "n3", "n4", "n5"}
          DCs = {{"n1", "n2", "n3"}, {"n4", "n5"}}
          QSize = 3
INVARIANT QuorumSurvives
CHECK_DEADLOCK FALSE
  1. By hand: how many elements does Quorum have for five members with QSize = 3? Check your count by adding ASSUME Cardinality(Quorum) = n, with your n, at the end of the module: TLC rejects a false assumption before it explores anything.
  2. Run all three proposals (for the third, use four members and QSize = 2, then QSize = 3). For each run, write down what TLC reports and which DC, if any, is fatal to lose.
  3. The third proposal can't be fixed by choosing a quorum size. Explain why in terms of the two properties the module checks.
  4. Find a layout of six members in three DCs, and a QSize, that passes both checks. Run it.

With the 2 + 2 + 1 layout and quorum 3, how many DCs can be lost at the same time without stopping writes?

Hint

QuorumSurvives asks for a quorum disjoint from the lost DC. QuorumsOverlap asks every two quorums to share a member. A quorum that fits inside one DC of the 2 + 2 layout satisfies the first and is exactly what breaks the second.

Solution

1. 10 + 5 + 1 = 16. With ASSUME Cardinality(Quorum) = 16 TLC runs as before; with 15 it reports the assumption false.

2. Results of the runs:

LayoutQSizeTLC says
3 + 23QuorumSurvives violated by the initial state lost = {"n1", "n2", "n3"}
2 + 2 + 13No error, 3 distinct states
2 + 22Assumption QuorumsOverlap is false
2 + 23QuorumSurvives violated by lost = {"n1", "n2"}
2 + 2 + 24No error, 3 distinct states (22 quorums)

In the 3 + 2 layout, losing the small DC is fine, but losing the large one leaves two members. The diagram shows both.

3. If either DC alone must be able to write, a quorum has to fit inside each DC. But then {n1, n2} and {n3, n4} are both quorums and share nobody: during a network split, each side could elect its own leader, which is the property Paxos and Raft assume can't happen. If quorums must overlap, a quorum needs at least three of the four members, and neither DC has three. With two DCs of equal size you can't have both properties, whatever QSize you choose.

4. Three DCs of two members each with QSize = 4: two quorums of four out of six share at least two members, and losing any DC leaves exactly four. TLC reports no error. Notice that a fourth member and a third DC improve nothing by themselves. What matters is that no single DC holds more than N − QSize members, the number a quorum system can do without.

Problem 3●●○Algorithms

Two leaders in one term

Draws on {{ref:consensus}}, {{ref:replication}}, {{ref:messages}} and {{ref:transactions}}.

A team is writing its own Raft-style leader election for a job scheduler. A server that hears nothing from a leader times out, moves to a higher term, votes for itself, and asks the others for votes. A server grants at most one vote per term. A candidate that collects votes from a majority becomes leader of that term. As in {{ref:consensus}}, a term plays the role of a ballot.

To keep the hot path fast, the implementation writes term to disk but keeps votedFor only in memory. After a deploy, the logs show two servers both acting as leader of term 1, both accepting jobs.

The module records votes as messages in a set that only grows, as in two-phase commit, and keeps the history leaders so that an invariant can talk about every election ever won. Logs are left out, so this checks only the election.

--------------------------- MODULE PSl7_Election ----------------------------
\* Leader election in the style of Raft, with votes as messages. Logs are
\* left out. A server that times out moves to a higher term, votes for
\* itself and asks for votes; it is leader of a term once a majority voted
\* for it in that term. Restart models a crash and reboot.
EXTENDS Integers
CONSTANTS Server, Majority, Term
ASSUME \A MS1, MS2 \in Majority : MS1 \cap MS2 # {}
None == "none"
VARIABLES term,      \* term[s]: the highest term s has seen
          votedFor,  \* votedFor[s]: whom s voted for in term[s], or None
          msgs,      \* every message ever sent
          leaders    \* every [srv, term] pair that has won an election
vars == <<term, votedFor, msgs, leaders>>

Init == /\ term = [s \in Server |-> 0]
        /\ votedFor = [s \in Server |-> None]
        /\ msgs = {}
        /\ leaders = {}

Timeout(s, t) ==
  /\ t > term[s]
  /\ term' = [term EXCEPT ![s] = t]
  /\ votedFor' = [votedFor EXCEPT ![s] = s]
  /\ msgs' = msgs \cup {[type |-> "request", term |-> t, from |-> s],
                        [type |-> "vote", term |-> t, from |-> s, to |-> s]}
  /\ UNCHANGED leaders

\* s grants its vote for term m.term at most once, unless it forgot.
Grant(s) ==
  \E m \in msgs :
    /\ m.type = "request"
    /\ \/ m.term > term[s]
       \/ m.term = term[s] /\ votedFor[s] \in {None, m.from}
    /\ term' = [term EXCEPT ![s] = m.term]
    /\ votedFor' = [votedFor EXCEPT ![s] = m.from]
    /\ msgs' = msgs \cup {[type |-> "vote", term |-> m.term, from |-> s, to |-> m.from]}
    /\ UNCHANGED leaders

BecomeLeader(s) ==
  /\ \E MS \in Majority :
       \A v \in MS : [type |-> "vote", term |-> term[s], from |-> v, to |-> s] \in msgs
  /\ leaders' = leaders \cup {[srv |-> s, term |-> term[s]]}
  /\ UNCHANGED <<term, votedFor, msgs>>

\* The process restarts. term is on disk; votedFor was kept only in memory.
Restart(s) ==
  /\ votedFor' = [votedFor EXCEPT ![s] = None]
  /\ UNCHANGED <<term, msgs, leaders>>

Next == \E s \in Server : \/ \E t \in Term : Timeout(s, t)
                          \/ Grant(s) \/ BecomeLeader(s) \/ Restart(s)
\* Both fields on disk: a restart then changes nothing in this model.
NextDurable == \E s \in Server : \/ \E t \in Term : Timeout(s, t)
                                 \/ Grant(s) \/ BecomeLeader(s)

OneLeaderPerTerm == \A l1, l2 \in leaders : l1.term = l2.term => l1.srv = l2.srv
=============================================================================
INIT Init
NEXT Next
CONSTANTS Server = {"s1", "s2", "s3"}
          Majority = {{"s1", "s2"}, {"s1", "s3"}, {"s2", "s3"}}
          Term = {1, 2}
INVARIANT OneLeaderPerTerm
CHECK_DEADLOCK FALSE
  1. Without TLC: suppose two different servers won term t. Use the ASSUME to show that some server sent a vote for each of them in term t. What in Grant is supposed to prevent that?
  2. Run TLC with Next. Report the length of the trace and the server whose two votes in term 1 let both candidates win.
  3. Run it again with NEXT NextDurable, which models keeping both fields on disk. Report TLC's result.
  4. Would keeping votedFor on disk and forgetting term on restart be safe? Decide by reading Grant, then answer the quiz.

Restart keeps votedFor but resets term to 0. Is OneLeaderPerTerm safe?

Hint

Two winners in term t means two sets of vote messages, each from a set in Majority. Any two such sets share a server. That server sent two votes in term t to different candidates. Look for the step after which Grant's guard no longer remembers the first one.

Solution

1. If s and s' both won term t, there are majorities MS and MS' whose members all sent term-t votes to s and to s' respectively. The ASSUME says MS ∩ MS' contains some server v, so v voted for both. In term term[v] = t, Grant allows a vote only when votedFor[v] is None or the same candidate. So two votes in one term can happen only if votedFor[v] went back to None while term[v] stayed t. Restart does exactly that.

2. TLC reports OneLeaderPerTerm violated after 8 states. The run here printed:

State 2: <Timeout("s1",1)>    \* s1 votes for itself in term 1
State 3: <Restart("s1")>      \* votedFor["s1"] = "none", term["s1"] = 1
State 4: <Timeout("s2",1)>    \* s2 votes for itself in term 1
State 5: <Grant("s1")>        \* s1 votes for s2 in term 1
State 6: <BecomeLeader("s2")> \* leaders = {[term |-> 1, srv |-> "s2"]}
State 7: <Grant("s3")>        \* s3 votes for s1 in term 1
State 8: <BecomeLeader("s1")> \* leaders = {[term |-> 1, srv |-> "s1"],
                               \*            [term |-> 1, srv |-> "s2"]}

The server that voted twice is s1. Its first vote was for itself, sent in state 2 and still in msgs. In your run the servers may be named differently, but the shape is the same: the double voter sits in the overlap of the two majorities. The overlap was there all along. What failed is that the server in it forgot what it had said, which is the restart warning from {{ref:consensus}} in another form.

3. No error: 1444 distinct states. The overlap argument from task 1 now goes through.

4. No. A server whose term drops to 0 treats any term-1 request as newer, and the first disjunct of Grant lets it vote without looking at votedFor. A vote record means something only together with the term it belongs to. That's why Raft requires both to reach stable storage before a server answers a vote request.

Problem 4●●●Databases

Synthesis: book the trip with Paxos Commit

Draws on {{ref:paxos-commit}}, {{ref:transactions}}, {{ref:tcommit}} and {{ref:ps-l6}}.

Return to the travel booking of {{ref:ps-l6}}: one transaction reserves a flight, a hotel room and a rental car, each held by its own resource manager (RM), coordinated with two-phase commit. Last month the coordinator's machine died after all three RMs had prepared. Each RM held its reservation and waited. Nobody could release the seat without risking a car booked for a trip with no flight. An engineer proposes Paxos Commit with three acceptors. Your job is to state precisely which failures each protocol survives, with a TLC run for each claim.

The first module is TwoPhase with RM = {flight, hotel, car} plus a crash: after Crash the TM never takes another step.

-------------------------- MODULE PSl7_TwoPCBooking -------------------------
\* Two-phase commit for the booking, plus a coordinator crash: after Crash
\* the TM takes no step ever again. RMs are unchanged from TwoPhase.
EXTENDS TwoPhase
VARIABLE tmUp
CInit == TPInit /\ tmUp = TRUE
Crash == /\ tmUp
         /\ tmUp' = FALSE
         /\ UNCHANGED vars
CNext == \/ Crash
         \/ /\ tmUp
            /\ \/ TMCommit \/ TMAbort
               \/ \E r \in RM : TMRcvPrepared(r)
            /\ UNCHANGED tmUp
         \/ /\ \E r \in RM : \/ RMPrepare(r) \/ RMChooseToAbort(r)
                             \/ RMRcvCommitMsg(r) \/ RMRcvAbortMsg(r)
            /\ UNCHANGED tmUp
NeverDecided == [type |-> "Commit"] \notin msgs /\ [type |-> "Abort"] \notin msgs
\* Everyone has voted yes and nobody can ever learn the outcome.
InDoubt == ~tmUp /\ NeverDecided /\ \A r \in RM : rmState[r] = "prepared"
NotInDoubt == ~InDoubt
=============================================================================
INIT CInit
NEXT CNext
CONSTANT RM = {"flight", "hotel", "car"}
INVARIANT TCConsistent
INVARIANT NotInDoubt
CHECK_DEADLOCK FALSE

The second module extends PaxosCommit, unchanged from the lecture. Only acceptors in Up take steps. Both claims at the bottom should fail when the protocol can still make progress: a counterexample to NeverAllCommitted is a run that commits the trip.

------------------------- MODULE PSl7_PaxosBooking --------------------------
\* Paxos Commit for the booking, with some acceptors crashed for good.
\* Only acceptors in Up ever take a step; the others stay silent forever.
\* Leader actions need no "up" flag: any live process may act as leader.
EXTENDS PaxosCommit
CONSTANT Up
ASSUME Up \subseteq Acceptor

UpNext ==
  \/ \E r \in RM : \/ RMPrepare(r) \/ RMChooseToAbort(r)
                   \/ RMRcvCommitMsg(r) \/ RMRcvAbortMsg(r)
  \/ \E bal \in Ballot \ {0}, r \in RM : Phase1a(bal, r) \/ Phase2a(bal, r)
  \/ PCDecide
  \/ \E acc \in Up : Phase1b(acc) \/ Phase2b(acc)

\* Claims that FAIL exactly when the protocol can still make progress:
NeverAllCommitted == \E r \in RM : rmState[r] # "committed"
NeverDecided == [type |-> "Commit"] \notin msgs /\ [type |-> "Abort"] \notin msgs
=============================================================================
INIT PCInit
NEXT UpNext
CONSTANTS RM = {"flight", "hotel", "car"}
          Acceptor = {"a1", "a2", "a3"}
          Majority = {{"a1", "a2"}, {"a1", "a3"}, {"a2", "a3"}}
          Ballot = {0, 1}
          Up = {"a1", "a2"}
INVARIANT TCConsistent
INVARIANT NeverAllCommitted
CHECK_DEADLOCK FALSE
  1. Run PSl7_TwoPCBooking. Using the guards of TwoPhase, explain why no step can change rmState once InDoubt holds.
  2. Run PSl7_PaxosBooking as shown, with a3 crashed. Does the trip commit? Which acceptors' phase 2b messages does PCDecide rely on?
  3. Now crash two acceptors: Up = {"a1"}, with INVARIANT NeverDecided instead of NeverAllCommitted. What does TLC report, and what does it mean?
  4. Run Paxos Commit with a single acceptor: Acceptor = {"tm"}, Majority = {{"tm"}}, and Up = {}, checking NeverDecided. Compare it with task 1.
  5. Fill in the table: for each failure, does two-phase commit, and does Paxos Commit with three acceptors, still reach a decision? The failures are: an RM crashes before voting, the TM crashes before deciding, one acceptor crashes, two acceptors crash.

In every run of this problem, TCConsistent held. What do the crashes cost?

Hint

For task 1, list every action and the first conjunct that is false in the InDoubt state. For task 2, Decided(r, v) in PCDecide needs phase 2b messages from every acceptor of one set in Majority, and only one of those sets avoids a3.

Solution

1. TLC reports NotInDoubt violated after 5 states: the TM crashes, then flight, hotel and car prepare (your trace may crash the TM later). In that state the TM actions are disabled by tmUp = FALSE. RMPrepare and RMChooseToAbort need "working". RMRcvCommitMsg and RMRcvAbortMsg need a decision message, and only the TM sends those. Crash isn't enabled either, and it never touches rmState anyway. All three reservations stay held forever.

2. Yes. TLC reports NeverAllCommitted violated with a 14-state trace: the three RMPrepare steps, three Phase2b("a1") steps, three Phase2b("a2") steps, PCDecide, and three RMRcvCommitMsg steps. PCDecide uses the majority {a1, a2} for all three instances. a3 never did anything, and nobody had to notice that it was gone. (Even this run explores more than 170,000 distinct states before it stops, which is why the lecture's model has two RMs.)

3. No error, 3375 distinct states: with a1 alone, no Commit or Abort is ever sent. No majority can form, so no instance can choose a value, and leaders' ballots can't complete either. Paxos Commit blocks too, but only when a majority of acceptors is gone.

4. No error, 216 distinct states: nothing is ever decided. A single acceptor is a single memory, which is what the TM was in two-phase commit. If it's down, every prepared RM waits, exactly as in task 1. Paxos Commit with three acceptors spreads that memory over three processes and needs any two of them.

5.

FailureTwo-phase commitPaxos Commit, 3 acceptors
An RM crashes before votingDecides: TMAbort is always enabled while tmState = "init"Decides: a leader runs ballot 1 for that RM's instance, hears no vote, and proposes "aborted"
TM crashes before decidingBlocks (task 1)There is no single TM: any process may run Phase1a, Phase2a and PCDecide

Both protocols keep TCConsistent in every case, because no step depends on anyone being up. What changes is who you need alive to finish. The price is more messages and more state. In general, with 2F + 1 acceptors the live ones still contain a majority after F crashes, which is the numeric question above.
