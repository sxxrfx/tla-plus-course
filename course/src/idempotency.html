Make retrying safe across a crash.

A retry is only safe if the effect and the record of that effect cannot be separated by a crash.

This builds on {{lesson:messages}}, where a client could not tell a lost request from a lost reply and so had to retry, and on {{lesson:inventory}}, where a check and an action in separate steps let another process slip between them. Now the thing that slips between them is a crash.

Suppose a worker processes charge request r and records “seen r” so retries can return the earlier result. A durable value survives a crash; a volatile one does not. In each row of the diagram, the arrow labelled “crash, retry” starts from what is left on disk.

In the top row the charge is on disk with no ID, so the retry charges again. In the middle row the ID is on disk with no charge, so the retry is told the work is done when it is not. Only the bottom row has no gap between the two writes. Step through the top and bottom rows here. This lab is an educational model, not TLC.

The contract

Start with what the system should appear to do, ignoring workers entirely. One atomic step records the request and applies its effect.

---------------- MODULE Once ----------------
EXTENDS Naturals
CONSTANT Requests
VARIABLES seen, effects
vars == <<seen,effects>>
Init == /\ seen = {}
        /\ effects = [r \in Requests |-> 0]
Apply(r) ==
    /\ r \notin seen
    /\ seen' = seen \cup {r}
    /\ effects' = [effects EXCEPT ![r] = @ + 1]
Next == \E r \in Requests: Apply(r)
Spec == Init /\ [][Next]_vars
TypeOK == /\ seen \subseteq Requests
          /\ effects \in [Requests -> 0..1]
Consistent == \A r \in Requests:
    (r \in seen) <=> (effects[r] = 1)
=============================================
SPECIFICATION Spec
CONSTANT Requests = {r1, r2}
INVARIANT TypeOK
INVARIANT Consistent
CHECK_DEADLOCK FALSE

TLC finds 4 distinct states and 5 generated, with both invariants holding. Duplicate deliveries do not appear here: at this level a repeated request is a stuttering step.

A worker that can crash

Now the implementation. effects and seen are durable, so Crash leaves them alone and resets only the volatile pc. Mode selects a design. Begin also models a redelivery, because it can run again whenever the worker is idle. The last two lines use a refinement mapping from {{lesson:refinement}} to state that this worker should implement Once.

---------------- MODULE Worker ----------------
EXTENDS Naturals
CONSTANTS Workers, Mode
ASSUME Mode \in {"EffectFirst", "IdFirst", "Atomic", "CheckThenCommit"}
VARIABLES effects, seen,   \* durable: survive a crash
          pc,              \* volatile: lost in a crash
          replied          \* the client has been told "done"
vars == <<effects, seen, pc, replied>>

Init == /\ effects = 0
        /\ seen = FALSE
        /\ pc = [w \in Workers |-> "idle"]
        /\ replied = FALSE

Go(w, where) == pc' = [pc EXCEPT ![w] = where]

\* A delivery reads the durable ID, then starts the chosen design.
Begin(w) ==
    /\ pc[w] = "idle"
    /\ UNCHANGED replied
    /\ IF seen
       THEN Go(w, "reply") /\ UNCHANGED <<effects, seen>>
       ELSE CASE Mode = "EffectFirst" ->
                   effects' = effects + 1 /\ UNCHANGED seen /\ Go(w, "record")
              [] Mode = "IdFirst" ->
                   seen' = TRUE /\ UNCHANGED effects /\ Go(w, "charge")
              [] Mode = "Atomic" ->
                   effects' = effects + 1 /\ seen' = TRUE /\ Go(w, "reply")
              [] Mode = "CheckThenCommit" ->
                   UNCHANGED <<effects, seen>> /\ Go(w, "commit")

Record(w) == /\ pc[w] = "record" /\ seen' = TRUE
             /\ UNCHANGED <<effects, replied>> /\ Go(w, "reply")
Charge(w) == /\ pc[w] = "charge" /\ effects' = effects + 1
             /\ UNCHANGED <<seen, replied>> /\ Go(w, "reply")
Commit(w) == /\ pc[w] = "commit"
             /\ effects' = effects + 1 /\ seen' = TRUE
             /\ UNCHANGED replied /\ Go(w, "reply")
Reply(w)  == /\ pc[w] = "reply" /\ replied' = TRUE
             /\ UNCHANGED <<effects, seen>> /\ Go(w, "idle")
Crash(w)  == /\ pc[w] # "idle"
             /\ UNCHANGED <<effects, seen, replied>> /\ Go(w, "idle")

Next == \E w \in Workers:
    Begin(w) \/ Record(w) \/ Charge(w) \/ Commit(w) \/ Reply(w) \/ Crash(w)
Spec == Init /\ [][Next]_vars

AtMostOnce  == effects <= 1
ReplyHonest == replied => effects >= 1
Bound       == effects <= 2     \* search limit for the buggy designs

Contract == INSTANCE Once WITH Requests <- {"r"},
                seen <- IF seen THEN {"r"} ELSE {},
                effects <- [r \in {"r"} |-> effects]
Refines == Contract!Spec
================================================

The two invariants split the problem. AtMostOnce says no duplicate effect. ReplyHonest says the client is never told “done” for work that did not happen. Each is easy to satisfy alone, so check both. The configuration for the safe design:

SPECIFICATION Spec
CONSTANTS Workers = {w1}
          Mode = "Atomic"
INVARIANT AtMostOnce
INVARIANT ReplyHonest
PROPERTY Refines
CONSTRAINT Bound
CHECK_DEADLOCK FALSE

Bound is a state constraint from {{lesson:scaling}}. It only keeps the buggy designs finite, since a crash loop could otherwise raise effects forever. Changing Mode and Workers gives these results:

Compare the two grids at the Crash column. It changes the same variable in both. The difference is what seen says afterwards. Checking Refines against EffectFirst also fails, at its very first step: effects changes while seen does not, and Once has no such step.

Predict: is “record the ID, then charge” safe, since it can never charge twice?

It is safe for AtMostOnce, and that is the trap. TLC’s trace for IdFirst is Begin, Crash, Begin, Reply: the ID is saved, the worker dies, the retry sees the ID and replies, and effects is still 0. You need both properties: no duplicate effect, and accepted work not silently lost.

A crash is not the only way in

The fourth row of the table is the instructive one. With one worker, CheckThenCommit passes, because its commit writes both values at once. Add a second worker and it fails with no crash at all. The diagram draws TLC’s trace.

Each worker’s commit is atomic, but the check came earlier, so this is the last-ticket race again. In a real store the fix is often a unique key on the request ID, so the second commit fails, or an equivalent compare-and-commit. Translate exactly that guarantee into your atomic boundary. The lesson for modeling: if the deployment has competing workers, a one-worker model can pass while the design is wrong.

Commit writes the effect and ID atomically, after an earlier read of the ID. What can still go wrong?

Worked architecture: process an uploaded receipt once

A receipt-scanning service awards loyalty points after processing an image. Job r42 may be delivered twice. Define the business effect as a durable credit row keyed by r42, and define attempts as separate worker executions. “Exactly once” at the application boundary concerns the credit, not whether a worker ever repeats the computation.

In the diagram, a crash between OCR and the commit would lose only temporary work. The crash shown comes after the commit, so the acknowledgement is lost and the queue redelivers along the dashed arrow. The worker then finds a saved answer.

That is why the store keeps a result, not just a flag. A bare seen boolean can suppress a duplicate, but it cannot reconstruct the points awarded. Define a retention policy too: deleting r42’s record while late attempts remain possible reopens the duplicate path.

If the effect sits at an external payment provider, a local transaction cannot include it. The provider needs compatible request-ID semantics, or you need a different protocol. A transactional outbox commits a local data change together with an intent to publish an event, which makes those two atomic. Downstream consumers still need their own duplicate handling.

Predict: the points credit is committed locally, but an email is sent before the transaction completes. Is the whole operation atomic?

No. The email is an external side effect. An outbox can durably record the intention to send alongside the credit, but delivery may repeat unless the email boundary has its own identity or repetition is acceptable. Specify each observable effect separately.
