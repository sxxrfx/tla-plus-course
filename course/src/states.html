A system is a graph of possibilities.

{{lesson:why}} said TLA+ checks conditions on individual executions. To do that, an execution has to be something precise. Here it becomes a sequence of states, and a whole system becomes a state machine that allows many such sequences.

The diagram shows two executions of the small C program you will meet below, drawn the way TLA+ sees them. Three words define that view: an execution is a sequence of discrete steps.

Discrete, sequence, step

Discrete. A digital system is a physical system whose continuous evolution we can abstract as separate events. Lamport's example is the first self-powered digital system, the escapement clock: its parts move continuously, but we can describe it as an abstract clock advancing in ticks. A computer running a program is the same kind of abstraction.

Sequence. It may seem odd to describe a concurrent system, where several things happen at once, as one sequence. It is clearly possible, since a sequential program can simulate a concurrent system. As the course goes on, you will see that it also works well.

Step. A state is an assignment of values to variables. A step is the change from one state to the next. A behavior is a sequence of states. So in the diagram, run 1 and run 2 are two behaviors, each with three states and two steps.

State machines

You want to describe all possible behaviors of a system, not just one. Programming languages, Turing machines, automata, and hardware description languages can all do that. TLA+ uses the abstraction underneath all of them, a state machine, which you describe by saying three things:

  1. What the variables are.
  2. Their possible initial values.
  3. The relation between their values in the current state and their possible values in the next state.

A state machine halts if it reaches a state with no possible next state.

A tiny example, and the problem it exposes

int i;
void main()
{ i = someNumber();
  i = i + 1;
}

Assume someNumber() returns an arbitrary number from 0 to 1000, possibly different on each execution. C initializes i to 0. The obvious model has one variable, i, with one initial value, 0. Now try to write item 2. What can follow i: 43?

Follow the red state in the diagram. In run 1, the call returned 42 and the increment produced 43, so the program has finished: there is no next value. In run 2, the call returned 43, so the next value must be 44. The same current state needs two incompatible rules. So this program can't be described as a state machine with i alone.

The missing part of the state says which statement runs next. It is called the control state, and we represent it with a second variable, pc, for program control. pc equal to "start" means the first assignment is next, "middle" means the second is next, and "done" means execution has finished.

In the diagram, there are now two distinct states with i: 43, and each has its own rule. The relation can be stated, for now in English:

if current value of pc equals "start"
  then next value of i in {0, 1, ..., 1000}
       next value of pc equals "middle"
  else if current value of pc equals "middle"
         then next value of i equals current value of i + 1
              next value of pc equals "done"
         else no next values

That is awkward to read, and {{lesson:program}} turns it into a formula. But notice what has already been gained. A program represents parts of its state differently because they are implemented differently: variables, control state, call stack, heap. A state machine represents every part the same way, as values of variables. Those implementation details are gone, and you have one simple abstraction.

Why does the model with only variable i fail?

Worked app example: a login screen

The same idea applies far from C. Model a login screen with a variable phase, whose values are idle, submitting, signedIn, and failed, and a variable for the request being processed.

From submitting, the diagram has two arrows. They are alternative next states, and any one behavior takes just one of them. To practice, draw the graph without code, put concrete values in each node, and name each arrow. Then invent a transition that should be impossible, like the dashed one from failed straight to signedIn. A graph is useful only if its rules exclude that arrow.

Now suppose a developer stores both phase and isLoading. The combination signedIn with isLoading true becomes representable, although it should never occur. A spinner is derived from phase equal to submitting, so unless it can really vary on its own, leave it out of the model. A state with fewer independent variables is easier to reason about.

Predict: are x = 1, y = 2 and x = 1, y = 3 the same state?

No, if both x and y are variables of the model. If you deliberately leave y out, those two situations become one state. What you choose to model decides which differences exist. In the C example, adding pc did the reverse: it split one state into two.

Predict: does a disabled Submit button mean the machine has no arrow from idle to submitting?

Only if the button is the only trigger. If a programmatic retry or another event can start a login, the arrow exists regardless of the button. Model what can actually happen, not what one control suggests.
