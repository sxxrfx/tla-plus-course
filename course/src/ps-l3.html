Problem set 3: run TLC and read what it tells you.

These problems practice Lecture 3: writing a module and its config file, running TLC, reading “distinct states found,” checking invariants, reading an error trace backward, and telling deadlock from termination. They draw on {{ref:tools}} and {{ref:counter}}, and the last problem checks a model from {{ref:ps-l2}}.

Every module here has been run through TLC, and every number in a checked answer is one TLC printed. Commands are in the command-line form from {{ref:tools}}, java -cp tla2tools.jar tlc2.TLC -config Name.cfg Name. In the Toolbox you enter the same things on the model's Overview page, and the VS Code extension reads the same .cfg file. Remember that the module name must match the file name.

Problem 1●○○API gateway

Does a fixed-window rate limiter keep its promise?

Draws on {{ref:logic}} and {{ref:counter}}.

An API gateway lets each client make 3 requests per minute. It uses a fixed window: a counter per client that resets when each minute starts on the clock, and a request is rejected when the counter is already at the limit. The product team has told the backend team: “a client never gets more than 3 requests through in any 60 seconds.”

To see time inside a minute, the model splits each minute into two halves. half is 1 or 2, the half of the current minute it is now. a1 and a2 count the requests accepted in the first and second half of the current minute, and p2 counts those accepted in the second half of the previous minute. Here is the module without its accept steps:

----------------- MODULE PSl3_RateLimit -----------------
EXTENDS Integers
VARIABLES half, a1, a2, p2

Limit == 3

Init == /\ half = 1
        /\ a1 = 0
        /\ a2 = 0
        /\ p2 = 0

Tick == \/ /\ half = 1
           /\ half' = 2
           /\ a1' = a1
           /\ a2' = a2
           /\ p2' = p2
        \/ /\ half = 2
           /\ half' = 1
           /\ p2' = a2
           /\ a1' = 0
           /\ a2' = 0

\* AcceptFirst, AcceptSecond and Next: yours to write
=========================================================

Tick moves time forward half a minute. At the end of a minute it saves the second half's count in p2 and resets the window. A rejected request changes nothing, so it needs no case. The figure shows which spans of time the counters cover.

  1. Write AcceptFirst and AcceptSecond: in the half it is now, a request is accepted when the window's total a1 + a2 is below Limit. Then define Next.
  2. Define WindowOK, “the current window never holds more than Limit accepted requests.” Save the module as PSl3_RateLimit.tla with a config PSl3_RateLimit.cfg containing INIT Init, NEXT Next and INVARIANT WindowOK, and run TLC. How many distinct states does it find? Why does it report no deadlock?
  3. The promise talks about any 60 seconds, including the span from the middle of the previous minute to the middle of this one. Define SlidingOK == p2 + a1 =< Limit, add a second INVARIANT line, and run again. Retell TLC's trace as a story with clock times.
  4. Is the gateway wrong, or the promise? Say what the fixed window really guarantees.

Hint

Each accept case needs three kinds of line: the guard (which half it is, and room in the window), the counter that grows, and x' = x for the other three variables. For the deadlock question, look for a case whose guard is true in every state.

Solution 
----------------- MODULE PSl3_RateLimit -----------------
EXTENDS Integers
VARIABLES half, a1, a2, p2

Limit == 3

Init == /\ half = 1
        /\ a1 = 0
        /\ a2 = 0
        /\ p2 = 0

AcceptFirst  == /\ half = 1
                /\ a1 + a2 < Limit
                /\ a1' = a1 + 1
                /\ a2' = a2
                /\ p2' = p2
                /\ half' = half

AcceptSecond == /\ half = 2
                /\ a1 + a2 < Limit
                /\ a2' = a2 + 1
                /\ a1' = a1
                /\ p2' = p2
                /\ half' = half

Tick == \/ /\ half = 1
           /\ half' = 2
           /\ a1' = a1
           /\ a2' = a2
           /\ p2' = p2
        \/ /\ half = 2
           /\ half' = 1
           /\ p2' = a2
           /\ a1' = 0
           /\ a2' = 0

Next == AcceptFirst \/ AcceptSecond \/ Tick

WindowOK  == a1 + a2 =< Limit
SlidingOK == p2 + a1 =< Limit
=========================================================

(b) TLC reports Model checking completed. No error has been found. and 56 distinct states found. You can account for the number: when half = 1, a2 is 0 and a1 and p2 each range over 0..3, giving 16 states; when half = 2, there are 10 pairs of a1 and a2 with a sum of at most 3, and 4 values of p2, giving 40. There is no deadlock because Tick has a case for each value of half, so some step is always possible. That is right for a model of time.

(c) TLC reports Invariant SlidingOK is violated. with this 7-state trace:

As a story: from 10:00:00 to 10:00:30 the client is quiet. At 10:00:40 and 10:00:50 it sends two requests, both accepted. At 10:01:00 the window resets. At 10:01:05 and 10:01:10 it sends two more, both accepted, since the new window is empty. That is 4 requests in 30 seconds, against a promise of 3 per 60 seconds. Four accepts and two ticks can't be done in fewer steps, so 7 states is the shortest possible behavior.

(d) The gateway does what a fixed window does: at most Limit accepted requests per clock minute, which is WindowOK. Near a boundary a client can get up to twice the limit in a short span: 3 just before the minute and 3 just after. To see it, change the bound in SlidingOK to 5; TLC then prints a 9-state behavior ending with p2 = 3 and a1 = 3. Either the promise should say “per clock minute,” or the gateway needs an algorithm that tracks a moving 60 seconds, such as a sliding-window log of request times. Which to choose is a product decision; the model makes the difference precise.

Problem 2●●○Concurrency

Read a TLC trace backward to find a double release

Draws on {{ref:logic}} and {{ref:counter}}.

A thumbnail service runs image-resize jobs, at most 2 at a time because each job needs a lot of memory. A semaphore with 2 permits enforces this: a worker takes a permit before starting a job and gives it back when the job ends. The code that ends a job calls release() in its error handler, and again in its finally block, which also runs after an error. Java's java.util.concurrent.Semaphore, like many semaphores, does not require a release to match an earlier acquire, so an extra release simply adds a permit.

The model counts running jobs and free permits; which worker runs which job is left out.

------------------ MODULE PSl3_Workers ------------------
EXTENDS Integers
VARIABLES running, permits

MaxJobs == 2

Init == /\ running = 0
        /\ permits = MaxJobs

Start  == /\ permits > 0
          /\ permits' = permits - 1
          /\ running' = running + 1

Finish == /\ running > 0
          /\ running' = running - 1
          /\ permits' = permits + 1

Fail   == /\ running > 0
          /\ running' = running - 1
          /\ permits' = permits + 2

Next == Start \/ Finish \/ Fail

AtMostTwo == running =< MaxJobs
=========================================================

A teammate ran TLC with INIT Init, NEXT Next and INVARIANT AtMostTwo and got:

Error: Invariant AtMostTwo is violated.
Error: The behavior up to this point is:
State 1: <Initial predicate>
/\ permits = 2
/\ running = 0

State 2: <Start line 10, col 11 to line 12, col 35 of module PSl3_Workers>
/\ permits = 1
/\ running = 1

State 3: <Start line 10, col 11 to line 12, col 35 of module PSl3_Workers>
/\ permits = 0
/\ running = 2

State 4: <Fail line 18, col 11 to line 20, col 35 of module PSl3_Workers>
/\ permits = 2
/\ running = 1

State 5: <Start line 10, col 11 to line 12, col 35 of module PSl3_Workers>
/\ permits = 1
/\ running = 2

State 6: <Start line 10, col 11 to line 12, col 35 of module PSl3_Workers>
/\ permits = 0
/\ running = 3
  1. Which state violates AtMostTwo? Now read the trace backward, as {{ref:counter}} did for the counter: for each step, ask whether the step itself was allowed and sensible. Which step first went wrong?
  2. Find a formula over permits and running that is true in states 1 to 3 and false from state 4 on. Why is it a sharper invariant for this design than AtMostTwo?
  3. Fix Fail, add your formula as a second invariant, and run TLC. How many distinct states does it find?
  4. If you run TLC with several worker threads, using its -workers option, it may print a different trace of the same length. Is that a different bug?
Which case of Next is wrong?

Hint

The state where the invariant fails is where the damage shows, not where it was done. Steps 4 to 5 and 5 to 6 are Start, and each had a permit available. So where did the extra permit come from?

Solution

(a) State 6, with 3 jobs running. Going backward: step 5 to 6 is Start with permits = 1, so its guard was true. Step 4 to 5 is Start with 2 permits, also allowed. But state 4 is already wrong: one job is running and 2 permits are free, so the semaphore will admit 2 more. Step 3 to 4 is Fail: one job ended and 2 permits came back. That is the error handler and the finally block each calling release().

(b) permits + running = MaxJobs. Each permit is either free or held by a running job, and this formula says exactly that. It fails at state 4, the moment the bookkeeping goes wrong, while AtMostTwo fails only two steps later when the extra permit happens to be used. An invariant that states why the design works catches errors closer to their cause.

(c) With Fail releasing one permit, TLC reports no error and 3 distinct states. Deadlock checking was on, and none was reported: from every state, either a job can start or one can end.

------------------ MODULE PSl3_WorkersFixed ------------------
EXTENDS Integers
VARIABLES running, permits

MaxJobs == 2

Init == /\ running = 0
        /\ permits = MaxJobs

Start  == /\ permits > 0
          /\ permits' = permits - 1
          /\ running' = running + 1

Finish == /\ running > 0
          /\ running' = running - 1
          /\ permits' = permits + 1

Fail   == /\ running > 0
          /\ running' = running - 1
          /\ permits' = permits + 1

Next == Start \/ Finish \/ Fail

AtMostTwo == running =< MaxJobs
PermitsOK == permits + running = MaxJobs
=========================================================

Fail and Finish are now the same formula. Keep both if you want the trace to say which way a job ended. In the code, the fix is to release only in the finally block.

(d) No. With one worker thread, TLC searches in a fixed order and printed the trace above. With several threads, our run printed Start, Fail, Start, Start, Start: the extra permit appears after the first job fails instead of the second. Both traces have 6 states and the same Fail step, so they show the same bug. Read any trace for the step that breaks the design's reasoning, not for its exact order.

Problem 3●●○Algorithms

Euclid's algorithm: termination, deadlock, and a loop that never ends

Draws on {{ref:program}}, {{ref:logic}} and {{ref:counter}}.

Euclid's algorithm finds the greatest common divisor (GCD) of two positive integers, the largest number that divides both. In its original form it uses only subtraction: while the two numbers differ, subtract the smaller from the larger. When they are equal, that value is the GCD of the numbers you started with. The GCD of 34 and 21 is 1.

------------------ MODULE PSl3_Euclid ------------------
EXTENDS Integers
VARIABLES x, y

M == 34
N == 21

Init == /\ x = M
        /\ y = N

SubY == /\ y < x
        /\ x' = x - y
        /\ y' = y

SubX == /\ x < y
        /\ y' = y - x
        /\ x' = x

Next == SubY \/ SubX

Positive == x > 0 /\ y > 0
Answer   == (x = y) => (x = 1)
========================================================

As with Max in {{ref:counter}}, the inputs are definitions; to try other inputs, edit them.

  1. Run TLC with a config containing only INIT Init and NEXT Next. It reports a deadlock. Look at the last state of the trace: is it a deadlock or a termination, in Lamport's sense?
  2. Add CHECK_DEADLOCK FALSE, INVARIANT Positive and INVARIANT Answer, and run again. How many distinct states does TLC find? Why is it the same as the number of states in the trace from (a)?
  3. Answer is an implication. In which states is it true only because x = y is false? If a bug kept the algorithm from ever reaching x = y, what would TLC report about Answer?
  4. A colleague changes SubY's guard to y =< x, “to handle equal numbers.” Predict, then run TLC twice: once with INVARIANT Positive (and deadlock checking on), and once with only INIT and NEXT. Explain each result.
  5. Change the inputs to 12 and 18, and Answer to x = 6. Run again.
What does TLC's deadlock report in (a) mean?

Hint

For (d), work out by hand what happens at x = 1, y = 1 with the new guard, and then at the state after it. Which case applies there, and what next state does it produce?

Solution

(a) TLC prints Error: Deadlock reached. and a trace of 8 states, shortened here:

State 1: <Initial predicate>
/\ x = 34
/\ y = 21
State 2: <SubY line 11, col 9 to line 13, col 17 of module PSl3_Euclid>
/\ x = 13
/\ y = 21
...
State 8: <SubY line 11, col 9 to line 13, col 17 of module PSl3_Euclid>
/\ x = 1
/\ y = 1

It is termination: the algorithm is supposed to stop when x = y, and x holds the GCD, 1. As {{ref:counter}} explained, nothing in the spec says stopping is intended, so TLC reports it. Here the report is even useful: it shows you where and how the algorithm stops.

(b) No error, and 8 distinct states. The guards y < x and x < y can't both be true, so every state has at most one next state. With one initial state, the reachable states form a single path, drawn above, and the deadlock trace in (a) was that whole path.

(c) In states 1 to 7, where x and y differ, Answer is true because its left side is false. It says something only in state 8. If a bug kept the algorithm from ever reaching x = y, Answer would be true in every state and TLC would report no error: this is the vacuous check from {{ref:logic}}. Answer says the result is right if the algorithm stops; it does not say the algorithm stops.

(d) With INVARIANT Positive, TLC reports Invariant Positive is violated in state 9, x = 0, y = 1: at x = 1, y = 1, the guard 1 =< 1 is true, so SubY subtracts. With only INIT and NEXT, TLC reports Model checking completed. No error has been found. and 9 distinct states. There is no deadlock now, because at x = 0, y = 1, SubX applies (0 < 1) and produces y' = 1 - 0 = 1, the same state again. The algorithm subtracts zero forever. So “no deadlock” here is bad news: the deadlock check finds states with no next step, and this bug creates a state whose only next step goes nowhere. Saying “the algorithm eventually stops” is a different kind of property, which the course reaches later. For now, notice that Positive caught the bug, and the deadlock report you got in (a) was a sign of health.

(e) The path is (12, 18), (12, 6), (6, 6): TLC finds 3 distinct states and no error, and Answer holds with 6.

Problem 4●●●Networking

Model-check the retry loop, then lose a response

Synthesis. Draws on {{ref:ps-l2}} (the retry loop), {{ref:orientation}}, {{ref:states}}, {{ref:logic}} and {{ref:counter}}.

In {{ref:ps-l2}}, problem 1, you wrote the HTTP client's retry loop as Init and Next. Now check it, and then make it more realistic.

  1. Save the solution module of that problem as PSl2_Retry.tla, with a config containing INIT Init and NEXT Next, and run TLC. It reports a deadlock. Read the last state of the trace: deadlock or termination?
  2. CHECK_DEADLOCK FALSE would silence this, but it would also silence a real hang added later. Instead, add a case to Next that allows the finished program to take a step that changes nothing: 
    Done == /\ pc = "done"
        /\ pc' = pc
        /\ attempts' = attempts
        /\ ok' = ok
    Run again with deadlock checking on and with INVARIANT BudgetOK and INVARIANT DoneOK. How many distinct states does TLC find, and what does a deadlock report now mean?
  3. Now model the network. send() becomes a request followed by a wait for the response, which may be "ok", "err", or lost. Add a variable resp, initially "none", add resp' = resp to every case that doesn't set it, and replace Send with these three cases: 
    Send == /\ pc = "send"
        /\ (resp' = "ok" \/ resp' = "err" \/ resp' = "lost")
        /\ pc' = "wait"
        /\ attempts' = attempts
        /\ ok' = ok

GotOk  == /\ pc = "wait"
          /\ resp = "ok"
          /\ ok' = TRUE
          /\ pc' = "count"
          /\ attempts' = attempts
          /\ resp' = resp

GotErr == /\ pc = "wait"
          /\ resp = "err"
          /\ ok' = FALSE
          /\ pc' = "count"
          /\ attempts' = attempts
          /\ resp' = resp
    Run with deadlock checking on and INVARIANT BudgetOK. What does TLC report?
  4. Is that report a real deadlock? Which line of real client code does it correspond to? Add a case Timeout that fixes it, and run again.
  5. The timeout counts a lost response as a failure and tries again. Using the upload example in {{ref:orientation}}, say what can go wrong on the server. What did this model leave out that hides the problem?

Hint

For (c), look at the figure: from wait, which values of resp have a case that leaves? For (d), a hang that the user sees as a spinner forever is exactly what an HTTP timeout is for.

Solution

(a) In our run the trace ended in the state attempts = 1, ok = TRUE, pc = "done": the first send succeeded and the loop exited. Your trace may end in another of the four done states. Either way, it is termination: the program is supposed to stop there.

(b) No error, and 20 distinct states, the same 20 as in {{ref:ps-l2}}. Done adds a step from each finished state to itself, so no state is left without a next state, and no new states appear. Now a deadlock report can only mean the program got stuck somewhere other than "done". This is a common way to separate the two: say in the spec that stopping at the end is intended, and leave deadlock checking on for everything else.

(c) TLC reports a deadlock with a 3-state trace:

Error: Deadlock reached.
Error: The behavior up to this point is:
State 1: <Initial predicate>
/\ resp = "none"
/\ attempts = 0
/\ ok = FALSE
/\ pc = "test"

State 2: <Test line 10, col 9 to line 16, col 23 of module PSl3_RetryNet>
/\ resp = "none"
/\ attempts = 0
/\ ok = FALSE
/\ pc = "send"

State 3: <Send line 25, col 9 to line 29, col 19 of module PSl3_RetryNet>
/\ resp = "lost"
/\ attempts = 0
/\ ok = FALSE
/\ pc = "wait"

In the figure, the red box marks these states: pc is "wait", the response was lost, and no case of Next applies.

(d) Yes, this one is real. The client waits for a response that will never come, which in code is an HTTP call with no timeout. Some popular HTTP libraries wait indefinitely unless you set a timeout, so this hang happens in production: the user sees a spinner forever. The fix is a case for the lost response:

----------------- MODULE PSl3_RetryNetFixed -----------------
EXTENDS Integers
VARIABLES attempts, ok, pc, resp

Init == /\ attempts = 0
        /\ ok = FALSE
        /\ pc = "test"
        /\ resp = "none"

Test == /\ pc = "test"
        /\ ~ok
        /\ attempts < 3
        /\ pc' = "send"
        /\ attempts' = attempts
        /\ ok' = ok
        /\ resp' = resp

Exit == /\ pc = "test"
        /\ (ok \/ ~(attempts < 3))
        /\ pc' = "done"
        /\ attempts' = attempts
        /\ ok' = ok
        /\ resp' = resp

Send == /\ pc = "send"
        /\ (resp' = "ok" \/ resp' = "err" \/ resp' = "lost")
        /\ pc' = "wait"
        /\ attempts' = attempts
        /\ ok' = ok

GotOk  == /\ pc = "wait"
          /\ resp = "ok"
          /\ ok' = TRUE
          /\ pc' = "count"
          /\ attempts' = attempts
          /\ resp' = resp

GotErr == /\ pc = "wait"
          /\ resp = "err"
          /\ ok' = FALSE
          /\ pc' = "count"
          /\ attempts' = attempts
          /\ resp' = resp

Timeout == /\ pc = "wait"
           /\ resp = "lost"
           /\ ok' = FALSE
           /\ pc' = "count"
           /\ attempts' = attempts
           /\ resp' = resp

Count == /\ pc = "count"
         /\ attempts' = attempts + 1
         /\ pc' = "test"
         /\ ok' = ok
         /\ resp' = resp

Done == /\ pc = "done"
        /\ pc' = pc
        /\ attempts' = attempts
        /\ ok' = ok
        /\ resp' = resp

Next == Test \/ Exit \/ Send \/ GotOk \/ GotErr \/ Timeout \/ Count \/ Done

BudgetOK == attempts \in 0..3
========================================================

TLC now reports no error and 38 distinct states, with deadlock checking on. That is evidence that the only place the client stops is "done", which you could not have learned with CHECK_DEADLOCK FALSE.

(e) A lost response does not mean a lost request. In the upload example of {{ref:orientation}}, the server committed the document and only the reply was lost; retrying created a second document. Here, a timeout after a request that the server did process leads to a second request, and if the request was “charge this card” or “create this order,” it happens twice. The model hides this because it has no server: it records only what the client sees. To check “at most one order per click,” the state would need the server's side too, such as the number of orders created, plus a way for the server to recognise a repeated request. Later lessons build that kind of model.
