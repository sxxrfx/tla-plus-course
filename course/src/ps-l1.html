Problem set 1: describe a system as states and steps.

These problems practice Lecture 1: what a state, a step and a behavior are, which claims a single execution can settle, and how abstraction decides which variables a model keeps. They draw on {{ref:orientation}}, {{ref:why}} and {{ref:states}}. You have no TLA+ syntax yet, so answer in English, lists of states, and drawings of state graphs.

Write your answer down before you open a hint, and open the solution only after the checked question agrees with you. When a problem says “state,” it means an assignment of values to the variables you chose, exactly as in {{ref:states}}.

Problem 1●○○Embedded control

Which logs are behaviors of an elevator controller?

Draws on {{ref:why}} and {{ref:states}}.

A small building has one elevator serving floors 1 to 3. Its controller tracks two things: the floor the car is at, and the door, which is closed, opening, open or closing. The design document gives these rules:

  • At power-on the car is at floor 1 with the door closed.
  • The door goes closed → opening → open → closing → closed, one change at a time.
  • While the door is closing, the obstruction sensor can send it back to opening.
  • The car moves one floor up or down at a time, and only while the door is closed.

Each change listed above is one step. The real controller also tracks motor current, the door's position in millimetres and several timers. This model leaves them out, which is the kind of abstraction {{ref:why}} described: they matter for building the controller, not for the question of which orders of events are possible.

An engineer copied five sequences from the controller's logs into the figure. Each cell is one state, written as floor and door.

  1. Describe the state machine in the three parts {{ref:states}} uses: the variables, their initial values, and the relation between a state and its possible next states. Write the relation in English, one case per kind of step.
  2. For each sequence A to E, decide whether it is a behavior of this state machine. For each one that isn't, name the first state or step that breaks a rule, and the rule.
  3. How many different states can the controller reach? Does the state machine ever halt?
  4. A field report claims the car once moved one floor with its door open. Which arrow would the state graph need for that to be a behavior? Is it there, and what does that tell you about the report?

Hint

A behavior has to start in an initial state, and every consecutive pair of states has to be one allowed step. A step either changes the door along the cycle (or from closing back to opening) and leaves the floor alone, or changes the floor by exactly one while the door stays closed.

Solution

(a) The variables are floor and door. Initially floor is 1 and door is closed. The relation has two kinds of case. A door step keeps the floor and changes the door from closed to opening, opening to open, open to closing, closing to closed, or closing to opening. A move is possible only when the door is closed; it keeps the door closed and changes the floor to one more or one less, staying within 1 to 3.

(b) A is a behavior: a full door cycle at floor 1, then a move to floor 2. C is a behavior too: the door starts closing, the sensor reopens it at state 5, and it opens. B breaks at the step from state 3 to state 4, where the floor changes while the door is opening. D breaks at its first step, from floor 1 to floor 3, which skips floor 2. E breaks before any step: its first state is floor 2, and the only initial state is floor 1 with the door closed. So 2 of the 5 are behaviors.

(c) 12. There are 3 × 4 = 12 combinations of floor and door, and each can be reached: move to the floor with the door closed, then step the door to the value you want. The machine never halts, because every door value has at least one next door value, so every state has a next state. For an elevator that is correct: it should keep running. We checked this machine with TLC, which you install in Lecture 3; it found 12 distinct states.

(d) An arrow from a state with the door open to a state on the next floor, still open. A move is allowed only when the door is closed, so no such arrow exists, and no behavior of this machine moves with the door open. If the report is true, the real elevator is not this state machine. Either the code does not follow the design, or the model left out something that matters, such as a maintenance override. The model doesn't tell you which, but it turns a vague report into a precise question to ask.

Problem 2●●○Databases

One state or a whole behavior? Claims about a transaction

Draws on {{ref:why}} and {{ref:states}}.

A relational database runs each transaction through a short lifecycle. After BEGIN the transaction is active. COMMIT makes its writes durable and visible to other sessions; ROLLBACK discards them. Postgres also has a failed status: if a statement inside a transaction block fails, the transaction becomes failed, every further statement is rejected with “current transaction is aborted, commands ignored until end of transaction block,” and, if no savepoints are in use, the only way out is to end the transaction, which rolls it back. This model leaves savepoints out.

Model one transaction with two variables: status, one of active, failed, committed and aborted, and visible, yes when other sessions can see its writes. The figure shows the state machine.

Your team wants to write down what the database promises. Someone collects these claims:

  1. The status is always one of active, failed, committed and aborted.
  2. If the status is committed, the writes are visible.
  3. If the writes are visible, the status is committed.
  4. Once a transaction is committed, its status never changes again.
  5. A transaction that was failed is never later committed.
  6. Every transaction eventually becomes committed or aborted.
  7. Fewer than 2% of transactions end aborted.
  1. Sort the claims into three groups: those you can judge by looking at each state of an execution on its own, those that need you to compare states across a whole behavior, and those that are not conditions on a single execution at all.
  2. Use the figure to explain why every behavior of this state machine satisfies claims 4 and 5.
  3. Which states halt? Is halting there a bug?
  4. Claim 7 matters to the operations team. Following the advice in {{ref:why}}, find a rule about single executions that sits underneath it, or explain why there isn't one.

Why does every behavior of the figure satisfy claim 4?

Hint

Words like “once,” “never later” and “eventually” talk about time, so they need more than one state. A claim about a percentage of transactions talks about many executions; {{ref:why}} showed that kind with the 99% example.

Solution

(a) One state at a time: claims 1, 2 and 3. Each can be broken by a single state, for example status committed with visible no breaks claim 2, and status active with visible yes breaks claim 3. Whole behavior: claims 4, 5 and 6. No single state breaks claim 4; you need a committed state followed later by a different status. Claim 5 needs a failed state followed later by a committed one. Claim 6 needs the whole sequence, because it says something must happen eventually. Not a condition on one execution: claim 7. One execution can't show that 2% of transactions abort, so TLA+ can't check it.

(b) A behavior moves only along arrows. No arrow leaves committed, so once a behavior reaches it, there is no later state with another status: claim 4 holds. For claim 5, the only arrow out of failed goes to aborted, and no arrow leaves aborted, so a behavior that passes through failed can never reach committed. The two claims are about behaviors, yet you proved them by looking at the arrows, one step at a time. That is the method this course builds on.

(c) Committed and aborted have no next state, so the machine halts there. That is correct: the transaction is over. {{ref:states}} defined halting as reaching a state with no possible next state, and nothing about it is wrong in itself. Whether a stop is intended is something you decide about each system. Notice that active has no self-arrow either. This model doesn't say how long a transaction stays active, only which status comes next. Claim 6 is about something eventually happening, a kind of claim the course treats with care later on; this model leaves the question open.

(d) A per-execution rule underneath claim 7 might be “a transaction aborts only after an error or an explicit ROLLBACK.” In this model that holds, because every arrow into aborted is labelled with one of them. The percentage itself depends on how often clients send errors and rollbacks, which is a statistic about the workload. It belongs in monitoring, not in the model.

Problem 3●●○Design systems

Choose the variables for a design-system Button

Draws on {{ref:orientation}}, {{ref:why}} and {{ref:states}}.

Your design system's Button is used for every asynchronous action in the product: Save, Pay, Send invite. The page sets its disabled prop and can change it at any time. Its onClick handler returns a promise. While the promise is pending, the button shows a spinner. When the promise resolves, it shows a check mark for two seconds and then returns to its normal look. When it rejects, it shows a red outline, and the user can click again to retry. Its styles also have hover and pressed colours and a 150 ms fade between looks.

A support ticket says a customer on a slow train connection double-clicked Pay and was charged twice. Before anyone changes code, the team wants a model of what the Button does. The figure shows the phases as one designer describes them.

  1. A teammate proposes four variables: phase (idle, loading, success or error), disabled (yes or no), hovered (yes or no) and spinnerVisible (yes or no). Which do you keep? For each one you drop, say whether it is redundant (its value is fixed by the others) or irrelevant to what a click can do. Where does the fade go?
  2. The teammate's model has 4 × 2 × 2 × 2 combinations of values. How many of them describe a screen the component can never show, given that the spinner is visible exactly when the phase is loading?
  3. With the variables you kept, suppose a second click while loading does start a second request. Write the step it causes. Can your model tell that state apart from the state before the click? If not, add the variable you need, and state “never two requests in flight” as a condition on a single state.
  4. Write one behavior, as a list of states, in which the page disables the button while a request is loading. What should happen when the response arrives?

Hint

{{ref:states}} dropped isLoading from the login screen because it was derived from the phase. Do the same test here for each variable: is it determined by the others, and does it change what can happen next? For (c), draw the dashed loop in the figure as a step between two states and compare the two states' values.

Solution

(a) Keep phase and disabled. disabled must stay because the page changes it independently of the phase, at any moment, including while loading. Drop spinnerVisible as redundant: it is just “phase is loading,” like isLoading in {{ref:states}}. Drop hovered as irrelevant: hover changes a colour, but no rule about clicks or requests depends on it. The pressed colour and the fade are irrelevant for the same reason, and they are also details of timing and rendering below the level of this model. If a future design made hover matter, for example a tooltip that blocks the click, you would add it back.

(b) 16. There are 32 combinations. For each choice of phase, disabled and hovered, one of the two values of spinnerVisible matches the phase and the other doesn't. Keeping a redundant variable doubles the number of combinations and makes half of them impossible, which is a good reason to leave it out.

(c) With only phase and disabled, the second click would be a step from (loading, no) to (loading, no). The two states are equal, so the model can't see the second request at all, and the double charge is invisible. Add inflight, the number of requests started and not yet finished. The click is then a step from (loading, no, 1) to (loading, no, 2), and the requirement is “in every state, inflight is 0 or 1.” That condition looks at one state, and the bad behavior idle, loading 1, loading 2 breaks it in its third state. This is the general lesson: if a requirement talks about something, the state must contain it. You now have three variables. The next problem set turns this model into formulas.

(d) One such behavior: (idle, no, 0), (loading, no, 1), (loading, yes, 1), (success, yes, 0), (idle, yes, 0). Disabling stops new clicks; it doesn't cancel a request that has already been sent, so the response still arrives and the phase still changes. Whether a disabled button should show the check mark is a design decision. The model forces you to make it.

Keep the upload example from {{ref:orientation}} in mind. Even a Button that ignores clicks while loading can't prevent a double charge by itself: if the reply is lost and the user reloads and pays again, the server needs a way to recognise the repeat. The model of the Button shows what the component can promise and what it can't.

Problem 4●●●CI/CD

Two deploys, twenty interleavings, one stale release

Synthesis. Draws on {{ref:orientation}}, {{ref:why}} and {{ref:states}}.

Your team's CI/CD pipeline deploys a service on every merge to the main branch. Each pipeline run does three steps, in order:

  1. test: run the test suite;
  2. read: read the version currently live from the deploy registry;
  3. write: if its own version is newer than the one it read, set the live version to its own.

The check in step 3 exists so that an old build never replaces a newer one. Two merges land a minute apart: run A builds version 41, run B builds version 42, and version 40 is live. The team has an end-to-end test that starts two pipelines a minute apart and checks that 42 ends up live. It has passed 1,000 times in a row. The figure shows the order of steps it produces every time.

Model the pair of runs as one state machine. Each numbered step of either run is one step of the machine. Each run does its own steps in order, but the two runs' steps can interleave, meaning they can mix in any order.

  1. Choose the variables. Each run needs its own control state, like pc in {{ref:states}}, and something else that the read step must leave behind for the write step.
  2. How many different interleavings of the six steps are there?
  3. In how many of them is 41 live after both runs finish? Describe exactly which interleavings they are.
  4. Write one bad behavior as a sequence of states. Then explain, using the two routes in {{ref:why}}, why 1,000 passing runs of the end-to-end test didn't find it.
  5. Write a prediction-notebook entry for the claim “after both runs finish, the newest version is live,” in the three lines {{ref:orientation}} suggests. Is the claim a condition on a single execution?

Hint

Write an interleaving as a string such as AABBBA, where the k-th A is run A's k-th step. For (c), ask when A's write can change the live version to 41 at all, and what A must have read for its check to pass.

Solution

(a) Five variables: live, the live version; pcA and pcB, each saying which step that run does next (test, read, write or done); and readA and readB, the version each run read. The read values are easy to forget, but the write step's check uses them, so they are part of the state. Initially live is 40 and both runs are at test.

(b) 20. Each run's steps stay in order, so an interleaving is fixed by choosing which 3 of the 6 positions hold A's steps, and there are 20 such choices.

(c) 6. For 41 to end up live, A's write must change the live version, so A must have read something older than 41, which means 40. And nothing may change it afterwards, so B's write must come before A's write. If B's write came before A's read, A would read 42 and do nothing. So B's write falls between A's read and A's write, and A's write is last. That makes the last two steps B's write then A's write. The first four steps, A's test and read and B's test and read, can come in any order that keeps each run's steps in order: 6 ways, namely AABB, ABAB, ABBA, BAAB, BABA and BBAA. So 6 of the 20 interleavings are bad. We checked this with a small TLA+ model of the two runs: TLC finds a state where both runs are done and 41 is live.

(d) The diagram shows ABABBA. Each column is a state, and each move to the next column is one step. In state 4 A has read 40, and B then reads 40 too. B's check passes and it writes 42. A's check compares 41 with the stale 40 it read, passes, and replaces 42 with 41. Every step did what its code says; the error is in the design, the gap between reading and writing. The end-to-end test takes the top route in the diagram of {{ref:why}}: it finds the error only if the timing happens to produce it. With A a minute ahead, A reads and writes seconds apart while B is still running its tests, so the test produces the interleaving in the first figure every time. A bad interleaving needs B to finish its read and write inside that short gap, for example when A's runner stalls between the two steps. That happens rarely in testing and eventually in production. The state machine contains all 20 interleavings equally, so a model checker doesn't depend on timing: TLC found a bad one in our model on its first run.

(e) Claim: after both runs finish, the newest version is live. Suspected breaking path: the newer run reads and writes between the older run's read and write. Evidence needed: whether the registry can do the comparison and the write as one step, so that no other run's step can fall between them. Yes, the claim is a condition on a single execution: look at the last state of one behavior and check which version is live. That is the kind of property TLA+ checks.
