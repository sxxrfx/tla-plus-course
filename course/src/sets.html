Three pieces of math describe a whole group of processes.

Die Hard had two jugs, so naming each one was easy. The next spec has a set of processes whose size you don't fix in advance. To write about all of them at once you need sets, functions, and the quantifiers "there exists" and "for all".

The diagram is one function, rmState. Each resource manager on the left has exactly one solid arrow to a value on the right. That is the whole idea of a function, and the dashed arrow is the only change that one step of the next spec will make.

Sets

A set is a collection with no order and no duplicates: it either contains a value or it doesn't. So {"r1", "r2", "r1"} and {"r2", "r1"} are the same set. You write membership as e \in S, and 1..3 is the set {1, 2, 3}.

In TLA+ every value is a set, even 42 and "abc", but the language doesn't say what their elements are. TLC reports an error if asked to evaluate 42 \in "abc". A module can therefore say CONSTANT RM and use RM as a set without declaring a type. A constant has the same value throughout every behavior, and you give it a value when you run TLC.

A function's domain can be any set, including one of strings or an infinite one. There are two expressions to tell apart:

sqr == [i \in 1..42 |-> i^2]     \* one function; sqr[3] = 9, DOMAIN sqr = 1..42
[RM -> {"working", "prepared"}]   \* a set: all functions from RM to those values

|-> builds one function. -> builds the set of all functions with that domain and those possible values. DOMAIN f gives the domain. (^ comes from the Integers module.)

In the diagram, the outer box is the value of [{"r1", "r2"} -> {"a", "b"}]. The highlighted inner box is the single function [r \in {"r1", "r2"} |-> "a"], which is one element of it. A type invariant such as rmState \in [RM -> ...] uses the outer form, and an initial state uses the inner one.

Changing one entry

A next-state formula can't say only that r's entry changes. Compare the middle and right columns.

rmState'[r2] = "prepared" says what the new value at r2 is. About every other resource manager it says nothing, which is why the middle column is full of question marks. You must give the whole new function:

rmState' = [s \in RM |-> IF s = r THEN "prepared" ELSE rmState[s]]
rmState' = [rmState EXCEPT ![r] = "prepared"]     \* the same thing, shorter

In the EXCEPT form, the ! means nothing. It's just syntax. EXCEPT doesn't modify anything: it is an expression for a new function, and rmState itself keeps its value in the current state.

Quantifiers

\E r \in RM : P(r) says there exists some r in RM for which P(r) is true. \A r \in RM : P(r) says P(r) is true for all r in RM. Over a finite set they are just a long "or" and a long "and":

Read the diagram from the top. One TRUE row makes the "or" true, and one FALSE row makes the "and" false. A few rules follow from this:

  • The bound name is local. \E xyz \in RM : ...xyz... means the same as \E r \in RM : ...r..., provided xyz isn't already declared or defined. TLA+ doesn't let you redefine a name that already has a meaning.
  • Abbreviation. \A r1, r2 \in RM : P abbreviates \A r1 \in RM : \A r2 \in RM : P.
  • Not and not-equal. ~P is "not P", and x # y is "x doesn't equal y".
  • Empty set. \A r \in {} : P is always true, since there is no counterexample, and \E r \in {} : P is always false.
  • Scope. A quantifier reaches as far as it can: to a closing bracket, or to the end of its /\ or \/ list item. Parentheses end it sooner.
\A x \in S : x = 1
    /\ \A x \in T : x = 2     \* illegal: this is inside the first \A, so x is redeclared

The parser rejects that with a multiply-defined symbol error.

Quantifier order changes the meaning

A cart holds a book and a mug. Compare two claims about shipping them.

\A i \in Items : \E w \in Warehouses : i \in CanShip[w]   \* true
\E w \in Warehouses : \A i \in Items : i \in CanShip[w]   \* false

The first says each item has some warehouse, and different items may have different ones (the left of the diagram). The second says one warehouse handles everything, and the dashed arrow on the right is why it fails. When you read a nested formula, invent a tiny example like this one.

Predict: which of the formulas in this lesson changes meaning if RM is empty?

With no resource managers, every \A r \in RM formula is true and every \E r \in RM formula is false. A check that "all RMs are prepared" passes trivially. That's why a claim such as "the cart can be checked out" needs its own "the cart isn't empty" condition: \A alone can't say so.

Worked example: a group chat

A chat has members and a read position for each member. Those are two concepts, so they get two shapes: a set for membership, a function for positions.

Members   == {"Ada", "Ben"}
lastRead  == [p \in Members |-> 0]
lastRead2 == [lastRead EXCEPT !["Ada"] = 2]     \* Ada 2, Ben still 0
lastRead2 \in [Members -> 0..3]                 \* true
\A p \in Members : lastRead2[p] <= 3            \* true

Because lastRead maps each person to a number, Ada and Ben can't accidentally share one cursor. Adding Cara to Members would leave the function's domain out of date, so both must change in one step. An ordered message history would need a sequence, which comes later with {{lesson:abp}}. Every formula in this lesson was checked by TLC as an assumption in a small module.
