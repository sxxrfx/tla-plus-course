A late cache fill can undo an invalidation.

An asynchronous read can finish after the data changed. Model the in-flight result as state; otherwise a stale-fill race is invisible.

This builds on {{lesson:app-state}}, where a late response overwrote a newer choice, and on {{lesson:inventory}}, where a check went stale before the action it guarded. Here the late response lands in a store that many readers trust, so it outlives the screen.

The concrete app

A shopping app caches a product’s price. A miss starts a database read. While that read is in flight, an administrator updates the price and invalidates the cache. The old read then returns and repopulates the cache.

In the chart, the writer’s two arrows are correct. The red arrow comes later and restores the old value. This can happen in one process when tasks interleave around await, or across several servers. A single-threaded event loop does not make a whole asynchronous operation atomic, so track BeginFill and FinishFill separately rather than drawing one instantaneous “read and cache” arrow.

Choose the exact contract

The property below is deliberately strong: whenever the cache is marked valid, its contents belong to the current source version. Version tags stand for payload identity. An invalid cache may hold old bytes because callers must not use them, so the predicate is conditional on valid.

The model assumes one authoritative source, increasing versions, one in-flight fill, and at most two writes. Write plus invalidation is one atomic action here, and so are the freshness check and publication. These are explicit abstraction boundaries, not guarantees that an ordinary database and remote cache provide. Later in this lesson you will break both.

Race a fill against invalidation

Source→In-flight fill→Cache

Complete bounded model: Cache.tla

---------------- MODULE Cache ----------------
EXTENDS Naturals
CONSTANT Fence
ASSUME Fence \in BOOLEAN
VARIABLES sourceVersion, cacheVersion, valid, loading, fillVersion
vars == <<sourceVersion, cacheVersion, valid, loading, fillVersion>>

Init == /\ sourceVersion = 0
        /\ cacheVersion = 0
        /\ valid = FALSE
        /\ loading = FALSE
        /\ fillVersion = 0

BeginFill ==
    /\ ~loading /\ ~valid
    /\ loading' = TRUE
    /\ fillVersion' = sourceVersion
    /\ UNCHANGED <<sourceVersion, cacheVersion, valid>>

WriteAndInvalidate ==
    /\ sourceVersion < 2
    /\ sourceVersion' = sourceVersion + 1
    /\ valid' = FALSE
    /\ UNCHANGED <<cacheVersion, loading, fillVersion>>

FinishFill ==
    /\ loading
    /\ loading' = FALSE
    /\ IF ~Fence \/ fillVersion = sourceVersion
          THEN /\ cacheVersion' = fillVersion
               /\ valid' = TRUE
          ELSE UNCHANGED <<cacheVersion, valid>>
    /\ UNCHANGED <<sourceVersion, fillVersion>>

Next == BeginFill \/ WriteAndInvalidate \/ FinishFill
Spec == Init /\ [][Next]_vars

TypeOK == /\ sourceVersion \in 0..2
          /\ cacheVersion \in 0..2
          /\ fillVersion \in 0..2
          /\ valid \in BOOLEAN
          /\ loading \in BOOLEAN
FreshWhenValid == valid => cacheVersion = sourceVersion
================================================

With Fence = TRUE, TLC completes with 15 distinct states and 20 generated, with both invariants holding. Change only the constant to Fence = FALSE, and TLC reports FreshWhenValid violated.

Read the counterexample

Read the grid by columns. BeginFill copies version 0 into fillVersion; this is the old response waiting to complete. The write advances the source to 1 while fillVersion stays at 0, because it is a copy. FinishFill without a fence then sets cacheVersion to 0 and valid to TRUE, with the source at 1.

In the fenced design, FinishFill sees that fillVersion differs from sourceVersion, discards the result, and clears loading. A later BeginFill captures version 1. Safety does not require every fill to succeed. This model also proves no response deadline: writes or scheduling can keep useful completion from occurring.

The fence discards a fill, so the next read misses again. Is that a violation of FreshWhenValid?

Break the two atomic boundaries

A generation counter serves a similar purpose in real caches: capture a generation before fetching, increment it when invalidating, publish only if it has not changed. The modeling question is whether compare-and-publish and write-and-invalidate are truly one step. The module CacheSplit below makes each optional. With neither split, it matches Cache exactly: 15 distinct states, 20 generated. Each split alone fails.

Mutation exercise: split the fence check from publication. What extra state is necessary, and does the fence still help?

You need a phase recording “checked,” here fill = "checked". The fence no longer helps: TLC’s 5-state trace appears below, where the check passes and a write then lands before the install. Restore an atomic conditional publication, or make invalidation also cancel previously authorized fills.

Predict: the fence stays atomic, but the database write and the invalidation are two separate steps. Does the invariant hold?

No. TLC’s trace is BeginFill, FinishFill, Write: a valid version 0 is in the cache when the source moves to 1, before the invalidation runs. This has nothing to do with the fill race. Either strengthen coordination or state a weaker contract, such as bounded staleness or freshness after a completed invalidation.

The full CacheSplit module 
---------------- MODULE CacheSplit ----------------
EXTENDS Naturals
CONSTANTS SplitCheck, SplitInvalidate
ASSUME SplitCheck \in BOOLEAN /\ SplitInvalidate \in BOOLEAN
VARIABLES sourceVersion, cacheVersion, valid, fill, fillVersion, wrote
vars == <<sourceVersion, cacheVersion, valid, fill, fillVersion, wrote>>
\* fill: "none", "loading", or "checked". The check is always fenced here.
\* wrote: TRUE between a source write and its separate invalidation.

Init == /\ sourceVersion = 0
        /\ cacheVersion = 0
        /\ valid = FALSE
        /\ fill = "none"
        /\ fillVersion = 0
        /\ wrote = FALSE

BeginFill ==
    /\ fill = "none" /\ ~valid
    /\ fill' = "loading"
    /\ fillVersion' = sourceVersion
    /\ UNCHANGED <<sourceVersion, cacheVersion, valid, wrote>>

\* The write and its invalidation, in one step or two.
Write ==
    /\ sourceVersion < 2 /\ ~wrote
    /\ sourceVersion' = sourceVersion + 1
    /\ IF SplitInvalidate
          THEN wrote' = TRUE /\ UNCHANGED valid
          ELSE valid' = FALSE /\ UNCHANGED wrote
    /\ UNCHANGED <<cacheVersion, fill, fillVersion>>
Invalidate ==
    /\ wrote
    /\ wrote' = FALSE
    /\ valid' = FALSE
    /\ UNCHANGED <<sourceVersion, cacheVersion, fill, fillVersion>>

Publish ==
    /\ cacheVersion' = fillVersion
    /\ valid' = TRUE
    /\ fill' = "none"
    /\ UNCHANGED <<sourceVersion, fillVersion, wrote>>

\* The fence check and the publication, in one step or two.
FinishFill ==
    /\ fill = "loading" /\ ~SplitCheck
    /\ IF fillVersion = sourceVersion
          THEN Publish
          ELSE /\ fill' = "none"
               /\ UNCHANGED <<sourceVersion, cacheVersion, valid,
                              fillVersion, wrote>>
CheckFence ==
    /\ fill = "loading" /\ SplitCheck
    /\ fill' = IF fillVersion = sourceVersion THEN "checked" ELSE "none"
    /\ UNCHANGED <<sourceVersion, cacheVersion, valid, fillVersion, wrote>>
Install == fill = "checked" /\ Publish

Next == BeginFill \/ Write \/ Invalidate \/ FinishFill \/ CheckFence \/ Install
Spec == Init /\ [][Next]_vars
FreshWhenValid == valid => cacheVersion = sourceVersion
===================================================
SPECIFICATION Spec
CONSTANTS SplitCheck = FALSE
          SplitInvalidate = FALSE
INVARIANT FreshWhenValid
CHECK_DEADLOCK FALSE

Avoid reusing generations while old fills remain outstanding, or an old generation can appear current again. And do not describe this small model as proof of a replicated cache protocol.

Predict: a 60-second TTL makes every cached read current. Is that true?

No. TTL can limit how long an entry is used under suitable clock and refresh assumptions; it does not prevent returning an old value during its lifetime. Delayed fills can also begin a new lifetime for an old result unless their version or generation is checked. “Current” and “not older than a chosen bound” are different contracts.
