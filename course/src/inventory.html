Find the interleaving that breaks the design.

In {{lesson:actions}}, one action was one indivisible step, and in {{lesson:transactions}} TLC tried the resource managers’ steps in every order. Here you use both ideas on purpose: you decide where one step ends, and TLC finds the order that breaks the design.

An interleaving is one order in which independent actors’ steps can happen. TLC does not simulate CPU instructions. It explores whichever steps you wrote, so choose the step boundaries from the guarantee your system actually has. The diagram shows why that matters: two buyers, one ticket, and a check that happens separately from the reservation. If A or B reserves before the other checks, that path dead-ends safely, as at the top and bottom. If both check first, the middle node, then the sale goes through twice.

Start with the guarantee you want

This module makes checking and updating one step, so Reserve is one edge in the graph.

---------------- MODULE Inventory ----------------
EXTENDS Naturals, FiniteSets
CONSTANT Buyers
VARIABLES remaining, booked
vars == <<remaining, booked>>
Init == /\ remaining = 1
        /\ booked = {}
Reserve(b) ==
    /\ remaining > 0
    /\ b \notin booked
    /\ remaining' = remaining - 1
    /\ booked' = booked \cup {b}
Next == \E b \in Buyers: Reserve(b)
Spec == Init /\ [][Next]_vars
TypeOK == /\ remaining \in 0..1
          /\ booked \in SUBSET Buyers
Conservation == remaining + Cardinality(booked) = 1
NoOverselling == Cardinality(booked) <= 1
==================================================
SPECIFICATION Spec
CONSTANT Buyers = {A, B}
INVARIANT TypeOK
INVARIANT Conservation
INVARIANT NoOverselling
CHECK_DEADLOCK FALSE

TLC finds 3 distinct states and no error. The diagram below is all of them.

This abstraction promises nothing about a database. It describes the guarantee a design must provide. Whether a real multi-step implementation provides it is the question from {{lesson:implementation}}.

Now split the step

Add a per-buyer stage. Check reads the stock and remembers the answer in the stage. Reserve relies on that memory and does not look again.

Check(b) ==
    /\ pc[b] = "idle"
    /\ remaining > 0
    /\ pc' = [pc EXCEPT ![b] = "checked"]
    /\ UNCHANGED <<remaining, booked>>
Reserve(b) ==
    /\ pc[b] = "checked"
    /\ remaining' = remaining - 1
    /\ booked' = booked \cup {b}
    /\ pc' = [pc EXCEPT ![b] = "done"]

The invariant is unchanged. TLC reports NoOverselling violated after 4 steps: both buyers check, then both reserve, leaving remaining = -1 and booked = {A, B}. With the invariant removed, the whole graph has the 9 states in the first diagram.

Predict: if you add remaining > 0 back to Reserve, what happens to the split model?

The second reservation is disabled, so the double sale goes away. In doing so you moved the real decision back into one atomic step, because the test and the update now happen together in Reserve. The earlier Check no longer decides anything.

Exercise: name an implementation guarantee needed by Reserve.

The availability test and the successful update must form one indivisible decision. A conditional update can provide this if the database enforces the required concurrency semantics and the application checks whether it succeeded. A transaction boundary alone is not a proof: isolation and retries matter.

The atomic model passes and the split model fails the same invariant. What changed?

Concrete architecture: a shopping cart is not a reservation

Suppose a storefront has one camera left. Ada adds it to a cart, and Ben adds it to another cart. That is not overselling if carts only express interest. Two carts are allowed; two successful reservations of the one unit are not. Naming both concepts “selected” makes the design harder to reason about, so checkout must be the step that decides.

Represent a reservation as a durable record keyed by request ID. On success, the stock count falls and the reservation appears in the same abstract step. Cancelling is the same move in reverse:

Cancel(b) ==          \* also models expiry of the hold
    /\ b \in held
    /\ held' = held \ {b}
    /\ remaining' = remaining + 1
    /\ UNCHANGED <<confirmed, paying>>

The guard blocks cancellation when no hold exists, and the two updates move the unit back. Cancelling the same hold twice is disabled, so stock cannot increase twice.

Real products add expiry and payment. Then ask whether a delayed payment callback can confirm a hold that has already expired. The TicketHold model tests this with Reserve, StartPayment, Cancel (which also stands for expiry) and LatePayment:

LatePayment(b) ==
    /\ b \in paying
    /\ b \in held     \* delete this line to get the bug
    /\ confirmed' = confirmed \cup {b}
    /\ held' = held \ {b}
    /\ paying' = paying \ {b}
    /\ UNCHANGED remaining

With the guard b \in held, TLC finds 16 states and OnePromise holds. Delete that line and it fails in the 5 steps shown below.

Look at the fourth step: A’s hold is gone and the ticket is back on sale, but A’s payment is still arriving. Confirmation checked only that a payment had started. Rechecking the hold closes this path. If the same buyer can reserve again after expiry, buyer identity is not enough, because an old callback would match the new hold. You would then need a reservation identity or generation.

Exercise: does adding Cancel preserve the property “once booked, always booked”?

No, and that may be intended. Conservation can still hold while bookings are removed. Choose properties that match the lifecycle: “at most one live reservation” is different from “a buyer never loses a reservation.”
