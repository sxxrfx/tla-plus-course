Problem set 5: say it about every process at once.

Lecture 5 gave you sets, functions and quantifiers, and the TCommit spec, which uses them to describe any number of participants. These problems use that notation on replicas, pods, services and servers. They still rely on guards, frames and the never-reached claim from {{ref:ps-l4}}, and on TLC's reports from {{lesson:counter}}.

UNCHANGED and records come with Lecture 6, so frames are still written out as v' = v. A function-valued variable that a step changes with EXCEPT needs no other frame. For trace lengths, run TLC with -workers 1.

Problem 1●○○Databases

A failover tool reads the replica map

Draws on {{ref:sets}}, {{ref:tcommit}} and {{ref:counter}}.

A Postgres primary streams its write-ahead log to three replicas. A failover tool keeps two functions with the same domain: status, modeled loosely on the state column of Postgres's pg_stat_replication view, and lag, each replica's last reported replay lag in seconds. When the primary dies, the tool promotes a candidate: a streaming replica with the smallest lag.

Evaluate these by hand, before using TLC. Each is TRUE or FALSE.

E1 == \A r \in Replicas : status[r] = "streaming" => lag[r] =< 5
E2 == \E r \in Replicas : \A s \in Replicas : lag[r] =< lag[s]
E3 == \A s \in Replicas : \E r \in Replicas : lag[r] < lag[s]
E4 == \A r \in Replicas : lag[r] =< 5
E5 == \A r \in {} : lag[r] > 100

Then look at the tool's rule, as the module below writes it. Next is one event: db1 crashes.

----------------------------- MODULE PSl5_Failover -----------------------------
EXTENDS Integers

Replicas == {"db1", "db2", "db3"}

\* Replay lag in seconds, as last reported.
lag == [r \in Replicas |-> IF r = "db1" THEN 0
                           ELSE IF r = "db2" THEN 4
                           ELSE 90]

VARIABLE status

Init == status = [r \in Replicas |-> IF r = "db3" THEN "catchup"
                                     ELSE "streaming"]

\* db1 crashes. Its last reported lag stays in the table.
Next == status' = [status EXCEPT !["db1"] = "down"]

Candidate(r) == /\ status[r] = "streaming"
                /\ \A s \in Replicas : lag[r] =< lag[s]

SomeCandidate == \E r \in Replicas : Candidate(r)
=============================================================================

The config is INIT Init, NEXT Next, INVARIANT SomeCandidate.

  1. Give the values of E1 to E5, with a one-line reason each.
  2. How many elements does [Replicas -> {"streaming", "catchup", "down"}] have? Write a type invariant for status using it.
  3. Which replicas satisfy Candidate in the initial state? Run TLC. What does it report, and why?
  4. Fix Candidate so that only streaming replicas are compared, and check it again.
Which of E2 and E3 is true?

Hint

Over a finite set, \A is a long “and” and \E a long “or”. Write them out for db1, db2 and db3. For the bug, ask which replicas the \A s in Candidate compares against after the crash.

Solution

(a) E1 is TRUE: the streaming replicas are db1 and db2, with lags 0 and 4. For db3 the left side of => is false, so its case is true. E2 is TRUE: take r = db1. E3 is FALSE: for s = db1, no lag is below 0. E4 is FALSE because of db3's 90. Compare it with E1, where the implication excused db3. E5 is TRUE, like every \A over the empty set.

(b) 27, since each replica independently gets one of three values. The type invariant is status \in [Replicas -> {"streaming", "catchup", "down"}].

(c) Initially only db1 is a candidate: it is streaming and its lag of 0 is no larger than anybody's. TLC reports Invariant SomeCandidate is violated in a 2-state trace:

State 1: <Initial predicate>
status = [db1 |-> "streaming", db2 |-> "streaming", db3 |-> "catchup"]

State 2: <Next ...>
status = [db1 |-> "down", db2 |-> "streaming", db3 |-> "catchup"]

TLC prints a function whose domain is a set of strings in this bracket form, the notation for records, which Lecture 6 introduces. After the crash, db2 is the obvious choice, but Candidate("db2") still compares its lag with db1's last reported 0 and fails. The dead replica's old number blocks every live one. A failover tool with this rule would refuse to promote anything in exactly the situation it exists for.

(d) Restrict the comparison to streaming replicas:

Candidate(r) == /\ status[r] = "streaming"
                /\ \A s \in Replicas : status[s] = "streaming" => lag[r] =< lag[s]

With this definition (module PSl5_FailoverFixed), TLC reports no error in 2 distinct states: db1 is the candidate before the crash and db2 after it. The fix uses the same pattern as E1, an implication inside \A that excuses the elements you don't care about. (The fixed rule still has a gap: if no replica is streaming, there is no candidate, and maybe that's what you want.)

Problem 2●●○Infrastructure

A rolling update that takes down two pods

Draws on {{ref:sets}}, {{ref:tcommit}} and {{ref:diehard-tlc}}.

A Kubernetes Deployment can replace pods one at a time: with maxSurge: 0 and maxUnavailable: 1, its rolling update keeps at most one replica unavailable, and a new pod counts as available only once it passes its readiness probe. Your team runs a stateful service whose pods need a custom drain step, so it wrote its own rollout script with the same goal: with three replicas, at least two serve traffic at every moment. Each pod goes from v1 to stopping, to starting, to v2, and serves only in v1 and v2. The script's rule for stopping a pod is “only if no other pod is stopping”.

------------------------------ MODULE PSl5_Rollout ------------------------------
CONSTANT Pod             \* the Deployment's replicas
VARIABLE pod             \* pod[p] is the state of replica p

TypeOK == pod \in [Pod -> {"v1", "stopping", "starting", "v2"}]

Init == pod = [p \in Pod |-> "v1"]

Serving(p) == pod[p] \in {"v1", "v2"}

\* The controller replaces one old pod. The guard is its availability rule.
Stop(p) == /\ pod[p] = "v1"
           /\ \A q \in Pod : pod[q] /= "stopping"
           /\ pod' = [pod EXCEPT ![p] = "stopping"]

\* The old container has exited; the new one is scheduled.
Start(p) == /\ pod[p] = "stopping"
            /\ pod' = [pod EXCEPT ![p] = "starting"]

\* The new container passes its readiness probe.
Ready(p) == /\ pod[p] = "starting"
            /\ pod' = [pod EXCEPT ![p] = "v2"]

Next == \E p \in Pod : Stop(p) \/ Start(p) \/ Ready(p)
=============================================================================
  1. Add the invariant AtMostOneDown: at most one pod is out of service. You don't have a way to count elements of a set yet, so say it with quantifiers.
  2. Run TLC with CONSTANT Pod = {"p1", "p2", "p3"}, INVARIANT TypeOK, INVARIANT AtMostOneDown and CHECK_DEADLOCK FALSE. Explain the trace. Why is the deadlock check off?
  3. Fix the guard of Stop. How many distinct states does TLC find now, and why that number?
  4. Use the trick from {{lesson:diehard-tlc}} to make TLC show you a complete rollout. How many steps does it take?
Which formula says “at least two of the three pods serve”?

Hint

“At most one” means: if two pods are both down, they are the same pod. For the fix, ask what the rule should look at: whether a pod is stopping, or whether it is serving.

Solution

(a) If two pods are both out of service, they are the same pod:

AtMostOneDown == \A p, q \in Pod : (~Serving(p) /\ ~Serving(q)) => p = q

(b) TLC reports Invariant AtMostOneDown is violated:

p1 is stopped and its replacement is starting. That pod is not stopping, so the script's guard \A q \in Pod : pod[q] /= "stopping" is true and p2 stops too. For as long as p1's new container takes to pass its probe, only p3 serves. The rule checked the wrong state: “stopping” is one way of being out of service, not the only one. The deadlock check is off because a finished rollout, with every pod on v2, has no next step, and that stop is intended.

(c) Make the guard the property you want: stop a pod only if every pod is serving.

Stop(p) == /\ pod[p] = "v1"
           /\ \A q \in Pod : Serving(q)
           /\ pod' = [pod EXCEPT ![p] = "stopping"]

TLC finds no error and 32 distinct states: the 8 where every pod is v1 or v2, plus the 24 where exactly one pod is stopping or starting. Counting reachable states by hand and matching TLC's number is a good check that the model allows what you think it allows, as {{lesson:tcommit}} advised.

(d) Claim NotRolledOut == ~(\A p \in Pod : pod[p] = "v2") as an invariant. TLC reports it violated with a 10-state trace: Stop, Start and Ready for p1, then the same for p2, then p3. That is 9 steps, 3 per pod, done strictly one pod at a time, which is what the rule promised. Kubernetes' maxSurge exists to speed this up by starting new pods before old ones stop. Modeling it would need a variable number of pods.

Problem 3●●○Microservices

All services move to schema v2, or none do

Draws on {{ref:tcommit}}, {{ref:sets}} and {{ref:diehard-tlc}}.

Three services, orders, billing and shipping, publish and consume OrderPlaced events on a shared topic. Version 2 of the event schema renames a field. A service on v1 code can't parse a v2 event, so the platform team sets two rules. First, nobody may emit v2 until every service has deployed a reader that understands both versions. Second, any team may back out, and if one does, nobody ever emits v2.

So each service goes through four states: "v1", "ready" (reads both, still emits v1), "v2" (emits v2), and "pinned" (backed out: stays on v1 for good). This should look familiar.

  1. Write the module, with CONSTANT Svc and one variable st, a function from services to states. Write the actions GetReady(s), Switch(s) and Cancel(s), and two invariants: Agreement (no service on v2 while another is pinned) and ReadersReady (if any service is on v2, every service is ready or on v2).
  2. Run TLC with the three services as strings. How many distinct states does it find? Why is that number familiar?
  3. A teammate argues that the switch guard is too strict, since a service only needs “nobody has backed out”. Replace the guard of Switch(s) by \A t \in Svc : st[t] # "pinned" and run again.

With the teammate's guard, which invariant does TLC report violated?

Hint

Match each state to one of TCommit's. Which TCommit formula says “everyone is ready”, and which one says “nobody has gone ahead”?

Solution

(a) In the diagram, each state carries its TCommit name. The module:

---------------------------- MODULE PSl5_Schema ----------------------------
CONSTANT Svc             \* services that produce and consume OrderPlaced events
VARIABLE st              \* st[s] is where service s is in the upgrade

TypeOK == st \in [Svc -> {"v1", "ready", "v2", "pinned"}]

Init == st = [s \in Svc |-> "v1"]

canSwitch == \A s \in Svc : st[s] \in {"ready", "v2"}

noneSwitched == \A s \in Svc : st[s] # "v2"

\* Deploy code that can read both v1 and v2 events; still emit v1.
GetReady(s) == /\ st[s] = "v1"
               /\ st' = [st EXCEPT ![s] = "ready"]

\* Start emitting v2 events.
Switch(s) == /\ st[s] = "ready"
             /\ canSwitch
             /\ st' = [st EXCEPT ![s] = "v2"]

\* Give up on v2 and stay on v1 for good.
Cancel(s) == /\ st[s] \in {"v1", "ready"}
             /\ noneSwitched
             /\ st' = [st EXCEPT ![s] = "pinned"]

Next == \E s \in Svc : GetReady(s) \/ Switch(s) \/ Cancel(s)

Agreement == \A s, t \in Svc : ~ /\ st[s] = "v2"
                                 /\ st[t] = "pinned"

ReadersReady == (\E s \in Svc : st[s] = "v2")
                  => \A t \in Svc : st[t] \in {"ready", "v2"}
=============================================================================

(b) With CONSTANT Svc = {"orders", "billing", "shipping"}, the two invariants and CHECK_DEADLOCK FALSE, TLC finds no error and 34 distinct states. That is TCommit's count for three RMs, and not by coincidence. Rename v1, ready, v2 and pinned to working, prepared, committed and aborted, and this module is TCommit with Decide split into its two branches. A schema rollout and a database commit are the same problem: a group must reach one decision, anyone may veto before it is made, and nobody may act on it early.

(c) With the weaker guard (module PSl5_SchemaEager), TLC reports Invariant ReadersReady is violated after 3 states: orders gets ready, then switches while billing and shipping are still on v1. Their consumers would choke on the first v2 event. Agreement alone doesn't catch this. Run with only Agreement and TLC finds no error, in 46 distinct states. Once orders is on v2, nobody can cancel, so the services do end up agreeing, after an outage.

This is why TCommit's commit branch requires canCommit. For a database it means that no RM commits until every RM has promised it can. Here it means that nobody emits v2 before everyone can read it. The consistency invariant TCConsistent doesn't state that requirement, which is why you want ReadersReady written down and checked too.

Problem 4 · Synthesis●●●Databases

Distributed cron: every job at most once

Draws on {{ref:sets}}, {{ref:tcommit}}, {{ref:counter}}, and the migration problem in {{ref:ps-l4}}.

Two application servers run the same crontab, so that the nightly jobs still run if one server is down. There are two jobs: backup, and report, which reads the backup. Neither may run twice in a night. Each server, for each job, reads the job's row in a shared jobs table. If owner is empty, it writes its own name and runs the job; otherwise it skips. A report must wait until some server has run the backup.

The module (open to copy) 
------------------------------ MODULE PSl5_Cron ------------------------------
CONSTANT Node                   \* servers that each run the same crontab
VARIABLES pc,                   \* pc[n][j]: where node n is with job j tonight
          owner                 \* owner[j]: the node in the jobs table, or "none"

Jobs == {"backup", "report"}

TypeOK == /\ pc \in [Node -> [Jobs -> {"idle", "seen", "ran", "skipped"}]]
          /\ \A j \in Jobs : owner[j] = "none" \/ owner[j] \in Node

Init == /\ pc = [n \in Node |-> [j \in Jobs |-> "idle"]]
        /\ owner = [j \in Jobs |-> "none"]

\* pc with node n's entry for job j set to v
Set(n, j, v) == [pc EXCEPT ![n] = [pc[n] EXCEPT ![j] = v]]

\* The report reads the backup, so it may start only after a backup ran.
Ready(j) == j = "report" => \E n \in Node : pc[n]["backup"] = "ran"

\* SELECT owner FROM jobs WHERE name = j  -- and see "none"
Check(n, j) == /\ pc[n][j] = "idle"
               /\ owner[j] = "none"
               /\ Ready(j)
               /\ pc' = Set(n, j, "seen")
               /\ owner' = owner

\* UPDATE jobs SET owner = n WHERE name = j; then run the job
Run(n, j) == /\ pc[n][j] = "seen"
             /\ owner' = [owner EXCEPT ![j] = n]
             /\ pc' = Set(n, j, "ran")

\* Someone else has it.
Skip(n, j) == /\ pc[n][j] = "idle"
              /\ owner[j] # "none"
              /\ pc' = Set(n, j, "skipped")
              /\ owner' = owner

Next == \E n \in Node : \E j \in Jobs : Check(n, j) \/ Run(n, j) \/ Skip(n, j)

AtMostOnce == \A j \in Jobs : \A n, m \in Node :
                (pc[n][j] = "ran" /\ pc[m][j] = "ran") => n = m
=============================================================================

The config:

INIT Init
NEXT Next
CONSTANT Node = {"n1", "n2"}
INVARIANT TypeOK
INVARIANT AtMostOnce
CHECK_DEADLOCK FALSE

pc is a function whose values are functions: pc[n] is node n's function from jobs to states, and pc[n][j] is one entry. Set(n, j, v) builds the new pc by applying EXCEPT at both levels.

  1. Read AtMostOnce aloud. Why does it end in n = m rather than n # m?
  2. Run TLC. Explain the trace in terms of SQL statements.
  3. Replace Check and Run by a single action Claim(n, j) that models one conditional UPDATE jobs SET owner = n WHERE name = j AND owner IS NULL: it succeeds and runs the job only if owner is still empty. Check AtMostOnce.
  4. The Ready guard plays the role the runbook guards played in the migration problem of {{ref:ps-l4}}. Use the same never-reached claim to make TLC produce a night's schedule in which both jobs run.
  5. Run your fixed module with the deadlock check on. Is the stop TLC reports a deadlock or termination? Add an action that tells TLC which stops are intended, so that the check can stay on.

With the deadlock check on, TLC reports “Deadlock reached” for the fixed module. What is it?

Hint

For (c), the check and the write must be one step, so the guard owner[j] = "none" and the change owner' = [owner EXCEPT ![j] = n] belong to the same action. For (e), an action whose guard says “everyone is finished” and whose frame keeps every variable the same is enabled exactly in the intended final states.

Solution

(a) “For every job, for any two nodes: if both ran it, they are the same node.” With n # m it would say that both ran it only if they are different nodes, and the case n = m would make it false in any state where some node ran the job. The \A n, m includes the pairs where n and m are equal. That is what makes “at most one” come out right.

(b) TLC reports Invariant AtMostOnce is violated with a 5-state trace:

Both servers ran SELECT owner and saw it empty before either wrote. n1's UPDATE doesn't change what n2 already read, and n2's UPDATE overwrites the owner with its own name. The backup runs twice, and the table even says n2 owns it. This is check-then-act: the decision is based on a value that may be stale by the time the action happens.

(c) Make the check part of the write:

--------------------------- MODULE PSl5_CronClaim ---------------------------
CONSTANT Node                   \* servers that each run the same crontab
VARIABLES pc,                   \* pc[n][j]: where node n is with job j tonight
          owner                 \* owner[j]: the node in the jobs table, or "none"

Jobs == {"backup", "report"}

TypeOK == /\ pc \in [Node -> [Jobs -> {"idle", "ran", "skipped"}]]
          /\ \A j \in Jobs : owner[j] = "none" \/ owner[j] \in Node

Init == /\ pc = [n \in Node |-> [j \in Jobs |-> "idle"]]
        /\ owner = [j \in Jobs |-> "none"]

Set(n, j, v) == [pc EXCEPT ![n] = [pc[n] EXCEPT ![j] = v]]

Ready(j) == j = "report" => \E n \in Node : pc[n]["backup"] = "ran"

\* UPDATE jobs SET owner = n WHERE name = j AND owner IS NULL
\* One statement: the check and the write are one step.
Claim(n, j) == /\ pc[n][j] = "idle"
               /\ owner[j] = "none"
               /\ Ready(j)
               /\ owner' = [owner EXCEPT ![j] = n]
               /\ pc' = Set(n, j, "ran")

Skip(n, j) == /\ pc[n][j] = "idle"
              /\ owner[j] # "none"
              /\ pc' = Set(n, j, "skipped")
              /\ owner' = owner

Next == \E n \in Node : \E j \in Jobs : Claim(n, j) \/ Skip(n, j)

AtMostOnce == \A j \in Jobs : \A n, m \in Node :
                (pc[n][j] = "ran" /\ pc[m][j] = "ran") => n = m

NotAllRan == ~(\A j \in Jobs : \E n \in Node : pc[n][j] = "ran")

AllFinished == \A n \in Node : \A j \in Jobs : pc[n][j] \in {"ran", "skipped"}

\* An intended stop: every node is done for the night. Nothing changes.
Finished == /\ AllFinished
            /\ pc' = pc
            /\ owner' = owner

NextOrDone == Next \/ Finished
=============================================================================

The module also holds the definitions for parts (d) and (e). With the config of (b), TLC finds no error and 21 distinct states. The model now says the check and the write are one step, so it is your job to make that true in the system too. A single UPDATE … WHERE owner IS NULL does it in Postgres at the default isolation level, read committed: when two such statements hit the same row, the second waits for the first to commit, then re-checks its WHERE clause against the new row and updates nothing. The server then sees that zero rows changed, and skips the job.

(d) Claim NotAllRan, which says that it never happens that every job has run somewhere. TLC reports it violated with a 3-state trace: Claim("n1", "backup"), then Claim("n1", "report"). The report comes second because Ready disables it until a backup has run, exactly as app = 2 forced the backfill after v2 in the migration runbook. The guard is the dependency, and TLC's trace is a schedule that respects it.

(e) With the deadlock check on, TLC reports Deadlock reached after a 5-state trace that ends with n1 having run both jobs and n2 having skipped both. Nothing is left to do, so this is termination, as with the counter in {{lesson:counter}}. Rather than turn the check off, the module defines Finished, which is enabled only when every entry of pc is "ran" or "skipped" and changes nothing, and NextOrDone == Next \/ Finished. With NEXT NextOrDone and the deadlock check on, TLC finds no error in 21 states. That shows something the earlier run couldn't: every state with no further step is a finished night. If Ready could block the report forever, this run would report the deadlock.

The pieces came from four chapters: functions and quantifiers for “at most once across nodes”, TCommit's style of guard that reads every process, the runbook guard and never-reached claim from {{ref:ps-l4}}, and the deadlock-or-termination question from Lecture 3.
