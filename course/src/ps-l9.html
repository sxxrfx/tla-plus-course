Problem set 9: say what must happen, and what it assumes.

Four problems on lecture 9: liveness properties, weak and strong fairness, and the alternating bit protocol. Each one asks TLC whether something eventually happens and then asks you why the answer depends on the fairness you assumed. The last problem returns to the trip booking of {{ref:ps-l6}}, {{ref:ps-l7}} and {{ref:ps-l8}}, now over a network that loses messages.

Every module shown was checked with TLC exactly as printed. Liveness counterexamples aren't unique: TLC may show you a different loop from the one described here, so check yours condition by condition, as {{ref:abp}} does. None of these models uses a symmetry set, since liveness checking must not.

Problem 1●○○Infrastructure

Will every background job run?

Draws on {{ref:fairness}}, {{ref:abspec}} and {{ref:abp}}.

A web app pushes slow work (sending receipts, resizing images) onto a background-job queue with a single worker. Support asks for a guarantee: every job that is submitted is eventually processed. The worker also sends a heartbeat to the scheduler, so a monitor can tell it's alive. Last week a customer's receipt never went out, although the job sat in the queue and the worker's heartbeat stayed green on the monitor the whole time. The module below has no deadlines, because "eventually" has none.

---------------------------- MODULE PSl9_JobQueue ---------------------------
\* A background-job queue with one worker. Each job is submitted once.
\* While running, the worker also sends heartbeats to the scheduler.
EXTENDS Integers, Sequences
CONSTANT Job
VARIABLES queue, submitted, done, beat
vars == <<queue, submitted, done, beat>>
Init == /\ queue = <<>>
        /\ submitted = {}
        /\ done = {}
        /\ beat = 0
Submit(j) == /\ j \notin submitted
             /\ submitted' = submitted \cup {j}
             /\ queue' = Append(queue, j)
             /\ UNCHANGED <<done, beat>>
Process == /\ queue # <<>>
           /\ done' = done \cup {Head(queue)}
           /\ queue' = Tail(queue)
           /\ UNCHANGED <<submitted, beat>>
Heartbeat == /\ beat' = 1 - beat
             /\ UNCHANGED <<queue, submitted, done>>
Next == Process \/ Heartbeat \/ \E j \in Job : Submit(j)
Spec == Init /\ [][Next]_vars
FairNext == Spec /\ WF_vars(Next)
FairWorker == Spec /\ WF_vars(Process)

EveryJobProcessed == \A j \in Job : (j \in submitted) ~> (j \in done)
=============================================================================
SPECIFICATION FairWorker
CONSTANT Job = {"j1", "j2", "j3"}
PROPERTY EveryJobProcessed
  1. Run TLC with SPECIFICATION Spec. What does the counterexample end with, and why is it allowed?
  2. Run it with FairNext. Describe the loop TLC reports, and explain why it satisfies WF_vars(Next).
  3. Run it with FairWorker, as in the cfg shown. Report the result.
  4. Nothing is fair about Submit. Should it be? Say what WF_vars(\E j \in Job : Submit(j)) would claim about the users of the app.

Why is weak fairness enough for Process?

Hint

WF_vars(Next) needs Next steps to keep happening while Next is enabled. Is there any state where some Next step is not possible? Which action is always enabled?

Solution

1. TLC reports EveryJobProcessed violated. In this run, some jobs are submitted and processed, and the trace ends with j1 still in the queue followed by "Stuttering". Spec says only what may happen, so a behavior may stop at any point. TLC even warns that the stuttering counterexample may come from a missing fairness condition.

2. TLC again reports a violation, this time ending in a loop. In the run here, j1 is submitted and processed, j3 and j2 are submitted, and then states 5 and 6 alternate by Heartbeat steps forever while j3 and j2 wait in the queue. Every step is a Next step, so WF_vars(Next) is satisfied. It requires only that Next steps keep happening, not that any particular one does. This is the same weakness {{ref:abp}} found in WF_vars(Next) for the alternating bit protocol.

3. No error, 76 distinct states. In a state where some job is in the queue, Process is enabled and stays enabled until it runs, so weak fairness forces a Process step. The queue is first-in first-out, so a submitted job reaches the head after the jobs before it have been processed.

4. No. That condition would say that users keep submitting jobs as long as some job hasn't been submitted, which is a claim about the environment, not the system, and it's false. Fairness belongs on actions the system promises to take. The property is already conditional: it talks only about jobs that are submitted.

Problem 2●●○Databases

A migration that never gets its lock

Draws on {{ref:fairness}}, {{ref:abp}} and {{ref:sets}}.

A database's lock manager lets many queries hold a table lock in shared mode, while a schema migration (ALTER TABLE) needs it exclusively. The first version grants a shared lock whenever no writer holds the table. On a busy table the migration has been waiting for an hour. The team's first idea is "make the scheduler fairer". The module below lets you test that idea. Queries release the lock eventually (weak fairness on every release), and the three specs differ only in the fairness of WriteAcquire and in one guard.

---------------------------- MODULE PSl9_RWLock -----------------------------
\* A table lock: queries take it shared, a schema migration takes it
\* exclusive. writer is "idle", "waiting" or "writing".
CONSTANT Reader
VARIABLES readers, writer
vars == <<readers, writer>>
Init == readers = {} /\ writer = "idle"

ReadAcquire(r) == /\ r \notin readers
                  /\ writer # "writing"
                  /\ readers' = readers \cup {r}
                  /\ writer' = writer
\* The fix: a waiting writer also blocks new readers.
ReadAcquireQueued(r) == writer = "idle" /\ ReadAcquire(r)
ReadRelease(r) == /\ r \in readers
                  /\ readers' = readers \ {r}
                  /\ writer' = writer
Request      == writer = "idle"    /\ writer' = "waiting" /\ readers' = readers
WriteAcquire == /\ writer = "waiting"
                /\ readers = {}
                /\ writer' = "writing"
                /\ readers' = readers
WriteRelease == writer = "writing" /\ writer' = "idle"    /\ readers' = readers

Next   == Request \/ WriteAcquire \/ WriteRelease
          \/ \E r \in Reader : ReadAcquire(r) \/ ReadRelease(r)
QNext  == Request \/ WriteAcquire \/ WriteRelease
          \/ \E r \in Reader : ReadAcquireQueued(r) \/ ReadRelease(r)

Releases == WF_vars(WriteRelease) /\ \A r \in Reader : WF_vars(ReadRelease(r))
WFSpec  == Init /\ [][Next]_vars  /\ Releases /\ WF_vars(WriteAcquire)
SFSpec  == Init /\ [][Next]_vars  /\ Releases /\ SF_vars(WriteAcquire)
QWFSpec == Init /\ [][QNext]_vars /\ Releases /\ WF_vars(WriteAcquire)

WriterProgress == (writer = "waiting") ~> (writer = "writing")
=============================================================================
SPECIFICATION WFSpec
CONSTANT Reader = {"q1", "q2"}
PROPERTY WriterProgress
  1. Run WFSpec with Reader = {"q1", "q2"}. Is WriteAcquire ever enabled in the loop TLC reports? Why doesn't weak fairness force it?
  2. Run SFSpec, first with Reader = {"q1"}, then with two readers. Explain why strong fairness helps with one reader and not with two.
  3. Run QWFSpec with two readers. What changed, and why is weak fairness enough now?
  4. PostgreSQL behaves like the fixed version: once a statement is waiting for an ACCESS EXCLUSIVE lock, later requests that conflict with it, even a plain SELECT's ACCESS SHARE, wait behind it. What does the fix cost while a long query holds the table, and why do migration guides recommend setting lock_timeout?

The migration starves under SFSpec with two queries. What has to change?

Hint

Write down, for each state of the loop, whether readers = {}. Weak fairness needs an action enabled continuously; strong fairness needs it enabled infinitely often. Neither says anything about an action that is never enabled.

Solution

1. TLC reports WriterProgress violated. In this run the writer requests the lock, then q2 acquires and releases forever. WriteAcquire is enabled in the states where readers = {} and disabled whenever q2 holds the lock. It is never continuously enabled, so weak fairness asks nothing of it. That's the flicker from {{ref:fairness}}.

2. With one query, SFSpec gives no error (5 distinct states). Each release by q1 makes the table free, so WriteAcquire is enabled infinitely often, and strong fairness forces it to happen. With two queries TLC again reports a violation:

q1 and q2 overlap, so one of them always holds the lock. readers is never empty, WriteAcquire is never enabled, and strong fairness, which talks only about enabled actions, doesn't apply. Each query still releases the lock infinitely often, so the release fairness holds too. No scheduler policy fixes this, because it isn't a scheduling problem.

3. No error (9 distinct states). ReadAcquireQueued refuses new shared locks while the writer is waiting. The current holders release because of their weak fairness, readers becomes empty and stays empty, and WriteAcquire is then continuously enabled, so weak fairness is enough. The fix changed the protocol, not the fairness.

4. While the migration waits behind one long-running query, every new query on that table waits behind the migration. To users, a slow report plus a migration looks like a table outage. Setting lock_timeout limits how long the migration waits in the queue: if it can't get the lock quickly, it fails and is retried later, and the other queries proceed. That's the same trade-off as the model: whoever waits blocks those behind it.

Problem 3●●○Networking

The alternating bit protocol over a link that reorders

Draws on {{ref:abp}}, {{ref:abspec}} and {{ref:messages}}.

A battery-powered temperature sensor (A) sends readings to a gateway (B) using the alternating bit protocol, the way the firmware team learned it. On the test bench, over a serial link that delivers in order, everything works. In the field the link is UDP, and UDP datagrams can be lost, duplicated, and delivered out of order. Now and then, the dashboard shows an old reading as new.

The module is the lesson's AB with one change: when Reorder is TRUE, a receiver may take any message in its channel, not just the head. PSl9_LinkSpec is ABSpec from {{ref:abspec}}, unchanged except for its name.

----------------------------- MODULE PSl9_Sensor ----------------------------
\* The alternating bit protocol between a sensor (A) and a gateway (B).
\* As module AB, except a receiver may take ANY message in its channel when
\* Reorder is TRUE, as over UDP. With Reorder = FALSE it is exactly AB.
EXTENDS Integers, Sequences
CONSTANTS Data, Reorder
Remove(i, seq) ==
  [j \in 1..(Len(seq) - 1) |-> IF j < i THEN seq[j] ELSE seq[j + 1]]
VARIABLES AVar, BVar, AtoB, BtoA
vars == <<AVar, BVar, AtoB, BtoA>>
TypeOK == /\ AVar \in Data \X {0, 1}
          /\ BVar \in Data \X {0, 1}
          /\ AtoB \in Seq(Data \X {0, 1})
          /\ BtoA \in Seq({0, 1})
Init == /\ AVar \in Data \X {1}
        /\ BVar = AVar
        /\ AtoB = <<>>
        /\ BtoA = <<>>
\* The positions a receiver may take a message from.
Pick(ch) == IF Reorder THEN 1..Len(ch) ELSE 1..1

ASnd == /\ AtoB' = Append(AtoB, AVar)
        /\ UNCHANGED <<AVar, BtoA, BVar>>
ARcv == /\ BtoA # <<>>
        /\ \E i \in Pick(BtoA) :
             /\ IF BtoA[i] = AVar[2]
                  THEN \E d \in Data : AVar' = <<d, 1 - AVar[2]>>
                  ELSE AVar' = AVar
             /\ BtoA' = Remove(i, BtoA)
        /\ UNCHANGED <<AtoB, BVar>>
BSnd == /\ BtoA' = Append(BtoA, BVar[2])
        /\ UNCHANGED <<AVar, BVar, AtoB>>
BRcv == /\ AtoB # <<>>
        /\ \E i \in Pick(AtoB) :
             /\ IF AtoB[i][2] # BVar[2]
                  THEN BVar' = AtoB[i]
                  ELSE BVar' = BVar
             /\ AtoB' = Remove(i, AtoB)
        /\ UNCHANGED <<AVar, BtoA>>
LoseMsg == /\ \/ /\ \E i \in 1..Len(AtoB) : AtoB' = Remove(i, AtoB)
                 /\ BtoA' = BtoA
              \/ /\ \E i \in 1..Len(BtoA) : BtoA' = Remove(i, BtoA)
                 /\ AtoB' = AtoB
           /\ UNCHANGED <<AVar, BVar>>
Next == ASnd \/ ARcv \/ BSnd \/ BRcv \/ LoseMsg
Spec == Init /\ [][Next]_vars

ABS == INSTANCE PSl9_LinkSpec
HighSafety == ABS!Spec
Bound == (Len(AtoB) <= 2) /\ (Len(BtoA) <= 2)
=============================================================================
SPECIFICATION Spec
CONSTANTS Data = {d1, d2}
          Reorder = TRUE
CONSTRAINT Bound
INVARIANT TypeOK
PROPERTY HighSafety
  1. Run it with Reorder = FALSE and check that you get the lesson's result.
  2. Run it with Reorder = TRUE, as shown. Report the length of the trace, and say which message is delivered out of order.
  3. In {{ref:abp}}, deleting B's bit test changed nothing on the in-order model. Which test does the reordered trace defeat, and why does a single bit not suffice?
  4. Describe a change to the messages that would let B tell a stale copy from a new value. What makes it hard to check with TLC on a finite model?

Why is the last step of the trace not allowed by ABS!Spec?

Hint

A keeps sending its current value, so old copies can stay in AtoB after the value has been acknowledged. With one bit, "different from my bit" means "new" only if nothing older than the previous value can still arrive.

Solution

1. No error, 216 distinct states, the same as module AB in {{ref:abp}}. With Reorder = FALSE, Pick is 1..1, so each receive takes the head, exactly as before.

2. TLC reports the action property of PSl9_LinkSpec violated after 7 states:

B acknowledges with bit 1 (state 2). A sends <<d1, 1>>, a copy of the value B already has (state 3), then receives the ack, picks the new value <<d1, 0>> (state 4), and sends it (state 5). B takes the newer message first, out of order (state 6). Then it takes the old <<d1, 1>>, sees a bit different from its own, and accepts it as new (state 7). The data happens to be d1 both times, but B has gone back to a stale copy of the previous value and treated it as a new one. With different readings, the dashboard shows an old reading as new, as in the field.

3. B's test: "the bit differs from mine, so this is new". On a first-in first-out channel, the old copies of the previous value were ahead of the new value in the channel, so by the time B accepts the new value they have been received or lost. With reordering, an old copy can arrive after the new value. Because the bit only alternates, a copy of the previous value carries the same bit as the next new value, so B can't tell them apart. One bit distinguishes a value only from its immediate neighbours.

4. Number each value with a counter instead of a bit, and have B accept only the number after the last one it accepted. That is the idea behind sequence numbers in protocols such as TCP. The counter grows without bound, so a TLC model needs another constraint on it, and you must say that the result holds only within that bound, just as with channel lengths in {{ref:abp}}. A counter that wraps around has the same weakness, if an old copy can survive until the counter comes back to its number.

Problem 4●●●Databases

Synthesis: does every booking eventually decide?

Draws on {{ref:fairness}}, {{ref:abp}}, {{ref:messages}}, {{ref:transactions}}, {{ref:ps-l6}}, {{ref:ps-l7}} and {{ref:ps-l8}}.

The trip booking from {{ref:ps-l6}} (flight, hotel and car RMs, one TM, two-phase commit) is moving to a network that loses messages. {{ref:ps-l8}} showed that its steps keep agreement, and {{ref:ps-l7}} showed how a coordinator crash blocks it. Product now asks the liveness question: does every reservation eventually end up committed or aborted, so that held seats, rooms and cars are always released?

In the module below, net holds messages in flight. Receiving or losing a message removes it, unlike msgs in TwoPhase. Messages are addressed to one RM, and the TM may abort at any time while undecided, which models a timeout. RMResend and TMResend are retries. Because net is a set of finitely many possible messages, the channel is bounded without a state constraint.

-------------------------- MODULE PSl9_BookingLive --------------------------
\* Two-phase commit for the trip booking over a network that loses messages.
\* net holds the messages in flight: receiving or losing one removes it, so
\* a lost message is gone unless someone sends it again. net is a set, so it
\* never holds more than the finitely many different messages.
CONSTANT RM
VARIABLES rmState, tmState, tmPrepared, net
vars == <<rmState, tmState, tmPrepared, net>>
Prep(r) == [type |-> "Prepared", rm |-> r]
Dec(r)  == [type |-> IF tmState = "commit" THEN "Commit" ELSE "Abort", rm |-> r]

Init == /\ rmState = [r \in RM |-> "working"]
        /\ tmState = "init"          \* then "commit" or "abort"
        /\ tmPrepared = {}
        /\ net = {}
-----------------------------------------------------------------------------
RMPrepare(r) == /\ rmState[r] = "working"
                /\ rmState' = [rmState EXCEPT ![r] = "prepared"]
                /\ net' = net \cup {Prep(r)}
                /\ UNCHANGED <<tmState, tmPrepared>>
RMChooseToAbort(r) == /\ rmState[r] = "working"
                      /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
                      /\ UNCHANGED <<tmState, tmPrepared, net>>
RMRcvCommit(r) == /\ [type |-> "Commit", rm |-> r] \in net
                  /\ rmState' = [rmState EXCEPT ![r] = "committed"]
                  /\ net' = net \ {[type |-> "Commit", rm |-> r]}
                  /\ UNCHANGED <<tmState, tmPrepared>>
RMRcvAbort(r) == /\ [type |-> "Abort", rm |-> r] \in net
                 /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
                 /\ net' = net \ {[type |-> "Abort", rm |-> r]}
                 /\ UNCHANGED <<tmState, tmPrepared>>
TMRcvPrepared(r) == /\ tmState = "init"
                    /\ Prep(r) \in net
                    /\ tmPrepared' = tmPrepared \cup {r}
                    /\ net' = net \ {Prep(r)}
                    /\ UNCHANGED <<rmState, tmState>>
\* The TM decides and sends one copy of the decision to every RM.
TMDecide ==
  /\ tmState = "init"
  /\ \/ /\ tmPrepared = RM
        /\ tmState' = "commit"
        /\ net' = net \cup {[type |-> "Commit", rm |-> r] : r \in RM}
     \/ /\ tmState' = "abort"                 \* e.g. after a timeout
        /\ net' = net \cup {[type |-> "Abort", rm |-> r] : r \in RM}
  /\ UNCHANGED <<rmState, tmPrepared>>
Lose == \E m \in net : /\ net' = net \ {m}
                       /\ UNCHANGED <<rmState, tmState, tmPrepared>>
\* Retries.
RMResend(r) == /\ rmState[r] = "prepared"
               /\ net' = net \cup {Prep(r)}
               /\ UNCHANGED <<rmState, tmState, tmPrepared>>
TMResend(r) == /\ tmState # "init"
               /\ net' = net \cup {Dec(r)}
               /\ UNCHANGED <<rmState, tmState, tmPrepared>>
-----------------------------------------------------------------------------
Core == \/ TMDecide \/ Lose
        \/ \E r \in RM : \/ RMPrepare(r) \/ RMChooseToAbort(r)
                         \/ RMRcvCommit(r) \/ RMRcvAbort(r) \/ TMRcvPrepared(r)
Next          == Core \/ \E r \in RM : RMResend(r) \/ TMResend(r)
NoTMRetryNext == Core \/ \E r \in RM : RMResend(r)
NoRMRetryNext == Core \/ \E r \in RM : TMResend(r)

Base == /\ WF_vars(TMDecide)
        /\ \A r \in RM : WF_vars(RMPrepare(r) \/ RMChooseToAbort(r))
WFRcv == \A r \in RM : /\ WF_vars(TMRcvPrepared(r))
                       /\ WF_vars(RMRcvCommit(r) \/ RMRcvAbort(r))
SFRcv == \A r \in RM : /\ SF_vars(TMRcvPrepared(r))
                       /\ SF_vars(RMRcvCommit(r) \/ RMRcvAbort(r))
RMRetry == \A r \in RM : WF_vars(RMResend(r))
TMRetry == \A r \in RM : WF_vars(TMResend(r))

WFSpec        == Init /\ [][Next]_vars /\ Base /\ WFRcv /\ RMRetry /\ TMRetry
SFSpec        == Init /\ [][Next]_vars /\ Base /\ SFRcv /\ RMRetry /\ TMRetry
NoTMRetrySpec == Init /\ [][NoTMRetryNext]_vars /\ Base /\ SFRcv /\ RMRetry
NoRMRetrySpec == Init /\ [][NoRMRetryNext]_vars /\ Base /\ SFRcv /\ TMRetry

Decided(r) == rmState[r] \in {"committed", "aborted"}
EveryoneDecides == \A r \in RM : <>Decided(r)
Consistent == \A r1, r2 \in RM : ~(rmState[r1] = "aborted" /\ rmState[r2] = "committed")
=============================================================================
SPECIFICATION SFSpec
CONSTANT RM = {"flight", "hotel", "car"}
INVARIANT Consistent
PROPERTY EveryoneDecides
CHECK_DEADLOCK FALSE
  1. Run WFSpec. Describe the loop in TLC's counterexample, and name the fairness condition that the loop escapes and why.
  2. Run SFSpec, as in the cfg shown. Report the result and connect it to the argument in {{ref:abp}}.
  3. Run NoTMRetrySpec and NoRMRetrySpec. One retry is essential and the other isn't. Which, and why?
  4. Add the coordinator crash of {{ref:ps-l7}}: after Crash, no TM action is enabled. Can any fairness condition on the TM's actions bring back EveryoneDecides? Answer, then check the quiz.

With the crash added, can fairness alone restore EveryoneDecides?

Hint

Every loop TLC can report under WFSpec must satisfy each WF condition. Look for a receive action that the loop keeps enabling with a retry and then disabling with Lose. For task 3, ask what the TM does if a Prepared message never arrives.

Solution

1. TLC reports EveryoneDecides violated, with a loop. In the run here the TM has decided abort, flight and car have aborted, and hotel is still prepared. Inside the loop, TMResend("hotel") puts an Abort for hotel into net, other steps follow, and Lose removes it before hotel takes it, again and again:

RMRcvAbort("hotel") is enabled for a while each time around and then disabled by Lose, so it is never continuously enabled. WF_vars(RMRcvCommit("hotel") \/ RMRcvAbort("hotel")) therefore asks nothing of it. The retries still happen as their weak fairness requires, so every condition of WFSpec holds on this behavior.

2. No error, 6560 distinct states. Retries make each receive action enabled infinitely often, and strong fairness on receives then forces it to happen. This is the argument for SF_vars(ARcv) and SF_vars(BRcv) in {{ref:abp}}: strong fairness doesn't stop losses, it says that a message sent again and again eventually gets through.

3. NoTMRetrySpec is violated: in the run here the TM aborts, Abort messages for flight and hotel are lost, and those two RMs stay prepared forever. Nothing would ever send them the decision again. NoRMRetrySpec gives no error (2933 distinct states). A lost Prepared message can't block anyone, because the TM may abort while it is undecided, and weak fairness on TMDecide makes it decide. Losing a vote costs a commit that could have happened. It doesn't cost liveness. The retry that matters is the one that carries the decision, because a prepared RM can't leave that state on its own, as {{ref:transactions}} showed.

4. No, as the quiz explains: a hidden run that adds Crash to SFSpec reports EveryoneDecides violated, ending with hotel prepared and the TM down. Fairness is an assumption about steps that can happen. It can't make a stopped process act. The booking can only be live if the decision survives the TM, either in a log that a restarted TM reads back, or in Paxos Commit's acceptors from {{ref:ps-l7}}, which needs a majority of them to keep working.
