Problem set 13: failures that outlive the step that caused them.

These problems practice the third Beyond part: durable and volatile state across a crash, leases and fencing tokens, and changing a cluster's membership. They draw on {{ref:idempotency}}, {{ref:fencing}} and {{ref:reconfiguration}}, and reach back to {{ref:messages}}, {{ref:replication}}, {{ref:fairness}} and {{ref:invariants}}.

Every module below is complete and was checked with TLC exactly as shown, so your state counts should match if your copy is identical. When a problem asks for the length of a trace, run TLC with one worker (-workers 1) so that its breadth-first search reports a shortest one. Each trace length counts the initial state.

Problem 1●○○Payments

An idempotency key that doesn't stop a double debit

Draws on {{ref:idempotency}}, {{ref:inventory}} and {{ref:ps-b1}}.

A wallet service stores balances in Postgres and exposes POST /debit. Following the convention of many payment APIs, the mobile app sends an Idempotency-Key header and, after a timeout, retries with the same key. The handler looks like this:

const prior = await db.query("SELECT response FROM idem WHERE key = $1", [key]);
if (prior.rows.length) return prior.rows[0].response;
await db.query("INSERT INTO ledger (account, amount) VALUES ($1, $2)", [acct, -amt]);
await db.query("INSERT INTO idem (key, response) VALUES ($1, 'ok')", [key]);
return "ok";

Each statement commits on its own. Support finds customers debited twice for one purchase, always during deploys, when a handler process can be killed mid-request. The module below models one key. ledger and stored are durable; each handler's pc is volatile, so Crash resets it. Receive can run whenever a handler is idle, so it stands for the first attempt and for every retry. Mode selects a design: NoTx is the code above, KeyThenDebit swaps the two INSERTs, TxAfterCheck wraps both INSERTs in one transaction after the SELECT, and KeyFirstTx runs one transaction that begins by inserting the key, which is the primary key of idem.

Select(h) == /\ pc[h] = "select" /\ Mode # "KeyFirstTx"
             /\ Go(h, IF stored THEN "reply" ELSE "write")

1. AtMostOnce fails. The trace is Receive(h1) (the request arrives), Select(h1) (no key), Debit(h1) (the ledger INSERT commits), Crash(h1) (the deploy kills the process before the second INSERT), then the retry: Receive(h1), Select(h1) finds no key, Debit(h1) and ledger = 2. The diagram draws it. The key exists to remember the debit, but the two are written by separate commits, so a crash can separate them.

2. OkMeansDebited fails, and AtMostOnce never does. With one handler: KeyFirst(h1) saves the key, Crash(h1), then the retry's Select finds the key and Reply tells the client "ok" with ledger = 0. The customer is told they paid and the merchant ships for free. This is the ID-first trap from {{ref:idempotency}}, and it is why the module checks two invariants: each design can pass one by failing the other.

3. One handler passes, two fail without any crash: both run Select while no key exists, then both Commit. A second handler is what a client timeout produces. The app gives up after ten seconds and retries, while the first attempt is still waiting on a slow query. A transaction makes the two INSERTs atomic, but the SELECT ran earlier, outside it. That is the stale check of {{ref:inventory}}.

4. KeyFirstTx passes with two handlers. The fix:

BEGIN;
INSERT INTO idem (key, response) VALUES ($1, 'ok');   -- key is the primary key
INSERT INTO ledger (account, amount) VALUES ($2, $3);
COMMIT;
-- on unique_violation: ROLLBACK, then SELECT the stored response and return it

Postgres enforces the unique index across concurrent transactions. If a second transaction inserts a key that an uncommitted transaction has already inserted, it waits; if the first commits, the second fails with a unique violation and writes nothing. So the outcome is always as if one whole transaction ran before the other, and a single atomic step models it. The check is no longer a separate read: the database performs it as part of the write. A crash at any point either rolls back both rows or leaves both.

This works because the debit is a row in the same database. If the effect were a charge at an external card network, no local transaction could include it, and you would need the provider's own idempotency contract, as {{ref:idempotency}} says.

Problem 2●●○Infrastructure

A garbage-collection pause outlives a lease

Draws on {{ref:fencing}}, {{ref:messages}}, {{ref:fifo}} and {{ref:ps-b1}}.

A nightly compaction job rewrites a table's data file in object storage. Two instances run for availability, and only the one holding a lease from a lock service may write. Each instance checks that its lease is still valid just before writing. One night instance c1 checks its lease, then stops for a long stop-the-world garbage-collection pause. Its lease expires, c2 gets the lease and writes, and then c1 wakes up and sends its write anyway. The file ends up with c1's stale data on top of c2's.

The module adds time explicitly, as {{ref:fencing}} recommends: now is the lock service's clock and Tick advances it. A lease lasts LeaseLen ticks. The pause is simply that any number of Tick steps may happen between Check(c) and Send(c). Writes travel over a network modeled as a set, so they can be delayed and reordered. Storage keeps log, the sequence of tokens whose writes it applied, so the property is an ordinary invariant. Fenced turns on the storage-side token check.

---------------- MODULE PSb3_Lease ----------------
EXTENDS Naturals, Sequences
CONSTANTS Clients, LeaseLen, MaxTime, Fenced, CheckAndSend
ASSUME Fenced \in BOOLEAN /\ CheckAndSend \in BOOLEAN /\ LeaseLen >= 1
VARIABLES now,      \* the lock service's clock
          holder,   \* the client the service granted the lease to
          expires,  \* the time at which that lease ends
          issued,   \* the highest fencing token issued so far
          token,    \* token[c]: the token client c received
          pc,       \* pc[c]: "idle", "checked" or "sent"
          net,      \* tokens of writes still on the network
          fence,    \* the highest token storage has accepted
          log       \* tokens of the writes storage accepted, in order
vars == <<now, holder, expires, issued, token, pc, net, fence, log>>
Tokens == 1..(MaxTime + 1)  \* at most one grant per tick, plus one at time 0

Init == /\ now = 0
        /\ holder = "none"
        /\ expires = 0
        /\ issued = 0
        /\ token = [c \in Clients |-> 0]
        /\ pc = [c \in Clients |-> "idle"]
        /\ net = {}
        /\ fence = 0
        /\ log = <<>>

Tick == /\ now < MaxTime
        /\ now' = now + 1
        /\ UNCHANGED <<holder, expires, issued, token, pc, net, fence, log>>

\* The service grants a lease when there is none or it has expired.
\* (Renewal is left out: a client never takes over its own lease.)
Acquire(c) == /\ holder = "none" \/ now >= expires
              /\ holder # c
              /\ pc[c] # "checked"
              /\ holder' = c
              /\ expires' = now + LeaseLen
              /\ issued' = issued + 1
              /\ token' = [token EXCEPT ![c] = issued + 1]
              /\ pc' = [pc EXCEPT ![c] = "idle"]
              /\ UNCHANGED <<now, net, fence, log>>

\* The client checks that its lease is still valid ...
Check(c) == /\ ~CheckAndSend
            /\ pc[c] = "idle" /\ holder = c /\ now < expires
            /\ pc' = [pc EXCEPT ![c] = "checked"]
            /\ UNCHANGED <<now, holder, expires, issued, token, net, fence, log>>
\* ... and later (after a pause of any length) sends its write.
Send(c) == /\ pc[c] = "checked"
           /\ net' = net \cup {token[c]}
           /\ pc' = [pc EXCEPT ![c] = "sent"]
           /\ UNCHANGED <<now, holder, expires, issued, token, fence, log>>
\* The variant with no gap between the check and the send.
CheckSend(c) == /\ CheckAndSend
                /\ pc[c] = "idle" /\ holder = c /\ now < expires
                /\ net' = net \cup {token[c]}
                /\ pc' = [pc EXCEPT ![c] = "sent"]
                /\ UNCHANGED <<now, holder, expires, issued, token, fence, log>>

\* Storage receives a write. With fencing it refuses old tokens.
Deliver(t) == /\ t \in net
              /\ net' = net \ {t}
              /\ IF Fenced /\ t < fence
                    THEN UNCHANGED <<fence, log>>
                    ELSE /\ log' = Append(log, t)
                         /\ fence' = IF t > fence THEN t ELSE fence
              /\ UNCHANGED <<now, holder, expires, issued, token, pc>>

Next == \/ Tick
        \/ \E c \in Clients : Acquire(c) \/ Check(c) \/ Send(c) \/ CheckSend(c)
        \/ \E t \in Tokens : Deliver(t)
Spec == Init /\ [][Next]_vars

\* Storage never applies an older lease's write after a newer one.
WritesInLeaseOrder ==
    \A i, j \in 1..Len(log) : i < j => log[i] <= log[j]
====================================================

  2. Someone proposes removing the pause window: check the lease and send the write in one step (CheckAndSend = TRUE). Predict whether that fixes the bug, then run it. What takes the pause's place in the trace?

With Fenced = TRUE, c2 holds token 2 but has not written yet. Can storage still accept c1's write with token 1?

Hint

A check that was true when it ran tells you nothing about the moment the write lands. Ask where the write is between the check and the moment storage applies it. For task 4, look at which variable remembers the past.

Solution

1. WritesInLeaseOrder fails with an 11-state trace. Acquire(c1) at time 0 gives token 1 and expires = 2. Tick to 1, then Check(c1): the lease is valid, since 1 < 2. Tick to 2: the lease has now expired, and c1 has not written. That gap is the pause. Send(c1) puts token 1 on the network. Acquire(c2) gives token 2, c2 checks and sends, and storage applies Deliver(2) and then Deliver(1): log = <<2, 1>>. The diagram draws this.

2. It still fails, now with a 9-state trace: Acquire(c1), Tick, CheckSend(c1), Tick, Acquire(c2), CheckSend(c2), Deliver(2), Deliver(1). The write leaves c1 while the lease is valid, but it waits in net while time passes. To storage, a paused process and a slow message look the same, which is the point {{ref:fencing}} makes. No client-side check can close a gap that lies after the client.

3. No error in either run: 186 distinct states with CheckAndSend = FALSE and 124 with TRUE. Storage drops token 1 because its fence is already 2.

4. log is a history variable: it records every accepted write, in order. "Never accepted a lower token after a higher one" is then a fact about the current value of log, so a state predicate can express it. The fence alone forgets the past, so with only fence you need an action property that compares two states. Both work. The history version gives a trace that ends with the evidence on screen.

The model still leaves things out: the clocks of c1 and c2 do not appear, because the lock service's clock decides expiry, and renewals are omitted. Fencing makes those questions matter less for safety: the order of writes no longer depends on any clock being right.

Problem 3●●○Distributed databases

Grow a three-node cluster to five

Draws on {{ref:reconfiguration}}, {{ref:replication}}, {{ref:sets}} and {{ref:ps-l7}}.

A configuration store runs on nodes A, B and C and decides with majority quorums. Load is growing and the team wants five nodes. One engineer edits the member list from three to five in one step. Another says that is unsafe and proposes two steps, adding D and then E, "because the old and new majorities of each step overlap". Before arguing, measure. The first module checks quorum overlap between two fixed memberships, using Init as a search over pairs of quorums.

---------------- MODULE PSb3_Quorums ----------------
EXTENDS Naturals, FiniteSets
CONSTANTS Old, New
Majorities(S) == {Q \in SUBSET S : 2 * Cardinality(Q) > Cardinality(S)}
VARIABLES q1, q2   \* an old-configuration quorum and a new one
InitAll == /\ q1 \in Majorities(Old)
           /\ q2 \in Majorities(New)
InitDisjoint == InitAll /\ q1 \cap q2 = {}
Next == UNCHANGED <<q1, q2>>     \* only the initial states matter
Overlap == q1 \cap q2 # {}
=====================================================
INIT InitAll
NEXT Next
CONSTANTS Old = {"A", "B", "C"}
          New = {"A", "B", "C", "D", "E"}
INVARIANT Overlap

In the "3to4to5" plan every consecutive pair of memberships has overlapping majorities. Why can it still decide two values?

Hint

Overlap is a fact about two particular quorums. In task 3, ask which two quorums actually decided, not which configurations are adjacent. For task 4, a decided value must be present wherever the next configuration's quorums can look.

Solution

1. {A, B} is a majority of three, and {C, D, E} is a majority of five; they are disjoint. For four nodes a majority has 3 members, and 2 + 3 > 4 means any old majority of 2 and new majority of 3 must share a node among the four, so no disjoint pair exists.

2. With five nodes TLC reports Overlap violated by an initial state, q1 = {"A", "B"} and q2 = {"C", "D", "E"}. With four, no error on 20 distinct states, which is every pair: 4 majorities of {A, B, C} times 5 of {A, B, C, D}. With InitDisjoint, five nodes give 3 distinct states and four give 0.

3. In the chain, A and B store X and C stores Y. X is decided in configuration 1 by {A, B}. Activate moves to {A, B, C, D}; D stores Y, so Y has 2 of 4, not a majority, and nothing is wrong yet. Activate again; E stores Y, and in configuration 3 Y holds C, D, E: 3 of 5, decided. The diagram shows that {A, B} and {C, D, E} miss each other. Each step's majorities did overlap. But the overlap argument from {{ref:replication}} only protects a decision if the quorum that made it intersects the quorum that might contradict it. Here those quorums are two configurations apart.

4. The guard says: switch to the next configuration only when a majority of it already stores every decided value. Then any quorum of the new configuration meets a node that holds X, and that node can never store Y. Applied at each step, the evidence is carried forward one configuration at a time, which repairs the chain. Raft's single-server changes rely on a similar fact supplied by the log. A change starts only after the previous configuration entry is committed in its configuration, and a log is ordered, so a majority that stores that entry also stores every entry before it. "Add one node at a time" is safe only together with that rule, which is the exercise in {{ref:reconfiguration}} made concrete.

Problem 4●●●Microservices

Ship every order once: the transactional outbox

Synthesis. Draws on {{ref:idempotency}}, {{ref:messages}}, {{ref:fairness}}, {{ref:invariants}} and {{ref:ps-l6}}.

A checkout service writes orders to Postgres. A shipping service prints a label for each order it hears about through a message broker. The first version commits the order and then publishes an OrderPlaced event, and some orders never ship: the process died between the commit and the publish. This is a dual write, two systems updated by separate steps. The team switches to a transactional outbox. The order and an outbox row are inserted in one transaction, and a relay process reads outbox rows, publishes them, and deletes them afterward. The broker delivers at least once. The shipping service deduplicates by inserting the order ID into a processed table in the same transaction that creates the label.

The broker is modeled as a set that Consume never removes from, as in {{ref:messages}}. That covers redelivery, the same idea you used for at-least-once delivery in {{ref:ps-l6}}. MaxCrashes bounds how many process crashes can happen. Shipped is the liveness requirement: every committed order eventually gets a label.

FairSpec == Spec /\ Fairness

OneLabel == \A o \in Orders : labels[o] <= 1
NoLostEvent == \A o \in orders :
    o \in outbox \/ o \in broker \/ handler[o] = "publish"
Shipped == \A o \in Orders : (o \in orders) ~> (labels[o] >= 1)
====================================================
SPECIFICATION FairSpec
CONSTANTS Orders = {o1, o2}
Mode = "Outbox"
Dedup = TRUE
MaxCrashes = 1
INVARIANT OneLabel
INVARIANT NoLostEvent
PROPERTY Shipped
CHECK_DEADLOCK FALSE
  1. Run Mode = "DualWrite", Dedup = TRUE with PROPERTY Shipped. Read TLC's counterexample, including its last line. Then check the same design with INVARIANT NoLostEvent instead, and compare the two traces.
  2. Run Mode = "Outbox", Dedup = FALSE with both invariants. Which fails? A relay crash between publish and delete is the obvious source of duplicates. Is it in TLC's trace? Explain.
  3. Run the configuration shown, with the outbox and deduplication. Report the distinct states.
  4. Remove one conjunct of Fairness at a time and rerun Shipped. Which conjunct can go? For the others, describe the behavior TLC reports.
  5. Why must crashes be bounded for Shipped to hold, and what would you assume about a real relay instead?

Which conjunct of Fairness can you remove from the outbox design and still have Shipped?

Hint

A liveness failure ends in a state the system can stay in forever. Ask what fact about that state already shows the order is lost: that fact is a safety property you can check much sooner. For task 2, adding an element to a set that already contains it changes nothing.

Solution

1. Shipped is violated: Place(o1), Crash (the handler dies before publishing), Place(o2), Publish(o2), Consume(o2), then "Stuttering". The behavior stays forever in a state where o1 is committed and nothing will ever ship it. Fairness cannot help, because no action that could deliver o1 is enabled. NoLostEvent says every committed order is in the outbox, in the broker, or about to be published by a live handler. It fails after 3 states: Place(o1), Crash. This is the method of {{ref:invariants}}: find the state fact that explains why the good thing will happen. A violation of it is found sooner, reads more easily, and needs no fairness.

2. OneLabel fails with Place(o1), RelayPublish(o1), Consume(o1), Consume(o1). No crash is needed. The broker never forgets an event, so any delivered event can be delivered again. A relay crash would republish o1, but adding o1 to broker again changes nothing, because duplicate sends and redeliveries look the same in a set model. That is why the model needs no separate duplicate action, and why the consumer, not the relay, must be idempotent. NoLostEvent holds: the outbox fixed the lost event.

3. No error, 84 distinct states, with OneLabel, NoLostEvent and Shipped all holding.

4. The fairness of Publish(o) can go: that action belongs to the dual-write design and is never enabled here. The run still finds 84 states and no error. Without WF_vars(RelayDelete), TLC's counterexample ends with the relay holding o2 forever after a republish, so RelayPublish(o1) is never enabled and o1 is never published. Without fairness on Consume, a crash makes the relay publish o2 twice and then everything stops, with o1's event sitting in the broker unconsumed. Each fairness condition is a claim about a real process: the relay keeps polling, and the consumer keeps reading.

5. If the relay could crash after every publish, forever, then RelayDelete would never happen, and o2 would block o1 indefinitely. Real systems assume that crashes eventually stop long enough for progress, or that a supervisor restarts the relay and it eventually completes a cycle. MaxCrashes is a finite stand-in for "finitely many crashes"; it is an assumption, not a fact about the relay. Notice too where exactly-once holds. Labels are at most once because the label row and the processed row commit together. If printing were an external call, you would be back in Problem 1.
