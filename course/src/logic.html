List the cases instead of nesting them.

The IF formula from {{lesson:program}} works, but it won't scale. Using “or” and “and” as bulleted lists turns the same formula into a tree you can read at a glance, and that form is how nearly every spec in this course is written.

From IF to “or”

Call the two THEN formulas A and B. The IF formula is true in exactly two cases: pc = "start" and A are both true, or pc = "middle" and B are both true. So the same formula can be written with “or,” which is || in some programming languages, ∨ in math, and \/ in ASCII. The final FALSE is no longer needed, because when pc is "done" neither case holds.

((pc = "start")  /\ A)
\/ ((pc = "middle") /\ B)

Now put A and B back, drop the parentheses that no longer help, and use the form TLA+ provides for lists. An extra /\ in front of the first item turns the items into a bulleted list, with a line per item. The list ends at the first token to the left of its bullets, so no closing parenthesis is needed. \/ works the same way:

Next == \/ /\ pc = "start"
           /\ i' \in 0..1000
           /\ pc' = "middle"
        \/ /\ pc = "middle"
           /\ i' = i + 1
           /\ pc' = "done"

This is what the tree at the top of the lesson shows. The outer \/ column is the root, with one branch for each case. Each /\ column is a node that requires all its lines. Indentation carries the structure, and widely separated matching parentheses are gone.

It is still a formula

The formula may look like commands, but it isn't. The order of lines carries no meaning, because \/ and /\ are commutative, meaning order makes no difference: swapping the two cases, or moving pc' = "middle" to the top of its list, yields an equivalent formula. The = means equality as in 2 + 2 = 4, while C's = means assignment, which isn't so simple.

The C code may look simpler because it is familiar, but compare the two on what someNumber() stands for. In the formula, nondeterminism takes a single line: i' \in 0..1000. Common programming languages were not designed to express this. We need it because we can't predict the order in which things happen in a real system, and in the math it is easy.

The complete spec

A spec lives in a module. The module name matches the file name. EXTENDS Integers imports arithmetic operators such as + and ... VARIABLES declares the variables. Identifiers must be defined or declared before they are used. Init and Next are only conventional names, but use them.

--------------- MODULE SimpleProgram ---------------
EXTENDS Integers
VARIABLES i, pc

Init == (pc = "start") /\ (i = 0)

Next == \/ /\ pc = "start"
           /\ i' \in 0..1000
           /\ pc' = "middle"
        \/ /\ pc = "middle"
           /\ i' = i + 1
           /\ pc' = "done"
====================================================

Decomposing with definitions

A real next-state formula can run to hundreds or thousands of lines. Math has a simple way to split it up: definitions. This spec doesn't need splitting, but you can see the method by naming the two cases. You could call them Fred and Mary, but descriptive names are better:

Pick == /\ pc = "start"
        /\ i' \in 0..1000
        /\ pc' = "middle"

Add1 == /\ pc = "middle"
        /\ i' = i + 1
        /\ pc' = "done"

Next == Pick \/ Add1

This Next is completely equivalent to the earlier one. We checked with TLC, and all three versions, the IF form, the bulleted form, and this one, produce the same 2003 states. The diagram shows why the names help: they name kinds of step, so you can label every arrow in the state graph.

Worked rules for a shopping cart

A cart can be submitted only when it contains items, the customer has accepted the terms, and the goods are in stock. Define the rule before attaching any step to it, to separate “may this happen?” from “what changes if it does?” Here, items, termsAccepted, and inStock are variables.

Eligible == /\ items > 0
            /\ termsAccepted

CanCheckout == /\ Eligible
               /\ inStock

In the diagram, the cart has items and the terms are accepted, so Eligible is true. But inStock is false, so CanCheckout is false.

The implication trap

P => Q is true whenever P is false. Take the module this cart comes from, where ordered records that checkout happened, and the claim ordered => termsAccepted. It holds in the checked model, but note what that claim would do in a model where checkout never happens: it would hold there too, since ordered is always false. A check that passes because its left side never occurs is called vacuous. An implication doesn't make Q happen, and it doesn't show that P ever happens.

Predict: with items = 2, termsAccepted = FALSE, inStock = TRUE, what are Eligible and CanCheckout?

Both false. Eligible fails on the terms, and CanCheckout includes Eligible. Being in stock can't make up for a missing requirement in a conjunction.
