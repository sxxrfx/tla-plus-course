Find the fact that makes the guarantee inevitable.

Since {{lesson:tcommit}} you have used invariants like TCConsistent, and TLC checks them by visiting every reachable state. Now ask a stronger question: why does the invariant hold? The answer is usually a larger fact, one that holds even in states no behavior reaches.

An invariant holds in all reachable states. An inductive invariant Inv also survives every Next step from any state satisfying it, including states Init never reaches. In the diagram, Inv is the blue box: no arrow leaves it. That is the condition that replaces walking an unbounded graph with one local argument. There are three obligations:

\* Proof obligations, not a standalone module:
Init => Inv
Inv /\ [Next]_vars => Inv'
Inv => Safety

First establish Inv initially. Then show every allowed step preserves it. Finally show it implies what you wanted. For a state predicate, stuttering preserves truth automatically, so the middle line is often written with Next alone.

Exercise: what if Inv is so strong that Init does not imply it?

It cannot establish the intended theorem. A preservation argument about an unreachable region says nothing about your actual initial states. Check the base case before the step case.

Worked example: money in transit

An app moves one unit from Alice to Bob through a worker. Debit and Credit are separate actions, as the steps in {{lesson:inventory}} were.

---------------- MODULE Transfer ----------------
EXTENDS Naturals
VARIABLES alice, transit, bob
vars == <<alice, transit, bob>>
Init == alice = 2 /\ transit = 0 /\ bob = 0
Debit == /\ alice = 2           \* one transfer only
         /\ alice' = alice - 1
         /\ transit' = transit + 1
         /\ UNCHANGED bob
Credit == /\ transit > 0
          /\ transit' = transit - 1
          /\ bob' = bob + 1
          /\ UNCHANGED alice
Next == Debit \/ Credit
Spec == Init /\ [][Next]_vars
TypeOK == /\ alice \in 0..2
          /\ transit \in 0..2
          /\ bob \in 0..2
Naive == alice + bob = 2
BobAtMostOne == bob <= 1
Inv == TypeOK /\ alice + transit + bob = 2
\* Start TLC from every state a candidate allows:
IndCandidate == TypeOK /\ BobAtMostOne
=================================================

The natural first guess fails: TLC reports Naive (alice + bob = 2) violated after one step. The money is not lost, it is just somewhere your invariant was not looking. Inv counts the third place and holds, and the normal check visits only the 3 states in the green box.

Asking TLC whether a fact is inductive

TLC can test preservation directly on a finite type. Replace the initial predicate with the candidate, so it starts from every state the candidate allows.

INIT Inv
NEXT Next
INVARIANT Inv
CHECK_DEADLOCK FALSE

This run starts from all 6 states in the blue box, and TLC reports no error, so Inv is inductive on this finite set of values. Now try BobAtMostOne. It holds in all 3 reachable states, so as an invariant it passes. Starting from TypeOK /\ BobAtMostOne instead, TLC finds the dashed arrow: from alice = 0, transit = 1, bob = 1, Credit gives bob = 2.

A counterexample like that one is called a counterexample to induction. It does not mean the system has a bug, because that start state is unreachable. It means your fact is too weak to explain itself, and you must strengthen it or give it up.

Predict: mutate Credit so it raises bob without lowering transit. And Debit so it lowers alice without raising transit. Does Inv catch both?

Yes, and differently. TLC’s trace for the bad Credit has total 3, after two steps; for the bad Debit it has total 1, after one. These are different bugs caught by one conservation equation. With several transfers, identify them separately: one scalar transit cannot tell you that one transfer was credited twice and another never.

Hand-check the argument too. Init gives 2 + 0 + 0 = 2. In Debit, subtracting and adding one cancel. In Credit, the guard transit > 0 keeps the result in type, and they cancel again. Each action moves a unit’s location and keeps the total.

Back to the ticket

NoOverselling from {{lesson:inventory}} looks like the property you want, and it is true. Is it inductive? Start TLC from all states satisfying TypeOK /\ NoOverselling, and it reports a violation from remaining = 1, booked = {B}, then Reserve(A).

The red edges start where stock and bookings disagree. The missing fact relates the two variables: Conservation, remaining + Cardinality(booked) = 1. Start from TypeOK /\ Conservation and TLC finds 3 states and no error. Because remaining is at least 0, Conservation also implies at most one booking. Relational facts like this one usually do more work than bounding each variable alone.

This check covers only the values you gave TLC. It can refute a candidate quickly, and a pass is good evidence, but it is not a theorem for all values. {{lesson:proofs}} builds the proof itself.

Predict: does this conservation proof establish that Bob eventually receives the money?

No. The behavior may stay at alice = 1, transit = 1, bob = 0 forever. Credit is possible but not required. Safety says where the money is; reaching the destination needs the fairness of {{lesson:fairness}}.
