First say what a channel should accomplish.

You now have two ways to read a spec: as what a system may do, and as a formula another spec can imply. The next lessons use one small protocol for sending data across a channel that loses messages. Before seeing how it works, you write what it should achieve, and that takes one more data structure: sequences.

Finite sequences

A finite sequence is another name for a tuple, and programmers would call it a list. <<-3, "xyz", {0, 2}>> has length 3. A sequence of length N is simply a function with domain 1..N, so <<-3, "xyz", {0, 2}>>[2] is "xyz", and [i \in 1..N |-> i^2] is the sequence of the first N squares. The standard module Sequences defines the operators. These values come from TLC, using the evaluation trick described below:

Seq(S) is the set of all finite sequences with elements in S. It is infinite: Seq({3}) contains <<>>, <<3>>, <<3, 3>>, and so on. Sequences are the last commonly used data type you need.

The protocol will need to delete a message from the middle of a channel. No built-in does this, so define it, by writing a function on a shorter domain and working out what each position holds:

Remove(i, seq) ==
  [j \in 1..(Len(seq) - 1) |-> IF j < i THEN seq[j] ELSE seq[j + 1]]

A definition like that deserves a test, and there's no need for a behavior to run one. In the Toolbox, type an expression into a model's results page and TLC computes it. In a plain module, write ASSUME PrintT(Remove(3, <<1, 2, 3, 4>>)) after EXTENDS TLC, and TLC prints <<1, 2, 4>> while checking assumptions.

The Cartesian product

S \X T is the set of all pairs <<a, b>> with a in S and b in T. So (1..3) \X {"a", "b"} has six elements. Keep the parentheses. Without them it parses as 1..(3 \X {"a", "b"}), and TLC stops with an error. S \X T \X U is the obvious set of triples.

What must the protocol accomplish?

Sender A sends a sequence of data items to receiver B. An obvious model uses two variables, AVar and BVar. A sets AVar to the string it wants to send. Then B sets BVar equal to it. Watching that, you would see Fred, Mary, Ted, Ann. But suppose A meant to send Mary twice. Nothing would change, and a value can't have been sent if nothing changed.

So something must change when a value is sent again. The lecture lets each variable be a pair: the value, and one bit that flips every time A chooses a value. The top figure sends Fred, Mary, Mary this way. The spec is short:

------------------------------- MODULE ABSpec -------------------------------
EXTENDS Integers
CONSTANT Data
VARIABLES AVar, BVar

TypeOK == /\ AVar \in Data \X {0, 1}
          /\ BVar \in Data \X {0, 1}

vars == <<AVar, BVar>>

Init == /\ AVar \in Data \X {1}
        /\ BVar = AVar

A == /\ AVar = BVar
     /\ \E d \in Data : AVar' = <<d, 1 - AVar[2]>>
     /\ BVar' = BVar

B == /\ AVar # BVar
     /\ BVar' = AVar
     /\ AVar' = AVar

Next == A \/ B

Spec == Init /\ [][Next]_vars

Inv == (AVar[2] = BVar[2]) => (AVar = BVar)

FairSpec == Spec /\ WF_vars(Next)
=============================================================================

The last line uses WF, which {{lesson:fairness}} explains; ignore it for now. 1 - AVar[2] complements the bit. A step of A needs the two variables equal, because B must have received the last value. A step of B needs them unequal and copies. There's no channel, no message, and no retransmission here, since those belong to how, not what.

Check it

Type correctness alone doesn't make a spec right. To find errors, check formulas that ought to be invariants. Here that is Inv: if the bits agree, the pairs agree. Make sure you see why before running it. The bits differ exactly between an A step and the following B step.

SPECIFICATION Spec
CONSTANT Data = {d1, d2, d3}
INVARIANT TypeOK
INVARIANT Inv

d1, d2, d3 are model values, as you used for RM. TLC finds no error: 39 states generated, 24 distinct, depth 4.

Predict: where do the 24 states come from?

There are 3 × 2 = 6 possible pairs. When the variables agree there is one state per pair, giving 6. When they differ, the bits must differ, by Inv, so AVar is any of 6 pairs and BVar any of the 3 pairs with the other bit, giving 18. And 6 + 18 = 24.

A has just set AVar to <<"Mary", 1>> and B has not copied it. Can A now replace it with <<"Ted", 0>>?

Like every spec so far, Spec says only what may happen. A behavior may stop right after A sets AVar, so nothing is ever received. {{lesson:fairness}} fixes that.
