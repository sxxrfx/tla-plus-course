Reduce the model without removing the question.

In {{lesson:transactions}}, a symmetry set took three-manager two-phase commit from 288 states to 80. Now you look at what happens as the model grows, and at when a reduction quietly stops testing what you meant to test.

Here are real TLC runs of the same two-phase commit spec. If each of n independent variables has k values, their product has kⁿ combinations, and per-process state, messages and histories add dimensions quickly. Good modeling is not a contest to reproduce production. It is a search for the smallest model that still permits the failure you suspect.

Four reductions with different meanings

TechniqueWhat changesQuestion to ask
Smaller constantsChecks a smaller instanceCan the bug require another participant or round?
AbstractionRemoves distinctionsAre all relevant concrete behaviors represented?
SymmetryCollapses interchangeable identitiesAre those identities interchangeable in the properties too?
State and action constraintsLimits explorationWhich paths have been excluded?

A constraint, written CONSTRAINT P in the config, tells TLC not to explore states where P is false. An invariant is a property you test. A constraint prunes the experiment.

A distinguished leader, a fixed account, or a process-specific progress formula breaks the symmetry you assumed. Do not combine symmetry with liveness checks unless your tools and reasoning explicitly support it; default to unreduced liveness runs.

Worked example: a CDN invalidation that loses a race

A content service publishes a new article version and invalidates cached copies. The origin serves version 2, but a fetch for version 1 began earlier. One key, one edge cache, two versions and one delayed fetch are enough.

---------------- MODULE CdnRace ----------------
EXTENDS Naturals
CONSTANT MaxVersion
VARIABLES origin, cached, inflight, floor
vars == <<origin, cached, inflight, floor>>
Init == /\ origin = 1
        /\ cached = 1          \* 0 means no cached copy
        /\ inflight = {}
        /\ floor = 0           \* invalidated through this version
Fetch == /\ origin \notin inflight
         /\ inflight' = inflight \cup {origin}
         /\ UNCHANGED <<origin, cached, floor>>
Publish == /\ origin < MaxVersion
           /\ origin' = origin + 1
           /\ UNCHANGED <<cached, inflight, floor>>
Invalidate == /\ floor < origin - 1
              /\ floor' = origin - 1
              /\ cached' = IF cached <= floor' THEN 0 ELSE cached
              /\ UNCHANGED <<origin, inflight>>
Fill(v) == /\ v \in inflight
           /\ v > floor
           /\ cached' = v
           /\ inflight' = inflight \ {v}
           /\ UNCHANGED <<origin, floor>>
Discard(v) == /\ v \in inflight
              /\ v <= floor
              /\ inflight' = inflight \ {v}
              /\ UNCHANGED <<origin, cached, floor>>
Next == Fetch \/ Publish \/ Invalidate
        \/ \E v \in inflight: Fill(v) \/ Discard(v)
Spec == Init /\ [][Next]_vars
NotResurrected == cached = 0 \/ cached > floor
Fresh == cached = 0 \/ cached = origin
================================================

Here floor records that everything through that version is invalidated, and Fill rejects anything at or below it. A deletion-only design remembers nothing, so it cannot tell a stale fill from a fresh one. Delete the guard v > floor to get that design, and run these experiments:

The two runs in quotation marks are false comfort. With one version nothing can be stale. The constraint case looks more reasonable: Fresh sounds like just the states you care about. But it removes the first state after Publish, so TLC reports “No error has been found” on the buggy design.

Only 2 states explored, on a model with at least two actions you meant to exercise, is the warning sign. Whenever you add a bound, compare what the run visited with what you expected.

Exercise: you bound retries to one and a duplicate-charge bug disappears. What next?

Check whether at least two deliveries are needed to trigger it. Restore that behavior, then reduce some unrelated dimension. A useful reduction preserves the causal path to the property of interest.

The useful reduction here keeps that path and removes the rest. One key is enough, since a thousand URLs add volume but no new cause. Two versions distinguish stale from fresh. A second edge becomes necessary only when the property concerns divergence between edges. This is a causal argument for the bound, not proof that every other bug fits it. The guarded model at MaxVersion 2, 3, 4 and 5 has 18, 82, 290 and 898 states, so raise it to check your argument, while you can still afford to.

Measure the right work

Track distinct states, generated states, search depth and whether the search finished. TLC stores a fingerprint of each visited state, which is a hash, not the state. Two different states could collide, and one would then go unexplored. So it prints an estimate, for example calculated (optimistic): val = 1.3E-13 for the 898-state run. This is why a completed run is a search, not a symbolic proof. Simulation mode (-simulate) samples behaviors and can find bugs in models too large to finish, but a sample with no violation is weaker evidence than a completed search.

Transfer exercise: can you remove message identities from this model?

Possibly for the single delayed response, but justify it. If duplicate delivery or retry identity affects whether the cache fills twice, keep enough identity to distinguish those events. Remove fields only after explaining why two states differing solely in that field have equivalent behavior for the property you are checking.
