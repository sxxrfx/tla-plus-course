Problem set 11: decide where one step ends.

Four concurrency problems. In each one the bug or the fix is a step boundary: a statement that is or isn't atomic, a check separated from its write, a counter published before its data, a lock that expires. You'll write PlusCal, read traces by their pc values, state a queue contract as a refinement, and ask the fairness questions of lecture 9 about a lock.

PlusCal modules are shown as you write them, before translation. Translate each one with java -cp tla2tools.jar pcal.trans -nocfg File.tla or your editor's command, then run TLC. Every count below is from the translated module, run exactly as shown.

Problem 1●○○Databases

Two refunds, one lost

Draws on {{ref:pluscal}}, {{ref:inventory}} and {{ref:program}}.

A payments service credits refunds to a wallet stored in Postgres. The handler reads the balance, adds the refund in application code, and writes the result back:

SELECT balance FROM accounts WHERE id = 1;          -- returns 100
UPDATE accounts SET balance = 110 WHERE id = 1;     -- 100 + 10, computed in the app

A customer returns two items and gets two refunds of 10, handled by two requests at the same moment. Support finds the wallet at 110 instead of 120. Each SQL statement is atomic on its own, so each becomes one labeled step, and the value carried between them becomes a process variable:

---------------- MODULE PSb1_Wallet ----------------
EXTENDS Naturals, FiniteSets
CONSTANT Clients
(*--algorithm Wallet
variables balance = 100;
define
    AllDone == \A c \in Clients : pc[c] = "Done"
    NoLostUpdate == AllDone => balance = 100 + 10 * Cardinality(Clients)
end define;
process Refund \in Clients
variable local = 0;
begin
Select:  \* SELECT balance FROM accounts WHERE id = 1
    local := balance;
Update:  \* UPDATE accounts SET balance = $1 WHERE id = 1, with $1 = local + 10
    balance := local + 10;
end process;
end algorithm; *)
====================================================
SPECIFICATION Spec
CONSTANT Clients = {A, B}
INVARIANT NoLostUpdate
  1. Translate and run it. Write down TLC's trace as a list of steps, and say at which step the refund was lost.
  2. Replace the two statements by one, UPDATE accounts SET balance = balance + 10 WHERE id = 1. Write it as one label and check it. Why is one label an honest model of that statement in Postgres?
  3. Keep two statements, but read with SELECT balance FROM accounts WHERE id = 1 FOR UPDATE, which locks the row until the transaction ends. Model the row lock with a variable holder and a Commit label that releases it. Check it with two clients and with three.

A teammate keeps a plain SELECT to read the balance, then runs SELECT … FOR UPDATE just before the UPDATE, still writing the value from the first read. Does that fix the lost refund?

Hint

For (c), put await holder = "none", holder := self and the read under one label, since SELECT … FOR UPDATE both waits for the lock and returns the row. A label starts a new atomic step, as in {{lesson:pluscal}}, so the waiting, locking and reading must not be split.

Solution

(a) TLC reports NoLostUpdate violated after five states, shown in the figure: Select(A), Select(B), Update(A), Update(B). The refund is lost at the second Select, when B reads a balance that A is about to change. The write that makes it visible comes two steps later. This is the {{lesson:pluscal}} LostUpdate race, with SQL statements as the steps. Without the invariant, the full graph has 13 distinct states.

(b) One label:

---------------- MODULE PSb1_WalletAtomic ----------------
EXTENDS Naturals, FiniteSets
CONSTANT Clients
(*--algorithm WalletAtomic
variables balance = 100;
define
    AllDone == \A c \in Clients : pc[c] = "Done"
    NoLostUpdate == AllDone => balance = 100 + 10 * Cardinality(Clients)
end define;
process Refund \in Clients
begin
Update:  \* UPDATE accounts SET balance = balance + 10 WHERE id = 1
    balance := balance + 10;
end process;
end algorithm; *)
==========================================================

TLC finds 4 distinct states and no error. One label is honest because of what Postgres does with that statement. An UPDATE locks the row it changes. Under the default isolation level, READ COMMITTED, a second UPDATE of the same row waits for the first transaction to finish, then re-evaluates its WHERE clause on the new row version and computes balance + 10 from it. So no other write can come between reading and writing the balance. The label is a claim about the database; it is only true because the database makes it true.

(c) With the row lock:

---------------- MODULE PSb1_WalletLock ----------------
EXTENDS Naturals, FiniteSets
CONSTANT Clients
(*--algorithm WalletLock
variables balance = 100, holder = "none";
define
    AllDone == \A c \in Clients : pc[c] = "Done"
    NoLostUpdate == AllDone => balance = 100 + 10 * Cardinality(Clients)
end define;
process Refund \in Clients
variable local = 0;
begin
Select:  \* SELECT balance FROM accounts WHERE id = 1 FOR UPDATE
    await holder = "none";
    holder := self;
    local := balance;
Update:  \* UPDATE accounts SET balance = $1 WHERE id = 1
    balance := local + 10;
Commit:  \* COMMIT releases the row lock
    holder := "none";
end process;
end algorithm; *)
========================================================

TLC finds no error: 13 distinct states with two clients, 46 with three (Clients = {A, B, C}). The lock makes Select wait while another client is between its read and its commit, so every read sees the latest committed balance. Note what the model assumes: every writer of this row uses FOR UPDATE. A plain SELECT doesn't take the lock and isn't blocked by it, which is why the quiz's version still fails (module PSb1_WalletLockLate, violation found).

Problem 2●●○Databases

Two passengers in seat 14C

Draws on {{ref:inventory}}, {{ref:pluscal}} and {{ref:tcommit}}.

An airline's seat picker checks whether a seat is free and then inserts a booking. Two passengers, Ada and Ben, click 14C at the same moment, and both boarding passes say 14C. The team's first answer is a unique constraint on the seat column: the database rejects a second row for 14C, whatever the application does. This problem checks that fix, and then the code around it.

---------------- MODULE PSb1_Seat ----------------
EXTENDS Naturals, FiniteSets
CONSTANT Users
(*--algorithm Seat
variables bookings = {}, told = [u \in Users |-> "waiting"];
define
    OneBooking == Cardinality(bookings) <= 1
    Honest == \A u \in Users : told[u] = "confirmed" => u \in bookings
end define;
process User \in Users
variables free = FALSE, inserted = FALSE;
begin
Check:   \* SELECT 1 FROM bookings WHERE seat = '14C'
    free := (bookings = {});
Insert:  \* INSERT INTO bookings (seat, user_id) VALUES ('14C', ...)
    if free then
        bookings := bookings \cup {self};
        inserted := TRUE;
    end if;
Reply:   \* the page the user sees
    told[self] := IF inserted THEN "confirmed" ELSE "taken";
end process;
end algorithm; *)
==================================================
SPECIFICATION Spec
CONSTANT Users = {A, B}
INVARIANT OneBooking Honest

told is what each passenger's page says. Honest says no page claims a booking the database doesn't have.

  1. Run it and give TLC's trace in terms of the labels.
  2. Model the unique constraint: the Insert step adds the row only if no row for 14C exists, and otherwise does nothing, leaving inserted false. (In Postgres the insert fails with a unique-violation error, which the application catches.) Check it.
  3. A teammate writes the reply as told[self] := IF free THEN "confirmed" ELSE "taken", since "we already checked the seat was free". Which invariant fails, and what does Ben see?
  4. With the constraint in place, delete the Check label and the free variable entirely. Does anything fail? What was the check for?

Which invariant fails for the teammate's reply in task (c)?

Hint

The constraint makes the test and the insert one indivisible decision, like moving remaining > 0 into Reserve in {{lesson:inventory}}. So the test belongs inside the Insert label. For (c), ask which value Ben's process holds in free when it replies.

Solution

(a) TLC reports OneBooking violated after five states: Check(A) and Check(B) both set free to TRUE, then Insert(A) and Insert(B) both add a row, leaving bookings = {A, B}. It is the split check and reserve from {{lesson:inventory}}.

(b) With the constraint:

---------------- MODULE PSb1_SeatUnique ----------------
EXTENDS Naturals, FiniteSets
CONSTANT Users
(*--algorithm SeatUnique
variables bookings = {}, told = [u \in Users |-> "waiting"];
define
    OneBooking == Cardinality(bookings) <= 1
    Honest == \A u \in Users : told[u] = "confirmed" => u \in bookings
end define;
process User \in Users
variables free = FALSE, inserted = FALSE;
begin
Check:
    free := (bookings = {});
Insert:  \* UNIQUE (seat): the INSERT fails if a row for 14C exists
    if free then
        if bookings = {} then
            bookings := bookings \cup {self};
            inserted := TRUE;
        end if;
    end if;
Reply:
    told[self] := IF inserted THEN "confirmed" ELSE "taken";
end process;
end algorithm; *)
========================================================

TLC finds 32 distinct states and no error. The inner test sits in the same label as the insert, because the database performs it atomically with the insert.

(c) Honest fails; OneBooking still holds. TLC's trace, shown in the figure: both check, Ada inserts, Ben's insert is rejected so his inserted stays false, and Reply(B) sets told[B] to "confirmed" while bookings = {A}. Ben sees a confirmation and arrives at a seat that is Ada's. The constraint protected the data, not the page. The reply must be based on the result of the step that decides, the insert, never on the check.

(d) Nothing fails (module PSb1_SeatNoCheck: 13 distinct states, both invariants hold):

---------------- MODULE PSb1_SeatNoCheck ----------------
EXTENDS Naturals, FiniteSets
CONSTANT Users
(*--algorithm SeatNoCheck
variables bookings = {}, told = [u \in Users |-> "waiting"];
define
    OneBooking == Cardinality(bookings) <= 1
    Honest == \A u \in Users : told[u] = "confirmed" => u \in bookings
end define;
process User \in Users
variables inserted = FALSE;
begin
Insert:  \* INSERT ... ; the unique constraint rejects a second row
    if bookings = {} then
        bookings := bookings \cup {self};
        inserted := TRUE;
    end if;
Reply:
    told[self] := IF inserted THEN "confirmed" ELSE "taken";
end process;
end algorithm; *)
=========================================================

Once the insert decides, the check decides nothing. It is still useful for the interface, for example to grey out seats that are already taken, but it is a hint. Postgres also offers INSERT … ON CONFLICT DO NOTHING, which reports zero rows inserted instead of raising an error; either way, the application has to read that result.

Problem 3●●○Algorithms

A lock-free ring buffer refines a bounded queue

Draws on {{ref:fifo}}, {{ref:pluscal}}, {{ref:refinement}} and {{ref:mutex}}.

A logging agent hands records from one producer thread to one consumer thread through a ring buffer: an array of N slots and two counters. tail counts records written and head counts records read, so tail - head records are waiting, and record number i lives in slot i % N. (a % b is the remainder, defined in Naturals.) There is no lock. Only the producer changes tail and only the consumer changes head. When the buffer is full the producer waits, which is the backpressure. The contract is the bounded FIFO queue of {{lesson:fifo}}, written here as its own module:

---------------- MODULE PSb1_Queue ----------------
EXTENDS Naturals, Sequences
CONSTANTS Values, Capacity
VARIABLE q
Init == q = <<>>
Enqueue(v) == /\ Len(q) < Capacity
              /\ q' = Append(q, v)
Dequeue == /\ Len(q) > 0
           /\ q' = Tail(q)
Next == (\E v \in Values : Enqueue(v)) \/ Dequeue
Spec == Init /\ [][Next]_q
===================================================

The producer sends 1, 2, …, K, so InOrder can check the order by value. The lines after the algorithm map the slots to the abstract queue.

---------------- MODULE PSb1_Ring ----------------
EXTENDS Naturals, Sequences
CONSTANTS N, K      \* N slots; the producer sends 1, 2, ..., K
(*--algorithm Ring
variables buf = [i \in 0..(N - 1) |-> 0], head = 0, tail = 0, got = <<>>;
define
    InOrder == \A i \in 1..Len(got) : got[i] = i
end define;
process Producer = "prod"
variable next = 1;
begin
P1: while next <= K do
P2:   await tail - head < N;        \* full: wait (backpressure)
      buf[tail % N] := next;        \* write the slot
P3:   tail := tail + 1;             \* publish it
      next := next + 1;
    end while;
end process;
process Consumer = "cons"
begin
C1: while Len(got) < K do
C2:   await tail > head;            \* empty: wait
      got := Append(got, buf[head % N]);
C3:   head := head + 1;             \* free the slot
    end while;
end process;
end algorithm; *)
\* Refinement: the occupied slots, oldest first, are the abstract queue.
Queued == [i \in 1..(tail - head) |-> buf[(head + i - 1) % N]]
Q == INSTANCE PSb1_Queue WITH Values <- 1..K, Capacity <- N, q <- Queued
QueueSpec == Q!Spec
==================================================
SPECIFICATION Spec
CONSTANTS N = 2
          K = 3
INVARIANT InOrder
PROPERTY QueueSpec
  1. Translate and run it. Which labeled steps map to Enqueue, which to Dequeue, and which to stuttering?
  2. Change the full test to await tail - head <= N. Run it with both checks, then with only INVARIANT InOrder. Which check fails first, and why earlier?
  3. Restore the test, and make the producer publish before writing: tail := tail + 1 under P2, then buf[(tail - 1) % N] := next under P3. What does each check report?
  4. Each label is atomic, and the labels of one process run in order. Which of these assumptions does a real CPU not give you for free?

In task (c), which check fails first?

Hint

The mapped queue only covers slots from head to tail - 1. Writing to slot tail % N is outside that range, unless the buffer is already full. For (d), think about what another core sees when one core writes buf and then tail.

Solution

(a) TLC finds no error: 96 states generated, 58 distinct. P3 (raise tail) maps to Enqueue(next), since the slot it exposes already holds next. C3 (raise head) maps to Dequeue. P2 writes a slot outside the occupied range, and C2 only copies the head into got, so they map to stuttering, as do the loop tests P1 and C1. This mapping is the one {{lesson:fifo}} hinted at: InOrder related the queue to an observer's history, and Queued says which part of the array is the queue.

(b) With both checks, TLC reports the action property of PSb1_Queue violated after nine states: the producer publishes 1 and 2, then, with two records unread, its P2 writes 3 into slot 0. The mapped queue goes from ⟨1, 2⟩ to ⟨3, 2⟩, which no queue step does. With InOrder alone, the trace has eleven states and ends with the consumer receiving 3 first, as in the figure. The refinement check sees the damage when it happens; the invariant sees it only when someone reads the result.

(c) The refinement check fails after three states: P1, then the early P2 makes tail = 1 while slot 0 still holds 0, so the mapped queue is ⟨0⟩. With InOrder alone, TLC needs five states: the consumer reads slot 0 before the producer writes it, and got = <<0>>. The order of the write and the publish is the whole algorithm.

(d) The model assumes each process's steps happen in program order as seen by the other process. Compilers and CPUs may reorder the writes to buf and tail, which turns the correct code into the bug in (c). Real ring buffers publish tail with a release store and read it with an acquire load, or use a language's atomic types, so that the order the model assumes is the order other threads see. The label structure is your statement of which orderings the code must guarantee.

Problem 4●●●Distributed systems

Guard the wallet with a Redis lock

Draws on {{ref:mutex}}, {{ref:pluscal}}, {{ref:fairness}}, Problem 1 of this set and {{ref:ps-l9}}.

Return to the wallet of Problem 1, but now it lives in a document store with no row locks, and workers on several servers apply refunds to it. The team guards the read-modify-write with a lock in Redis. A worker runs SET wallet:7:lock <worker id> NX, which sets the key only if it doesn't exist, retrying until it succeeds, and later deletes the key. committed counts writes, only so the invariant can say what the balance should be.

---------------- MODULE PSb1_RedisLock ----------------
EXTENDS Naturals, FiniteSets
CONSTANT Workers
(*--algorithm RedisLock
variables balance = 100, lock = "none", committed = 0;
define
    NoLostUpdate == balance = 100 + 10 * committed
    Holding == {w \in Workers : pc[w] \in {"Read", "Write", "Release"}}
    MutualExclusion == Cardinality(Holding) <= 1
end define;
fair process Worker \in Workers
variable local = 0;
begin
Acquire:  \* SET wallet:7:lock <worker id> NX
    await lock = "none";
    lock := self;
Read:
    local := balance;
Write:
    balance := local + 10;
    committed := committed + 1;   \* bookkeeping for the check only
Release:  \* DEL wallet:7:lock
    lock := "none";
end process;
end algorithm; *)
=======================================================
SPECIFICATION Spec
CONSTANT Workers = {A, B}
INVARIANT NoLostUpdate MutualExclusion
PROPERTY Termination
  1. Run it. Then let a worker crash at Release: either lock := "none"; or skip; end either;. What does TLC report, and why isn't it a liveness violation?
  2. Locks that outlive their owner are why Redis locks get an expiry: SET … NX PX 10000 deletes the key after 10 seconds. Drop the crash, and add a process that can expire the lock whenever it is held. Check MutualExclusion, then only NoLostUpdate. Can any fairness assumption remove the violation?
  3. The workers become a background loop: acquire, work, release, forever. In the module below, check NoStarvation with Spec, then with SpecSF. Explain TLC's counterexample, and say what a real lock would need to justify SpecSF.
---------------- MODULE PSb1_RedisLockLoop ----------------
CONSTANT Workers
(*--algorithm RedisLockLoop
variable lock = "none";
define
    NoStarvation == \A w \in Workers :
                      (pc[w] = "Acquire") ~> (pc[w] = "Work")
end define;
fair process Worker \in Workers
begin
Loop:
    while TRUE do
Acquire:  \* SET wallet:7:lock <worker id> NX, retried until it succeeds
        await lock = "none";
        lock := self;
Work:
        skip;               \* read and write the balance
Release:
        lock := "none";
    end while;
end process;
end algorithm; *)
\* Strong fairness for each worker's Acquire, on top of fair process.
SpecSF == Spec /\ \A w \in Workers : SF_vars(Acquire(w))
===========================================================

What does TLC report for the crash in task (a)?

Hint

For (b), write the expiry as its own process, process Expiry = "ttl", with a while TRUE loop that awaits a held lock and clears it. For (c), compare the four abstract lock specs in {{lesson:mutex}}: which one is fair process giving you here?

Solution

(a) TLC finds no error: 17 distinct states, and Termination holds because of fair process. With the crash (module PSb1_RedisLockCrash), TLC reports Deadlock reached after five states: A acquires, reads, writes, and crashes at Release with the key still set. A is at Done, B waits at Acquire forever, and no step is enabled. That is a safety failure, a reachable state with no way out, so TLC reports it before it looks at any temporal property.

(b) The expiry process (module PSb1_RedisLockTTL, which also drops fair, since this part checks only safety):

process Expiry = "ttl"   \* the key's PX timeout runs out
begin
Expire:
    while TRUE do
        await lock # "none";
        lock := "none";
    end while;
end process;

MutualExclusion fails after four states: A acquires, the lock expires, B acquires, and both are past Acquire. With only NoLostUpdate, TLC reports eight states, the lost update of Problem 1 again: A acquires, the lock expires, A reads 100, B acquires and reads 100, A writes 110, B writes 110. In production, A is a worker paused by garbage collection or a slow network after its lock expired, not a dead one, the case {{lesson:mutex}} warned about. No fairness assumption helps. Fairness only says some steps must eventually happen; it never forbids an order of steps, and this violation is a finite prefix. The fix has to be in the protocol: the store must reject a write from a worker whose lock has expired. The model also exposes a second problem: A's later Release deletes the key while B holds it. The Redis documentation recommends releasing with a script that deletes the key only if it still holds your own value.

(c) With Spec, TLC reports NoStarvation violated, with the cycle in the figure: A waits at Acquire while B loops, acquires, works and releases, forever. fair process is weak fairness of each worker's whole step, close to the SpecWF row of {{lesson:mutex}}. A's Acquire is enabled only in the two states where the lock is free, so it is never continuously enabled, and weak fairness never forces it. With SpecSF, which adds strong fairness of each Acquire, TLC finds that NoStarvation holds, in the same 12 distinct states.

But SpecSF is an assumption about the lock, not something SET NX provides. A retry loop gives no priority to the worker that has waited longest, and if B's retries tend to be faster, A can lose every race. To justify strong fairness, a real lock needs a queue of waiters served in order, or another mechanism that the model would then include as steps.
