TLA+ is a language for describing systems and asking precise questions about their behavior. This course follows Leslie Lamport's TLA+ Video Course lecture by lecture, then carries the same method into failure-prone architectures.

Follow the route in the diagram. The top row starts from nothing and ends with your first real protocol. The second row runs right to left through commit protocols and into the question of what it means for one spec to implement another. The bottom row has no videos. It applies what you learned to concurrency, large models, failures, and application design, and it ends with review.

TLA stands for Temporal Logic of Actions. A specification, or spec, is a precise description of what a system is allowed to do. It is not a program that serves requests. You decide what matters, how it can change, and what must stay true, and then a tool searches for a counterexample. The value is often finding that a design you can explain convincingly still allows a bad execution.

The video in this lesson is Lamport's talk “Thinking Above the Code.” Watch it for motivation. No later lesson depends on its details, so you can return to it at any point. Its main example, Quicksort, is worked through at the end of this lesson as a lab, as code, and as a TLA+ spec.

A first example: an upload button

Here is the kind of question the course teaches you to ask. A document-sharing app has an Upload button, and a designer says, “Disable the button while the upload is running.” That sentence hides several choices. Can the request succeed after the screen times out? Does Retry create another document?

Each box in the diagram records only two things: where the upload is, and how many documents exist. The upper path is the one everyone pictures. On the lower path the server commits, the reply is lost, the screen times out, and the user retries. No single screen looks wrong, and the final box has two documents. Nothing about the button's appearance appears in the diagram, because the button is not what went wrong.

Keep a prediction notebook with three lines for each claim: claim, suspected breaking path, evidence needed. For this app: “one upload creates at most one document; a lost reply followed by a retry might break it; inspect how the server recognizes a repeated request.” That is a concrete question for implementation, not a vague instruction to make uploads reliable. By the end of the lectures you will be able to write this as a spec and have a tool find the lower path for you.

Predict: is disabling the Upload button enough to guarantee one document?

No. It prevents one local interaction but says nothing about the lost reply and retry in the diagram. The server needs a way to connect a repeated request to the same result. The button can improve the experience, but the server has to enforce the rule.

Quicksort, above the code

The main example in Lamport's talk is Quicksort. Most programmers describe it as a recursive procedure: partition the array, then sort each half. That describes code. Lamport describes it one level up, without recursion:

  1. Keep a set U of index intervals that still need sorting. At the start it holds one interval, the whole array.
  2. Remove any interval from U. If it has one element, it is already sorted.
  3. Otherwise, partition it at some index p, so that every value in the left part is at most every value in the right part. Put both parts back in U.
  4. When U is empty, the array is sorted.

The important word is “any.” The description doesn't say which interval to take next. A recursive program takes the newest one, so it is using a stack. A loop over a work queue takes the oldest one. Several threads could each take a different interval at the same time. All three are Quicksort, because each does something the description allows.

Sort it yourself

Each bar is one array element, with its index underneath. The brackets under the bars are the intervals in U, and a green bar is in its final place. Press an interval in the first row to choose it yourself. The next two buttons choose for you, the way a program would. U remembers the order in which intervals were added. Newest (stack) takes the interval added most recently, like taking the top plate from a stack. That is what the code below does with pop. Oldest (queue) takes the interval that has waited longest, like the front of a line, so the array is split one level at a time. A partition adds its left part first and then its right part, so the right part is always the newest. The dashed line shows where the last partition split its interval. This runs the JavaScript code printed below one step at a time; it is not TLC.

Sort the array once with each button, then compare the two readouts. The steps come in a different order and the arrays in between differ, but both runs end with the same sorted array. Also notice when a bar turns green: only when its interval is down to one element, and after that it never moves.

The iterative code

This is the program the lab runs. The array todo plays the part of U, and pop makes it a stack. Change pop to shift and it becomes a queue, and it still sorts.

function quicksort(a) {
  const todo = [[0, a.length - 1]];  // U: intervals still to sort
  while (todo.length > 0) {
    const [lo, hi] = todo.pop();     // choose one: here, the newest
    if (lo >= hi) continue;          // one element is already sorted
    const p = partition(a, lo, hi);
    todo.push([lo, p], [p + 1, hi]);
  }
  return a;
}

// Hoare's partition. Returns p with lo <= p < hi, and
// rearranges a[lo..hi] so every a[lo..p] <= every a[p+1..hi].
function partition(a, lo, hi) {
  const pivot = a[Math.floor((lo + hi) / 2)];
  let i = lo - 1, j = hi + 1;
  for (;;) {
    do i++; while (a[i] < pivot);
    do j--; while (a[j] > pivot);
    if (i >= j) return j;
    [a[i], a[j]] = [a[j], a[i]];
  }
}

Hoare's partition is the hard part to get right, with its two indexes that cross. The description doesn't care how it works, only what it guarantees: p lies between lo and hi - 1, values outside lo..hi don't move, and every value up to p is at most every value after it.

The same algorithm in TLA+

Here is the description written as a TLA+ spec. For now, read it for its shape; Lectures 2 to 4 teach the notation. Init says the array may hold any values and that U holds the whole array. Partition is one step. It chooses any interval in U, then any p and any rearranged array B that meet the three conditions of a partition. Nothing in it mentions pivots, swaps, stacks, or recursion.

------------------------------ MODULE QuickSort ------------------------------
EXTENDS Integers, FiniteSets
CONSTANTS N, Values
Idx == 0..(N-1)
VARIABLES A, U       \* the array, and the set of intervals still to sort
vars == <<A, U>>

Count(B, v) == Cardinality({i \in Idx : B[i] = v})
IsPerm(B) == \A v \in Values : Count(B, v) = Count(A, v)
Sorted == \A i, j \in Idx : i < j => A[i] =< A[j]

Init == /\ A \in [Idx -> Values]
        /\ U = {<<0, N-1>>}

\* Pick ANY interval in U. The spec does not say which one.
Partition == \E I \in U :
    LET lo == I[1]
        hi == I[2]
    IN  IF lo < hi
        THEN \E p \in lo..(hi-1), B \in [Idx -> Values] :
               /\ \A i \in Idx \ (lo..hi) : B[i] = A[i]
               /\ IsPerm(B)
               /\ \A i \in lo..p, j \in (p+1)..hi : B[i] =< B[j]
               /\ A' = B
               /\ U' = (U \ {I}) \cup {<<lo, p>>, <<p+1, hi>>}
        ELSE /\ U' = U \ {I}
             /\ UNCHANGED A

Done == U = {} /\ UNCHANGED vars
Next == Partition \/ Done
Spec == Init /\ [][Next]_vars /\ WF_vars(Partition)

SortedWhenDone == U = {} => Sorted
Terminates == <>(U = {})
==============================================================================

With 4 elements and values from 1 to 3, TLC tries all 81 starting arrays and every order of choosing intervals, 731 distinct states, in about a second. SortedWhenDone says the array is sorted once U is empty, and Terminates says U does become empty. That leaves a separate and smaller question: is every step of the code a step the spec allows? {{lesson:implementation}} is about that question.

Predict: a bug puts only the left part back, <<lo, p>>. Which property fails, and how long is the shortest failing behavior?

SortedWhenDone fails, and TLC needs only three states. The array 1, 1, 1, 2 is partitioned at p = 0 into 1, 1, 2, 1. The bug drops the right part, the left part has one element, and U is empty while 2 still comes before 1. Terminates still holds, since a program that forgets work finishes sooner. Tests on arrays that are already sorted would all pass.
