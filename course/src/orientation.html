Reason about every possible next step.

TLA+ is a language for describing systems and asking precise questions about their behavior. This course follows Leslie Lamport's TLA+ Video Course lecture by lecture, then carries the same method into failure-prone architectures.

Follow the route in the diagram. The top row starts from nothing and ends with your first real protocol. The second row runs right to left through commit protocols and into the question of what it means for one spec to implement another. The bottom row has no videos. It applies what you learned to concurrency, large models, failures, and application design, and it ends with review.

TLA stands for Temporal Logic of Actions. A specification, or spec, is a precise description of what a system is allowed to do. It is not a program that serves requests. You decide what matters, how it can change, and what must stay true, and then a tool searches for a counterexample. The value is often finding that a design you can explain convincingly still allows a bad execution.

The video in this lesson is Lamport's talk “Thinking Above the Code.” Watch it for motivation. No later lesson depends on its details, so you can return to it at any point.

How to study with the videos

Each lecture has one or more lessons here, in the lecture's order and with its examples. When a lecture spans several lessons, each lesson says which part of the lecture it covers. Its “While you watch” section tells you what to look for, where to stop and try the problem yourself, and what the lesson adds. Each video is meant to be viewed along with its web page on Lamport's course site. The videos and that site need internet; the lesson text and the labs work offline.

  1. Watch a segment, not a whole lecture. Lamport often tells you to stop the video and solve something. Do it.
  2. Predict. Before you click a step or open an answer, write down what you expect.
  3. Run it. Step the lab, or run the real tool once you have installed it.
  4. Break it. Weaken a condition or change a step, then predict the failure.
  5. Explain it. Close the lesson and rebuild the model or the argument from memory.

The dashed arrow in the diagram is the most useful one: a surprise means your mental model and the system differ, so go back and predict again. In your next session, recall the previous lesson before continuing. Mark a lesson studied only when you can explain its exercise without looking. The Mac app saves completed lessons, notes, and reading position on this Mac. The standalone file saves in your browser when browser storage is available.

A lab is not a verification. The interactive labs run small, purpose-built JavaScript models. They do not read TLA+ and they are not the model checker. Complete modules are printed so you can check them with the real tools, which you install in {{lesson:tools}}.

Scope and prerequisites

You need basic programming intuition, not a mathematics degree. Each piece of notation is introduced when it is first needed. The lectures cover safety, liveness, and implementation. The later parts add concurrency, proof structure, model reduction, time, crash recovery, and consensus. This is a substantial foundation, not a complete language reference or a proof of any deployed system.

A first example: an upload button

Here is the kind of question the course teaches you to ask. A document-sharing app has an Upload button, and a designer says, “Disable the button while the upload is running.” That sentence hides several choices. Can the request succeed after the screen times out? Does Retry create another document?

Each box in the diagram records only two things: where the upload is, and how many documents exist. The upper path is the one everyone pictures. On the lower path the server commits, the reply is lost, the screen times out, and the user retries. No single screen looks wrong, and the final box has two documents. Nothing about the button's appearance appears in the diagram, because the button is not what went wrong.

Keep a prediction notebook with three lines for each claim: claim, suspected breaking path, evidence needed. For this app: “one upload creates at most one document; a lost reply followed by a retry might break it; inspect how the server recognizes a repeated request.” That is a concrete question for implementation, not a vague instruction to make uploads reliable. By the end of the lectures you will be able to write this as a spec and have a tool find the lower path for you.

Predict: is disabling the Upload button enough to guarantee one document?

No. It prevents one local interaction but says nothing about the lost reply and retry in the diagram. The server needs a way to connect a repeated request to the same result. The button can improve the experience, but the server has to enforce the rule.
