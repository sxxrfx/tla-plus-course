Model the queue contract.

{{lesson:abp}} used sequences, with Append and Tail, to model message channels. Give a sequence a capacity and you have a queue, a first architecture with ordering, backpressure and boundary cases but no complicated network.

---------------- MODULE BoundedFIFO ----------------
EXTENDS Naturals, Sequences
CONSTANTS Values, Capacity
ASSUME Capacity \in Nat /\ Capacity > 0
VARIABLE q
vars == <<q>>
Init == q = <<>>
Enqueue(v) == /\ Len(q) < Capacity
              /\ q' = Append(q,v)
Dequeue == /\ Len(q) > 0
           /\ q' = Tail(q)
Next == (\E v \in Values: Enqueue(v)) \/ Dequeue
Spec == Init /\ [][Next]_vars
TypeOK == /\ q \in Seq(Values)
          /\ Len(q) <= Capacity
===================================================
SPECIFICATION Spec
CONSTANT Values = {A, B}
CONSTANT Capacity = 2
INVARIANT TypeOK

Here, duplicate values are distinct entries, since q is a sequence. TLC finds 7 distinct states and no error, and they are the 7 nodes above: 1 + 2 + 4. Seq(Values) contains sequences of every finite length, but the capacity guard bounds the reachable ones. The diagram also shows the two boundaries: from a length-2 node only dequeue leaves, and from ⟨⟩ only enqueue. Capacity blocks insertion, and the empty queue blocks removal.

TypeOK does not say first-in, first-out

Nothing in this module would notice a queue that hands out the wrong item, because it has no output. In the diagram, swap the targets of the two middle deq edges and TypeOK still holds. To state the contract, record what went in and what came out. Bound the history so the state space stays finite.

---------------- MODULE FIFOOrder ----------------
EXTENDS Naturals, Sequences
CONSTANTS Values, Capacity, MaxSends
VARIABLES q, sent, received
vars == <<q, sent, received>>
Init == q = <<>> /\ sent = <<>> /\ received = <<>>
Enqueue(v) == /\ Len(q) < Capacity
              /\ Len(sent) < MaxSends
              /\ q' = Append(q,v)
              /\ sent' = Append(sent,v)
              /\ UNCHANGED received
Dequeue == /\ Len(q) > 0
           /\ received' = Append(received, Head(q))
           /\ q' = Tail(q)
           /\ UNCHANGED sent
Next == (\E v \in Values: Enqueue(v)) \/ Dequeue
Spec == Init /\ [][Next]_vars
TypeOK == /\ q \in Seq(Values)
          /\ Len(q) <= Capacity
InOrder == received \o q = sent
===================================================
SPECIFICATION Spec
CONSTANTS Values = {A, B}
          Capacity = 2
          MaxSends = 3
INVARIANT TypeOK
INVARIANT InOrder
CHECK_DEADLOCK FALSE

InOrder says everything sent is either received already or still queued, in the same order. The operator \o is sequence concatenation. This is close in spirit to the refinement mappings of {{lesson:refinement}}: it relates internal state to what an outside observer can see. TLC finds 41 distinct states and no error.

Predict: make Dequeue take the last item instead of the first. Which invariant fails?

Only InOrder. With TypeOK alone, the mutated module passes with 69 distinct states, because length and element types are still correct. With InOrder, TLC reports a violation after 3 steps, shown below.

Worked architecture: upload processing

A photo app accepts uploads A and B, then generates thumbnails in the background. Give each upload an immutable job ID. The user-visible contract is that accepted jobs do not disappear. FIFO ordering is a separate scheduling promise. A job moving from the waiting queue to a worker must not be mistaken for a completed upload.

Claim == /\ Len(waiting) > 0
         /\ active' = active \cup {Head(waiting)}
         /\ waiting' = Tail(waiting)
         /\ UNCHANGED <<accepted, done>>
ExactlyOnePlace ==
    /\ Waiting \cup active \cup done = accepted
    /\ Waiting \cap active = {}
    /\ Waiting \cap done = {}
    /\ active \cap done = {}

This comes from the complete UploadJobs module with Jobs = {A, B}, which also has Accept and Finish. Claim removes the head and records it as active in one step, and TLC finds 17 distinct states with ExactlyOnePlace holding. The disjointness lines matter: a count alone could hide one missing job and one duplicate.

Now try the bad implementation, the dashed edge. A is removed from waiting and the worker crashes before recording it as active:

CrashAfterRemove == /\ Len(waiting) > 0
                    /\ waiting' = Tail(waiting)
                    /\ UNCHANGED <<accepted, active, done>>

TLC reports the violation in 2 steps: Accept(A), then the crash, leaving accepted = {A} and A nowhere else. A durable claim, or a visibility protocol that permits redelivery, changes the model so this edge no longer exists.

Do not combine “FIFO” with “completion order” by accident. Two workers can claim A before B while B’s thumbnail finishes first, because Finish takes any active job. If ordered completion is required, add a publication barrier rather than asserting an order the architecture cannot provide.

Predict: the worker writes A’s thumbnail and crashes before acknowledging A. Where should A go?

Redelivery is reasonable if processing is idempotent or detects the existing result by job ID. The queue may deliver A again; the user-visible result should still be recorded once. Model claim attempts separately from logical upload identities.
