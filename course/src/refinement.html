A refinement mapping says how one state stands in for another.

{{lesson:impl-general}} ended with AB2 behaving like AB although it has no AtoB or BtoA. Ordinary implication can't say so. The fix is small: write down how the missing variables are computed from the ones that exist. That expression is a refinement mapping, and it's the general meaning of implementation.

What "AB2 implements AB" means

The claim is stronger than the one you checked last lesson. AB2 doesn't just implement ABSpec. It implements the AB protocol, with each CorruptMsg step implementing a LoseMsg step. Losing a message may feel like something the environment does, not the protocol. But specs say nothing about who performs a step; that is an interpretation we put on the formula.

Here's the meaning. Take any behavior of AB2 and change each state as in the figure, deleting Bad from each channel. The result must be a behavior of AB.

The top half of this figure shows it on one behavior. A corrupting step maps to a LoseMsg step, since a message disappears from the mapped channel. An ARcv that consumes Bad maps to stuttering, because the mapped state doesn't change. This is the same idea as TMAbort in {{lesson:implementation}}.

From meaning to something checkable

To make it a formula, invent a spec SpecH whose states also contain AtoB and BtoA, always equal to the cleaned channels. Module AB2H defines it:

SpecH == /\ AB2!Spec
         /\ [] /\ AtoB = RemoveBad(AtoB2)
               /\ BtoA = RemoveBad(BtoA2)

RemoveBad is RemoveX from last lesson, with Bad in place of "X". Here AtoB and BtoA are imaginary variables, with no effect on what the other four can do. So THEOREM SpecH => AB!Spec says just what we want. But TLC can't check it, because SpecH doesn't have the standard form of an initial formula and [][Next]_vars. You could rewrite it, and module AB2H does so as SpecHH. The lecture instead takes a longer path that teaches more.

Follow the figure from the top. SpecH implies the always formula, so by the Temporal Substitution Law, AB!Spec may be replaced by its substituted version. That version no longer mentions AtoB or BtoA, so the always conjunct of SpecH has nothing left to do, and it goes. SpecH has now vanished. Only AB2!Spec remains on the left, and inside module AB2 that's plain Spec, which TLC can handle.

INSTANCE ... WITH

One problem remains: WITH so far is lecture notation, not TLA+. But the real INSTANCE statement has a WITH clause. After expanding definitions, formula Spec of AB contains only operators and AB's declared symbols, Data, AVar, BVar, AtoB, BtoA. To import it elsewhere, you give an expression for each. Omitting one means "the symbol of the same name," which is what every INSTANCE so far has done without saying so. So these lines go at the end of AB2:

RECURSIVE RemoveBad(_)
RemoveBad(seq) == IF seq = <<>>
                    THEN <<>>
                    ELSE IF Head(seq) = Bad
                           THEN RemoveBad(Tail(seq))
                           ELSE <<Head(seq)>> \o RemoveBad(Tail(seq))

AB == INSTANCE AB WITH AtoB <- RemoveBad(AtoB2),
                       BtoA <- RemoveBad(BtoA2)

THEOREM Spec => AB!Spec

These substitutions are the refinement mapping, and AB2 implements AB under it. Check it like any other implementation, with a model whose behavior spec is Spec and whose property is AB!Spec. With Data = {d1, d2}, Bad a model value, and channels of length at most 2, TLC finds no error: 6926 states generated, 1008 distinct, depth 16.

Predict: map AtoB <- AtoB2 and BtoA <- BtoA2, keeping the Bad slots. What does TLC say?

It reports the action property of AB violated after three states: BSnd, then CorruptMsg. That is the bottom half of the figure above. A mapped channel containing Bad changes in a way that no AB action allows, because LoseMsg removes a message and doesn't rewrite one.

A mapping that discards information fails too. Map both channels to <<>>, and TLC finds the violation in three states: BSnd, then an ARcv in which A chooses a new value while the mapped channel is empty. No AB step could do that.

What implementation means, in general

If Spec2 doesn't contain all the variables of Spec1, then Spec2 can implement Spec1 only under a refinement mapping that assigns expressions of Spec2 to the missing variables. This is the usual case. Even a variable they share may be mapped to something other than itself.

So what does it mean for a program to implement a TLA+ spec? That you could, in principle, write a spec of the program which implements the spec under a suitable mapping. In practice that spec would be far too long. But you can still explain informally how the spec's variables are represented by the program's state. Writing it down, perhaps as comments in the code, explains what the program does, and can expose errors in it.

Why can't Spec of AB implement Spec of AB2 under a plain refinement mapping?

Imaginary variables

You've now seen two uses: AtoBgood and BtoAgood to state liveness, and AtoB and BtoA to explain implementation. Adding imaginary variables to a spec means the new and old specs allow the same behaviors if you ignore those variables. They need not describe real state, they aren't meant to be implemented, and if their values can be computed from the original variables, you don't need them, as this lesson's mapping shows. But they may be necessary. As the quiz above shows, AB can implement AB2 only with added variables recording where lost messages were. They are usually called auxiliary variables, and the lecture points to the paper Auxiliary Variables in TLA+.

Extension: choosing a mapping in a real product

This section goes beyond the lecture and isn't model-checked. A document editor shows "ca". The user types "t" and immediately sees "cat". A request goes out, the server durably commits it, and an acknowledgement comes back. The draft on screen, the durable log, and what the client knows are three different states. Which belongs in the abstract contract is your first decision.

Suppose the abstract object promises durable edits, with one variable savedText. Map it to the result of applying the durable log in order. In the figure, only the commit is an abstract edit. If the server commits but the reply is lost, a retry must not insert a second "t", so requests need identities, and the mapped text should stay "cat", not "catt". Mapping savedText to the draft instead describes a different contract, speculative display. A later rejection could then remove the "t", which a durable-only abstract spec forbids. That's a failed mapping, not necessarily an editor bug.

Linearizability is a related but specific contract, and a generic refinement check doesn't give it to you automatically. It gives each completed operation one point between its invocation and response, with a legal sequential order that respects the real-time order of non-overlapping operations. To check for it, the abstract interface must include invocations, responses, and the treatment of pending operations. With several editors, refining to one sequential text object promises more than replicas eventually converging.

Transfer exercise: an editor shows "Saved" before the server commits. Which property exposes the problem?

Represent the status change as an acknowledgement event and require that each acknowledged operation is durable under the modeled failures. Crash after showing "Saved" and before committing. If recovery loses the edit, the client-visible durability contract fails, however good the optimistic draft looked.
