A whole specification can be one formula.

So far you have handed TLC two formulas: an initial one and a next-state one, as you did for TwoPhase in {{lesson:transactions}}. A single formula can say both, if it is true or false of a whole behavior. To write it you first sort expressions by how much of a behavior they need, then add one operator, always.

Implication, briefly

Everything in this lesson and the next is stated with =>, read "implies." P => Q means: if P is true then Q is true, and otherwise we know nothing. Mathematically, "we know nothing" is the value TRUE, so it equals IF P THEN Q ELSE TRUE.

PQP => Q~Q => ~P
TRUETRUETRUETRUE
TRUEFALSEFALSEFALSE
FALSETRUETRUETRUE
FALSEFALSETRUETRUE

The last two columns match, so P => Q equals ~Q => ~P. "If it's raining the ground is wet" therefore means the same as "if the ground is not wet it's not raining." That sounds wrong because in speech if suggests a cause. In math, implication asserts only that two truths go together.

Four kinds of expression

Here an expression is complete: after expanding definitions it contains only built-in operators, numbers and strings, declared constants and variables, and identifiers bound inside it. \E v \in Nat : x' = x + v is complete. Its part x' = x + v is not, because v is bound outside that part. A formula is a Boolean-valued expression. The figure sorts expressions from the inside out.

  • Constant. No declared variables, no ', no UNCHANGED. An ASSUME must be a constant formula.
  • State. May also contain declared variables, so it has a value on a state. If a state gives v the set Nat and w the value -42, then v \cup {w} has the value Nat \cup {-42} there.
  • Action. May also contain ' and UNCHANGED, so it has a value on a step. If s gives p the value 42 and t gives q the value 24, then p - q' has the value 18 on the step from s to t. An action formula is simply called an action.
  • Temporal. New here. It has a value on a behavior. TLA+ has only Boolean ones.

Each level is a special case of the next. A state expression is an action expression whose value depends only on the first state of the step. You may also prime any state expression, not just a variable: e' on a step is the value of e in the second state. So UNCHANGED <<x, y, z>> is <<x, y, z>>' = <<x, y, z>>, which is (x' = x) /\ (y' = y) /\ (z' = z).

From two formulas to one

TPSpec should be true on a behavior exactly when TPInit holds on the first state and TPNext holds on every step. The figure shows both duties on a real TLC trace. The first duty needs nothing new, because a state formula counts as a temporal formula that is true on a behavior when it is true on the first state. The second needs the always operator, typed []. []TPNext is true on a behavior when TPNext is true on every step.

That suggests TPSpec == TPInit /\ []TPNext. It is almost right. The definition at the end of module TwoPhase is:

TPSpec == TPInit /\ [][TPNext]_<<rmState, tmState, tmPrepared, msgs>>

Applied to a state formula, always needs no brackets or subscript: []TPTypeOK means TPTypeOK holds on every state, because its value on each step depends only on that step's first state.

The subscript allows stuttering

[TPNext]_vars abbreviates TPNext \/ UNCHANGED vars, where vars is the tuple of the spec's variables. A step that leaves all of them unchanged is a stuttering step. So the formula says every step is a TPNext step or changes nothing. In the figure, the two stutter columns are allowed and the red one is not.

Why a spec should allow steps that do nothing is the subject of {{lesson:implementation}}. For now, take the two facts it implies. A formula of this form can never require anything to happen, and it can never be violated by a pause.

Predict: TPSpec has variables rmState, tmState, tmPrepared, msgs. Is a step that changes only tmPrepared always allowed?

No. It is not stuttering, because tmPrepared changed. It is allowed only if it is a TPNext step, namely TMRcvPrepared(r) for a resource manager whose Prepared message is in msgs while tmState is "init".

Stuttering is not deadlock

A deadlock report from TLC is about Next only: a reachable state with no Next successor. Take SimpleProgram from {{lesson:program}}. TLC reports "Deadlock reached" at pc = "done", as the solid arrows in the figure predict. The dashed loops don't count, even though the formula allows them.

You can silence that report by writing the loop into the next-state formula: Next \/ UNCHANGED vars. TLC then finishes with no error, with 2003 distinct states. Nothing got better, the program still stops there, and a blocked protocol patched this way looks healthy. Likewise, a livelock is endless Next steps with no useful progress, and neither report catches it. Properties that do catch it arrive in {{lesson:fairness}}.

Theorems, and checking them

THEOREM TF asserts that temporal formula TF is true on every possible behavior, not just behaviors of some spec. So implication is the way to talk about a spec:

THEOREM TPSpec => []TPTypeOK

For every behavior, if it satisfies TPSpec, then TPTypeOK holds on all its states. That is what "TPTypeOK is an invariant of TPSpec" means. TLC does not read theorems; they tell your reader what you expect. To check this one, name TPSpec as the behavior spec and []TPTypeOK as a property. In the Toolbox that is the Properties list. With the VS Code extension or the command line, a .cfg file says the same, and a property must be a defined name, so a small wrapper module adds AlwaysTypeOK == []TPTypeOK:

SPECIFICATION TPSpec
CONSTANT RM = {r1, r2, r3}
INVARIANT TPTypeOK
PROPERTY AlwaysTypeOK

On this configuration TLC finds no error: 1146 states generated, 288 distinct, depth 11. Since this is an invariance property, the INVARIANT line alone would be enough. The two lines are the same assertion written at two levels.

A behavior starts with tmState = "ouch", so it does not satisfy TPSpec. Is TPSpec => []TPTypeOK true on it?
