Two majorities always share someone, and that's where evidence survives.

Two-phase commit depends on one TM remembering the decision. The fix in lecture 7 is to spread that memory over several processes and count on overlapping groups. This lesson teaches the set operators the lecture uses, and the quorum idea, on a simpler example: copies of a stored value.

Two sets of acceptors, each a majority of three. \cap is the part in both, and in the diagram that's a2. An acceptor is just a process whose job is to record votes; {{lesson:paxos-commit}} says what they vote on. Whichever two majorities you pick, some acceptor is in both.

Why majorities overlap

With the set operators you can state the property directly, rather than counting:

Majority == {Q \in SUBSET Acceptor : Cardinality(Q) = 2}   \* with 3 acceptors
\A MS1, MS2 \in Majority : MS1 \cap MS2 # {}               \* the property that matters

Each row of the diagram is one set in Majority, and each column an acceptor. Pick any two green rows: some column is filled in both. Now look at the red row, {a3}. It shares no column with {a1, a2}. A set of "majorities" containing it fails the property even though every row looks like a reasonable group. Paxos Commit assumes only the property, not a count. You will see TLC break that assumption on purpose.

The general rule for N replicas: if a read set has R members and a write set has W, then R + W > N forces overlap, because R + W elements can't fit into N places without sharing one. That is a statement about sets and nothing more.

Worked architecture: a replicated product price

A price is stored on replicas A, B, and C, all at version 7. A write of version 8 counts as acknowledged once 2 replicas (W = 2) store it. A read afterward asks R replicas and keeps the newer version it hears.

----------------------------- MODULE PriceQuorum ----------------------------
EXTENDS Integers, FiniteSets
CONSTANTS Replica, W, R          \* write-set size and read-set size
VARIABLES stored, acked, result  \* result: what a read returned (0 = none yet)
vars == <<stored, acked, result>>

WriteSets == {Q \in SUBSET Replica : Cardinality(Q) = W}
ReadSets  == {Q \in SUBSET Replica : Cardinality(Q) = R}

PInit == /\ stored = [n \in Replica |-> 7]
         /\ acked = FALSE
         /\ result = 0

Store(n) == /\ stored' = [stored EXCEPT ![n] = 8]
            /\ UNCHANGED <<acked, result>>

Ack == /\ \E Q \in WriteSets : \A n \in Q : stored[n] = 8
       /\ acked' = TRUE
       /\ UNCHANGED <<stored, result>>

\* A read after the ack hears from one read set and keeps the newer version.
Read == /\ acked
        /\ result = 0
        /\ \E Q \in ReadSets :
             result' = IF \E n \in Q : stored[n] = 8 THEN 8 ELSE 7
        /\ UNCHANGED <<stored, acked>>

PNext == Ack \/ Read \/ \E n \in Replica : Store(n)

SeesAckedWrite == result \in {0, 8}
=============================================================================
INIT PInit
NEXT PNext
CONSTANTS Replica = {"A", "B", "C"}
          W = 2
          R = 2
INVARIANT SeesAckedWrite
CHECK_DEADLOCK FALSE

With R = 2: no error, 16 distinct states. With R = 1: SeesAckedWrite is violated in a 5-state trace.

In that trace (the diagram) version 8 reaches C and A, the write is acknowledged, and a read asks only B. Nothing has failed. No machine lost data or broke a local rule, and the client still reads the old price. With R = 2, any read set contains A or C, as the last column shows.

Find the worst-case intersection

Predict: N = 5, R = 2, W = 3. Can a read miss every written replica?

Yes. Write to {A, B, C}; read from {D, E}. Their intersection is empty, and TLC confirms such a pair exists. With R = 3, it confirms that every pair of size-3 sets intersects.

The model is deliberately easy: one writer, one write, and a version order given in advance. Overlap gives you a place to find evidence. It doesn't say how to interpret it. With two concurrent writers, "the newer version" needs a definition, and overlap alone doesn't supply one. Likewise, if a replica acknowledges before storing durably, its restart can erase what the overlap was counting on.

From stored prices to votes

Replace the pieces. The write set becomes a majority of acceptors that voted for an outcome. The read becomes a new leader asking a majority what they've voted for, because it suspects that the old leader died. Every majority it asks contains someone who voted, so if an outcome was already decided, the new leader can find out. That one sentence is the core of {{lesson:paxos-commit}}: the leader can take over without the old leader's memory, because the memory was in the overlap.

What does Paxos Commit's Majority assumption require?

Predict: R + W > N, so is every read correct, whatever else happens?

No. You still need to know which versions replies represent, how a read chooses, how concurrent writes are ordered, when a write completes, and what survives a crash. Intersection is a place to look; it isn't an answer.
