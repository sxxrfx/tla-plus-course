Paxos Commit keeps the decision alive when the transaction manager doesn't.

In two-phase commit, one process holds the decision. If it stops, prepared RMs wait forever. Lecture 7 opens with that problem, shows why the obvious fix is wrong, and then reads the spec of Paxos Commit: a real algorithm by Jim Gray and Leslie Lamport, and a tour of the last TLA+ constructs you need.

This is a TLC trace of TwoPhase plus one TMCrash action, with two RMs. It takes 4 states to reach the bottom of the diagram. There, r1 and r2 are prepared, and the only actions that move a prepared RM need a Commit or Abort message that only the TM can send. Checking the property "once blocked, no step changes anything" gives no error over 112 distinct states. TCConsistent holds as well: nothing is wrong except that nothing happens.

While you watch

Lamport states plainly that the lecture is about TLA+ and that the paper explains the algorithm, so he goes through the operators and doesn't explain the protocol. This lesson does the reverse order: first the idea, with diagrams, then the operators. Follow the spec alongside him at the Phase2a definition. Pause at the model values and decide whether Acceptor can be a symmetry set before he answers. {{lesson:consensus}} covers one Paxos instance by itself.

The fix that fails

The textbook answer is a backup TM that takes over when the primary fails. It's simple to build and to test. Then one day the primary decides to commit and pauses. The backup concludes the primary has died.

This run came from TwoPhase plus a BackupAbort action, with two RMs: TLC reports a TCConsistent violation in a 9-state trace, drawn above. The backup can't distinguish slow from dead, and both TMs' messages are valid. Testing won't easily catch this, because it needs a rare pause. Finding it needs a spec.

The idea: several acceptors remember each RM's vote

Paxos Commit replaces the TM's one memory with a set of acceptors, with the overlap property from {{lesson:replication}}. It runs one separate decision, called an instance, per RM, whose outcome is either "prepared" or "aborted". The field ins in each message says which RM's instance it belongs to.

A leader is any process that believes it's in charge. The spec doesn't care who it is, or how many there are; several may act at once. Here's the normal case, for one RM's instance.

r1 votes by sending a phase2a message in ballot 0, the ballot number reserved for the RM itself. Each acceptor records its vote and announces it in phase2b. Once a majority voted the same value in the same ballot, that value is chosen. a3 was slow and it didn't matter. When every instance has chosen "prepared", a leader may send Commit; if any chose "aborted", it may send Abort. No single process has to survive.

What a new ballot does

If an RM's vote seems stuck, a leader starts a higher ballot (Phase1a). An acceptor receiving that message promises to ignore lower ballots by raising mbal, and reports its last vote (Phase1b). Having heard from a majority, the leader sends one value (Phase2a):

  • If anyone reported a vote, it sends the value from the highest ballot reported.
  • If nobody did, it sends "aborted". An RM with no recorded vote can't be assumed prepared.

On the left, a1 and a2 voted "prepared" in ballot 0, so it's chosen. A leader in ballot 1 hears from a2 and a3. The overlap is a2, whose report forces the leader to send "prepared" too. So the old result survives without the old leader. On the right, no such acceptor exists, and the leader hears nothing: this is the experiment at the end of this lesson.

The spec's new constructs

Maximum(S) == IF S = {} THEN -1
                        ELSE CHOOSE n \in S : \A m \in S : n >= m

CHOOSE. CHOOSE v \in S : P is some value v in S satisfying P. If there are several, TLA+ doesn't say which; if none, its value is unspecified and TLC reports an error. It isn't random. Like any expression, it equals itself, so TLC gets the same answer every time. Hence x' \in 1..99 allows 99 next values and x' = CHOOSE i \in 1..99 : TRUE allows just one. Use it when exactly one v qualifies, as in Maximum, or when the larger expression doesn't depend on which you get. Here's the second kind:

Phase2a(bal, r) ==
  /\ ~\E m \in msgs : /\ m.type = "phase2a"
                      /\ m.bal = bal
                      /\ m.ins = r
  /\ \E MS \in Majority :
       LET mset == {m \in msgs : /\ m.type = "phase1b"
                                 /\ m.ins = r
                                 /\ m.mbal = bal
                                 /\ m.acc \in MS}
           maxbal == Maximum({m.bal : m \in mset})
           val == IF maxbal = -1
                    THEN "aborted"
                    ELSE (CHOOSE m \in mset : m.bal = maxbal).val
       IN  /\ \A ac \in MS : \E m \in mset : m.acc = ac
           /\ Send([type |-> "phase2a", ins |-> r, bal |-> bal, val |-> val])
  /\ UNCHANGED <<rmState, aState>>

LET-IN makes definitions local to one expression. mset filters and {m.bal : m \in mset} maps, the two constructors from {{lesson:replication}}. Several messages in mset may have the top ballot, so CHOOSE may have several choices, but the lecture points out that in any reachable state they all have the same val. Lamport calls this the most subtle part of the algorithm.

Nested EXCEPT. The acceptor state is aState[r][a], a record per acceptor per instance, with fields mbal, bal, and val.

aState' = [aState EXCEPT ![m.ins][acc].mbal = m.bal,
                         ![m.ins][acc].bal  = m.bal,
                         ![m.ins][acc].val  = m.val]

Read it as three programming assignments to aState[m.ins][acc]'s fields. The first form abbreviates nested EXCEPTs, one per level. Lamport's advice is to remember the idiom rather than decode it.

Show the complete module that was checked
----------------------------- MODULE PaxosCommit ----------------------------
EXTENDS Integers

Maximum(S) == IF S = {} THEN -1
                        ELSE CHOOSE n \in S : \A m \in S : n >= m

CONSTANTS RM,        \* The set of resource managers
          Acceptor,  \* The set of acceptors
          Majority,  \* The sets of acceptors that count as a majority
          Ballot     \* The set of ballot numbers

ASSUME /\ Ballot \subseteq Nat
       /\ 0 \in Ballot
       /\ Majority \subseteq SUBSET Acceptor
       /\ \A MS1, MS2 \in Majority : MS1 \cap MS2 # {}

Messages ==
  [type : {"phase1a"}, ins : RM, bal : Ballot \ {0}]
    \cup
  [type : {"phase1b"}, ins : RM, mbal : Ballot, bal : Ballot \cup {-1},
   val : {"prepared", "aborted", "none"}, acc : Acceptor]
    \cup
  [type : {"phase2a"}, ins : RM, bal : Ballot, val : {"prepared", "aborted"}]
    \cup
  [type : {"phase2b"}, acc : Acceptor, ins : RM, bal : Ballot,
   val : {"prepared", "aborted"}]
    \cup
  [type : {"Commit", "Abort"}]
-----------------------------------------------------------------------------
VARIABLES rmState, aState, msgs

PCTypeOK ==
  /\ rmState \in [RM -> {"working", "prepared", "committed", "aborted"}]
  /\ aState \in [RM -> [Acceptor -> [mbal : Ballot,
                                     bal  : Ballot \cup {-1},
                                     val  : {"prepared", "aborted", "none"}]]]
  /\ msgs \subseteq Messages

PCInit ==
  /\ rmState = [r \in RM |-> "working"]
  /\ aState = [r \in RM |->
                 [ac \in Acceptor |-> [mbal |-> 0, bal |-> -1, val |-> "none"]]]
  /\ msgs = {}

Send(m) == msgs' = msgs \cup {m}
-----------------------------------------------------------------------------
\* Resource manager actions. RMs vote by sending a ballot 0 phase 2a message.
RMPrepare(r) ==
  /\ rmState[r] = "working"
  /\ rmState' = [rmState EXCEPT ![r] = "prepared"]
  /\ Send([type |-> "phase2a", ins |-> r, bal |-> 0, val |-> "prepared"])
  /\ UNCHANGED aState

RMChooseToAbort(r) ==
  /\ rmState[r] = "working"
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ Send([type |-> "phase2a", ins |-> r, bal |-> 0, val |-> "aborted"])
  /\ UNCHANGED aState

RMRcvCommitMsg(r) ==
  /\ [type |-> "Commit"] \in msgs
  /\ rmState' = [rmState EXCEPT ![r] = "committed"]
  /\ UNCHANGED <<aState, msgs>>

RMRcvAbortMsg(r) ==
  /\ [type |-> "Abort"] \in msgs
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ UNCHANGED <<aState, msgs>>
-----------------------------------------------------------------------------
\* Leader actions: any process that believes it is the leader may do these.
Phase1a(bal, r) ==
  /\ Send([type |-> "phase1a", ins |-> r, bal |-> bal])
  /\ UNCHANGED <<rmState, aState>>

Phase2a(bal, r) ==
  /\ ~\E m \in msgs : /\ m.type = "phase2a"
                      /\ m.bal = bal
                      /\ m.ins = r
  /\ \E MS \in Majority :
       LET mset == {m \in msgs : /\ m.type = "phase1b"
                                 /\ m.ins = r
                                 /\ m.mbal = bal
                                 /\ m.acc \in MS}
           maxbal == Maximum({m.bal : m \in mset})
           val == IF maxbal = -1
                    THEN "aborted"
                    ELSE (CHOOSE m \in mset : m.bal = maxbal).val
       IN  /\ \A ac \in MS : \E m \in mset : m.acc = ac
           /\ Send([type |-> "phase2a", ins |-> r, bal |-> bal, val |-> val])
  /\ UNCHANGED <<rmState, aState>>

PCDecide ==
  /\ LET Decided(r, v) ==
           \E b \in Ballot, MS \in Majority :
             \A ac \in MS : [type |-> "phase2b", ins |-> r,
                             bal |-> b, val |-> v, acc |-> ac] \in msgs
     IN  \/ /\ \A r \in RM : Decided(r, "prepared")
            /\ Send([type |-> "Commit"])
         \/ /\ \E r \in RM : Decided(r, "aborted")
            /\ Send([type |-> "Abort"])
  /\ UNCHANGED <<rmState, aState>>
-----------------------------------------------------------------------------
\* Acceptor actions.
Phase1b(acc) ==
  \E m \in msgs :
    /\ m.type = "phase1a"
    /\ aState[m.ins][acc].mbal < m.bal
    /\ aState' = [aState EXCEPT ![m.ins][acc].mbal = m.bal]
    /\ Send([type |-> "phase1b", ins |-> m.ins, mbal |-> m.bal,
             bal |-> aState[m.ins][acc].bal, val |-> aState[m.ins][acc].val,
             acc |-> acc])
    /\ UNCHANGED rmState

Phase2b(acc) ==
  /\ \E m \in msgs :
       /\ m.type = "phase2a"
       /\ aState[m.ins][acc].mbal <= m.bal
       /\ aState' = [aState EXCEPT ![m.ins][acc].mbal = m.bal,
                                   ![m.ins][acc].bal  = m.bal,
                                   ![m.ins][acc].val  = m.val]
       /\ Send([type |-> "phase2b", ins |-> m.ins, bal |-> m.bal,
                val |-> m.val, acc |-> acc])
  /\ UNCHANGED rmState
-----------------------------------------------------------------------------
PCNext ==
  \/ \E r \in RM : \/ RMPrepare(r) \/ RMChooseToAbort(r)
                   \/ RMRcvCommitMsg(r) \/ RMRcvAbortMsg(r)
  \/ \E bal \in Ballot \ {0}, r \in RM : Phase1a(bal, r) \/ Phase2a(bal, r)
  \/ PCDecide
  \/ \E acc \in Acceptor : Phase1b(acc) \/ Phase2b(acc)
-----------------------------------------------------------------------------
TC == INSTANCE TCommit
TCConsistent == TC!TCConsistent
=============================================================================

This was adapted from the official example to the lecture's names and its Maximum. The lecture imports with INSTANCE; here TC == INSTANCE TCommit keeps TCommit's Decide from clashing, so the leader's action is called PCDecide.

Check a small model

The lecture's model is the smallest that could reveal a non-trivial error:

---- MODULE MCPaxosCommit ----
EXTENDS PaxosCommit, TLC
CONSTANTS a1, a2, a3, r1, r2
Acceptors == {a1, a2, a3}
RMs == {r1, r2}
Majorities == {{a1, a2}, {a1, a3}, {a2, a3}}
Sym == Permutations(Acceptors) \cup Permutations(RMs)
====
INIT PCInit
NEXT PCNext
CONSTANTS a1 = a1
          a2 = a2
          a3 = a3
          r1 = r1
          r2 = r2
          Acceptor <- Acceptors
          RM <- RMs
          Majority <- Majorities
          Ballot = {0, 1}
SYMMETRY Sym
INVARIANT PCTypeOK
INVARIANT TCConsistent
CHECK_DEADLOCK FALSE

Can Acceptor be a symmetry set when a1, a2, a3 appear in the value of Majority? Yes, because that expression is symmetric: swap a1 and a3, and you get the same set. This is the rule promised in {{lesson:transactions}}: elements of a symmetry set may be used in another constant's value only if that expression is symmetric in them, and those elements, or any constant assigned them, must not appear in a CHOOSE. The CHOOSEs here range over messages and numbers, not over RM or Acceptor.

Result: no error, 119,992 distinct states (1,545,109 generated), with PCTypeOK and TCConsistent invariant, in line with the lecture's figure. Time and space grow exponentially with model size. Lamport says one more ballot makes it vastly bigger; that model wasn't re-run here.

What good is such a small model?

Break the overlap: delete a2 from the last element, so Majority is { {a1, a2}, {a1, a3}, {a3} }. It's no longer symmetric, so Acceptor stops being a symmetry set. Comment out the conjunct in ASSUME, since TLC would otherwise reject it. TLC reports TCConsistent violated, with a 14-state trace, as in the lecture.

StatesTLC's actionsWhat happened
2–3RMPrepare(r1), RMPrepare(r2)Both RMs vote prepared in ballot 0
4–6Phase1a(1,r1), Phase1b(a1), Phase1b(a2)A leader polls {a1, a2} for r1; no one has voted
7Phase2a(1,r1)So it sends "aborted" in ballot 1
8–9Phase2b(a3) twicea3 votes r1 prepared (ballot 0), then aborted (ballot 1)
10–11PCDecide, RMRcvAbortMsg(r1){a3} "chose" aborted for r1: Abort sent, r1 aborts
12–14Phase2b(a3), PCDecide, RMRcvCommitMsg(r2)a3's vote for r2 means both instances "chose" prepared: Commit sent, r2 commits

Every phase2b message stays in msgs, so a3's old vote for r1 still counts. A leader that consulted {a1, a2} couldn't see a3, which is the right panel of the overlap diagram. Even a very small model catches a real error in a real algorithm.

Predict: does Paxos Commit still block if a majority of acceptors stops?

Yes. No new ballot can complete, so an undecided instance stays undecided. What improves is the failure it tolerates: any process can act as leader, and any single acceptor can fail, with three acceptors. Safety never relied on anyone being up; the checked model allows steps simply never to happen.

Why can a new leader safely take over in Paxos Commit but not a backup TM in two-phase commit?
