Implication runs out when the variables differ.

Implementation as implication, from {{lesson:implementation}}, worked because every variable of the high-level spec also appeared in the low-level one. TwoPhase had rmState, and AB has AVar and BVar. This lesson builds a protocol where that fails for an obvious pair of specs, and collects the two tools needed to repair it, recursion and substitution, in time for {{lesson:refinement}}.

Recursive definitions

Suppose you want an operator that removes every "X" from a sequence of strings. There's no single formula for the position of each element, as there was for Remove. Define it in terms of itself on a shorter sequence, and declare first that you are doing so:

RECURSIVE RemoveX(_)
RemoveX(seq) == IF seq = <<>>
                  THEN <<>>
                  ELSE IF Head(seq) = "X"
                         THEN RemoveX(Tail(seq))
                         ELSE <<Head(seq)>> \o RemoveX(Tail(seq))

The _ marks one argument. If you've used a functional language, this will feel natural. Otherwise, reach for it where a program would use a loop. TLC evaluates RemoveX(<<"Tom", "X", "Dick", "Harry", "X">>) to <<"Tom", "Dick", "Harry">>.

Substitution, and when it's allowed

For this lecture only, write f WITH v <- e for f with expression e substituted for symbol v. This is not TLA+ notation. For example, (y^3 - y) WITH y <- x + 2 is (x + 2)^3 - (x + 2). Ordinary math has a basic law, which the lecture calls the Simple Substitution Law:

THEOREM (v = e) => (f = (f WITH v <- e))

It holds for declared constants and constant expressions, the only things ordinary math has. It fails for declared variables. Take f to be y', v to be y, and e to be x + 2. The law then says (y = x + 2) => (y' = (x + 2)'): if y = x + 2 holds in the first state, it holds in the second. Run 1 in the figure refutes that. Adding always gives the Temporal Substitution Law, which holds when v is a variable and e a state expression:

THEOREM [](v = e) => (f = (f WITH v <- e))

It generalizes to several variables at once, f WITH v1 <- e1, v2 <- e2. The substitutions are simultaneous, not one after the other. You'll use this general form in {{lesson:refinement}}.

Predict: is the simple law true when v is a constant and e a constant expression, even with no always?

Yes. Their values don't depend on the state, so v = e is true on the first state exactly when it's true on all of them. [](v = e) says the same as v = e, and the temporal law reduces to the ordinary one.

The AB2 protocol

AB2 is AB with one change. Messages are detectably corrupted instead of lost. A corrupted message is represented by a constant Bad, assumed unequal to any real message, and the action that hurts messages replaces them in place:

CONSTANTS Data, Bad

ASSUME Bad \notin (Data \X {0, 1}) \cup {0, 1}

VARIABLES AVar, BVar, AtoB2, BtoA2

TypeOK == /\ AVar \in Data \X {0, 1}
          /\ BVar \in Data \X {0, 1}
          /\ AtoB2 \in Seq((Data \X {0, 1}) \cup {Bad})
          /\ BtoA2 \in Seq({0, 1, Bad})

BRcv == /\ AtoB2 # <<>>
        /\ IF (Head(AtoB2) # Bad) /\ (Head(AtoB2)[2] # BVar[2])
             THEN BVar' = Head(AtoB2)
             ELSE BVar' = BVar
        /\ AtoB2' = Tail(AtoB2)
        /\ UNCHANGED <<AVar, BtoA2>>

CorruptMsg == /\ \/ /\ \E i \in 1..Len(AtoB2) :
                         AtoB2' = [AtoB2 EXCEPT ![i] = Bad]
                    /\ BtoA2' = BtoA2
                 \/ /\ \E i \in 1..Len(BtoA2) :
                         BtoA2' = [BtoA2 EXCEPT ![i] = Bad]
                    /\ AtoB2' = AtoB2
              /\ UNCHANGED <<AVar, BVar>>

Init, ASnd, and BSnd only rename the channels. ARcv needs no change beyond that: Bad isn't 0 or 1, so the test Head(BtoA2) = AVar[2] is false and A ignores it. BRcv gets a new conjunct, because Head(AtoB2)[2] means nothing when the head is Bad. Next has CorruptMsg where AB had LoseMsg.

A value for Bad

The obvious model sets Bad to the string "Bad". TLC stops while evaluating the assumption:

Attempted to check equality of integer 0 with non-integer:
"Bad"

You think "Bad" differs from 0, but the semantics of TLA+ don't say so, and TLC won't guess. The answer is a model value, which TLC assumes unequal to any value you'd expect it to differ from. In a cfg file that's CONSTANT Bad = Bad, and the Toolbox has a model value option for it.

Checking AB2 against ABSpec

As in {{lesson:abp}}, the model needs data values and a state constraint. The lecture uses three values and channel lengths below 4. A smaller instance shows the same thing quickly:

SPECIFICATION Spec
CONSTANT Data = {d1, d2}
CONSTANT Bad = Bad
CONSTRAINT Bound
INVARIANT TypeOK
PROPERTY HighSafety

With Bound limiting both channels to length 2, and HighSafety naming ABS!Spec in a wrapper module, TLC finds no error: 6926 states generated, 1008 distinct, depth 16.

Liveness needs something imaginary

Copy AB's FairSpec onto AB2 and check it against ABS!FairSpec. TLC reports a violation:

Strong fairness can't help, since ARcv steps do occur. Each one just receives Bad. Lamport says he believes fairness on subactions of Next can't guarantee that any message is received before it's corrupted. So the safety spec has to change. The idea is that sending a message also decides whether it may ever be corrupted.

These flags are imaginary variables: not meant to be implemented, used only to state fairness. Choosing in advance doesn't change what AB2's own variables can do, so ignoring AtoBgood and BtoAgood, SpecP and Spec allow the same behaviors. Lamport's module AB2P extends AB2 this way. What follows is this course's own version, written to test the idea, and it may differ from his download. Corruption requires a false flag, and weak fairness applies to the receives and to sending a good message:

FairSpecP == SpecP /\ WF_varsP(ARcvP) /\ WF_varsP(BRcvP)
                   /\ WF_varsP(SndA(TRUE)) /\ WF_varsP(SndB(TRUE))

On the same bound, TLC finds no error against ABS!FairSpec and against AB2's Spec, with 4212 distinct states. Requiring only that some message keeps being sent, whether good or not, brings the violation back.

Predict: AB needed strong fairness on its receives. Why does weak fairness suffice for ARcvP and BRcvP here?

Corruption doesn't remove messages. Once a channel is non-empty, only a receive can empty it, so the receive stays continuously enabled, and there's no flicker for strong fairness to handle.
