Two-phase commit puts the minister back, as a process with messages.

TCommit let one step read every RM's state. Lecture 6 replaces that impossible step with a protocol: a transaction manager (TM) collects "prepared" messages and then announces the result. First you need one more data type, the record, because messages are records.

This is a real run of the spec below, printed by TLC with two RMs, and it has 8 states. An RM's "prepared" message and its change of state happen in one step. The TM commits only once tmPrepared holds every RM.

Records

r == [prof |-> "Fred", num |-> 42]     \* r.prof = "Fred", r.num = 42
[prof : {"Fred", "Ted"}, num : 0..99]   \* the set of all such records
[r EXCEPT !.prof = "Red"]               \* same as r except field prof

A record is like a C struct, except that field order doesn't matter. It is really a function whose domain is a set of strings: r.prof abbreviates r["prof"], and !.prof abbreviates !["prof"]. So you already know how they behave.

The spec

------------------------------- MODULE TwoPhase -----------------------------
CONSTANT RM              \* The set of resource managers
VARIABLES
  rmState,               \* rmState[r] is the state of RM r
  tmState,               \* "init" or "done"
  tmPrepared,            \* the RMs the TM knows are prepared
  msgs                   \* every message ever sent
vars == <<rmState, tmState, tmPrepared, msgs>>

Messages == [type : {"Prepared"}, rm : RM] \cup [type : {"Commit", "Abort"}]

TPTypeOK ==
  /\ rmState \in [RM -> {"working", "prepared", "committed", "aborted"}]
  /\ tmState \in {"init", "done"}
  /\ tmPrepared \subseteq RM
  /\ msgs \subseteq Messages

TPInit ==
  /\ rmState = [r \in RM |-> "working"]
  /\ tmState = "init"
  /\ tmPrepared = {}
  /\ msgs = {}
-----------------------------------------------------------------------------
TMRcvPrepared(r) ==
  /\ tmState = "init"
  /\ [type |-> "Prepared", rm |-> r] \in msgs
  /\ tmPrepared' = tmPrepared \cup {r}
  /\ UNCHANGED <<rmState, tmState, msgs>>

TMCommit ==
  /\ tmState = "init"
  /\ tmPrepared = RM
  /\ tmState' = "done"
  /\ msgs' = msgs \cup {[type |-> "Commit"]}
  /\ UNCHANGED <<rmState, tmPrepared>>

TMAbort ==
  /\ tmState = "init"
  /\ tmState' = "done"
  /\ msgs' = msgs \cup {[type |-> "Abort"]}
  /\ UNCHANGED <<rmState, tmPrepared>>

RMPrepare(r) ==
  /\ rmState[r] = "working"
  /\ rmState' = [rmState EXCEPT ![r] = "prepared"]
  /\ msgs' = msgs \cup {[type |-> "Prepared", rm |-> r]}
  /\ UNCHANGED <<tmState, tmPrepared>>

RMChooseToAbort(r) ==
  /\ rmState[r] = "working"
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ UNCHANGED <<tmState, tmPrepared, msgs>>

RMRcvCommitMsg(r) ==
  /\ [type |-> "Commit"] \in msgs
  /\ rmState' = [rmState EXCEPT ![r] = "committed"]
  /\ UNCHANGED <<tmState, tmPrepared, msgs>>

RMRcvAbortMsg(r) ==
  /\ [type |-> "Abort"] \in msgs
  /\ rmState' = [rmState EXCEPT ![r] = "aborted"]
  /\ UNCHANGED <<tmState, tmPrepared, msgs>>
-----------------------------------------------------------------------------
TPNext ==
  \/ TMCommit \/ TMAbort
  \/ \E r \in RM : TMRcvPrepared(r) \/ RMPrepare(r) \/ RMChooseToAbort(r)
                     \/ RMRcvCommitMsg(r) \/ RMRcvAbortMsg(r)
-----------------------------------------------------------------------------
INSTANCE TCommit
=============================================================================

Three pieces of notation are new:

  • S \cup T (or \union) is the set of elements in S or T or both.
  • S \subseteq T says every element of S is in T.
  • UNCHANGED <<a, b>> says each listed variable keeps its value. <<a, b>> is an ordered tuple; vars names the tuple of all four variables.

msgs holds every message ever sent. A Prepared record goes from r to the TM. A Commit or Abort record goes from the TM to all RMs. The formulas with no primes at the start of an action are its enabling conditions: conditions on the first state of a step. Put them first. That is easier to read, and TLC often can't handle the action otherwise. Finally, INSTANCE TCommit imports TCommit's definitions, including TCConsistent, applied to this module's rmState.

A trace where an RM aborts

r2 aborts on its own, shown as a note because no message is sent. In a real system it would tell the TM, but that is an optimization the spec omits. r1 is prepared and can't abort itself; it has to wait to hear from the TM. Nothing makes the TM wait, because TMAbort is enabled whenever tmState = "init".

This order is one of many. TLC, asked for any run with this outcome, returned a 5-state trace with TMAbort as the very first step, before anyone had done anything. That is also allowed. The diagram shows the order you would expect in practice, and the guards permit both.

Check it with TLC

INIT TPInit
NEXT TPNext
CONSTANT RM = {"r1", "r2", "r3"}
INVARIANT TPTypeOK
INVARIANT TCConsistent
CHECK_DEADLOCK FALSE

Result: no error, 288 distinct states (1146 generated), the same count the lecture reports. The lecture uses that number as a test of your own definitions: paste one in, rerun, and if TLC finds no error and again 288 states, it's probably correct.

Symmetry and model values

All RMs play the same role. Swap r1 and r3 everywhere in a reachable state, as in the diagram, and you get another reachable state. Swap them in a whole behavior and you get another allowed behavior, so TLC needn't check both. A set with this property is a symmetry set. To use one, make its elements model values: special values not equal to anything else, written as bare identifiers. In the Toolbox you tick "Symmetry set". In a .cfg file you need a small wrapper module:

---- MODULE MCTwoPhase ----
EXTENDS TwoPhase, TLC
CONSTANTS r1, r2, r3
RMs == {r1, r2, r3}
Sym == Permutations(RMs)
====
INIT TPInit
NEXT TPNext
CONSTANTS r1 = r1
          r2 = r2
          r3 = r3
          RM <- RMs
SYMMETRY Sym
INVARIANT TPTypeOK
INVARIANT TCConsistent
CHECK_DEADLOCK FALSE

RM <- RMs replaces the constant by the module's definition RMs. Permutations comes from the TLC module. Result: no error, 80 distinct states examined, out of the same 288 reachable ones. Be careful: TLC may miss errors if you declare a symmetry set falsely. For now it's safe if the model values aren't used elsewhere; {{lesson:paxos-commit}} gives the full rule.

Is it correct?

The run above also checks TCConsistent: one RM can't commit while another aborts. TwoPhase actually does more than keep that invariant: it implements TCommit. That claim needs its own definition, given in {{lesson:implementation}}.

Explore the TM's decision

In the lab, "coordinator" is the common industry name for the TM, and participants A and B are RMs. It is an educational model, not TLC: it leaves out msgs and tmPrepared, treating "prepared" as instantly known. Prepare both RMs and crash the coordinator. No commit can happen, and nothing lets a prepared RM move. Agreement isn't violated, but the transaction is stuck, which is the starting point of {{lesson:paxos-commit}}.

Predict: both RMs are prepared and the TM has gone silent. Is it safe for an RM to abort on its own?

No. The TM may already have sent Commit, and the other RM may have received it. Not having heard is no evidence that no decision exists. The spec gives a prepared RM no way to leave that state except by receiving a message.

Worked architecture: reserve a seat and charge a wallet

A purchase spans an inventory RM and a wallet RM. Preparing means each one promises it can honor a commit and holds what it needs: the seat, the funds. That promise is what makes prepared different from "looks available".

Trace a hard run with the first diagram. Both prepare; the TM sends Commit; inventory receives it and marks the seat sold, and the wallet hasn't heard yet. For a while one RM is committed and another prepared. TCConsistent allows this, because it forbids only committed alongside aborted. If the wallet then gave up and aborted on a timeout, that would be the forbidden state: a seat sold and no money taken.
